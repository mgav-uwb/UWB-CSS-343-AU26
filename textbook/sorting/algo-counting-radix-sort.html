Counting Sort & Radix Sort

Radix sort is older than electronic computers: punched-card sorting machines, descended from Herman Hollerith’s 1890 census equipment, sorted a deck one digit column at a time, least significant first. D. E. Knuth, The Art of Computer Programming, Volume 3, §5.2.5

The sorting lower bound says comparison sorts cannot beat \(\Omega(n\log n)\). Counting sort and radix sort beat it anyway, running in linear time, because they never compare two keys: they read the keys’ digits and use them as array indices. This handout builds the one primitive both rest on, key-indexed counting, unrolls it completely, and then chains it into radix sort, where the primitive’s stability turns out to carry the whole correctness argument.

1. Beating \(n\log n\) without contradicting it

The lower bound is a statement about a model: any algorithm whose only way to learn about the keys is asking “is \(a_i < a_j\)?” must, in the worst case, ask \(\Omega(n\log n)\) times, because \(n!\) possible orderings need \(\log_2(n!) = \Theta(n\log n)\) yes/no answers to tell apart. The bound says nothing about algorithms that get information any other way.

Counting sort gets its information another way. If the keys are known to be integers in \(\{0, 1, \dots, R-1\}\), a key is not an opaque thing you can only compare: it is an address. One array read count[key] extracts \(\log_2 R\) bits of information about the key at once, where a comparison extracts one bit. The decision-tree argument simply does not apply, and \(\Theta(n+R)\) running time is possible.

Definition (key-indexed model) A sort is comparison-free (key-indexed) if it never evaluates \(a_i < a_j\), and instead uses keys, or digits of keys, as indices into arrays of size \(R\). Here \(R\) is called the radix (for digits) or alphabet size (for characters). The assumption bought: keys are, or decompose into, small integers.
Definition (stability) A sort is stable if records with equal keys appear in the output in the same relative order as in the input. Stability is what lets sorts be chained: sorting stably by key \(B\) after sorting by key \(A\) yields order “by \(B\), ties broken by \(A\)”.

The plan: build a stable \(\Theta(n+R)\) sort for one small-integer key (key-indexed counting), then handle big keys by splitting them into \(d\) small digits and running one stable pass per digit.

2. Key-indexed counting, fully unrolled

Key-indexed counting sorts \(n\) records whose keys lie in \(\{0,\dots,R-1\}\) in four passes, none of which compares anything:

  1. Histogram. Count how many records have each key: count[a[i].key]++.
  2. Prefix sums. Convert counts to start positions: start[r] = number of records with key \(< r\) = where key \(r\)’s block begins in the output.
  3. Stable placement. Scan the input left to right; drop each record at aux[start[key]] and increment start[key].
  4. Copy back. a[i] = aux[i].
// Key-indexed counting: stable sort of n keys in {0..R-1}. Theta(n + R).
void countingSort(int a[], int n, int R) {
    int* count = new int[R]();                  // 1) histogram of keys
    for (int i = 0; i < n; i++) count[a[i]]++;
    int* start = new int[R];                    // 2) prefix sums:
    for (int r = 0, s = 0; r < R; r++) {        //    start[r] = #keys < r
        start[r] = s; s += count[r];
    }
    int* aux = new int[n];                      // 3) stable placement:
    for (int i = 0; i < n; i++)                 //    left-to-right scan
        aux[start[a[i]]++] = a[i];              //    keeps ties in order
    for (int i = 0; i < n; i++) a[i] = aux[i];  // 4) copy back
    delete[] count; delete[] start; delete[] aux;
}

# Key-indexed counting: stable sort of n keys in {0..R-1}. Theta(n + R).
def counting_sort(a, R):
    count = [0] * R
    for x in a:                       # 1) histogram of keys
        count[x] += 1
    start, s = [0] * R, 0             # 2) prefix sums:
    for r in range(R):                #    start[r] = #keys < r
        start[r] = s
        s += count[r]
    aux = [None] * len(a)             # 3) stable placement: left-to-right
    for x in a:                       #    scan keeps ties in order
        aux[start[x]] = x
        start[x] += 1
    a[:] = aux                        # 4) copy back
// Key-indexed counting: stable sort of n keys in {0..R-1}. O(n + R).
fn counting_sort(a: &mut [usize], r_radix: usize) {
    let mut count = vec![0usize; r_radix];      // 1) histogram of keys
    for &x in a.iter() { count[x] += 1; }
    let mut start = vec![0usize; r_radix];      // 2) prefix sums:
    let mut s = 0;                              //    start[r] = #keys < r
    for r in 0..r_radix { start[r] = s; s += count[r]; }
    let mut aux = vec![0usize; a.len()];        // 3) stable placement:
    for &x in a.iter() {                        //    left-to-right scan
        aux[start[x]] = x;                      //    keeps ties in order
        start[x] += 1;
    }
    a.copy_from_slice(&aux);                    // 4) copy back
}

Claim (correct, stable, \(\Theta(n+R)\)) Key-indexed counting sorts correctly and stably in \(\Theta(n+R)\) time with \(\Theta(n+R)\) extra space.
Correct: start[r] begins as the number of keys less than \(r\), so the blocks \([\,\texttt{start}[r], \texttt{start}[r{+}1]\,)\) partition \(\texttt{aux}\) with key \(r\)’s block before key \(r'\)’s for \(r < r'\), and each block has exactly count[r] slots. Placement drops each record into its own key’s block, filling it left to right, so no slot is written twice and the result is ordered by key. Stable: within a block, slots are assigned in input-scan order, so equal keys keep their input order. Cost: the four passes touch \(n\), \(R\), \(n\), \(n\) array entries respectively, each \(\Theta(1)\) per entry: \(\Theta(n+R)\) total. Space: \(\texttt{aux}\) is \(n\) slots and \(\texttt{count}/\texttt{start}\) are \(R\). ∎
Two ways to lose stability Both of these produce a correct ordering of plain integers but break stability of records, which matters in the next section: scanning the input right to left while filling blocks left to right reverses ties; and filling each block from its right end (using end positions and --end[key]) while scanning left to right also reverses ties. The rule: scan direction and fill direction must agree. (Scanning right to left while filling from block ends is again stable, and is the form some texts use.)

3. LSD radix sort

Counting sort needs \(R\) small. To sort keys from a big universe, decompose each key into \(d\) base-\(R\) digits and run one counting pass per digit, least-significant digit first: sort the whole array by the last digit, then by the next-to-last, and so on. Each pass must be stable; the invariant below is why. 

// LSD radix sort: d stable counting passes over base-R digits,
// least-significant digit first. Theta(d(n + R)).
void lsdSort(int a[], int n, int d, int R) {
    int* aux   = new int[n];
    int* start = new int[R];
    long pw = 1;                                   // R^p: digit p extractor
    for (int p = 0; p < d; p++, pw *= R) {         // digit p = (x / pw) % R
        for (int r = 0; r < R; r++) start[r] = 0;
        for (int i = 0; i < n; i++)                // histogram of digit p
            start[(a[i] / pw) % R]++;
        for (int r = 0, s = 0; r < R; r++) {       // counts -> start slots
            int c = start[r]; start[r] = s; s += c;
        }
        for (int i = 0; i < n; i++)                // stable placement
            aux[start[(a[i] / pw) % R]++] = a[i];
        for (int i = 0; i < n; i++) a[i] = aux[i]; // copy back
    }
    delete[] aux; delete[] start;
}

def lsd_sort(a, d, R):
    pw = 1                            # R**p: digit p extractor
    for _ in range(d):                # digit p of x is (x // pw) % R
        count = [0] * R
        for x in a:                   # histogram of digit p
            count[(x // pw) % R] += 1
        start, s = [0] * R, 0         # counts -> start slots
        for r in range(R):
            start[r] = s
            s += count[r]
        aux = [None] * len(a)
        for x in a:                   # stable placement
            dgt = (x // pw) % R
            aux[start[dgt]] = x
            start[dgt] += 1
        a[:] = aux                    # copy back
        pw *= R
// LSD radix sort: d stable counting passes over base-R digits,
// least-significant digit first. O(d(n + R)).
fn lsd_sort(a: &mut [u64], d: u32, r_radix: u64) {
    let n = a.len();
    let mut aux = vec![0u64; n];
    let mut pw: u64 = 1;                           // R^p: digit p extractor
    for _ in 0..d {                                // digit p = (x / pw) % R
        let mut start = vec![0usize; r_radix as usize];
        for &x in a.iter() {                       // histogram of digit p
            start[((x / pw) % r_radix) as usize] += 1;
        }
        let mut s = 0;                             // counts -> start slots
        for r in 0..r_radix as usize {
            let c = start[r]; start[r] = s; s += c;
        }
        for &x in a.iter() {                       // stable placement
            let dgt = ((x / pw) % r_radix) as usize;
            aux[start[dgt]] = x;
            start[dgt] += 1;
        }
        a.copy_from_slice(&aux);                   // copy back
        pw *= r_radix;
    }
}

Digit-by-digit trace

Sort seven 3-digit numbers (\(d=3\), \(R=10\)). Each row is the whole array after one stable counting pass on the highlighted digit:

Watch the ties do the work. The ones pass has two tie pairs (457, 657 on digit 7; 329, 839 on digit 9); each pair keeps its input order. The tens pass has three tie groups: digit 2 holds \(\{720, 329\}\), digit 3 holds \(\{436, 839\}\), and digit 5 holds \(\{355, 457, 657\}\); within each group, stability preserves the ones-pass order, so after the tens pass every group is internally sorted by its last two digits (355 < 457 < 657). The hundreds pass then ties \(\{329, 355\}\) and \(\{436, 457\}\), and again stability keeps each tie group in its already-correct order. The final array is fully sorted.

Invariant (why LSD works) After the pass on digit \(p\) (digits numbered \(0\) = least significant), the array is sorted by the number formed by digits \(p, p-1, \dots, 0\), i.e. by the key’s last \(p+1\) digits. Hence after the pass on digit \(d-1\), the array is sorted.
Induction on \(p\). Base: the pass on digit 0 sorts by digit 0. Step: assume the array is sorted by the last \(p\) digits, and run the stable pass on digit \(p\). Take any two keys \(x, y\) with \(x < y\) on their last \(p+1\) digits. Either they differ on digit \(p\), and the counting pass puts \(x\)’s block before \(y\)’s; or they agree on digit \(p\), so \(x < y\) already on the last \(p\) digits, so \(x\) preceded \(y\) before the pass (induction hypothesis), and stability preserves that order through the pass. ∎

Stability is load-bearing: a broken run

The induction’s second case is the entire role of stability: a pass on digit \(p\) is blind to digits below \(p\), so the only thing protecting the earlier passes’ work is that ties survive unreordered. Replace the stable pass with an unstable one (same bucket contents, ties reversed; for instance, filling each bucket from its right end while scanning the input left to right) and radix sort silently breaks:

The ones pass is identical in both columns (its digits 1, 3, 5 are all distinct, so there are no ties to mishandle). The tens pass is where it breaks: all three keys tie on digit 2, so the pass’s only job is to leave them alone; the unstable version reverses them and outputs \(25, 23, 21\). Wrong, even though every individual pass put every key in the correct bucket.

LSD in practice LSD radix sort is the standard way to sort fixed-length keys that decompose into digits: 32- and 64-bit integers (bytes as digits, \(R = 256\)), fixed-length strings (characters as digits, \(R\) = alphabet size), IP addresses, dates packed as integers. It is itself stable (a chain of stable passes), and its cost is guaranteed, with no bad inputs. Punched-card sorters ran exactly this algorithm mechanically: deal the deck into \(R=10\) bins by one column, restack the bins in order (that restack is the stable pass), repeat for the next column.

4. MSD radix sort, sketched

The other order also works, with a different shape. MSD (most-significant-digit) radix sort runs one counting pass on the leading digit, which splits the array into \(R\) blocks, then recurses independently within each block on the next digit. On the seven numbers of the trace, the first pass splits by hundreds digit:

The recursion must stay inside each block: a later full-array pass on a lower digit would destroy the leading-digit order (this is exercise 3). MSD stops recursing the moment a block has one element, so it examines only enough leading digits to distinguish the keys, while LSD always runs all \(d\) passes. That makes MSD win when:

  • Keys are long but distinguished early. Sorting long strings or multi-word keys: if most keys differ in their first few characters, MSD touches only those characters, giving about \(\Theta(n \cdot \bar{\ell} + \text{blocks} \cdot R)\) where \(\bar{\ell}\) is the average distinguishing-prefix length, versus LSD’s full \(d\) passes.
  • Keys have variable length. LSD needs all keys the same length (or padding); MSD handles variable-length strings naturally with an “end of string” pseudo-digit that sorts shorter prefixes first.

Its costs: recursion bookkeeping, and a fresh \(R\)-slot count array at every recursive call, which for many small blocks makes the \(R\) term dominate; practical MSD implementations cut over to insertion sort on small blocks for exactly this reason. The recursion tree of MSD radix sort is the same shape as the R-way trie of the keys: each node fans out by one digit into \(R\) children, and MSD is in effect building and reading off that trie’s leaves in order.

5. Cost, and the choice of radix

Claim (LSD cost) LSD radix sort on \(n\) keys of \(d\) base-\(R\) digits runs in \(\Theta(d(n+R))\) time and \(\Theta(n+R)\) extra space, on every input.
Each pass is one key-indexed counting sort on digit values in \(\{0,\dots,R-1\}\): \(\Theta(n+R)\) by the claim in the key-indexed counting section (digit extraction is \(\Theta(1)\) per element). There are exactly \(d\) passes, always: no pass can be skipped and no input makes a pass cheaper, so the total is \(\Theta(d(n+R))\). The \(\texttt{aux}\) and \(\texttt{start}\) arrays are reused across passes: \(\Theta(n+R)\) space. ∎

The radix \(R\) is a dial, because \(d\) and \(R\) trade against each other. Keys from a universe of size \(U\) (so \(w = \log_2 U\) bits) have \(d = \lceil \log_R U \rceil = \lceil w / \log_2 R \rceil\) base-\(R\) digits: raising \(R\) means fewer, fatter passes, but each pass pays \(\Theta(R)\) to build and scan its count array whether or not the buckets are used. Concretely, for 32-bit keys:

radix \(R\)passes \(d\)cost \(d(n+R)\)at \(n = 1000\)at \(n = 10^6\)
\(2^8 = 256\)4\(4(n + 256)\)5 024\(\approx 4.0 \times 10^6\)
\(2^{16} = 65\,536\)2\(2(n + 65\,536)\)133 072\(\approx 2.1 \times 10^6\)

At \(n = 1000\) the big radix is a disaster: the \(R\) term swamps the \(n\) term, and 26 times the work of \(R = 256\). At \(n = 10^6\) the big radix wins, because \(n \gg R\) makes each pass cost essentially \(n\) and halving the pass count halves the total. The balance point: take \(R \approx n\) (i.e. \(\log_2 R \approx \log_2 n\) bits per pass), which makes each pass \(\Theta(n)\) and gives total \(\Theta(n \cdot w / \log n)\); whenever the key width \(w\) is \(O(\log n)\), that is \(\Theta(n)\), linear. This is the precise sense in which radix sort is a linear-time sort: linear for keys polynomial in \(n\) (so \(w = O(\log n)\)), not for arbitrary keys. For truly long keys (\(d\) large, distinguishing prefixes short), MSD or a comparison sort can win; \(\Theta(d \cdot n)\) is not automatically better than \(\Theta(n \log n)\) when \(d \gg \log n\).

Bucket sort A cousin with a different assumption. Bucket sort handles keys that are not small integers (say, reals in \([0,1)\)) by dropping each of the \(n\) keys into bucket \(\lfloor n \cdot x \rfloor\) of \(n\) buckets, sorting each bucket with insertion sort, and concatenating. If the keys are drawn uniformly at random, each bucket holds \(O(1)\) keys in expectation and the total expected cost is \(\Theta(n)\). The assumption moved: counting sort assumes a small key universe; bucket sort assumes a benign key distribution. Feed bucket sort skewed data (all keys in one bucket) and it degrades to its per-bucket sort, \(\Theta(n^2)\) for insertion sort. It is the only sort in this handout whose linear time is probabilistic rather than guaranteed.

6. Where this sits

The Sorting Lower Bound handout proves the \(\Omega(n\log n)\) floor these sorts step around, and delimits exactly the model in which they live. Among comparison sorts, Mergesort is the stable one, and its merge plays the same tie-breaking-discipline role that the left-to-right placement scan plays here; Quicksort is the standard unstable contrast. The Tries handout is the search made from the same move as the sort: an R-way trie uses one digit or character as an index into an \(R\)-slot child array at each node, exactly as a counting pass uses it as an index into an \(R\)-slot count array, and MSD radix sort’s recursion tree is that trie.

7. Exercises (with solutions)

  1. Run key-indexed counting on the characters of b a c c a b (alphabet \(\{a,b,c\}\) mapped to \(\{0,1,2\}\), so \(R=3\)). Give the count array, the start array, and, for each character in scan order, the aux slot it lands in.
    solution Histogram: two of each, so \(\texttt{count} = [2,2,2]\). Prefix sums: \(\texttt{start} = [0,2,4]\) (0 keys before a, 2 before b, 4 before c). Placement, in scan order: b→aux[2], a→aux[0], c→aux[4], c→aux[5], a→aux[1], b→aux[3]. Result: a a b b c c, with the first a of the input first in the output (stable). Verify the slots against the start array: b’s block is aux[2..3], a’s aux[0..1], c’s aux[4..5], each filled left to right.
  2. Trace 2-digit LSD radix sort on \([21, 25, 23]\) where each pass uses the unstable placement of the broken-run section (correct buckets, ties reversed). Which pass goes wrong, and why does the other one not?
    solution Ones pass: digits 1, 5, 3 are all distinct, so each bucket holds one key and there are no ties to reverse; the pass gives \([21, 23, 25]\), same as the stable pass. Tens pass: all three keys have tens digit 2, one bucket, all ties; the unstable pass reverses them to \([25, 23, 21]\). Final answer \([25, 23, 21]\), not sorted. Instability only shows when a pass has ties, and only hurts when the tied keys’ earlier-pass order carried information.
  3. A student runs full-array counting passes most-significant digit first (hundreds, then tens, then ones), without MSD’s recursion, on \([329, 457, 657, 839, 436, 720, 355]\). Each pass is stable. Give the array after each pass and explain the final answer’s order.
    solution After hundreds: \([329, 355, 457, 436, 657, 720, 839]\). After tens (full array, so hundreds order is discarded except as tie order): \([329, 720, 436, 839, 355, 457, 657]\). After ones: \([720, 355, 436, 457, 657, 329, 839]\). The last full-array pass dominates: the result is sorted by ones digit (0, 5, 6, 7, 7, 9, 9), with earlier passes surviving only as tie-breaks among equal ones digits, exactly backwards. This is why LSD runs least-significant first (each pass’s order is the least important so far, refined by later passes) and why MSD must recurse within blocks rather than re-scan the whole array.
  4. You sort \(n = 10^6\) records with 64-bit keys by LSD radix sort with \(R = 2^8\) (one byte per digit). How many passes run, and roughly how many array operations does the sort do, counting each pass as \(n + R\) slot-touches? Compare against \(n \log_2 n\) for a comparison sort.
    solution \(64/8 = 8\) passes. Work \(\approx 8 \cdot (10^6 + 256) = 8\,002\,048\) slot-touches, about \(8n\). A comparison sort does about \(n\log_2 n = 10^6 \cdot \log_2 10^6 \approx 1.99 \times 10^7\) comparisons, each with its own memory traffic: radix does roughly 2.5× less key-touching work here, and the gap widens as \(n\) grows while \(d = 8\) stays fixed. (Constant factors, cache behavior, and the \(\Theta(n)\) buffer decide real-world winners; the asymptotic point is that \(d\) does not grow with \(n\).)
  5. For 32-bit keys, compare \(R = 2^8\) (4 passes) against \(R = 2^{16}\) (2 passes) at \(n = 1000\), counting each pass as \(n + R\). Which radix wins, by what factor, and what changes at large \(n\)?
    solution \(R = 2^8\): \(4 \cdot (1000 + 256) = 5\,024\). \(R = 2^{16}\): \(2 \cdot (1000 + 65\,536) = 133\,072\). The small radix wins by a factor of about 26: with \(n \ll R\), each big-radix pass wastes \(\Theta(R)\) work scanning a count array that is almost entirely zeros. At large \(n\) (say \(n \geq 10^6 \gg 2^{16}\)) the \(R\) term is negligible in both, and the 2-pass version does about half the work of the 4-pass version. Rule of thumb: choose \(R\) around \(n\), never far above it.
  6. Keys lie in \(\{0, \dots, n^2 - 1\}\). Direct counting sort costs \(\Theta(n + n^2) = \Theta(n^2)\), worse than mergesort. Fix it with radix sort in \(\Theta(n)\).
    solution Write each key in base \(R = n\): since keys are below \(n^2\), every key has \(d = 2\) base-\(n\) digits (\(x = q \cdot n + r\) with \(q = \lfloor x/n \rfloor\), \(r = x \bmod n\), both in \(\{0,\dots,n-1\}\)). LSD radix sort with these digits runs 2 stable counting passes, each \(\Theta(n + n) = \Theta(n)\): total \(\Theta(n)\). Check on \(n = 10\) keys below 100: \([41, 19, 50, 83, 6, 9, 68, 12, 46, 74]\); the ones pass then the tens pass yields \([6, 9, 12, 19, 41, 46, 50, 68, 74, 83]\). The same trick gives \(\Theta(kn)\) for keys below \(n^k\), which is the “linear for polynomial-size keys” statement of the cost section.
  7. Sort the twelve 3-letter strings dab cab fad bad dad ebb ace add fed bed fee bee by LSD radix sort (\(d = 3\) character positions, \(R = 26\)). In what order are the character positions processed, and what is the output? What structure would you get if you instead ran MSD all the way down without stopping early?
    solution Positions are processed right to left: position 2 (last letter), then 1, then 0. Output: ace add bad bed bee cab dab dad ebb fad fed fee. Full MSD recursion builds, level by level, the R-way trie of the strings: first-letter buckets are the root’s children, second-letter sub-buckets their children, and reading the leaves left to right gives the same sorted order; see the Tries handout.
