The Sorting Lower Bound

Data Structures & Algorithms. Foundation.
The decision-tree argument that any algorithm sorting \(n\) keys by comparisons alone makes \(\Omega(n\log n)\) comparisons in the worst case: \(n!\) orderings need \(n!\) leaves, and a binary tree that tall has height \(\log_2(n!) = \Theta(n\log n)\). Includes the tree drawn in full for \(n = 3\) with every ordering walked to its leaf, the two-sided bound on \(\log_2(n!)\) without Stirling, and the non-comparison sorts (counting, radix) the bound does not cover. With exercises.

Sorting has a provable difficulty floor: any algorithm that orders keys only by comparing them makes \(\Omega(n\log n)\) comparisons in the worst case. The argument is a counting argument about information, not about any particular algorithm, and it licenses two conclusions: mergesort and quicksort are asymptotically optimal among comparison sorts, and only a sort that exploits key structure instead of comparing can run faster.

1. Why comparison sorts stop at \(n\log n\)

Mergesort and quicksort both reach \(\Theta(n\log n)\); no algorithm that sorts by comparing keys does asymptotically better, and the reason is a counting argument about information, not about any particular algorithm.

Theorem (comparison-sort lower bound) Any sorting algorithm that only compares keys makes \(\Omega(n\log n)\) comparisons in the worst case.
Proof (decision tree). A comparison sort on \(n\) elements is a binary decision tree: each internal node is a comparison with two outcomes, and each leaf is one of the possible sorted outputs. To sort correctly the tree must have a leaf for each of the \(n!\) possible input orderings, so it has at least \(n!\) leaves. A binary tree of height \(h\) has at most \(2^h\) leaves, so \(2^h \ge n!\), giving \[ h \;\ge\; \log_2(n!) \;=\; \Theta(n\log n) \] by the two-sided bound below. ∎

Here is the whole object for \(n = 3\), keys \(a_1, a_2, a_3\). Each internal node compares two keys; each leaf \(\langle i, j, k \rangle\) asserts the sorted order \(a_i \le a_j \le a_k\). There are \(3! = 6\) orderings, so the tree needs \(6\) leaves, and all \(6\) appear:

“All six appear” is a claim worth checking rather than asserting, and with six inputs it can be checked exhaustively. Feed the tree each of the \(3! = 6\) orderings, writing \(a_1 a_2 a_3\) as a permutation of \(1, 2, 3\), and record the branch taken at each node:

Six inputs, six different leaves, which is the property the proof needs: if two orderings ever reached the same leaf, the algorithm would emit the same permutation for both and be wrong on at least one. Check one row against its leaf to see that the leaf really is the answer: the input \((2, 3, 1)\) lands at \(\langle 3, 1, 2\rangle\), which asserts \(a_3 \le a_1 \le a_2\), and indeed \(1 \le 2 \le 3\). The depths are \(2, 3, 3, 2, 3, 3\), so this tree makes \(3\) comparisons in the worst case and \(16/6 \approx 2.67\) on average, against an information-theoretic average floor of \(\log_2 6 \approx 2.58\).

Example (one input walks the tree) Sort \((a_1, a_2, a_3) = (8, 3, 5)\). At the root, \(a_1 : a_2\) is \(8 > 3\): go right. Next, \(a_1 : a_3\) is \(8 > 5\): go right again. Finally \(a_2 : a_3\) is \(3 \le 5\): go left, reaching the leaf \(\langle 2, 3, 1 \rangle\), which asserts \(a_2 \le a_3 \le a_1\), i.e. \(3 \le 5 \le 8\). Three comparisons, and the leaf is the answer: everything the algorithm ever learns about the input is which path it took. The four inputs whose paths end at depth \(3\) (leaves \(\langle 1,3,2\rangle, \langle 3,1,2\rangle, \langle 2,3,1\rangle, \langle 3,2,1\rangle\)) are the worst cases; the two at depth \(2\) got lucky.
Why \(\log_2(n!) = \Theta(n\log n)\), without Stirling Bound the product from both sides. Every factor is at most \(n\), so \[ n! \;\le\; n^n \quad\Longrightarrow\quad \log_2(n!) \;\le\; n\log_2 n. \] For the other direction, throw away the smaller half of the factors: the remaining \(n/2\) of them (those from \(n/2\) up to \(n\)) are each at least \(n/2\), so \[ n! \;\ge\; (n/2)^{n/2} \quad\Longrightarrow\quad \log_2(n!) \;\ge\; \tfrac{n}{2}\log_2\tfrac{n}{2}. \] Both bounds are \(\Theta(n\log n)\), so \(\log_2(n!)\) is too. Discarding half the factors costs only a constant factor: the standard trick for bounding a product from below. Stirling gives the sharp constant (\(\log_2(n!) = n\log_2 n - n\log_2 e + O(\log n)\)); the lower bound does not need it. The height \(h\) is the worst-case number of comparisons, so every comparison sort makes \(\Omega(n\log n)\) of them. ∎

So mergesort and quicksort are asymptotically optimal among comparison sorts: a rare case where we can prove a problem’s difficulty, not just an algorithm’s cost. The escape hatch is to stop comparing:

Non-comparison sorts If the keys have exploitable structure, you can sort in linear time. Counting sort tallies how many keys take each value and is \(\Theta(n + k)\) for keys in a range of size \(k\); radix sort sorts fixed-width keys digit by digit in \(\Theta(d\,n)\) for \(d\) digits (both are worked in the Counting and Radix Sort handout). Neither ever compares two keys, so the \(\Omega(n\log n)\) bound simply does not apply to them. The price is that the keys must be small integers or fixed-width strings, and extra space is needed; when the data fits, these are unbeatable.

2. Exercises (with solutions)

  1. A comparison sort claims to sort any \(8\)-element array in at most \(10\) comparisons. Show this is impossible.
    solution An \(8\)-element sort must distinguish \(8! = 40320\) orderings, so its decision tree needs at least \(40320\) leaves. A binary tree of height \(10\) has at most \(2^{10} = 1024\) leaves, far fewer than \(40320\), so some orderings share a leaf and are sorted wrongly. The minimum possible worst case is \(\lceil \log_2 8! \rceil = \lceil 15.3 \rceil = 16\) comparisons, so no comparison sort can promise \(10\).
  2. You are sorting one million \(32\)-bit integers and can spare extra memory. Can you beat \(\Theta(n\log n)\)? If so, name the method and its cost; if not, explain why.
    solution Yes: the \(\Omega(n\log n)\) bound applies only to comparison sorts, and these keys have structure. Radix sort in a few passes over fixed-width digits (say four \(8\)-bit passes) is \(\Theta(d\,n)\) with \(d = 4\), i.e. linear in \(n\), using counting sort within each pass. It never compares two keys, so the lower bound does not apply. The cost is the extra \(\Theta(n + k)\) space per pass, which the problem allows.
  3. Draw the decision tree an algorithm would need for \(n = 3\) if it always made exactly two comparisons, and say which orderings it gets wrong. Then explain why \(\lceil \log_2 (n!) \rceil\) is a lower bound on the worst case but not a promise that it is achievable.
    solution A tree of height \(2\) has at most \(4\) leaves, but \(3! = 6\) orderings must be told apart, so at least two pairs of orderings share a leaf. Whichever permutation such a leaf emits, it is wrong for at least one of the two inputs that reach it; which orderings suffer depends on the two comparisons chosen, but some pair always does. The counting argument bounds the height from below and says nothing about whether a tree of that height exists: it is a statement about information, and building a tree also requires that every internal node’s question be answerable by one comparison of two keys, which is a real constraint. For \(n = 3\) the bound \(\lceil \log_2 6\rceil = 3\) is met, and for \(n = 4\) and \(n = 5\) the bounds \(\lceil 4.58 \rceil = 5\) and \(\lceil 6.91 \rceil = 7\) are met as well; but at \(n = 12\) the bound is \(\lceil \log_2 12! \rceil = \lceil 28.84 \rceil = 29\) while no algorithm does better than \(30\). A lower bound is a floor, not a blueprint.
