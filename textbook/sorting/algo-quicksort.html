Quicksort

Tony Hoare invented quicksort in 1959, as a visiting student in Moscow, to sort the words of sentences for a machine translation project. C. A. R. Hoare, “Quicksort,” The Computer Journal 5(1), 1962

Quicksort sorts in place by divide-and-conquer with the work in the divide step: a linear partition around a pivot. The average cost is \(\Theta(n\log n)\) with a constant small enough to make it the practical default; the worst case is \(\Theta(n^2)\), and pivot choice is what keeps it away. The paradigm and the master theorem are in the Divide-and-Conquer handout; the \(\Omega(n\log n)\) floor no comparison sort can beat is in the Sorting Lower Bound handout.

1. The algorithm: partition, then recurse

Quicksort is mergesort’s mirror image: the divide does the work and the combine is free. It partitions the array around a chosen pivot so that smaller elements come before it and larger after (leaving the pivot in its final sorted position), then recurses on each side. Once both sides are sorted, the whole array is sorted, in place, with no merge buffer.

Example (Lomuto partition, pivot = last) Partition \([3, 7, 1, 9, 4, 8, 6, 2, 5]\) with pivot \(5\). The index \(i\) marks the boundary of the “\(< 5\)” region; whenever an element beats the pivot, grow the region and swap the element in: Every row of that trace is the loop body if (a[j] < pivot) swap(a[++i], a[j]); with a different j: a take is the test succeeding, a skip is the test failing, and nothing else ever happens inside the loop. j is the scan and visits every slot once; i is the boundary of the “< pivot” region and advances only when something belongs in it. When i and j are the same slot the swap is a no-op (as at j=0): harmless, and not worth a branch to avoid. The pivot \(5\) lands at index \(4\), its final sorted position; everything left is \(< 5\), everything right is \(> 5\), though neither side is yet sorted; the keys the scan skipped, \(7, 9, 8, 6\), end up on the right as \(8, 6, 9, 7\), because a partition promises nothing about the order within a side. That single linear pass is what quicksort recurses around. 
// Lomuto partition around the last element as pivot. Elements < pivot are moved
// to the front; the pivot ends in its final sorted slot, whose index is returned.
int partition(int a[], int lo, int hi) {
    int pivot = a[hi];
    int i = lo - 1;                       // boundary of the "< pivot" region
    for (int j = lo; j < hi; j++)
        if (a[j] < pivot)
            swap(a[++i], a[j]);           // grow the region, swap the element in
    swap(a[i + 1], a[hi]);                // drop the pivot just past the region
    return i + 1;                         // the pivot's final index
}

// Quicksort: partition, then recurse on each side. No combine step.
void quicksort(int a[], int lo, int hi) {
    if (hi <= lo) return;                 // base case: 0 or 1 element
    int p = partition(a, lo, hi);         // pivot lands at its final index p
    quicksort(a, lo, p - 1);              // sort the smaller side
    quicksort(a, p + 1, hi);              // sort the larger side
}

// Lomuto partition around the last element as pivot. Elements < pivot are moved
// to the front; the pivot ends in its final sorted slot, whose index is returned.
fn partition(a: &mut [i32], lo: usize, hi: usize) -> usize {
    let pivot = a[hi];
    let mut i = lo;                       // next free slot of the "< pivot" region
    for j in lo..hi {
        if a[j] < pivot {
            a.swap(i, j);                 // swap the element into the region
            i += 1;
        }
    }
    a.swap(i, hi);                        // drop the pivot into its final slot
    i                                     // the pivot's final index
}

// Quicksort: partition, then recurse on each side. No combine step.
fn quicksort(a: &mut [i32], lo: usize, hi: usize) {
    if hi <= lo { return; }               // base case: 0 or 1 element
    let p = partition(a, lo, hi);         // pivot lands at its final index p
    if p > lo { quicksort(a, lo, p - 1); }   // guard: usize cannot go below 0
    quicksort(a, p + 1, hi);              // sort the larger side
}

The partition loop has only two branches (take the element, or skip it), but the partition as a whole has three outcomes that matter, decided by where the pivot lands:

Example (the two degenerate pivots) The pivot ends at index \(p\), splitting the range into \(p - lo\) elements on the left and \(hi - p\) on the right. The extremes are where quicksort goes quadratic, and both are worth running by hand. Both peel exactly one element off a range of size \(m\) after \(m-1\) comparisons, so a run of them obeys \(T(n) = T(n-1) + \Theta(n)\), which sums to \(\Theta(n^2)\). Already-sorted input with a last-element pivot hits the second case at every level: on \([1,2,3,4,5,6]\) the pivots are \(6, 5, 4, 3, 2\), five nested partitions doing \(5+4+3+2+1 = 15 = \binom{6}{2}\) comparisons and not a single useful swap. An all-equal array hits the first case at every level, because a[j] < pivot is false for every element.

Hoare’s partition

Lomuto is the one to learn first; Hoare’s original scheme (1961) is the one libraries use. The pivot is now a[lo], the FIRST element, and two pointers walk toward each other: i moves right while keys are smaller than the pivot, j moves left while keys are bigger. When both stop, the two keys they are looking at are on the wrong sides of each other, so one swap fixes both. When the pointers cross, j marks where the pivot belongs.

The difference in one sentence Lomuto asks “does this element belong on the left?” once per element and pays a swap every time the answer is yes; Hoare asks “is this pair inverted?” and pays one swap per inverted pair. A random array straddling a pivot has far fewer inverted pairs than it has small elements, so Hoare moves much less data.

One swap inside the scan against Lomuto’s four on the same array, and the keys between the pointers were never touched. Two details are where implementations go wrong. First, the scans stop on keys equal to the pivot rather than running past them; that looks wasteful and is the opposite: it is what keeps duplicates from degenerating (below). Second, the loop does not place the pivot; the final swap does. CLRS teaches a variant that returns a split point without placing the pivot, so its recursion is sort(lo, j) and sort(j+1, hi) rather than excluding an index; both are correct, but mixing the two is an infinite recursion.

The last row is the one that matters. With every key equal, Lomuto’s test a[j] < pivot is false for every element, so i never advances, the pivot lands at the boundary, and each level peels off exactly one element: \(\Theta(n^2)\). Hoare’s scans both stop immediately on equal keys, so the pointers meet in the middle and the recursion stays balanced. Measured at \(n = 8, 16, 24\): Lomuto takes \(28, 120, 276\) comparisons (about \(0.46n^2\)) and Hoare \(18, 50, 90\) (about \(0.78 n\log_2 n\)). So “quicksort is quadratic on duplicates” is a statement about Lomuto; the case that defeats both is many duplicates but not all, which is what 3-way partitioning is for.

Why the average really is \(n\log n\)

“Average \(\Theta(n\log n)\)” is usually justified by assuming the pivot splits the array in half, which is the best case wearing an average’s clothes. The honest argument counts comparisons over all pivot sequences, and it is short.

Fix the sorted order and name the elements by rank, \(z_1 < z_2 < \cdots < z_n\). Quicksort only ever compares an element against a pivot, so any two elements are compared at most once. When are \(z_i\) and \(z_j\) (\(i < j\)) compared at all? Consider the block of ranks \(z_i, \ldots, z_j\) and ask which of them is chosen as a pivot first. If it is \(z_i\) or \(z_j\), the two are compared. If it is any of the \(j-i-1\) elements strictly between them, that pivot separates them into different subarrays and they are never compared again. With a random pivot each of the \(j-i+1\) ranks is equally likely to be drawn first, so \[ \Pr[z_i \text{ and } z_j \text{ are compared}] \;=\; \frac{2}{j-i+1}. \] Summing over all pairs, with \(k = j - i + 1\), \[ E[\text{comparisons}] \;=\; \sum_{i=1}^{n}\sum_{j>i} \frac{2}{j-i+1} \;<\; \sum_{i=1}^{n} \sum_{k=2}^{n} \frac{2}{k} \;=\; 2n\,H_n \;\approx\; 2n\ln n \;\approx\; 1.39\,n\log_2 n. \]

What the constant tells you Mergesort makes about \(n\log_2 n\) comparisons; quicksort averages \(1.39\,n\log_2 n\): more. Quicksort is faster in practice despite comparing more, because it sorts in place, moves less data, and scans contiguously. When someone says “quicksort is faster,” they are talking about the constant on memory traffic, not on comparisons.

The worst case, and how to defeat it

Quicksort’s balance depends on the pivot, and a bad pivot is disastrous.

Proposition (quicksort cost) With balanced pivots quicksort obeys \(T(n) = 2T(n/2) + \Theta(n) = \Theta(n\log n)\). With a pivot that always peels off one element, \(T(n) = T(n-1) + \Theta(n)\), it degrades to \(\Theta(n^2)\).

The quadratic case is not exotic: a fixed last-element pivot on already-sorted input picks the maximum every time, peeling one element per level for \(n\) levels: exactly \(n-1 + n-2 + \cdots + 1 = \binom{n}{2}\) comparisons. The fix is the pivot:

  • a first or last element pivot is \(\Theta(n^2)\) on sorted data: never use it there;
  • a random pivot (or shuffling first) gives expected \(\Theta(n\log n)\) on every input: the \(\Theta(n^2)\) event now depends on coin flips, not the data, so an adversary who knows your code still cannot force it;
  • median-of-three (first, middle, last) is a cheap heuristic that dodges the sorted-input trap in practice.
Proposition (expected comparisons, CLRS) Randomized quicksort makes \(2(n+1)H_n - 4n \approx 2n\ln n \approx 1.39\,n\log_2 n\) comparisons in expectation, where \(H_n\) is the \(n\)-th harmonic number.
Sketch (indicator random variables). Let \(z_1 < z_2 < \cdots < z_n\) be the elements in sorted order. Two elements are compared at most once during the whole sort, and \(z_i\) and \(z_j\) are compared exactly when the first pivot chosen from the range \(\{z_i, \dots, z_j\}\) is \(z_i\) or \(z_j\) themselves; if any middle element is picked first, it splits them into different subarrays and they never meet. Among the \(j - i + 1\) equally likely first-pivots in that range, two are favorable, so \(\Pr[z_i \text{ compared with } z_j] = \tfrac{2}{j-i+1}\). By linearity of expectation the total is \[ \sum_{i<j}\frac{2}{j-i+1} = \sum_{i=1}^{n-1}\sum_{k=1}^{n-i}\frac{2}{k+1} = O(n\log n), \] the inner sum being a harmonic number \(\approx \ln n\). ∎

So quicksort averages about \(39\%\) more comparisons than the \(n\log_2 n\) information-theoretic floor of the Sorting Lower Bound handout, yet it is the fastest sort in practice, because each comparison and swap is so cheap and cache-friendly that its small constant beats mergesort’s larger one. Asymptotics tie; the constant, and the memory traffic behind it, decide.

Space: the recursion stack

Quicksort partitions in place, so it allocates no buffer at all. Its auxiliary space is entirely the call stack, and the same pivot luck that decides the time decides the depth.

Proposition (auxiliary space) Each frame of quicksort holds a constant number of indices, so the auxiliary space is \(\Theta(1)\) times the depth of the recursion. That depth is \(\Theta(\log n)\) in expectation with a random pivot and \(\Theta(n)\) in the worst case. Recursing into the smaller side and looping on the larger makes it \(O(\log n)\) unconditionally.
Why. The depth is the height of the recursion tree. Worst case: the two degenerate pivots above peel one element per level, so the tree is a path of \(n-1\) frames and the stack is \(\Theta(n)\). This is a real failure mode and not a theoretical one: a last-element pivot on a large already-sorted array overflows the call stack before it ever exhausts its time budget. Expected case: call a pivot good if its rank falls in the middle half of its range, that is, between \(m/4\) and \(3m/4\) of a range of size \(m\). Half the ranks qualify, so a uniformly random pivot is good with probability \(\tfrac12\), and a good pivot leaves both sides with at most \(\tfrac34 m\) elements. Follow one root-to-leaf path: after \(k\) good pivots the range is down to \((3/4)^k n\) elements, which reaches \(1\) once \(k \ge \log_{4/3} n \approx 2.41\log_2 n\). Since each pivot on the path is good with probability \(\tfrac12\), the expected number of pivots needed to collect that many good ones is at most \(2\log_{4/3} n \approx 4.8\log_2 n\), so the expected depth is \(\Theta(\log n)\); a Chernoff bound upgrades this to “every path is \(O(\log n)\) deep” with probability \(1 - n^{-c}\). The unconditional fix: after partitioning, recurse into the smaller side and replace the call on the larger side with an assignment to lo or hi and a loop back to the top, which costs no stack at all. The smaller side of a range of size \(m\) has at most \(\lfloor (m-1)/2 \rfloor\) elements, so a frame at depth \(d\) covers at most \(n/2^d\) elements and the depth cannot exceed \(\log_2 n\), whatever the pivots do. The comparison count is unchanged. ∎

So mergesort’s \(\Theta(n)\) buffer against quicksort’s \(\Theta(\log n)\) stack is quicksort’s other advantage, and the one that decides the matter when the array is large enough that the buffer will not fit beside it (the Space Complexity handout works the byte counts).

Duplicates and 3-way partitioning Lomuto is quadratic on an array of many equal keys (its test never fires, so the pivot lands at the boundary every level); Hoare splits such an array down the middle and is \(\Theta(n\log n)\), which is fine but still makes \(\log n\) passes over keys already known to be equal. Splitting into three regions (less than, equal to, and greater than the pivot) parks every equal key in the middle, done, so recursion touches only the strictly-smaller and strictly-larger parts: all-equal input becomes a single linear pass. This makes quicksort robust on real data with repeated keys.

The classical version is Dijkstra’s three-way partition (the “Dutch national flag” problem: sort a row of red, white and blue in one pass). One scan index \(i\) and two boundaries maintain three regions plus an unexamined middle, and the loop body has exactly three branches, one per comparison outcome: 

// Three-way (Dutch national flag) quicksort. Invariant during the scan:
//   a[lo..lt-1] < v      a[lt..i-1] == v      a[i..gt] unexamined      a[gt+1..hi] > v
void sort3way(int a[], int lo, int hi) {
    if (hi <= lo) return;                 // base case: 0 or 1 element
    int v = a[lo];                        // pivot: the first element
    int lt = lo, i = lo + 1, gt = hi;
    while (i <= gt) {
        if      (a[i] < v) swap(a[lt++], a[i++]);  // grow the "< v" region
        else if (a[i] > v) swap(a[i], a[gt--]);    // grow the "> v" region; RESCAN i
        else               i++;                    // equal: leave it, it is home
    }
    sort3way(a, lo, lt - 1);              // strictly smaller keys only
    sort3way(a, gt + 1, hi);              // strictly larger keys only
}

static void sort3way(int[] a, int lo, int hi) {

    int v = a[lo];                        // pivot: the first element
    int lt = lo, i = lo + 1, gt = hi;
    while (i <= gt) {
        if (a[i] < v) {                   // grow the "< v" region
            int t = a[lt]; a[lt] = a[i]; a[i] = t; lt++; i++;
        } else if (a[i] > v) {            // grow the "> v" region; RESCAN i
            int t = a[i]; a[i] = a[gt]; a[gt] = t; gt--;
        } else {
            i++;                          // equal: leave it, it is home
        }
    }
    sort3way(a, lo, lt - 1);              // strictly smaller keys only
    sort3way(a, gt + 1, hi);              // strictly larger keys only
}

def sort3way(a, lo, hi):
    if hi <= lo:                          # base case: 0 or 1 element
        return
    v = a[lo]                             # pivot: the first element
    lt, i, gt = lo, lo + 1, hi
    while i <= gt:
        if a[i] < v:                      # grow the "< v" region
            a[lt], a[i] = a[i], a[lt]
            lt += 1
            i += 1
        elif a[i] > v:                    # grow the "> v" region; RESCAN i
            a[i], a[gt] = a[gt], a[i]
            gt -= 1
        else:
            i += 1                        # equal: leave it, it is home
    sort3way(a, lo, lt - 1)               # strictly smaller keys only
    sort3way(a, gt + 1, hi)               # strictly larger keys only
// Three-way (Dutch national flag) quicksort. Invariant during the scan:
//   a[lo..lt-1] < v   a[lt..i-1] == v   a[i..gt] unexamined   a[gt+1..hi] > v
fn sort3way(a: &mut [i32], lo: usize, hi: usize) {
    if hi <= lo { return; }               // base case: 0 or 1 element
    let v = a[lo];                        // pivot: the first element
    let (mut lt, mut i, mut gt) = (lo, lo + 1, hi);
    while i <= gt {
        if a[i] < v {                     // grow the "< v" region
            a.swap(lt, i); lt += 1; i += 1;
        } else if a[i] > v {              // grow the "> v" region; RESCAN i
            a.swap(i, gt); gt -= 1;
        } else {
            i += 1;                       // equal: leave it, it is home
        }
    }
    if lt > lo { sort3way(a, lo, lt - 1); }   // guard: usize cannot go below 0
    sort3way(a, gt + 1, hi);                  // strictly larger keys only
}

Example (three-way partition on repeated keys) Partition \([5, 3, 5, 9, 5, 1, 5]\) with \(v = a[lo] = 5\): four copies of the pivot value, which is exactly the case Lomuto handles worst. The scan starts at \(i = lo+1\) because \(a[lo]\) is the pivot itself and is already in the “\(=v\)” region. Now \(i > gt\) and the pass is over after six steps on seven elements. The result is \([\,3\ 1\ \mid\ 5\ 5\ 5\ 5\ \mid\ 9\,]\): the four \(5\)s are in their final slots \(2..5\) and are never looked at again, so the recursion runs on \([3, 1]\) and on \([9]\) only. The one detail worth flagging is that the \(a[i] > v\) branch does not advance \(i\): the value swapped in from position \(gt\) has never been examined, so it must be rescanned, and the row after the swap does exactly that on the \(5\) that arrived from index \(6\). With every key equal, the pass is all middle branch: Compare that with Lomuto’s \(\Theta(n^2)\) and Hoare’s \(\Theta(n\log n)\) on the same input, and with the general bound: three-way quicksort runs in time proportional to \(n H\), where \(H\) is the entropy of the key distribution, so an array with a constant number of distinct values is sorted in linear time. This is why library sorts partition three ways when duplicates are expected.

2. Choosing a sort in practice

The two great sorts are duals (mergesort works in the combine, quicksort in the divide), and each wins where the other is weak.

mergesortquicksort
dividetrivial (split)partition (the work)
combinemerge (the work)trivial (in place)
time\(\Theta(n\log n)\) always\(\Theta(n\log n)\) avg, \(\Theta(n^2)\) worst
space\(\Theta(n)\) buffer\(\Theta(\log n)\) stack (expected)
stableyesno

Their asymptotics tie, so the constant factor decides, and quicksort’s is smaller: it sorts in place (no buffer to allocate or pollute the cache), and its partition is a contiguous scan the prefetcher loves. That is why the C++ default std::sort is quicksort-based, while mergesort is chosen when you need a guaranteed \(\Theta(n\log n)\), stability, or are sorting a linked list (merge needs no random access) or external data too big for memory. Real library sorts are hybrids that get the best of each:

  • introsort (std::sort) runs quicksort, falls back to heapsort if the recursion goes too deep (guaranteeing \(\Theta(n\log n)\)), and uses insertion sort on tiny subarrays where its low overhead wins;
  • Timsort (Python’s sort, Java’s object sort) is a mergesort that detects existing sorted runs; it is stable and very fast on partly-sorted real data.

There is no single best sort; the choice depends on \(n\), the key type, and whether you need stability or a worst-case guarantee, the same “match the tool to the requirement” reasoning as the hash-table-versus-balanced-tree decision. And mergesort, quicksort, and quickselect are one paradigm read by one theorem: each is “split, recurse, combine,” and its cost falls straight out of its recurrence (the Divide-and-Conquer handout), quickselect’s single recursive call (\(T(n/2)+\Theta(n)\), not \(2T(n/2)+\Theta(n)\)) being exactly why it is linear rather than \(n\log n\).

  1. Partition \([5, 9, 3, 8, 6, 7]\) with the Lomuto scheme and pivot \(7\) (the last element). Show the array after placement, the pivot’s final index, and the two sides.
    solution \(5 < 7\) (\(i{=}0\)); \(9\) no; \(3 < 7\) swap \(\to 5\ 3\ 9\ 8\ 6\); \(8\) no; \(6 < 7\) swap \(\to 5\ 3\ 6\ 8\ 9\); place pivot by swapping index \(3\) with the last \(\to [5, 3, 6, 7, 9, 8]\). The pivot \(7\) lands at index \(3\); the left side is \(5\ 3\ 6\) (all \(< 7\)) and the right is \(9\ 8\) (all \(> 7\)); neither side is yet sorted.
  2. Exactly how many comparisons does quicksort with a last-element pivot make on the already-sorted input \([1, 2, 3, \dots, n]\), and why?
    solution The last element is always the maximum, so each partition places it at the top and leaves a sorted subarray of size \(n-1\), peeling one element per level. Partitioning a size-\(m\) subarray does \(m-1\) comparisons, so the total is \((n-1) + (n-2) + \cdots + 1 = \binom{n}{2} = \Theta(n^2)\). This is the worst case; a random pivot or an initial shuffle makes it expected \(\Theta(n\log n)\) instead.
  3. Run Hoare’s partition on \([6, 2, 8, 1, 9, 3]\) with pivot \(a[lo] = 6\). Give the swaps, the crossing point, and the final array.
    solution \(i\) walks right past \(2\) and stops at \(a[2] = 8\) (\(\ge 6\)); \(j\) walks left past nothing and stops at \(a[5] = 3\) (\(\le 6\)). \(i = 2 < j = 5\), so swap: \([6, 2, 3, 1, 9, 8]\). Restart: \(i\) passes \(3, 1\) and stops at \(a[4] = 9\); \(j\) passes \(9\) and stops at \(a[3] = 1\). Now \(i = 4 \ge j = 3\): crossed, no swap. The final swap(a[lo], a[j]) gives \([1, 2, 3, 6, 9, 8]\) with the pivot at index \(3\). One swap inside the scan plus the placement, and the pivot lands in the middle; Lomuto on the same array (pivot \(a[hi] = 3\)) makes three swaps and leaves the pivot at index \(2\).
  4. Partition \([4, 4, 2, 4, 7, 4]\) three ways with \(v = a[lo] = 4\), and say which subarrays the recursion then visits. How many comparisons does the whole three-way sort make on \([4,4,4,4,4,4]\)?
    solution \(lt = 0, i = 1, gt = 5\). \(a[1] = 4\) equal, \(i = 2\). \(a[2] = 2 < 4\): swap \(a[0], a[2]\), giving \([2, 4, 4, 4, 7, 4]\), \(lt = 1, i = 3\). \(a[3] = 4\) equal, \(i = 4\). \(a[4] = 7 > 4\): swap \(a[4], a[5]\), giving \([2, 4, 4, 4, 4, 7]\), \(gt = 4\), \(i\) unchanged. \(a[4] = 4\) equal, \(i = 5 > gt\): done. The result is \([\,2 \mid 4\ 4\ 4\ 4 \mid 7\,]\) with \(lt = 1, gt = 4\), so the recursion visits only \([0,0] = [2]\) and \([5,5] = [7]\), both base cases: the array is sorted. On the all-equal array every element takes the equal branch once, so the pass makes \(n - 1 = 5\) comparisons against \(v\) (each element compared for \(<\) then for \(>\), so \(10\) key comparisons on a strict count), both recursive ranges are empty, and the total is \(\Theta(n)\). Lomuto on the same input makes \(\binom{6}{2} = 15\) comparisons.
  5. A colleague reports that their quicksort crashes with a stack overflow on a \(10\)-million-element array that is already sorted, while the same code on a shuffled array of the same size runs fine. Explain, and give the one-line fix that bounds the stack without changing the comparison count.
    solution A last-element pivot on sorted input takes the “pivot is the largest” case at every level, so the recursion is a path of \(n - 1\) frames: \(\Theta(n)\) stack, which at \(10^7\) frames is far past any default stack size. On a shuffled array the expected depth is \(\Theta(\log n)\), about \(24\) levels, which is why that run survives. The fix is to recurse into the smaller side and iterate on the larger (if (p - lo < hi - p) { sort(lo, p-1); lo = p + 1; } else { sort(p+1, hi); hi = p - 1; } inside a while (lo < hi) loop): every frame then covers at most half the elements of its parent, so the depth is at most \(\log_2 n \approx 24\) whatever the input. It does not fix the \(\Theta(n^2)\) time; only the pivot choice does that.
