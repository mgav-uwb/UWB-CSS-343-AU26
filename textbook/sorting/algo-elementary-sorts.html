Elementary Sorts

Computer manufacturers of the 1960s estimated that more than a quarter of the running time on their machines was spent sorting. D. E. Knuth, The Art of Computer Programming, Volume 3, 1973

Three sorting methods run in \(\Theta(n^2)\) time and about ten lines of code: selection sort, insertion sort, and their refinement shellsort. They are the sorts the faster methods are built out of and measured against: insertion sort is the finisher inside production quicksort and mergesort, selection sort fixes the exact compare count that the \(\Omega(n\log n)\) lower bound argument is contrasted with, and shellsort is the one sort in wide use whose running time nobody has managed to characterize. This handout gives each of them in code, traces each of them completely on one input, and argues each cost rather than quoting it.

1. The problem, and how cost is counted

The input is an array \(a[0..n-1]\) of items drawn from a totally ordered set: any two items \(x\) and \(y\) satisfy exactly one of \(x < y\), \(x = y\), \(x > y\), and the order is transitive. The output is a permutation of the input in nondecreasing order.

Definitions A comparison sort learns about the input only by comparing pairs of items; it never inspects a key's internal structure. All four sorts here are comparison sorts.
  • A sort is in place if it uses \(O(1)\) auxiliary memory beyond the input array (a fixed number of index and item variables, independent of \(n\)).
  • A sort is stable if items with equal keys appear in the output in the same relative order they had in the input.
  • An inversion of an array is a pair of positions \(i < j\) with \(a[i] > a[j]\): a pair that is out of order. An array of \(n\) distinct items has between \(0\) inversions (sorted) and \(\binom{n}{2} = n(n-1)/2\) inversions (reversed).

Cost is counted in two operations, because the two scale differently with the size of an item: compares (evaluations of a[i] < a[j]) and exchanges (swaps of two array entries). Comparing two integers is cheap and comparing two long strings is not; moving a 4-byte integer is cheap and moving a 400-byte record is not. A sort with few exchanges and many compares can beat one with the opposite profile, or lose to it, depending on the item type, so both counts are reported throughout.

One eight-element array runs through the whole handout: 

  a = [ 6, 5, 3, 1, 8, 7, 2, 4 ]      n = 8, 16 inversions

The \(16\) inversions are the pairs \((6,5), (6,3), (6,1), (6,2), (6,4), (5,3), (5,1), (5,2), (5,4), (3,1), (3,2), (8,7), (8,2), (8,4), (7,2), (7,4)\). Out of a possible \(28\), so the array is moderately, not pathologically, disordered.

2. Selection sort

Selection sort makes the sorted prefix grow one position per round. At round \(i\) it scans \(a[i..n-1]\) for the smallest remaining item and exchanges that item into position \(i\). After \(n-1\) rounds, position \(n-1\) necessarily holds the largest item, and the array is sorted.

Invariant Before round \(i\): the entries \(a[0..i-1]\) are in final sorted position, and every one of them is \(\le\) every entry of \(a[i..n-1]\). Round \(i\) preserves the invariant with \(i\) increased by one, because the item it puts at position \(i\) is a minimum of \(a[i..n-1]\), hence \(\ge\) everything in the prefix (by the second half of the invariant) and \(\le\) everything left behind. 
// Selection sort: n-1 rounds; round i puts the minimum of a[i..n-1] at a[i].
// Compares: exactly n(n-1)/2. Exchanges: exactly n-1. On every input.
void selection_sort(int a[], int n) {
    for (int i = 0; i < n - 1; i++) {
        int min = i;                          // index of the smallest seen
        for (int j = i + 1; j < n; j++)       // scan the unsorted suffix
            if (a[j] < a[min]) min = j;       // the ONE compare of this step
        std::swap(a[i], a[min]);              // no-op when min == i
    }
}
// Selection sort: n-1 rounds; round i puts the minimum of a[i..n-1] at a[i].
// Compares: exactly n(n-1)/2. Exchanges: exactly n-1. On every input.
static void selectionSort(int[] a) {
    int n = a.length;
    for (int i = 0; i < n - 1; i++) {
        int min = i;                          // index of the smallest seen
        for (int j = i + 1; j < n; j++)       // scan the unsorted suffix
            if (a[j] < a[min]) min = j;       // the ONE compare of this step
        int t = a[i]; a[i] = a[min]; a[min] = t;   // no-op when min == i
    }
}
# Selection sort: n-1 rounds; round i puts the minimum of a[i..n-1] at a[i].
# Compares: exactly n(n-1)/2. Exchanges: exactly n-1. On every input.
def selection_sort(a):
    n = len(a)
    for i in range(n - 1):
        m = i                                 # index of the smallest seen
        for j in range(i + 1, n):             # scan the unsorted suffix
            if a[j] < a[m]:                   # the ONE compare of this step
                m = j
        a[i], a[m] = a[m], a[i]               # no-op when m == i
// Selection sort: n-1 rounds; round i puts the minimum of a[i..n-1] at a[i].
// Compares: exactly n(n-1)/2. Exchanges: exactly n-1. On every input.
fn selection_sort(a: &mut [i32]) {
    let n = a.len();
    for i in 0..n.saturating_sub(1) {
        let mut min = i;                      // index of the smallest seen
        for j in (i + 1)..n {                 // scan the unsorted suffix
            if a[j] < a[min] { min = j; }     // the ONE compare of this step
        }
        a.swap(i, min);                       // no-op when min == i
    }
}

Two features of the trace are worth naming. Round \(i = 2\) exchanges \(a[2]\) with itself, because \(3\) is already in place: the code still performs the swap, so the exchange count stays at exactly \(n-1 = 7\) regardless of input (\(6\) of the \(7\) move something here). And the array is fully sorted after round \(i = 6\), yet the algorithm cannot know that: it has no test that could stop it early, which is the next theorem.

Exactly \(n(n-1)/2\) compares, on every input

Theorem On an array of \(n\) items, selection sort as written above performs exactly \(n(n-1)/2\) compares and exactly \(n-1\) exchanges, for every input array.
The outer loop runs once for each \(i \in \{0, 1, \dots, n-2\}\), a fixed set determined by \(n\). For a fixed \(i\), the inner loop runs once for each \(j \in \{i+1, \dots, n-1\}\) and performs exactly one compare per iteration, namely \(a[j] < a[\mathit{min}]\). That is \(n-1-i\) compares. Nothing inside the inner loop can change the loop bounds: the body's only effect is the assignment \(\mathit{min} \leftarrow j\), which alters which entry the next compare reads but not how many compares occur. Summing, \[ \sum_{i=0}^{n-2} (n-1-i) \;=\; \sum_{k=1}^{n-1} k \;=\; \frac{n(n-1)}{2}. \] The exchange count is immediate: the outer loop body contains exactly one unconditional swap, and the body runs \(n-1\) times. Both totals depend on \(n\) alone. □

The trace confirms the count: \(7 + 6 + 5 + 4 + 3 + 2 + 1 = 28 = 8 \cdot 7 / 2\), which is the last entry of the running column.

Oblivious to input order A stronger statement than the count holds: the sequence of index pairs selection sort compares is \((0,1), (0,2), \dots\) determined by \(n\) alone, identical for every input. Running selection sort on the already-sorted \([1,2,3,4,5,6,7,8]\) costs the same \(28\) compares and \(7\) exchanges as running it on \([8,7,6,5,4,3,2,1]\). There is no best case and no worst case: best, average, and worst are all \(\Theta(n^2)\) compares and \(\Theta(n)\) exchanges. Selection sort is therefore the wrong choice when inputs are often nearly sorted, and the right choice in exactly one situation: when an exchange is enormously more expensive than a compare, since \(n-1\) exchanges is the fewest of any sort here, and no other sort in this handout can promise a linear bound on data movement.
Example (selection sort is not stable) Label two equal keys to tell them apart: input \([\,2_a,\ 2_b,\ 1\,]\). Round \(i = 0\) finds the minimum \(1\) at index \(2\) and swaps it with \(a[0] = 2_a\), giving \([\,1,\ 2_b,\ 2_a\,]\). Round \(i = 1\) compares \(2_a\) against \(2_b\), finds nothing smaller, and swaps \(a[1]\) with itself. Output: \([\,1,\ 2_b,\ 2_a\,]\). The two equal keys came out reversed, so the sort is not stable. The culprit is the long-distance swap, which can throw an item over an equal one arbitrarily far away.

3. Insertion sort

Insertion sort also grows a sorted prefix, but it grows it by taking the next item and sliding it left into its place among the items already seen, the way a hand of playing cards gets sorted. The difference from selection sort is decisive: the prefix is sorted but not final, because a later item can land anywhere inside it.

Invariant Before step \(i\): the entries \(a[0..i-1]\) are in sorted order among themselves, and they are exactly the first \(i\) items of the input (in some order). Step \(i\) exchanges \(a[i]\) leftward past every entry strictly greater than it and stops at the first entry that is \(\le\) it, restoring the invariant for \(i+1\). Nothing to the right of \(i\) has been touched. 
// Insertion sort: slide a[i] left past every strictly larger entry.
// Exchanges = number of inversions. Compares = exchanges + (stops before 0).
void insertion_sort(int a[], int n) {
    for (int i = 1; i < n; i++)
        // STRICT < is what makes the sort stable: an equal entry stops the
        // slide, so a[i] never passes an equal key that came before it.
        for (int j = i; j > 0 && a[j] < a[j - 1]; j--)
            std::swap(a[j], a[j - 1]);
}
// Insertion sort: slide a[i] left past every strictly larger entry.
// Exchanges = number of inversions. Compares = exchanges + (stops before 0).
static void insertionSort(int[] a) {
    for (int i = 1; i < a.length; i++)
        // STRICT < is what makes the sort stable: an equal entry stops the
        // slide, so a[i] never passes an equal key that came before it.
        for (int j = i; j > 0 && a[j] < a[j - 1]; j--) {
            int t = a[j]; a[j] = a[j - 1]; a[j - 1] = t;
        }
}
# Insertion sort: slide a[i] left past every strictly larger entry.
# Exchanges = number of inversions. Compares = exchanges + (stops before 0).
def insertion_sort(a):
    for i in range(1, len(a)):
        j = i
        # STRICT < is what makes the sort stable: an equal entry stops the
        # slide, so a[i] never passes an equal key that came before it.
        while j > 0 and a[j] < a[j - 1]:
            a[j], a[j - 1] = a[j - 1], a[j]
            j -= 1
// Insertion sort: slide a[i] left past every strictly larger entry.
// Exchanges = number of inversions. Compares = exchanges + (stops before 0).
fn insertion_sort(a: &mut [i32]) {
    for i in 1..a.len() {
        let mut j = i;
        // STRICT < is what makes the sort stable: an equal entry stops the
        // slide, so a[i] never passes an equal key that came before it.
        while j > 0 && a[j] < a[j - 1] {
            a.swap(j, j - 1);
            j -= 1;
        }
    }
}

      a[j + 1] = key;                                         // drop it in
  }

What the counts are, exactly

Theorem On an array with \(I\) inversions, insertion sort performs exactly \(I\) exchanges, and \(C\) compares with \[ \max(I,\ n-1) \;\le\; C \;\le\; I + n - 1 . \]
Exchanges. Every exchange is of adjacent entries \(a[j-1]\) and \(a[j]\) with \(a[j] < a[j-1]\). Swapping two adjacent entries leaves the relative order of every other pair untouched and flips the order of this one pair, so it changes the inversion count by exactly \(-1\) here. The array starts with \(I\) inversions and ends sorted, with \(0\), so exactly \(I\) exchanges occur.
Compares. Step \(i\) performs one compare per move plus, if the slide stops before reaching index \(0\), one final failed compare. Hence \(C = I + s\), where \(s\) is the number of steps that stop in the interior, and \(0 \le s \le n-1\) since there are \(n-1\) steps. That gives \(I \le C \le I + n - 1\). Each of the \(n-1\) steps performs at least one compare (either it moves at least once, or it stops at once), so \(C \ge n-1\) as well. □

The trace matches: the array has \(I = 16\) inversions and the trace ends at \(16\) exchanges. Four steps stopped in the interior (\(i = 4, 5, 6, 7\)), so \(s = 4\) and \(C = 16 + 4 = 20\), inside the predicted window \([16, 23]\).

Best case, sorted input. Every step fails its first compare and moves nothing: \(n-1 = 7\) compares, \(0\) exchanges, \(\Theta(n)\) time. No sort in this handout beats that, and selection sort does not come close to it. Worst case, reversed input. Every item is smaller than everything before it, so step \(i\) makes \(i\) moves and \(i\) compares: \(\sum_{i=1}^{n-1} i = n(n-1)/2 = 28\) of each, \(\Theta(n^2)\). Average case, over a uniformly random permutation of distinct keys: each of the \(\binom{n}{2}\) pairs is an inversion with probability \(1/2\), so \(\mathbb{E}[I] = n(n-1)/4\), and both counts are \(\sim n^2/4\), half the worst case but still quadratic.

Why this makes insertion sort useful \(C \le I + n - 1\) is a much sharper statement than \(O(n^2)\): the running time is linear in the amount of disorder, not in the size. An array where no item is more than \(k\) positions from its final place has \(I \le kn\), so insertion sort finishes it in \(O(kn)\) time, which is \(O(n)\) for constant \(k\). Two consequences used elsewhere: an almost-sorted array (a sorted log with a few late arrivals appended, say) is sorted in near-linear time; and a small subarray, of size at most \(k\), is sorted in \(O(k^2)\) time with a tiny constant, which is why insertion sort is the finisher inside faster sorts (§7).
Example (insertion sort is stable) Same labelled input \([\,2_a,\ 2_b,\ 1\,]\). Step \(i = 1\) compares \(2_b < 2_a\), which is false (the test is strict), so nothing moves: \([\,2_a,\ 2_b,\ 1\,]\). Step \(i = 2\) slides \(1\) past \(2_b\) and then past \(2_a\), reaching index \(0\): \([\,1,\ 2_a,\ 2_b\,]\). The equal keys kept their input order. In general an item never passes an equal item, because the loop guard a[j] < a[j-1] is false on equality, so equal keys can never change relative order; and every move is a swap of adjacent entries, which cannot leapfrog anything. Replacing < with <= destroys stability without changing the sorted output.

4. Shellsort

Insertion sort's weakness is visible in its own theorem: exchanges equal inversions, and each exchange removes exactly one inversion, because each exchange moves an item one position. An item that belongs \(k\) positions to the left needs \(k\) exchanges to get there. Shellsort (D. L. Shell, 1959) attacks that by sorting items that are far apart first, so that a single exchange can move an item a long distance and cancel many inversions at once.

Definition (\(h\)-sorted, \(h\)-sorting) An array is \(h\)-sorted if \(a[i] \le a[i+h]\) for every \(i\) with \(0 \le i < n - h\); equivalently, each of the \(h\) interleaved subsequences \(a[r], a[r+h], a[r+2h], \dots\) (for \(r = 0, \dots, h-1\)) is sorted. \(h\)-sorting an array means making it \(h\)-sorted, and the way to do it is insertion sort with the step size \(h\) in place of \(1\): the code is the insertion sort of §3 with every \(1\) replaced by \(h\). A \(1\)-sorted array is sorted.

Shellsort is: \(h\)-sort the array for each \(h\) in a decreasing gap sequence that ends at \(1\). The last pass is an ordinary insertion sort, so the output is correct no matter what the earlier passes did; the earlier passes exist only to make that last pass cheap. The gap sequence below is Shell's original, repeated halving, which for \(n = 8\) gives \(4, 2, 1\). 

// Shellsort with Shell's original halving gaps: n/2, n/4, ..., 1.
// The h == 1 pass IS insertion sort, so correctness never depends on the gaps.
void shellsort(int a[], int n) {
    for (int h = n / 2; h > 0; h /= 2)            // decreasing gaps, last is 1
        for (int i = h; i < n; i++)               // h-sort a[0..n-1]
            for (int j = i; j >= h && a[j] < a[j - h]; j -= h)
                std::swap(a[j], a[j - h]);        // one exchange of distance h
}
// Shellsort with Shell's original halving gaps: n/2, n/4, ..., 1.
// The h == 1 pass IS insertion sort, so correctness never depends on the gaps.
static void shellsort(int[] a) {
    int n = a.length;
    for (int h = n / 2; h > 0; h /= 2)            // decreasing gaps, last is 1
        for (int i = h; i < n; i++)               // h-sort a[0..n-1]
            for (int j = i; j >= h && a[j] < a[j - h]; j -= h) {
                int t = a[j]; a[j] = a[j - h]; a[j - h] = t;
            }
}
# Shellsort with Shell's original halving gaps: n//2, n//4, ..., 1.
# The h == 1 pass IS insertion sort, so correctness never depends on the gaps.
def shellsort(a):
    n = len(a)
    h = n // 2
    while h > 0:                                  # decreasing gaps, last is 1
        for i in range(h, n):                     # h-sort a[0..n-1]
            j = i
            while j >= h and a[j] < a[j - h]:
                a[j], a[j - h] = a[j - h], a[j]   # one exchange of distance h
                j -= h
        h //= 2
// Shellsort with Shell's original halving gaps: n/2, n/4, ..., 1.
// The h == 1 pass IS insertion sort, so correctness never depends on the gaps.
fn shellsort(a: &mut [i32]) {
    let n = a.len();
    let mut h = n / 2;
    while h > 0 {                                 // decreasing gaps, last is 1
        for i in h..n {                           // h-sort a[0..n-1]
            let mut j = i;
            while j >= h && a[j] < a[j - h] {
                a.swap(j, j - h);                 // one exchange of distance h
                j -= h;
            }
        }
        h /= 2;
    }
}

Why the passes help

The final pass of shellsort did the same job insertion sort does alone, but on an array with \(3\) inversions instead of \(16\): \(9\) compares and \(3\) exchanges, against \(20\) and \(16\). The two cheap earlier passes bought that reduction for \(14\) compares and \(7\) exchanges. Totals on this array:

The honest reading of that table: at \(n = 8\), shellsort saves six exchanges and pays three extra compares, and the margin over insertion sort is a rounding error. It has to be. Three passes over eight items cannot beat one pass by much, because the fixed cost of the extra passes (one compare per position per pass, at minimum) is a large fraction of the total. What the trace shows is the mechanism, and the mechanism is what scales: the inversion count fell \(16 \to 15 \to 3 \to 0\), and the expensive pass ran last, when there was almost nothing left to do.

The mechanism is clearest on the input that is worst for insertion sort, the reversed array \([8,7,6,5,4,3,2,1]\), where insertion sort needs \(28\) compares and \(28\) exchanges. Shellsort with the same gaps needs \(22\) and \(12\). The \(h = 4\) pass alone costs \(4\) compares and \(4\) exchanges and removes \(16\) of the \(28\) inversions:

A single exchange across a gap of \(h\) can remove up to \(2h-1\) inversions, against exactly \(1\) for insertion sort's adjacent exchange. That is the entire idea.

Lemma (\(h\)-sortedness survives later passes) If an array is \(h\)-sorted, then \(g\)-sorting it for any \(g\) leaves it \(h\)-sorted.
The proof is not short, and the standard reference (Knuth, The Art of Computer Programming, vol. 3, §5.2.1) argues it through the following fact about \(g\)-sorting: if \(x_1 \le y_1,\ \dots,\ x_m \le y_m\) are two sequences compared elementwise, then sorting the \(x\)'s and sorting the \(y\)'s preserves the elementwise inequality. Apply it with the \(x\)'s the positions \(i, i+g, i+2g, \dots\) and the \(y\)'s the positions \(i+h, i+h+g, \dots\): \(h\)-sortedness says \(x_k \le y_k\) throughout, the \(g\)-sort sorts both sequences (they are two of the interleaved subsequences the \(g\)-pass sorts), and the conclusion is exactly \(h\)-sortedness of the result. □

The trace shows the lemma at work: \([2, 1, 3, 4, 6, 5, 8, 7]\) is still 4-sorted after the \(h = 2\) pass. Without the lemma, a later pass could undo the work of an earlier one and the gap sequence would be pointless. With it, the array entering the \(h = 1\) pass is simultaneously \(h\)-sorted for every gap used, and the more gaps, the more constrained (that is, the fewer inversions) it must be.

What is known about shellsort's running time

Very little, and this is not a gap in the exposition: the running time of shellsort is a genuine open problem, and it is the reason shellsort is worth knowing about beyond its practical use. The cost depends entirely on the gap sequence, and the analysis is hard because after the first pass the array is no longer a random permutation but a conditioned one.

The halving sequence's \(\Theta(n^2)\) is easy to see and worth seeing, because it explains why the sequence in the code above is the one to replace in practice. Take \(n\) a power of two, put the \(n/2\) largest values in the even positions and the \(n/2\) smallest in the odd positions: 

  n = 16:  9 1 10 2 11 3 12 4 13 5 14 6 15 7 16 8       36 inversions

Every gap before the last is even, so every pass before \(h = 1\) compares only even positions with even positions and odd with odd. The evens are already sorted among themselves and so are the odds, so the \(h = 8, 4, 2\) passes make zero exchanges (\(8 + 12 + 14 = 34\) wasted compares), and the \(h = 1\) pass then faces all \(36\) inversions: \(50\) compares and \(36\) exchanges. Generalizing, the construction leaves \(\sum_{k=1}^{n/2} k = \Theta(n^2)\) inversions for the final pass. The cure is a sequence whose gaps are relatively prime, such as \(3x+1\).

What is not known is more interesting:

  • No tight worst-case bound is known for the \(3x+1\) sequence, the one most commonly recommended in practice.
  • The average-case running time is unknown for every gap sequence in practical use, including \(3x+1\) and Sedgewick's. It is not known even for three-gap sequences in general.
  • No sequence is known that makes shellsort \(O(n\log n)\), and none exists: Plaxton, Poonen and Suel proved in 1992 that every gap sequence forces \(\Omega\!\left(n \log^2 n / (\log\log n)^2\right)\) in the worst case, which is asymptotically above \(n\log n\). Pratt's \(\Theta(n\log^2 n)\) is within a \((\log\log n)^2\) factor of that barrier, but it uses \(\Theta(\log^2 n)\) gaps, and the per-pass overhead makes it slower than the alternatives at practical sizes.

The practical summary: shellsort is the sort to reach for when the code must be short and in place, recursion is unwelcome (embedded systems, kernel code, hard real-time constraints on stack depth), and \(n\) is in the thousands: it is a few times slower than a tuned quicksort and several times faster than anything quadratic, in about six lines.

Example (shellsort is not stable) Input \([\,2_a,\ 2_b,\ 1,\ 3\,]\) with gaps \(2, 1\). The \(h = 2\) pass compares \(a[2] = 1\) against \(a[0] = 2_a\) and swaps them, giving \([\,1,\ 2_b,\ 2_a,\ 3\,]\); it then compares \(3\) against \(2_b\) and stops. The \(h = 1\) pass finds nothing out of order. Output \([\,1,\ 2_b,\ 2_a,\ 3\,]\): the equal keys are reversed. Any pass with \(h > 1\) moves items across long distances and can jump an item over an equal one, exactly as selection sort's swap does.

5. Bubble sort

Bubble sort Bubble sort makes repeated left-to-right passes, exchanging each adjacent out-of-order pair as it meets it. One pass carries the largest remaining item all the way to the right end, so after pass \(k\) the last \(k\) positions are final and the next pass can stop \(k\) short. A pass with no exchange means the array is sorted, which lets the sort exit early on nearly-sorted input. 
void bubble_sort(int a[], int n) {
    for (int i = 0; i < n - 1; i++) {
        bool swapped = false;
        for (int j = 0; j < n - 1 - i; j++)     // last i entries are final
            if (a[j] > a[j + 1]) { std::swap(a[j], a[j + 1]); swapped = true; }
        if (!swapped) return;                   // sorted: stop early
    }
}

Bubble sort exchanges only adjacent out-of-order pairs, so, by the same argument as insertion sort's theorem, it performs exactly \(I\) exchanges: \(16\) here, matching insertion sort exactly. Its compares are the problem. Insertion sort stops each step as soon as the item lands, whereas bubble sort's inner loop always runs to the end of the unsorted region: \(27\) compares here against \(20\), and \(\Theta(n^2)\) compares on every input with more than one misplaced item, even when the array is nearly sorted. Bubble sort is stable and in place, and it is dominated by insertion sort on both counts on essentially every input; it appears here because it is widely taught and needs to be recognized, not because it should be used.

6. Stability, space, and the four side by side

All four sorts are in place: each uses a fixed number of index and item variables and no array proportional to \(n\). Two are stable, and the split is not accidental. A sort whose only data movement is the exchange of adjacent entries, performed only when they are strictly out of order, cannot reorder equal keys; a sort that moves items across distances greater than one can, and does.

\(I\) is the number of inversions in the input, between \(0\) and \(n(n-1)/2\), averaging \(n(n-1)/4\) over random permutations of distinct keys. Shellsort's best case is \(\Theta(n \log n)\) for a sequence of \(\Theta(\log n)\) gaps, since each pass makes at least one compare per position even when nothing moves.

Any unstable sort can be made stable by attaching the original index to each item as a tiebreaker, at a cost of \(\Theta(n)\) extra space. Stability is worth paying for because it makes sorting composable: to order records by department and then by name within each department, sort by name first, then stably by department, and the name order survives inside each department's block.

7. Where this sits

Everything in this handout is \(\Theta(n^2)\) or unproven, and the \(\Theta(n\log n)\) sorts take over from here. All three are in the catalog: Mergesort splits at the midpoint and does its work merging, buying a \(\Theta(n\log n)\) guarantee on every input and stability at the price of a \(\Theta(n)\) buffer; Quicksort partitions around a pivot and does its work dividing, running in place with the best constants of the three but a \(\Theta(n^2)\) worst case that randomization makes vanishingly unlikely; Heapsort reaches \(\Theta(n\log n)\) in place and without randomization by paying in cache locality. The shared method behind the first two is Divide and Conquer, and the reason none of them can do better is The Sorting Lower Bound: \(\Omega(n\log n)\) compares for any comparison sort. That lower bound is also the sharpest thing to say about selection sort's \(n(n-1)/2\): the information-theoretic minimum is \(\lceil \log_2 n! \rceil\) compares, which for \(n = 8\) is \(16\), against selection sort's \(28\) and insertion sort's \(20\) on the array traced above. Escaping \(\Omega(n\log n)\) requires giving up comparisons entirely, which is what Counting Sort & Radix Sort do; the same partition-based idea applied to selection rather than sorting is Quickselect.

Insertion sort does not retire when the faster sorts arrive: it becomes their base case. Both mergesort and quicksort recurse down to subarrays of size \(1\), and at that scale the recursion overhead (a call, two index computations, a partition or a merge setup) dominates the actual sorting work. Production implementations stop the recursion at a cutoff \(k\), typically between \(7\) and \(16\), and finish with insertion sort. For quicksort the standard arrangement is to leave every subarray of size \(\le k\) unsorted and run one insertion sort over the whole array at the end: after the partitioning, no item is more than \(k\) positions from its final place, so \(I \le kn\) and the finisher costs \(O(kn) = O(n)\) by the bound of §3. The three properties that make insertion sort right for the job are exactly the ones established above: it is in place, its constant factor is tiny, and its cost is proportional to the disorder that is left rather than to the size of the array.

The counting conventions used throughout (compares and exchanges, best against worst against average, the \(\Theta\) and \(\Omega\) notation) are set out in Asymptotic Notation and Time Analysis; the in-place claims are the \(O(1)\) auxiliary space of Space Complexity. Selection sort also has a second life: repeatedly removing the minimum from a binary heap is selection sort with the linear scan for the minimum replaced by a \(\Theta(\log n)\) heap operation, and that substitution is exactly heapsort.

8. Exercises (with solutions)

  1. Without running the algorithm, state how many compares selection sort makes on each of \([1,2,3,4,5,6,7,8]\), \([8,7,6,5,4,3,2,1]\), and \([6,5,3,1,8,7,2,4]\). Then say how many exchanges it makes on the first of the three, and how many of those exchanges move an item.
    solution \(28\) compares on all three, since the count \(n(n-1)/2\) with \(n = 8\) depends only on \(n\). On the sorted array the code performs \(n-1 = 7\) exchanges, every one of them a swap of \(a[i]\) with itself, so \(0\) of them move an item. This is the content of obliviousness: an already-sorted input is not detected and is not cheaper.

  3. Give a three-element input on which selection sort is not stable and insertion sort is, and identify the single operation responsible for the difference.
    solution \([\,2_a,\ 2_b,\ 1\,]\). Selection sort's first round swaps the minimum \(1\) (at index \(2\)) with \(a[0] = 2_a\), producing \([\,1,\ 2_b,\ 2_a\,]\), and the second round changes nothing: the equal keys are reversed. Insertion sort leaves \(2_b\) alone at step \(1\) (the test \(2_b < 2_a\) is false) and then slides \(1\) leftward past both, producing \([\,1,\ 2_a,\ 2_b\,]\). The operation responsible is the long-distance swap: selection sort throws \(a[0]\) to index \(2\), over an equal key, in one move. Insertion sort only ever exchanges adjacent entries, and only when they are strictly out of order, so equal keys can never cross.
  4. Prove that exchanging two entries \(a[i]\) and \(a[j]\) with \(i < j\) and \(a[i] > a[j]\) changes the inversion count by an odd amount, and that it removes at most \(2(j-i)-1\) inversions. Use this to bound how many inversions one exchange of shellsort's \(h\)-pass can remove, and compare with insertion sort.
    solution Write \(X = a[i]\) and \(Y = a[j]\), so \(X > Y\). Classify the pairs of positions by how many of \(i, j\) they contain. Neither: untouched. One endpoint, partner outside \([i,j]\): take such a position \(k\) and consider its two pairs, one with \(i\) and one with \(j\), together. Before the swap those two pairs compare \(a[k]\) against \(X\) and against \(Y\); after the swap they compare \(a[k]\) against \(Y\) and against \(X\). The same two comparisons occur in the other order, and \(k\) is on the same side of both \(i\) and \(j\), so their combined contribution is unchanged. The pair \((i,j)\) itself: it was an inversion and is not one afterwards, a change of \(-1\). One endpoint, partner strictly between: let \(Z = a[m]\) with \(i < m < j\). The pairs \((i,m)\) and \((m,j)\) contribute \([X > Z] + [Z > Y]\) before and \([Y > Z] + [Z > X]\) after. If \(Y < Z < X\) that is \(2\) before and \(0\) after, a change of \(-2\); otherwise (\(Z < Y\) or \(Z > X\)) it is \(1\) before and \(1\) after, a change of \(0\). So the total change is \(-1\) plus an even number: odd, and always a decrease. The most that can be removed is \(1 + 2(j-i-1) = 2(j-i)-1\), attained when every one of the \(j-i-1\) values in between lies strictly between \(Y\) and \(X\). For shellsort's \(h\)-pass, \(j - i = h\), so one exchange removes at most \(2h-1\) inversions and at least \(1\); for insertion sort \(h = 1\) and the answer is exactly \(1\). That is why shellsort's early passes can make so much progress for so few exchanges, and why its total exchange count can be far below the inversion count while insertion sort's is exactly equal to it.
  5. Shellsort with the halving sequence on \([\,9,\ 1,\ 10,\ 2,\ 11,\ 3,\ 12,\ 4,\ 13,\ 5,\ 14,\ 6,\ 15,\ 7,\ 16,\ 8\,]\) (\(n = 16\), gaps \(8, 4, 2, 1\)). How many exchanges do the \(h = 8, 4, 2\) passes make, and why? What does that make the total cost, and what property of the gap sequence is to blame?
    solution Zero exchanges in all three passes. The array places the eight largest values \(9..16\) in the even positions, in increasing order, and the eight smallest \(1..8\) in the odd positions, also in increasing order. The gaps \(8, 4, 2\) are all even, so every compare in those passes is between two even positions or between two odd positions, and both of those subsequences are already sorted: every compare succeeds and nothing moves. The three passes spend \(8 + 12 + 14 = 34\) compares learning nothing. The \(h = 1\) pass then faces the full inversion count, which is \(1 + 2 + \dots + 8 = 36\) (value \(k\) sits at index \(2k-1\) preceded by exactly \(k\) larger values), and costs \(50\) compares and \(36\) exchanges, for \(84\) and \(36\) overall. Generalizing the construction to any \(n = 2^m\) leaves \(\sum_{k=1}^{n/2} k = \Theta(n^2)\) inversions for the final pass, which is the \(\Theta(n^2)\) worst case of the halving sequence. The blame is that all its gaps share the factor \(2\), so positions of different parity are never compared until the end; a sequence of relatively prime gaps such as \(3x+1\) (\(1, 4, 13, 40, \dots\)) has no such blind spot.
  6. A quicksort implementation leaves every subarray of size \(\le k\) unsorted and runs a single insertion sort over the whole array at the end. Show that the finisher costs \(O(kn)\), and explain what goes wrong if selection sort or bubble sort is used instead.
    solution When the partitioning stops, the array is a concatenation of blocks of size at most \(k\), and every element is \(\le\) every element of every later block (that is what partitioning guarantees). An inversion can therefore only be between two positions in the same block, and a block of size \(s \le k\) contributes at most \(\binom{s}{2} < sk/2\) inversions. Summing over blocks whose sizes total \(n\) gives \(I < kn/2\), so by the theorem of §3 insertion sort finishes in \(C \le I + n - 1 = O(kn)\) compares and \(I = O(kn)\) exchanges, which is \(O(n)\) for constant \(k\). Selection sort would cost \(n(n-1)/2\) compares no matter how nearly sorted the array is, destroying the whole point: its cost does not depend on the input at all. Bubble sort would perform the right number of exchanges (\(I\), by the same adjacent-exchange argument) but \(\Theta(n^2)\) compares, because each of its passes scans the entire unsorted region and it needs one pass per block-sized displacement rather than stopping each item as soon as it lands. Only insertion sort's cost is proportional to the disorder that remains.
  7. Insertion sort's compares can be reduced by finding the insertion point with binary search instead of a linear scan (binary insertion sort). Give the resulting compare count and explain why the running time is still \(\Theta(n^2)\).
    solution Step \(i\) binary-searches a sorted prefix of length \(i\), using \(\lceil \log_2 (i+1) \rceil\) compares, so the total is \(\sum_{i=1}^{n-1} \lceil \log_2(i+1)\rceil = \Theta(n\log n)\) compares in the worst case, an improvement over \(\Theta(n^2)\). The running time does not improve, because the compares were never the bottleneck: the item still has to be moved into place, and moving it past \(m\) entries costs \(m\) shifts however the insertion point was located. The number of shifts is still exactly \(I\), which is \(\Theta(n^2)\) in the worst and average cases. Binary insertion sort is worth using precisely when a compare is much more expensive than a move, for instance when the keys are long strings and the array holds pointers to them. It also loses insertion sort's \(\Theta(n)\) best case: on sorted input it still spends \(\Theta(n\log n)\) compares confirming that nothing needs to move.
  8. After the \(h = 2\) pass of the §4 trace the array is \([2, 1, 3, 4, 6, 5, 8, 7]\). Verify that it is 2-sorted and 4-sorted, and use the lemma to argue that an array which is both 2-sorted and 3-sorted has each element at most one position from its final place. Which gap sequence does that suggest?
    solution 2-sorted: \(2\le3,\ 1\le4,\ 3\le6,\ 4\le5,\ 6\le8,\ 5\le7\), all true. 4-sorted: \(2\le6,\ 1\le5,\ 3\le8,\ 4\le7\), all true, and that 4-sortedness was inherited from the \(h = 4\) pass and preserved by the \(h = 2\) pass, which is the lemma. Now suppose an array is both 2-sorted and 3-sorted. Every index \(k \ge 2\) can be written as a nonnegative combination \(2p + 3q\), so \(a[i] \le a[i+k]\) for every \(k \ge 2\) by chaining the two guarantees along such a decomposition (\(a[i] \le a[i+2] \le a[i+4] \le \dots\), inserting one step of \(3\) if \(k\) is odd). The only pairs that may be out of order are the adjacent ones, so no element is more than one position from where it belongs, and the \(h = 1\) pass costs \(O(n)\). Generalizing, an array \(h\)-sorted for all \(h\) in a set whose numerical semigroup covers everything above some bound is nearly sorted; the gap sequence built from this observation is Pratt's, the numbers of the form \(2^p 3^q\), and it is the sequence with the best proved worst case, \(\Theta(n\log^2 n)\).
