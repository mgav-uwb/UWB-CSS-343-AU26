Mergesort

Data Structures & Algorithms. Algorithm (divide-and-conquer).
Mergesort, the “easy divide, hard combine” sort: cut the array in half, sort each half recursively, and merge the two sorted halves in linear time. The recurrence \(T(n) = 2T(n/2) + \Theta(n)\) and its \(\Theta(n\log n)\) solution, guaranteed on every input; top-down and bottom-up variants; stability; the \(\Theta(n)\) auxiliary buffer. With a worked merge trace, the merge’s four branches, a whole run unrolled call by call, the recursion tree, a link to the demo, and exercises.

Mergesort sorts by divide-and-conquer with the work in the combine step: a linear merge of two sorted halves. Its recurrence \(T(n) = 2T(n/2) + \Theta(n)\) solves to \(\Theta(n\log n)\) on every input by the master theorem (the Divide-and-Conquer handout), and the sort is stable; the price is a \(\Theta(n)\) auxiliary buffer.

1. The algorithm and its analysis

Mergesort is the “easy divide, hard combine” instance: cut the array in half (trivial), sort each half recursively, and merge the two sorted halves (the work). Because the split is always at the midpoint, the recursion is perfectly balanced and the \(\Theta(n\log n)\) is guaranteed on every input.

Example (the merge) Merge two sorted runs by repeatedly taking the smaller front element: 
  L: 2 5 8    R: 1 3 9    out: [ ]
  1 < 2 → out 1        L: 2 5 8   R: 3 9
  2 < 3 → out 2        L: 5 8     R: 3 9
  3 < 5 → out 3        L: 5 8     R: 9
  5 < 9 → out 5;  8 < 9 → out 8;  R tail 9 → out 9
  → 1 2 3 5 8 9
Each element is copied exactly once, so the merge is \(\Theta(n)\). The subtlety is the tail: when one run empties, append the rest of the other. Note that the merge cannot be done in place cheaply (it writes into a \(\Theta(n)\) auxiliary buffer, then copies back), which is mergesort’s one real drawback.
Example (the merge’s four branches) The loop body has exactly four branches, tested in this order. Every output position takes one of them, so a merge is fully described by which branch fires at each \(k\).

The trace above fires three of them: 1 < 2 and 3 < 5 are “right smaller”; 2, 5 and 8 are “left wins”; and the final \(9\) is “left exhausted”, since \(L\) emptied first. The other two branches need their own runs: 
  right exhausted     L: 9 82   R: 10      out 9 (left wins), 10 (right smaller),
                                              then j > hi → out 82 from the left tail
                                              → 9 10 82

  a tie goes LEFT     L: 2₁ 4   R: 2₂ 5     2₂ < 2₁ is FALSE → take the left 2₁
                                              then 2₂ < 4 → out 2₂;  5 < 4 false → out 4;
                                              i > mid → out 5
                                              → 2₁ 2₂ 4 5    (the two 2s keep their order)
Writing the tie test as aux[j] <= aux[i] instead would take the right run’s copy first and lose stability, for no other gain: one character is the whole difference. 
// Merge two adjacent sorted runs a[lo..mid] and a[mid+1..hi] into sorted order,
// using aux[] as scratch. Every element is copied once: Theta(n).
void merge(int a[], int lo, int mid, int hi, int aux[]) {
    for (int k = lo; k <= hi; k++) aux[k] = a[k];    // copy into scratch
    int i = lo, j = mid + 1;
    for (int k = lo; k <= hi; k++) {
        if (i > mid)              a[k] = aux[j++];    // left run exhausted
        else if (j > hi)          a[k] = aux[i++];    // right run exhausted
        else if (aux[j] < aux[i]) a[k] = aux[j++];    // take the smaller front
        else                      a[k] = aux[i++];    // ties take left: STABLE
    }
}

// Top-down mergesort: sort each half, then merge. T(n) = 2T(n/2) + Theta(n).
void mergesort(int a[], int lo, int hi, int aux[]) {
    if (hi <= lo) return;                 // base case: 0 or 1 element
    int mid = lo + (hi - lo) / 2;
    mergesort(a, lo, mid, aux);           // sort the left half
    mergesort(a, mid + 1, hi, aux);       // sort the right half
    merge(a, lo, mid, hi, aux);           // combine
}

# Merge two adjacent sorted runs of a[lo..hi] (split at mid) using aux as
# scratch. Every element is copied once: Theta(n).
def merge(a, lo, mid, hi, aux):
    aux[lo:hi + 1] = a[lo:hi + 1]         # copy into scratch
    i, j = lo, mid + 1
    for k in range(lo, hi + 1):
        if i > mid:                       # left run exhausted
            a[k] = aux[j]
            j += 1
        elif j > hi:                      # right run exhausted
            a[k] = aux[i]
            i += 1
        elif aux[j] < aux[i]:             # take the smaller front (ties: left)
            a[k] = aux[j]
            j += 1
        else:                             # ties take left: STABLE
            a[k] = aux[i]
            i += 1

# Top-down mergesort. T(n) = 2T(n/2) + Theta(n).
def mergesort(a, lo, hi, aux):
    if hi <= lo:                          # base case: 0 or 1 element
        return
    mid = (lo + hi) // 2
    mergesort(a, lo, mid, aux)            # sort the left half
    mergesort(a, mid + 1, hi, aux)        # sort the right half
    merge(a, lo, mid, hi, aux)            # combine
// Merge sorted runs a[lo..=mid] and a[mid+1..=hi] using aux as scratch. O(n).
fn merge(a: &mut [i32], lo: usize, mid: usize, hi: usize, aux: &mut [i32]) {
    aux[lo..=hi].copy_from_slice(&a[lo..=hi]);       // copy into scratch
    let (mut i, mut j) = (lo, mid + 1);
    for k in lo..=hi {
        if i > mid {                                 // left run exhausted
            a[k] = aux[j]; j += 1;
        } else if j > hi {                           // right run exhausted
            a[k] = aux[i]; i += 1;
        } else if aux[j] < aux[i] {                  // take the smaller front
            a[k] = aux[j]; j += 1;
        } else {                                     // ties take left: STABLE
            a[k] = aux[i]; i += 1;
        }
    }
}

// Top-down mergesort. T(n) = 2T(n/2) + O(n).
fn mergesort(a: &mut [i32], lo: usize, hi: usize, aux: &mut [i32]) {
    if hi <= lo { return; }               // base case: 0 or 1 element
    let mid = lo + (hi - lo) / 2;
    mergesort(a, lo, mid, aux);           // sort the left half
    mergesort(a, mid + 1, hi, aux);       // sort the right half
    merge(a, lo, mid, hi, aux);           // combine
}

Example (a whole run, unrolled) Sort \([38, 27, 43, 3, 9, 82, 10]\). Seven elements is deliberately odd, so no split is ever even: mid = lo + (hi − lo)/2 rounds down, which gives the left half the extra element. Seven elements, seven base cases, six merges (one per internal node of the call tree), and the array is sorted. Notice that a size-\(1\) subarray is never merged with anything on its own: it is returned as already sorted, and the merge one level up is what orders it against its sibling. Seven positions, seven branch decisions, and the two runs interleave \(3 \mid 9\ 10 \mid 27\ 38\ 43 \mid 82\) rather than alternating: the merge takes runs of whichever side is currently smaller, which is why a nearly sorted input costs the same as any other. The cost is one comparison and one copy per output slot, hence \(\Theta(n)\) for the merge.

The recurrence \(T(n) = 2T(n/2) + \Theta(n)\) is master-theorem case 2, and the recursion tree shows why directly:

Top-down or bottom-up; and stability The recursion above is top-down. The same merges can run bottom-up: merge adjacent runs of size \(1\), then \(2\), then \(4\), and so on (iterative, no call stack, same \(\Theta(n\log n)\)). Either way, mergesort is stable (equal keys keep their input order, because the merge breaks ties toward the left run), which matters when sorting records by a secondary key and then stably by a primary key. Its profile: \(\Theta(n\log n)\) time on every input, \(\Theta(n)\) auxiliary space, stable (the guaranteed, stable, but not-in-place sort).

2. Exercises (with solutions)

  1. Why is mergesort stable while quicksort (as written here) is not? Give a three-element input where a naive quicksort reorders equal keys.
    solution Mergesort’s merge, on a tie, takes from the left run first, so equal keys keep their original relative order: stability. The Lomuto partition swaps distant elements, which can reorder equal keys. Label equal keys to see it: on \([2_a,\ 2_b,\ 1]\) with pivot \(1\) (last), the scan finds nothing \(< 1\), then swaps the pivot into index \(0\), giving \([1,\ 2_b,\ 2_a]\): \(2_a\) and \(2_b\) have swapped order, so the sort is not stable.
  2. Merge \(L = [1, 4, 4, 9]\) with \(R = [2, 4, 5]\), naming the branch taken at every output position. Which \(4\) comes out first?
    solution Label the copies \(4_a, 4_b\) in \(L\) and \(4_c\) in \(R\). \(2 < 1\) is false, so left wins: emit \(1\). \(2 < 4_a\), right smaller: emit \(2\). \(4_c < 4_a\) is false (a tie), so left wins: emit \(4_a\), then again for \(4_b\). Now \(L = [9]\), \(R = [4_c, 5]\): \(4_c < 9\), right smaller, emit \(4_c\); \(5 < 9\), right smaller, emit \(5\); then \(j > hi\), right exhausted, emit \(9\). Result \(1\ 2\ 4_a\ 4_b\ 4_c\ 5\ 9\): the two left copies come out first, in their input order, which is stability. Seven positions, seven branches, three of the four kinds used.
  3. Sorting \(n = 7\) elements, how many calls to mergesort hit the base case, and how many merge calls run? Does the answer change if the array is already sorted?
    solution The call tree has one leaf per element, so \(7\) base cases, and one merge per internal node, so \(6\) merges. The counts depend only on \(n\), not on the values, because the split is always at the midpoint and nothing is ever skipped. That is exactly why mergesort has no bad input and no good one: \(\Theta(n\log n)\) on every array of size \(n\). (Timsort earns its speed on sorted input precisely by breaking this property: it detects existing runs instead of splitting blindly.)
