Heaps & Priority Queues

J. W. J. Williams introduced the binary heap in 1964 as the data structure behind heapsort. J. W. J. Williams, “Algorithm 232: Heapsort,” CACM 7(6), 1964

A stack serves the newest item and a queue the oldest; both order by when a thing arrived. A priority queue orders by a key you choose and serves the most important item next: the highest-priority thread, the most critical patient, the earliest pending event. Both operations must be fast: inserting a new item and removing the best one, over and over, as the collection changes. Neither a sorted nor an unsorted array makes both cheap. The binary heap does: it keeps just enough order (each parent at least its children) to read the maximum in \(\Theta(1)\) and to restore order after any change by touching a single root-to-leaf path. It can be built from \(n\) keys in linear time, and it is the priority queue inside Dijkstra (Dijkstra’s Algorithm), Prim (Prim’s Algorithm), and Huffman Coding. Run to exhaustion, it also sorts an array in place (Heapsort).

1. The priority-queue ADT

A stack orders by insertion time and returns the newest item; a queue returns the oldest. A priority queue keeps a collection of keyed items and returns the one whose key is best: largest, for a max-priority-queue. The rule is a comparison on the data itself rather than on arrival order, which is what many algorithms need: an operating-system scheduler runs the highest-priority ready thread, an emergency room treats the most critical patient first, a discrete-event simulator processes the earliest pending event next.

Definition (max-priority-queue) A max-priority-queue over comparable keys supports insert(x) (add a key), max() (return the largest key), delMax() (remove and return the largest key), together with isEmpty() and size(). A min-priority-queue is the mirror image, with min() and delMin(); we build the max version and everything flips symmetrically.

The defining workload is that insert and delMax interleave. A discrete-event simulator is the canonical case: 

  PQ = min-PQ keyed by event time
  insert the first few events
  while PQ not empty:
      e = delMin()          // the earliest remaining event
      process e             // may schedule NEW future events -> insert

New events appear in the middle of processing, out of time order, yet delMin must always return the chronologically next one. A sorted array would answer delMin in \(\Theta(1)\) but pay \(\Theta(n)\) to absorb each mid-run insertion; an unsorted array flips the costs. Each simple choice makes one operation cheap by making the other linear:

implementationinsertdelMax
unordered array / list\(\Theta(1)\)\(\Theta(n)\)
ordered array / list\(\Theta(n)\)\(\Theta(1)\)
binary heap\(\Theta(\log n)\)\(\Theta(\log n)\)

The unsorted array must scan to find the max; the sorted array must shift to make room. The heap makes both operations logarithmic by keeping the data only partially ordered: enough order to find the max in \(\Theta(1)\), little enough to insert cheaply.

Isn’t a balanced tree already a priority queue? It is. An AVL tree (AVL Trees) does insert and delete-max in \(\Theta(\log n)\); the max is the rightmost node. The heap does less and therefore costs less: it stores keys in a plain array with no per-node pointers (the arithmetic of Space Complexity: a pointer node costs several times the memory of an array slot, and nodes scatter across memory), it needs no rotations, its code is about twenty lines, and it can be built from \(n\) keys in \(\Theta(n)\) rather than \(\Theta(n\log n)\). A balanced tree can answer “is key \(x\) present?” and “what is the \(k\)-th smallest?”; a heap cannot, and it pays nothing to support those queries. The heap is not the only priority queue (Section 6 lists others); it is the cheapest one for this workload.

2. The binary heap: a complete tree in an array

Definition (binary max-heap) A binary max-heap is a binary tree that is both complete (every level is full except possibly the last, which is filled left-to-right with no gaps) and heap-ordered (every node’s key is \(\ge\) both of its children’s keys).

The two conditions do separate jobs. Completeness controls the shape: no gaps, so the tree fits an array and stays logarithmically shallow. Heap order controls the values: the maximum is on top. Every operation below temporarily breaks one condition and restores it.

No pointers: store the tree in an array

Because a complete tree has no gaps, we can number its nodes level by level, left to right, from \(1\) to \(n\), and store them in an array a[1..n]. The tree structure then becomes arithmetic. The 1-based convention leaves a[0] unused so the root sits at index \(1\) and the index formulas stay short: 

  parent(k) = k / 2       // integer division, floor
  left(k)   = 2k
  right(k)  = 2k + 1

Going to a child is a multiply by two; going to a parent is a divide by two. There is no dereferencing, no pointer to follow, nothing to allocate per node. (A 0-based array works too, with \(\texttt{parent}(k)=\lfloor(k-1)/2\rfloor\), \(\texttt{left}(k)=2k+1\), \(\texttt{right}(k)=2k+2\); the course, its assignments, and every snippet here use the 1-based form.)

This is why the heap is the default priority queue: a complete tree maps onto a contiguous array, which gives a tree’s structure with an array’s cache behavior and no pointer overhead. A classic space-saver stores the size \(n\) in the otherwise-wasted a[0].

Height, and why every operation is \(\Theta(\log n)\)

Proposition (height) A complete binary tree on \(n\) nodes has height \(h = \lfloor \log_2 n \rfloor\).
Proof. Every level except the last is completely full, so levels hold \(1, 2, 4, \dots, 2^{h-1}\) nodes and then between \(1\) and \(2^h\) nodes on the last. A tree of height \(h\) therefore has at least \(1 + 2 + \dots + 2^{h-1} + 1 = 2^h\) nodes and at most \(2^{h+1}-1\) nodes, so \(2^h \le n \le 2^{h+1}-1\), which gives \(h \le \log_2 n \lt h+1\), i.e. \(h = \lfloor \log_2 n \rfloor\). ∎

Completeness thus guarantees logarithmic height with no balancing and no rotations, unlike the rebalancing in AVL Trees. Any operation that walks a single root-to-leaf path costs \(O(\log n)\), which is where the heap’s \(\Theta(\log n)\) insert and delete come from. The maximum, meanwhile, is always a[1], read in \(\Theta(1)\).

Heap is not a BST A heap and a binary search tree draw the same picture (a binary tree) under different invariants, and confusing them is a common error. A BST orders \(\text{left} \lt \text{node} \lt \text{right}\) and can find any key in order; a heap orders \(\text{parent}\ge\text{children}\) and can find only the max. A BST can be lopsided; a heap is always complete. You cannot binary-search a heap for an arbitrary key; that is a \(\Theta(n)\) scan. The heap gives up general search to make “find the max” and “stay balanced” trivial.

3. What the invariants imply

Two local conditions, parent-versus-child and level-by-level, imply four global facts, used by the proofs that follow.

Every subtree is a heap

Heap order is checked one parent at a time, so it still holds when we restrict attention to any subtree; and a subtree of a complete tree is itself complete. Hence every subtree of a heap is a heap: a heap is heaps all the way down. This is the recursion that the correctness proofs of sink and of heapify both lean on.

Max on top, min at a leaf

Along any downward path the keys only shrink, so by transitivity the root is the global maximum. Conversely any node that has a child is \(\ge\) that child and so cannot be the minimum; the minimum must sit at a leaf. But no rule says which leaf, so finding the minimum of a max-heap is a \(\Theta(n)\) scan: partial order makes one end of the order \(\Theta(1)\) to read and leaves the other end as slow as in an unsorted array. Assuming distinct keys the minimum is unique; with duplicates, a minimum sits at a leaf.

The leaves are the back half of the array

Node \(k\) has a child exactly when \(2k \le n\). So the internal nodes are \(k = 1, \dots, \lfloor n/2 \rfloor\) and the leaves are \(k = \lfloor n/2\rfloor + 1, \dots, n\): at least half of any heap is leaves.

Two consequences. The \(\Theta(n)\) scan for the minimum need only look in the back half. And heapify (Section 5) starts at \(\lfloor n/2\rfloor\) because everything past it is a leaf, hence already a one-node heap needing no work: half the nodes cost nothing, a first sign that the build can beat \(n\log n\).

Paths are sorted; levels are not

Every root-to-leaf path is non-increasing, but nothing at all is guaranteed across subtrees. A key deep in one subtree can exceed a key one level higher in another:

Only ancestor–descendant pairs are ordered; siblings and cousins are not. A heap’s array is therefore not roughly sorted (a common misreading), and level \(2\) does not dominate level \(3\). A heap answers “who is on top?” but cannot answer rank, \(k\)-th-largest, or range queries without paying \(\Theta(n)\) or dismantling itself; and because it holds far less information than a sorted array, the \(\Theta(n)\) build does not contradict the \(\Omega(n\log n)\) sorting bound (Section 5).

4. The two primitives: swim and sink

Both priority-queue operations follow one pattern: do the easy structural thing that keeps the tree complete, which may break heap order along a single path, then repair that one path. Repairing upward is swim; repairing downward is sink. Everything built on the heap (the linear-time build, heapsort, Dijkstra, Huffman) is built from these two. 

// a[1..n] is a heap, except that a[k] may be larger than its parent.
// Lift a[k] until its parent is at least as large.
void swim(int a[], int k) {
    while (k > 1 && a[k/2] < a[k]) {
        std::swap(a[k/2], a[k]);       // the larger key moves up
        k = k/2;                       // continue from the parent
    }
}

// a[1..n] is a heap, except that a[k] may be smaller than a child.
// Push a[k] down, always under its larger child.
void sink(int a[], int k, int n) {
    while (2*k <= n) {                 // a[k] has a left child
        int j = 2*k;
        if (j < n && a[j] < a[j+1]) j++;   // j: the larger child
        if (a[k] >= a[j]) break;       // a[k] >= both children
        std::swap(a[k], a[j]);
        k = j;
    }
}

// Exchange a[i] and a[j].
static void swap(int[] a, int i, int j) {
    int t = a[i];
    a[i] = a[j];
    a[j] = t;
}

// a[1..=n] is a heap, except that a[k] may be larger than its parent.

pub fn swim(a: &mut [i32], mut k: usize) {
    while k > 1 && a[k/2] < a[k] {
        a.swap(k/2, k);                // the larger key moves up
        k = k/2;                       // continue from the parent
    }
}

// a[1..=n] is a heap, except that a[k] may be smaller than a child.
// Push a[k] down, always under its larger child.
pub fn sink(a: &mut [i32], mut k: usize, n: usize) {
    while 2*k <= n {                   // a[k] has a left child
        let mut j = 2*k;
        if j < n && a[j] < a[j+1] { j += 1; }   // j: the larger child
        if a[k] >= a[j] { break; }     // a[k] >= both children
        a.swap(k, j);
        k = j;
    }
}

In swim the moving key compares against its one parent and climbs while it is larger. In sink the moving key compares against both children and must swap with the larger one, which is what the line if (j < n && a[j] < a[j+1]) j++; selects; it is the most error-prone line of the structure. Swap with the smaller child instead and a bigger key is left stranded beneath a smaller one; the code still runs and mostly works, failing only silently. Each loop climbs or descends one level per iteration, so both cost at most \(h = \lfloor\log_2 n\rfloor\) swaps: \(\Theta(\log n)\). (Sedgewick names these swim and sink; Carrano’s text calls them percolate up and percolate down.)

insert: append, then swim

To insert, place the new key at the end (a[++n]), which keeps the tree complete, then swim it: the only edges that can now violate heap order lie on the new node’s path to the root, and swim fixes exactly that path. To remove the max, swap a[1] with the last element and shrink, which parks the old max just past the live array and keeps the tree complete, then sink the new root. 

class MaxHeap {
public:
    bool isEmpty() const { return n == 0; }
    int  size()    const { return n; }
    int  max()     const { return a[1]; }   // the root: Theta(1)
    void insert(int key);                   // append, then swim
    int  delMax();                          // swap with the last, then sink
private:
    int a[CAP + 1];                         // a[1..n]; a[0] unused
    int n = 0;
};

void MaxHeap::insert(int key) {
    a[++n] = key;                  // append: the tree stays complete
    swim(a, n);                    // repair the path to the root
}

int MaxHeap::delMax() {
    int top = a[1];
    std::swap(a[1], a[n--]);       // the max to the end; shrink
    sink(a, 1, n);                 // repair the path from the root
    return top;
}

    def __init__(self, cap):
        self.a = [0] * (cap + 1)            # a[1..n]; a[0] unused
        self.n = 0

    def is_empty(self): return self.n == 0
    def size(self):     return self.n

        self.n += 1
        self.a[self.n] = key           # append: the tree stays complete
        swim(self.a, self.n)           # repair the path to the root

        self.a[1], self.a[self.n] = self.a[self.n], self.a[1]   # the max to the end

        self.n += 1;
        self.a[self.n] = key;          // append: the tree stays complete

        self.a.swap(1, self.n);        // the max to the end

Example (insert 95) Start from the heap \(a = [\,90\;80\;70\;30\;60\;50\,]\) (\(n=6\)) and insert \(95\). Append at index \(7\), the right child of \(70\); it beats \(70\), then beats \(90\), swimming twice to the root: The left subtree \((80, 30, 60)\) never moves; swim touches one path. The displaced keys \(70\) and \(90\) each slide down exactly one level. Result: \([\,95\;80\;90\;30\;60\;50\;70\,]\).
Example (insert 85: a partial swim) Not every inserted key reaches the root. From the same start \(a = [\,90\;80\;70\;30\;60\;50\,]\), insert \(85\) instead: 
  append:  90 80 70 30 60 50 85        // 85 at a[7], child of a[3]=70
  swap@3:  90 80 85 30 60 50 70        // 85 > parent 70, one level up
  stop:    parent a[1]=90 ≥ 85        // loop condition fails
\(85\) climbs one level and settles at index \(3\): \([\,90\;80\;85\;30\;60\;50\;70\,]\). The third outcome is no motion at all. Insert \(40\) into the same starting heap instead: 
  append:  90 80 70 30 60 50 40        // 40 at a[7], child of a[3]=70
  stop:    parent a[3]=70 ≥ 40        // loop body never runs: zero swaps
Swim therefore has exactly three outcomes: climb all the way to the root (the \(95\) above), climb partway and stop under a larger ancestor (this \(85\)), or stop before the first swap (this \(40\), which stays at index \(7\): \([\,90\;80\;70\;30\;60\;50\;40\,]\)).

delMax: swap to the end, then sink

Example (delMax undoes the insert) Continue from \(a = [\,95\;80\;90\;30\;60\;50\;70\,]\) (\(n=7\)) and call delMax. The answer is \(a[1]=95\). Swap it with the last key \(70\) and shrink to \(n=6\); the new root \(70\) then sinks, comparing against both children and following the larger each time: 
  swap 95↔70, shrink:  70 80 90 30 60 50        // 95 parked past the end
  70 vs max(80,90)=90:  90 80 70 30 60 50        // swap with the larger child
  70 vs child 50:       90 80 70 30 60 50        // 70 ≥ 50, stop
delMax returns \(95\) and leaves \([\,90\;80\;70\;30\;60\;50\,]\), the heap from before the insert of \(95\): here the delMax undoes the insert. Note the two choice points: at the root, \(70\) is compared with both \(80\) and \(90\) and moves under the larger, \(90\); had sink taken the smaller child it would have left \(90\) buried under \(70\), silently breaking the heap.
Example (a lone child, and a sink that runs to a leaf) That sink stopped after one swap, and the node it stopped at had only one child. Here is a longer run that swaps at every shape of node. Take the heap \([\,90\;85\;70\;60\;30\;40\;50\;45\;20\,]\) (\(n=9\); Section 5 builds exactly this one) and call delMax: swap the root with \(a[9]=20\), shrink to \(n=8\), and sink the promoted \(20\). 
  swap 90↔20, shrink:  20 85 70 60 30 40 50 45   // 90 parked at a[9]
  k=1, max(85,70)=85:   85 20 70 60 30 40 50 45   // two children, right one loses
  k=2, max(60,30)=60:   85 60 70 20 30 40 50 45   // two children, left one wins
  k=4, lone child 45:   85 60 70 45 30 40 50 20   // 2k=8=n, so no right sibling
  k=8: 2k=16 > n:       85 60 70 45 30 40 50 20   // a leaf: loop ends
The result \([\,85\;60\;70\;45\;30\;40\;50\;20\,]\) is a heap (\(85\ge60,70\); \(60\ge45,30\); \(70\ge40,50\); \(45\ge20\)), and \(90\) sits parked at \(a[9]\). Between this run and the one above, every branch of the sink loop has now appeared: a node with two children, taken once to the right and once to the left; a node with a single child, which happens only at index \(\lfloor n/2 \rfloor\) and only when \(n\) is even; a node that already dominates its children, so the loop breaks with no swap at all (\(70 \ge 50\) in the previous example, and the row sink 4 of the build in Section 5, where \(90\) beats both \(45\) and \(20\)); and a node that reaches a leaf, where the loop guard \(2k \le n\) fails.

5. Building a heap, and why it is \(\Theta(n)\)

Given \(n\) keys already sitting in an array in arbitrary order, make the array a heap. The obvious way treats it as \(n\) insertions, swimming each element in turn: 

  for i = 1 .. n:  swim(a, i)       // n successive inserts

Its worst case is ascending input: each new key is the largest so far and swims its full depth. The total is the sum of the nodes’ depths, and in a complete tree most nodes lie near the bottom at depth \(\approx \log n\), so the sum is \(\Theta(n\log n)\). With all the keys present up front, a faster build exists.

Heapify: sink bottom-up

Leave the keys where they are (a complete tree with the wrong values) and sink every internal node, from the last one down to the root (its code appears with heapsort’s, in Heapsort): 

  heapify(a, n):
      for k = n/2 down to 1:  sink(a, k, n)

Two facts make this work. The nodes past \(\lfloor n/2\rfloor\) are leaves (Section 3), already one-node heaps, so we skip them. And processing bottom-up means that when sink(a, k, n) runs, the two subtrees under \(k\) have already been sunk (they are heaps), so one sink merges two valid heaps under a new root. Going top-down would fail: sinking the root first pushes it into subtrees that are still unordered, and nothing ever re-fixes the top.

Correctness

Lemma (one sink) If both subtrees rooted at the children of \(k\) are heaps, then sink(a, k, n) makes the whole subtree rooted at \(k\) a heap.
Proof. The only possibly-misplaced node is the one at \(k\); everything below it already satisfies heap order. sink promotes the larger child, call it \(c\). Then \(c\) was \(\ge\) its sibling (that is what “larger child” means) and \(\ge\) everything in its own former subtree (it was that subtree’s root, a heap), so after the swap \(c\) dominates both of its new children: the top edge is now correct. The demoted key sits at \(c\)’s old position with two heap subtrees beneath it and is the only node that can still violate order: the identical one-bad-node picture, one level lower. By induction on the height of \(k\) the process ends with \(k\) rooting a heap, either because the key comes to dominate its children or because it reaches a leaf. ∎
Proposition (heapify is correct) After heapify(a, n), which runs sink(a, k, n) for \(k = \lfloor n/2\rfloor\) down to \(1\), the array is a heap.
Proof (loop invariant). Maintain: when the loop is about to process \(k\), every node with index \(\gt k\) roots a valid heap. Initialization (\(k=\lfloor n/2\rfloor\)): the nodes \(\lfloor n/2\rfloor+1, \dots, n\) are leaves, each a one-node heap. Maintenance: the children of \(k\) have indices \(2k, 2k+1 \gt k\), so by the invariant they root heaps; the Lemma then makes \(k\) root a heap, and no node \(\gt k\) was touched, so the invariant holds for \(k-1\). Termination: after \(k=1\), node \(1\) roots a heap: the whole array. ∎

This is the establish–maintain–harvest shape of the loop invariants in Analysis of Algorithms: Time. Two facts from Section 3 carry it: “every subtree is a heap” gives the induction unit and “leaves are the back half” gives the base case.

Why the cost is \(\Theta(n)\)

Repeated insertion pays each node its depth (swim rises from a leaf); heapify pays each node its height (sink falls toward the leaves). In a complete tree almost every node lives near the bottom, with large depth but tiny height, so building bottom-up bills every node for the cheap direction.

Count it exactly for a full tree of height \(h\), where \(n = 2^{h+1}-1\). A node at depth \(d\) has height \(h-d\), there are \(2^d\) of them, and its sink costs at most \(h-d\) swaps. Summing over levels,

Theorem (linear build) Building a heap of \(n\) keys by bottom-up sinks costs fewer than \(n\) swaps; heapify runs in \(\Theta(n)\) time.
Proof. Let \(S\) be the total number of swaps on a full tree of height \(h\): \[ S = \sum_{d=0}^{h} 2^d\,(h-d) = h\cdot 1 + (h-1)\cdot 2 + (h-2)\cdot 4 + \dots + 1\cdot 2^{h-1}. \] Double it, which shifts every term one power of two to the right, and line the two rows up by matching powers: 
  S  =  h·1 + (h−1)·2 + (h−2)·4 + ··· + 1·2^(h−1)
  2S =         h·2   + (h−1)·4 + ··· + 2·2^(h−1) + 1·2^h
In each shared power-of-two column the \(2S\) coefficient exceeds the \(S\) coefficient by exactly one, so subtracting collapses the sum: \[ 2S - S = -h\cdot 1 + \big(2 + 4 + \dots + 2^{h}\big) = -h + \big(2^{h+1}-2\big), \] using the geometric sum \(2 + 4 + \dots + 2^h = 2^{h+1}-2\). Since \(2S-S = S\), \[ S = 2^{h+1} - h - 2. \] On a full tree \(2^{h+1} = n+1\), so \(S = (n+1) - h - 2 = n - h - 1 \lt n\): strictly fewer swaps than keys. For an arbitrary complete tree of height \(h\) we have \(2^h \le n\), and \(S \le 2^{h+1}-h-2 \lt 2\cdot 2^h \le 2n\), so the swap count is \(\Theta(n)\); each swap does \(O(1)\) comparisons, and the algorithm must at least inspect each key, so the total is \(\Theta(n)\). ∎

Only the root can sink the full height \(h\), and there is one root; the leaves, half the nodes, cost nothing, and the quarter just above them at most one swap each.

Both yield a heap; heapify wins whenever the keys are all present up front. A live priority queue, whose keys arrive over time, has no choice but to swim them one at a time. (Re-heapifying a live PQ after every insert would cost \(\Theta(n)\) per insert, against \(\Theta(\log n)\) for one swim.)

A \(\Theta(n)\) build does not beat the sorting bound Comparison sorting needs \(\Omega(n\log n)\) (The Sorting Lower Bound), and a linear-time heap build does not contradict it, because a heap is not sorted. Heap order constrains only ancestor–descendant pairs (Section 3), pinning down far less than a full ordering: exponentially many arrays are valid heaps of the same multiset. The build pays \(\Theta(n)\) for correspondingly little structure. Extracting the keys in sorted order still costs \(n\) removals of \(\Theta(\log n)\) each; that is heapsort, covered in Heapsort. Sedgewick & Wayne make the same point: partial order is cheap to build, full order is not.

6. The priority-queue landscape

The binary heap is the default priority queue, not the only one. Two of the variants below, indexed and \(d\)-ary heaps, come up again with Dijkstra’s and Prim’s algorithms.

Indexed priority queues

Eager forms of Dijkstra (Dijkstra’s Algorithm) and Prim (Prim’s Algorithm) need to decrease the key of an item already in the queue: “this vertex just got closer.” A plain heap cannot even find that item (Section 3: no search order). An indexed priority queue adds a companion array mapping each item to its current heap position, updated on every swap, so decreaseKey(i, v) can locate item \(i\) in \(O(1)\) and then swim it, and contains(i) is \(O(1)\). The heap operations stay \(\Theta(\log n)\); the cost is a second array. (The lazy alternative, the default in Dijkstra’s Algorithm, avoids it: push a duplicate and skip stale entries when they pop.)

Beyond two children: \(d\)-ary heaps

Nothing forces the branching factor to be two. Give each node \(d\) children and the same array trick applies, with children of \(k\) at \(d(k-1)+2, \dots, dk+1\). The tree grows shallower, height \(\log n / \log d\), so swim (and decreaseKey) speeds up; but each sink level now compares \(d\) children, so delMax slows. The common sweet spot is \(d=4\): shallower and cache-friendlier (four children share a cache line), and a fine choice for Dijkstra on dense graphs where decrease-keys vastly outnumber deletions. This is the same “widen the node to lower the height” trade as the B-trees of B-Trees; and \(d=n\) degenerates to an unsorted array, the first row of Section 1’s table, so the simple implementations are the endpoints of the \(d\)-ary family.

A leftist heap keeps each node’s right spine short (\(\le \log n\)) and melds two heaps by merging right spines in \(\Theta(\log n)\), after which insert and delMax are both just special cases of meld. A Fibonacci heap (Cormen et al.) defers cleanup to reach \(\Theta(1)\) amortized decrease-key, which gives Dijkstra its best theoretical bound; practical Dijkstra implementations still use a binary or \(4\)-ary heap because the constant factors dominate.

Library priority queues, and the bug that follows You will rarely hand-roll one. C++ std::priority_queue is a max-heap; Java java.util.PriorityQueue and Python heapq are min-heaps (negate keys, or push \(-k\), for max behavior). All are binary heaps: push/pop \(\Theta(\log n)\), build \(\Theta(n)\), peek \(\Theta(1)\). Getting the direction wrong (a min-heap where you meant max) is the most common heap bug; the others are a sink that fails to pick the larger child, off-by-one errors from running 1-based math on a 0-based array, and doing \(n\) inserts (\(\Theta(n\log n)\)) where heapify (\(\Theta(n)\)) was intended. None of the three libraries ships decreaseKey, which is why the Dijkstra of Dijkstra’s Algorithm deletes lazily.
Where this heap reappears The heap is the priority queue inside three algorithms covered in their own handouts. Huffman coding (Huffman Coding) builds an optimal prefix code by repeatedly pulling the two least-frequent nodes from a min-heap and pushing their merge, \(n\) symbols in \(\Theta(n\log n)\). Dijkstra (Dijkstra’s Algorithm) and Prim (Prim’s Algorithm) grow a tree by repeatedly pulling the nearest frontier vertex from a min-heap. In each, a priority queue drives a greedy loop (“take the best remaining”), and the heap’s \(\Theta(\log n)\) operations are what make that loop efficient.

7. Exercises (with solutions)

  1. Starting from an empty max-heap, insert \(5, 15, 10, 20, 8\) in that order. Give the array (1-based) after each insert, and the final tree’s shape.
    solution After \(5\): \([5]\). After \(15\): append then swim past \(5\) ⇒ \([15, 5]\). After \(10\): append at index \(3\); \(10 \lt 15\), no swim ⇒ \([15, 5, 10]\). After \(20\): append at \(4\), swim past \(5\) (index \(2\)) then past \(15\) (index \(1\)) ⇒ \([20, 15, 10, 5]\). After \(8\): append at \(5\); parent is \(a[2]=15 \ge 8\), no swim ⇒ \([20, 15, 10, 5, 8]\). Final tree: root \(20\); children \(15\) and \(10\); \(15\) has children \(5\) and \(8\). Check: \(20\ge15,10\) and \(15\ge5,8\). ✓
  2. Call delMax on the heap \([20, 15, 10, 5, 8]\). Show the returned key and the resulting array.
    solution Return \(a[1]=20\). Swap it with the last key \(8\) and shrink to \(n=4\): \([8, 15, 10, 5]\). Sink \(8\): its children are \(15\) and \(10\), larger is \(15\); \(8 \lt 15\) so swap ⇒ \([15, 8, 10, 5]\). Now \(8\) is at index \(2\) with the single child \(a[4]=5\); \(8 \ge 5\), stop. Result \([15, 8, 10, 5]\), which is a valid heap (\(15\ge8,10\), \(8\ge5\)).
  3. Call delMax on the heap \([20, 5, 18, 4, 3, 17, 16]\) (\(n=7\)) and show every comparison the sink makes. One of its steps exercises the j < n guard; point it out.
    solution Return \(a[1]=20\). Swap it with the last key \(16\) and shrink to \(n=6\): \([16, 5, 18, 4, 3, 17]\), with the parked \(20\) at \(a[7]\). Sink \(16\): children \(5\) and \(18\), larger \(18\); \(16 \lt 18\), swap ⇒ \([18, 5, 16, 4, 3, 17]\). Now \(16\) sits at index \(3\) with left child index \(2\cdot3 = 6 = n\): the guard \(j \lt n\) fails, so there is only the one child \(a[6]=17\) and the larger-child test is skipped; \(16 \lt 17\), swap ⇒ \([18, 5, 17, 4, 3, 16]\). Index \(6\) has no children (\(12 \gt 6\)), stop. Result \([18, 5, 17, 4, 3, 16]\); verify \(18\ge5,17\), \(5\ge4,3\), \(17\ge16\). The guard is load-bearing here: without it the sink would compare against \(a[7]\), which holds the parked \(20\), and wrongly drag it back into the heap.
  4. Build a heap from \([4, 7, 3, 9, 1, 6, 2]\) (\(n=7\)) by bottom-up heapify. Show the array after each sink.
    solution Start at \(k=\lfloor 7/2\rfloor=3\). sink 3: \(a[3]=3\), children \(6, 2\), larger \(6\); swap ⇒ \([4, 7, 6, 9, 1, 3, 2]\). sink 2: \(a[2]=7\), children \(9, 1\), larger \(9\); swap ⇒ \([4, 9, 6, 7, 1, 3, 2]\). sink 1: \(a[1]=4\), children \(9, 6\), larger \(9\); swap ⇒ \([9, 4, 6, 7, 1, 3, 2]\); now \(4\) at index \(2\) has children \(7, 1\), larger \(7\); swap ⇒ \([9, 7, 6, 4, 1, 3, 2]\). Final heap: verify \(9\ge7,6\), \(7\ge4,1\), \(6\ge3,2\). ✓
  5. Explain why heapify sinks nodes from \(\lfloor n/2\rfloor\) down to \(1\), and why the reverse order (\(1\) up to \(\lfloor n/2\rfloor\)) does not produce a heap.
    solution The one-sink lemma requires both child subtrees of \(k\) to already be heaps. Processing indices in decreasing order guarantees this: the children \(2k, 2k+1\) exceed \(k\), so they were sunk earlier, and the leaves past \(\lfloor n/2\rfloor\) are heaps to begin with. Going upward breaks the precondition: sinking the root first pushes its key into subtrees that are still unsorted, so the key stops at a wrong place, and no later step revisits the top. The result need not be heap-ordered.
  6. A max-heap holds \(15\) distinct keys in \(a[1..15]\). Where can the second-largest key be? The third-largest? The smallest? At what cost can you verify that an array is a heap?
    solution Every key larger than a given key must be one of its ancestors, and a node at depth \(d\) has exactly \(d\) ancestors. The second-largest has one key above it, so depth \(\le 1\): index \(2\) or \(3\) (a child of the root). The third-largest has depth \(\le 2\): indices \(2\)–\(7\). The smallest is a leaf (any node with a child is larger than it): indices \(8\)–\(15\). Verifying the heap is just checking \(a[k] \ge a[2k]\) and \(a[k] \ge a[2k+1]\) for every internal \(k = 1..7\), i.e. \(\Theta(n)\).
  7. True or false, with justification: “A descending-sorted array is always a valid max-heap.”
    solution True. If \(a[1] \ge a[2] \ge \dots \ge a[n]\), then for every \(k\) and any child index \(j \in \{2k, 2k+1\}\) we have \(j \gt k\), so \(a[k] \ge a[j]\) by the sortedness: heap order holds at every node, and the array is complete by construction. (The converse fails: a max-heap need not be sorted, e.g. \([90, 30, 80]\) is a heap but \(30 \lt 80\). And an ascending-sorted array is instead a valid min-heap.)
