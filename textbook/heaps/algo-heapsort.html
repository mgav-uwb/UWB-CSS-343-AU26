Heapsort

Data Structures & Algorithms. Algorithm.
Heapsort sorts an array in place in guaranteed \(\Theta(n\log n)\) time: build a max-heap over the keys in \(\Theta(n)\), then repeatedly swap the maximum to the end of a shrinking heap. It is the only comparison sort that is simultaneously worst-case \(\Theta(n\log n)\) and \(\Theta(1)\) in extra space, which is why introsort falls back on it. With the full code, a worked trace, the cost proof, a link to the interactive demo, and exercises.

Heapsort is the binary heap run to exhaustion. All of its machinery lives in Heaps & Priority Queues: the 1-based array layout, the sink primitive that restores heap order along one root-to-leaf path, and the \(\Theta(n)\) bottom-up build. This handout assembles those pieces into a sort, proves its \(\Theta(n\log n)\) cost, and places it against mergesort and quicksort.

1. The algorithm: heapify, then sort down

The problem. Given \(n\) comparable keys sitting in an array in arbitrary order, rearrange the array into ascending order, using no second array, and with a worst-case running time that no adversarial input can degrade.

Selection sort repeatedly finds the maximum of the unsorted part by a \(\Theta(n)\) scan, for \(\Theta(n^2)\) overall. A heap is a find-max machine: replace the scan with delMax and each of the \(n\) rounds drops from \(\Theta(n)\) to \(\Theta(\log n)\). Better yet, delMax already swaps the maximum into the last live slot before shrinking (exactly where a descending selection pass would place it), so the sorted region grows in the same array at no extra cost. That is heapsort: heapify, then sort down. 

// In-place heapsort of a 1-based array a[1..n] (a[0] unused), ascending.
// Theta(n log n), Theta(1) extra space, NOT stable. Uses sink from swim-sink.
void heapsort(int a[], int n) {
    for (int k = n / 2; k >= 1; k--)   // build-heap bottom-up: Theta(n)
        sink(a, k, n);                 // every internal node, last to first
    for (int end = n; end >= 2; end--) {   // sortdown: n-1 delMax steps
        std::swap(a[1], a[end]);       // park the current max at the boundary
        sink(a, 1, end - 1);           // re-heapify the shrunken heap a[1..end-1]
    }
}
// In-place heapsort of a 1-based array a[1..n] (a[0] unused), ascending.
// Theta(n log n), Theta(1) extra space, NOT stable. Uses sink from swim-sink.
static void heapsort(int[] a, int n) {
    for (int k = n / 2; k >= 1; k--)   // build-heap bottom-up: Theta(n)
        sink(a, k, n);                 // every internal node, last to first
    for (int end = n; end >= 2; end--) {   // sortdown: n-1 delMax steps
        int t = a[1]; a[1] = a[end]; a[end] = t;   // park the max at the boundary
        sink(a, 1, end - 1);           // re-heapify the shrunken heap a[1..end-1]
    }
}
# In-place heapsort of a 1-based list a[1..n] (a[0] unused), ascending.
# Theta(n log n), Theta(1) extra space, NOT stable. Uses sink from swim-sink.
def heapsort(a, n):
    for k in range(n // 2, 0, -1):     # build-heap bottom-up: Theta(n)
        sink(a, k, n)                  # every internal node, last to first
    for end in range(n, 1, -1):        # sortdown: n-1 delMax steps
        a[1], a[end] = a[end], a[1]    # park the current max at the boundary
        sink(a, 1, end - 1)            # re-heapify the shrunken heap a[1..end-1]
// In-place heapsort of a 1-based slice a[1..=n] (a[0] unused), ascending.
// Theta(n log n), Theta(1) extra space, NOT stable. Uses sink from swim-sink.
fn heapsort(a: &mut [i32], n: usize) {
    for k in (1..=n / 2).rev() {       // build-heap bottom-up: Theta(n)
        sink(a, k, n);                 // every internal node, last to first
    }
    for end in (2..=n).rev() {         // sortdown: n-1 delMax steps
        a.swap(1, end);                // park the current max at the boundary
        sink(a, 1, end - 1);           // re-heapify the shrunken heap a[1..=end-1]
    }
}

Both loops call one primitive, sink(a, k, n), defined and proved in Heaps & Priority Queues. It is repeated here in pseudocode because every step of the trace below is a step of it, and because its two guards are exactly what make the cases the trace has to show: 

  sink(a, k, n):                       // push a[k] down inside a[1..n]
      while 2k ≤ n:                   // a[k] has a left child
          j = 2k                       // the left child
          if j < n and a[j] < a[j+1]:   // a RIGHT child exists and is bigger
              j = j + 1                // compare against the LARGER child
          if a[k] ≥ a[j]:  break       // a[k] already dominates: stop
          swap a[k], a[j]              // demote under the larger child
          k = j                        // move down one level

The loop guard 2k ≤ n stops the descent at a leaf; the guard j < n is what distinguishes a node with two children from a node whose left child is the very last live slot; and the break is the early stop. Note that n here is the live heap size, which the sortdown shrinks by one each round: it is the only thing that keeps the sorted tail out of the heap.

The first loop is the \(\Theta(n)\) bottom-up build proved in Heaps & Priority Queues. The second runs \(n-1\) rounds: swap the root (the current maximum) to the boundary a[end], exclude it by passing end - 1 as the heap size, and sink the new root through the shrunken heap.

Invariant (sortdown) Before each round, a[1..end] is a heap holding the \(end\) smallest keys and a[end+1..n] holds the remaining keys, sorted and in their final positions.

Initialization is the post-heapify state (the whole array is the heap, the tail empty). Each round removes the maximum of the current heap; it is \(\ge\) every key already parked, and it lands immediately to their left, so the sorted tail grows correct by one. At termination (\(end=1\)) the lone remaining key is the smallest, and the array is fully sorted: ascending, even though we used a max-heap, precisely because each maximum is parked at the far right. A min-heap with the same sort-down would produce descending order, a classic gotcha.

Every round is one swap plus one sink, but the sink itself can take four distinct shapes, and a full trace should show each: a swap with the larger of two children; a swap with a lone child (when the left-child index equals the live heap size, so the j < n guard skips the larger-child test); an immediate stop with no swap (the promoted key already dominates); and the final two-element round, whose sink runs on a one-key heap and does nothing at all. The trace below, a complete run from the raw array through the build to the sorted result, hits all four.

Proposition (heapsort cost) Heapsort sorts \(n\) keys in \(O(n\log n)\) time (\(\Theta(n\log n)\) in the worst case) using \(\Theta(1)\) extra space.
Proof. The build is \(\Theta(n)\) (Heaps & Priority Queues). The sortdown does \(n-1\) rounds; the round on a heap of size \(m\) sinks the new root through height \(\le \lfloor\log_2 m\rfloor \le \lfloor\log_2 n\rfloor\), so the whole sortdown is \(O(n\log n)\), and with the linear build the total is \(O(n\log n)\). For the matching lower bound, note that after the build the heap’s deepest level holds up to \(\lceil n/2\rceil\) keys; on a worst-case input the key promoted to the root each round is small and sinks essentially the full current height, and the first \(n/2\) rounds each sink through a heap of size \(\gt n/2\) and thus height \(\ge \log_2 n - 1\), giving \(\Omega(n\log n)\): heapsort’s worst case is \(\Theta(n\log n)\) (The Sorting Lower Bound). Only a constant number of scalar variables are used beyond the input array, so the extra space is \(\Theta(1)\). ∎

Heapsort is not stable: parking a maximum at a distant slot reorders equal keys. Three keys are enough to see it happen.

Example (equal keys come out reversed) Sort \([\,5_a\;5_b\;3\,]\), where \(5_a\) and \(5_b\) are equal keys carrying distinct payloads and \(5_a\) started first. A stable sort must return \(3, 5_a, 5_b\). 
  build:      5a 5b 3      // sink 1: 5a ≥ larger child 5b, no swap; already a heap
  park 5a:    5b 3 | 5a    // swap a[1],a[3]; sink 3 in a[1..2]: lone child 5b, swap
  park 5b:    3 | 5b 5a    // swap a[1],a[2]; sink in a[1..1]: nothing to do
The result is \(3, 5_b, 5_a\): the tie is inverted. The culprit is the first park, which flung \(5_a\) from index \(1\) all the way to index \(3\), jumping it over its equal twin. Any sort that moves keys across long distances rather than between neighbors is exposed to this, which is why quicksort is unstable as well; mergesort avoids it by breaking every tie in favor of the left run. If stability matters, sort \((\text{key}, \text{original index})\) pairs, which makes all keys distinct and costs \(\Theta(n)\) extra space for the indices.

Heapsort’s niche is clear against its rivals:

sortworst caseextra spacestablein practice

heapsort\(\Theta(n\log n)\)\(\Theta(1)\)nothe safety net

Heapsort is the only one of the three that is simultaneously guaranteed \(\Theta(n\log n)\) and in place. It loses to quicksort on constant factors and cache behavior (its accesses jump around the array by powers of two rather than sweeping linearly), and it is not stable, so it is nobody’s default. But it is everybody’s fallback: this is exactly why std::sort (introsort) begins with quicksort and switches to heapsort when the recursion goes too deep, buying quicksort’s speed with heapsort’s worst-case guarantee. Its two rivals have their own handouts, Mergesort and Quicksort.

2. Exercises (with solutions)

  1. Run two rounds of heapsort sortdown on the heap \([9, 7, 6, 4, 1, 3, 2]\) (\(n=7\)). Show the array after each round and explain why the output ends up ascending.
    solution Round \(end=7\): swap \(a[1]=9\) with \(a[7]=2\) ⇒ \([2,7,6,4,1,3,\mid 9]\); sink \(2\) in \(a[1..6]\): larger child of the root is \(7\), swap ⇒ \([7,2,6,4,1,3\mid 9]\); \(2\) at index \(2\) has larger child \(4\), swap ⇒ \([7,4,6,2,1,3\mid 9]\). Round \(end=6\): swap \(a[1]=7\) with \(a[6]=3\) ⇒ \([3,4,6,2,1\mid 7,9]\); sink \(3\) in \(a[1..5]\): larger child is \(6\), swap ⇒ \([6,4,3,2,1\mid 7,9]\); \(3\) at index \(3\) has no child, stop. After two rounds: \([6,4,3,2,1,7,9]\) with sorted tail \(7, 9\). The order is ascending because each round removes the current maximum and parks it at the right boundary, filling the final positions from largest down to smallest.
  2. You build a min-heap and run the identical sortdown loop: swap the root to the current boundary, shrink, sink. Is the output ascending or descending, and what would you change to reverse it?
    solution Descending. Each round now removes the current minimum and parks it at the right end, so the largest keys end up on the left: the array comes out from largest (index \(1\)) to smallest. To get ascending order from a min-heap you would park each extracted minimum at the front instead (growing the sorted region leftward), or simply use a max-heap as in the main text. This direction mismatch is a frequent bug: the sort direction is fixed by the heap’s orientation, not by intent.
  3. In the main trace, the round that parks \(80\) sinks without a single swap: the promoted \(70\) already dominates. Prove that with distinct keys this can only happen late: every sortdown round on a live heap \(a[1..end]\) with \(end \ge 4\) begins with a swap at the root.
    solution The round moves \(a[end]\) to the root and sinks it through \(a[1..end-1]\). For \(end \ge 4\), the index \(end\) lies inside the subtree rooted at \(2\) or at \(3\), so the promoted key was a proper descendant of \(a[2]\) or of \(a[3]\) and, keys being distinct, strictly smaller than that child of the root. Hence it is smaller than \(\max(a[2], a[3])\), the larger child it is compared against, and the first comparison of the sink swaps. The exception needs \(end \le 3\): at \(end = 3\) the promoted key is the root’s own right child, which heap order does not relate to its sibling \(a[2]\), so it may dominate (in the trace, \(70 \ge 60\): no swap); at \(end = 2\) the shrunken heap has one key and the sink loop body never runs at all.
  4. A common slip writes sink(a, 1, end) instead of sink(a, 1, end - 1) in the sortdown loop. Run the buggy version on the same input \([\,70\;80\;95\;90\;60\,]\) and say exactly what goes wrong.
    solution The build is unaffected, giving the heap \([\,95\;90\;70\;80\;60\,]\). Round \(end=5\): swap \(95\) to slot \(5\), leaving \([\,60\;90\;70\;80\;95\,]\), then sink \(60\) through \(a[1..5]\), which still contains the parked \(95\). The \(60\) swaps with \(90\), then at index \(2\) compares its children \(80\) and \(95\) and swaps with \(95\), dragging the maximum back into the live heap: \([\,90\;95\;70\;80\;60\,]\), which is not even heap-ordered. The remaining rounds churn without progress, and the array ends as \([\,95\;90\;70\;80\;60\,]\): the original heap, wholly unsorted. The lesson is that end - 1 is not an off-by-one detail but the entire mechanism that removes a key from the heap: the sorted tail exists only because the sink is forbidden to look at it.
