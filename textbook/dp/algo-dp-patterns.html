DP Patterns: Grid, Interval, Coin Change & LIS

Data Structures & Algorithms. Algorithm (dynamic programming).
The remaining DP table shapes: grid DP (cheapest and counted monotone paths through a cost grid), interval DP (matrix-chain multiplication and optimal binary search trees, where the state is a range and the transition scans every split point), and two more one-dimensional DPs, coin change and the longest increasing subsequence, each with the state-design lesson it teaches. A summary table indexes the shapes. The method itself is the Dynamic Programming Method handout. With a demo and exercises.

Most DP tables have one of a few shapes, and recognizing the shape hands you the state and the fill order, the two hardest steps of the recipe (the Dynamic Programming Method handout). This handout completes the shape library: grids, where the table mirrors the input; intervals, where a cell is a range; and two more one-dimensional tables, coin change and the longest increasing subsequence.

1. Grid DP and interval DP

Knapsack and edit distance (the 0/1 Knapsack and Edit Distance handouts) are both “2-D table, few fixed neighbors” DPs. Two more shapes complete the pattern library: grids, where the table is the input, and intervals, where a cell is a range and the transition scans every split point.

Grid DP: paths through a cost grid

Definition (minimum-cost path) Given a grid of nonnegative cell costs, move from the top-left to the bottom-right corner stepping only right or down, minimizing the total cost of cells visited. The DP is \[ \mathit{dp}[i][j] = \mathit{cost}[i][j] + \min\bigl(\mathit{dp}[i-1][j],\; \mathit{dp}[i][j-1]\bigr), \] with the top-left cell as base case and edge cells reading their only available neighbor.
Example (a 3×3 grid)

Each \(dp\) cell adds its own cost to the cheaper of the cell above and the cell to the left: \(dp[1][2] = 1 + \min(5, 7) = 6\), and the corner \(dp[2][2] = 1 + \min(6, 8) = 7\) is the minimum path cost. The highlighted cells are the optimal path \(1 \to 3 \to 1 \to 1 \to 1\) (right, right, down, down), total \(7\), recovered, as always, by tracing back through whichever neighbor produced each cell.
Example (the same grid, cell by cell)

A grid DP has three kinds of cell, and all three occur in nine cells. The origin has no predecessor at all. An edge cell has exactly one: a top-row cell can only be reached from its left, a left-column cell only from above, so there is no minimum to take. Only an interior cell reads two neighbors and chooses. Filling row by row, left to right, every predecessor is ready when it is read.

Both interior outcomes appear: left wins at \(dp[1][1]\) and \(dp[2][1]\), up wins at \(dp[1][2]\) and \(dp[2][2]\). Note that \(dp[1][1] = 7\) is never used by the answer, and that the expensive \(5\) in the middle of the grid is exactly what the optimal path routes around. In code the two edge cases are usually folded away by padding the table with a border of \(\infty\) (for a minimum) or by initializing row \(0\) and column \(0\) with running sums; both are the same statement that a missing neighbor must never win the \(\min\).

The same table flexes to relatives by changing only the combine step. Counting monotone paths sums instead of minimizing, \(\mathit{dp}[i][j] = \mathit{dp}[i-1][j] + \mathit{dp}[i][j-1]\), with the edges at \(1\): on a \(3\times 3\) grid the rows fill \(1\,1\,1\) / \(1\,2\,3\) / \(1\,3\,6\), and the corner’s \(6 = \binom{4}{2}\) counts the arrangements of two rights and two downs: the DP rediscovers a binomial coefficient. Obstacles force a cell’s count to \(0\) (or its cost to \(\infty\)); extra move directions just add source neighbors. Robot-path planning, seam carving in image resizing, and dynamic-time-warping all ride this one shape. 

// Grid DP. Cheapest right/down path through a grid of nonnegative costs.
// The two edge loops exist so that no interior min ever reads a missing
// neighbor. Theta(mn) time and space.
int minCostPath(const vector<vector<int>>& cost) {
    int m = cost.size(), n = cost[0].size();
    vector<vector<int>> dp(m, vector<int>(n));
    dp[0][0] = cost[0][0];                             // origin: no predecessor
    for (int j = 1; j < n; j++)
        dp[0][j] = cost[0][j] + dp[0][j-1];            // top edge: left only
    for (int i = 1; i < m; i++)
        dp[i][0] = cost[i][0] + dp[i-1][0];            // left edge: up only
    for (int i = 1; i < m; i++)
        for (int j = 1; j < n; j++)
            dp[i][j] = cost[i][j] + min(dp[i-1][j],    // interior: choose
                                        dp[i][j-1]);
    return dp[m-1][n-1];
}

// Same cells, same order, sum instead of min: how many monotone paths reach
// the corner. A blocked cell contributes 0, erasing every path through it.
long long countPaths(const vector<vector<bool>>& blocked) {
    int m = blocked.size(), n = blocked[0].size();
    vector<vector<long long>> dp(m, vector<long long>(n, 0));
    for (int i = 0; i < m; i++)
        for (int j = 0; j < n; j++) {
            if (blocked[i][j]) continue;               // stays 0
            if (i == 0 && j == 0) { dp[0][0] = 1; continue; }
            dp[i][j] = (i ? dp[i-1][j] : 0) + (j ? dp[i][j-1] : 0);
        }
    return dp[m-1][n-1];
}

// Grid DP. Cheapest right/down path through a grid of nonnegative costs.
// The two edge loops exist so that no interior min ever reads a missing
// neighbor. Theta(mn) time and space.
fn min_cost_path(cost: &[Vec<u64>]) -> u64 {
    let (m, n) = (cost.len(), cost[0].len());
    let mut dp = vec![vec![0u64; n]; m];
    dp[0][0] = cost[0][0];                             // origin: no predecessor
    for j in 1..n { dp[0][j] = cost[0][j] + dp[0][j - 1]; }   // top edge
    for i in 1..m { dp[i][0] = cost[i][0] + dp[i - 1][0]; }   // left edge
    for i in 1..m {
        for j in 1..n {
            dp[i][j] = cost[i][j] + dp[i - 1][j].min(dp[i][j - 1]);
        }
    }
    dp[m - 1][n - 1]
}

// Same cells, same order, sum instead of min: how many monotone paths reach
// the corner. A blocked cell contributes 0, erasing every path through it.
fn count_paths(blocked: &[Vec<bool>]) -> u64 {
    let (m, n) = (blocked.len(), blocked[0].len());
    let mut dp = vec![vec![0u64; n]; m];
    for i in 0..m {
        for j in 0..n {
            if blocked[i][j] { continue; }             // stays 0
            if i == 0 && j == 0 { dp[0][0] = 1; continue; }
            let up = if i > 0 { dp[i - 1][j] } else { 0 };
            let left = if j > 0 { dp[i][j - 1] } else { 0 };
            dp[i][j] = up + left;
        }
    }
    dp[m - 1][n - 1]
}

Interval DP: the state is a range

Definition (interval DP) In interval DP the subproblem is a contiguous range \([i, j]\) of the input, and the transition optimizes over the split point \(k\): \[ \mathit{dp}[i][j] = \min_{i \le k < j}\bigl(\mathit{dp}[i][k] + \mathit{dp}[k+1][j] + \mathit{cost}(i, j, k)\bigr), \] filled in order of increasing range length. With \(\Theta(n^2)\) ranges and \(\Theta(n)\) splits each, interval DPs typically cost \(\Theta(n^3)\).

The canonical instance is matrix-chain multiplication. Matrix multiplication is associative (every parenthesization of \(A_1 A_2 \cdots A_n\) gives the same product) but not equally priced: multiplying a \(p \times q\) by a \(q \times r\) matrix costs \(p\,q\,r\) scalar multiplications, and the order changes the totals wildly. For \(A\ (10{\times}30)\), \(B\ (30{\times}5)\), \(C\ (5{\times}60)\): 

  (AB)C :  10·30·5  +  10·5·60  =  1500 +  3000  =   4,500
  A(BC) :  30·5·60  + 10·30·60  =  9000 + 18000  =  27,000     6× worse

The last-decision question is which multiplication happens last, the outermost split \(k\): \[ \mathit{dp}[i][j] = \min_{i \le k < j}\bigl(\mathit{dp}[i][k] + \mathit{dp}[k+1][j] + \mathit{rows}_i \cdot \mathit{cols}_k \cdot \mathit{cols}_j\bigr), \] the two halves optimally parenthesized by induction plus the cost of the final multiply. Base case: a single matrix costs \(0\). \(\Theta(n^3)\) overall, and the traceback (store the winning \(k\) per range) recovers the parenthesization itself.

Example (one interval DP filled completely)

Three matrices leave only two parenthesizations, so the split loop never really runs. Add a fourth, \(D\ (60{\times}10)\), to the chain above: \(A\ (10{\times}30)\), \(B\ (30{\times}5)\), \(C\ (5{\times}60)\), \(D\ (60{\times}10)\). Write the shared dimensions as \(p = [10, 30, 5, 60, 10]\), so matrix \(i\) is \(p_{i-1} \times p_i\) and the final multiply for a range \([i,j]\) split at \(k\) costs \(p_{i-1}\, p_k\, p_j\). Ranges are filled in order of increasing length; \(dp[i][i] = 0\), since one matrix needs no multiply.

The answer is \(dp[1][4] = 5000\) at split \(k = 2\), which reads \((AB)(CD)\): multiply \(AB\) for \(1500\), multiply \(CD\) for \(3000\), then combine the \(10{\times}5\) and \(5{\times}10\) results for \(500\). Following the stored splits into each half (\(dp[1][2]\) at \(k=1\), \(dp[3][4]\) at \(k=3\)) confirms there is nothing left to bracket.

Three things the fill makes visible. The split loop genuinely searches: at \(dp[1][4]\) the three candidates are \(7500\), \(5000\), \(10500\), and the winner is the middle one, so neither the leftmost nor the rightmost split is a safe guess. The fill order must be by length, not by row: \(dp[1][4]\) reads \(dp[1][2]\), \(dp[1][3]\), \(dp[3][4]\) and \(dp[2][4]\), all shorter ranges, and all already final. And the winning outer split is not the winning inner one: \(dp[1][3]\) alone prefers \(k = 2\) at cost \(4500\), yet the full chain does not use \(dp[1][3]\) at all. Optimal substructure says every used sub-range is solved optimally, not that every optimally solved sub-range gets used. Ten split evaluations for four matrices; the brute force over parenthesizations would consider \(C_3 = 5\) of them here and Catalan-many in general.

The triple loop that produces that table (range length outermost, range start next, split point innermost) and the traceback that turns the stored splits into printed parentheses are given in full, in all four languages, in the Matrix-Chain Multiplication handout.

The same shape gives the optimal binary search tree (BST): given keys with known access frequencies, \( \mathit{dp}[i][j]\) is the cheapest expected search cost of a BST over keys \(i..j\), and the split is which key becomes the root, with \(\sum_{k=i}^{j}\mathit{freq}(k)\) added because choosing any root sinks every key in the range one level deeper. Frequently-searched keys settle near the root: the reason a balanced tree (the Trees & Binary Search Trees handout) is not optimal under skewed access, and the principle behind frequency-weighted index structures in real databases. Interval DP is the trickiest of the shapes (the fill order is by range length, not row order), but the recipe is unchanged: state, transition, base, order, answer.

2. Two more one-dimensional DPs: coin change and LIS

Coin change, revisited

The Greedy Method handout showed greedy coin change failing on the system \(\{1, 3, 4\}\): making \(6\), greedy grabs the \(4\) and finishes \(4 + 1 + 1\), three coins, when two \(3\)s suffice. The DP fix is one line: state = the amount, transition = try every coin as the last coin used: \[ \mathit{dp}[a] = 1 + \min_{\,c \,\le\, a}\; \mathit{dp}[a - c], \qquad \mathit{dp}[0] = 0. \]

Example (coins {1, 3, 4}, amounts 0–6)
a0123456
dp[a] 0121122
\(dp[6]\) tries a last coin of \(1\) (\(1 + dp[5] = 3\)), of \(3\) (\(1 + dp[3] = 2\)), and of \(4\) (\(1 + dp[2] = 3\)), and keeps \(2\): the \(3 + 3\) that greedy missed. Cost \(\Theta(a \cdot k)\) for \(k\) coin kinds; and note the family resemblance: this is unbounded knapsack (the 0/1 Knapsack handout’s aside) with values minimized instead of maximized: a coin can be reused, so the transition stays within the same “row.”

Written as stated, the recurrence quietly assumes an amount is always payable. It is not: drop the \(1\)-coin and most amounts become unreachable. The fix is a sentinel, and it has to be handled in two places.

Example (coins {3, 5}: the unreachable amounts)

Initialize \(\mathit{dp}[0] = 0\) and every other entry to \(\infty\). A candidate coin \(c\) is usable at amount \(a\) only if \(c \le a\) and \(\mathit{dp}[a - c] \ne \infty\); if no candidate survives, the cell stays \(\infty\), meaning “no set of coins sums to \(a\).”

a012345678
dp[a] 0∞∞ 1∞1 2∞2

Cell by cell:

  • \(a = 1, 2\): both coins exceed the amount, no candidate at all, so \(\mathit{dp} = \infty\).
  • \(a = 3\): coin \(3\) gives \(1 + \mathit{dp}[0] = 1\). Coin \(5\) is too large. \(\mathit{dp}[3] = 1\).
  • \(a = 4\): coin \(3\) fits by size but lands on \(\mathit{dp}[1] = \infty\), so it is not usable; coin \(5\) is too large. \(\mathit{dp}[4] = \infty\). This is the case a naive \(1 + \min(\ldots)\) gets wrong: adding \(1\) to \(\infty\) and storing the result would report a finite-looking count for an impossible amount, and that wrong value would then propagate into \(\mathit{dp}[7]\) and beyond.
  • \(a = 5\): coin \(3\) lands on \(\mathit{dp}[2] = \infty\); coin \(5\) gives \(1 + \mathit{dp}[0] = 1\). \(\mathit{dp}[5] = 1\).
  • \(a = 6\): coin \(3\) gives \(1 + \mathit{dp}[3] = 2\); coin \(5\) lands on \(\mathit{dp}[1] = \infty\). \(\mathit{dp}[6] = 2\).
  • \(a = 7\): coin \(3\) lands on \(\mathit{dp}[4] = \infty\), coin \(5\) on \(\mathit{dp}[2] = \infty\). \(\mathit{dp}[7] = \infty\).
  • \(a = 8\): coin \(3\) gives \(1 + \mathit{dp}[5] = 2\), coin \(5\) gives \(1 + \mathit{dp}[3] = 2\). A tie; \(\mathit{dp}[8] = 2\), by \(3 + 5\) either way.

The unreachable amounts are \(1, 2, 4, 7\), and every amount from \(8\) upward is payable, since \(8, 9, 10\) are and any larger amount reduces to one of them by removing a \(3\). In an implementation the sentinel is usually a large integer rather than a floating \(\infty\); pick one big enough to lose every \(\min\) but small enough that \(1 + \text{sentinel}\) does not overflow, and test for it before using a neighbor. Reporting the impossible case is part of the answer, not an error. 

// Coin change. dp[a] = fewest coins summing to a, or NONE if a is unreachable.
// A coin is usable at a only if it fits AND the amount it leaves is reachable;
// skipping that second test would invent counts for impossible amounts.
// Theta(amount * coins.size()) time, Theta(amount) space.
const int NONE = -1;
int coinChange(const vector<int>& coins, int amount) {
    vector<int> dp(amount + 1, NONE);
    dp[0] = 0;                                       // base: no coins needed
    for (int a = 1; a <= amount; a++)
        for (int c : coins)
            if (c <= a && dp[a - c] != NONE &&
                (dp[a] == NONE || dp[a - c] + 1 < dp[a]))
                dp[a] = dp[a - c] + 1;               // this coin used last
    return dp[amount];                               // NONE: not payable
}

# A coin is usable at a only if it fits AND the amount it leaves is reachable;
# skipping that second test would invent counts for impossible amounts.
# Theta(amount * len(coins)) time, Theta(amount) space.
def coin_change(coins, amount):
    dp = [None] * (amount + 1)
    dp[0] = 0                                        # base: no coins needed
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a and dp[a - c] is not None and \
                    (dp[a] is None or dp[a - c] + 1 < dp[a]):
                dp[a] = dp[a - c] + 1                # this coin used last

// Coin change. dp[a] = fewest coins summing to a, or None if a is unreachable.
// A coin is usable at a only if it fits AND the amount it leaves is reachable;
// skipping that second test would invent counts for impossible amounts.
// Theta(amount * coins.len()) time, Theta(amount) space.
fn coin_change(coins: &[usize], amount: usize) -> Option<usize> {
    let mut dp: Vec<Option<usize>> = vec![None; amount + 1];
    dp[0] = Some(0);                                 // base: no coins needed
    for a in 1..=amount {
        for &c in coins {
            if c <= a {
                if let Some(prev) = dp[a - c] {      // reachable remainder
                    dp[a] = Some(match dp[a] {
                        Some(cur) => cur.min(prev + 1),
                        None => prev + 1,
                    });
                }
            }
        }
    }
    dp[amount]                                       // None: not payable
}

Longest increasing subsequence

Definition (LIS) The longest increasing subsequence (LIS) of an array is the longest subsequence (order kept, gaps allowed; the Longest Common Subsequence handout’s distinction) whose values strictly increase. The DP state is the subtle part: let \(\mathit{dp}[i]\) be the length of the longest increasing subsequence ending exactly at index \(i\); then \[ \mathit{dp}[i] = 1 + \max\{\, \mathit{dp}[j] : j < i,\; a[j] < a[i] \,\} \qquad (\text{or } 1 \text{ if no such } j), \] and the answer is \(\max_i \mathit{dp}[i]\), anywhere in the array.
Example
a[i] 31415926
dp[i] 11213424
Each \(dp[i]\) extends the best earlier subsequence ending in a smaller value: \(dp[4] = 3\) via \(1, 4, 5\) (or \(3,4,5\)), \(dp[5] = 4\) via \(1, 4, 5, 9\), and \(dp[7] = 4\) via \(1, 4, 5, 6\). The LIS length is \(4\); tracing back from either maximum recovers \(1\ 4\ 5\ 9\) or \(1\ 4\ 5\ 6\).
Example (the same array, index by index)

Every index takes one of two branches. If some earlier index holds a strictly smaller value, \(a[i]\) extends the best such subsequence. If none does, there is nothing to extend and \(a[i\,]\) starts a new subsequence of length \(1\). The inner loop scans all of \(j < i\) and keeps the largest \(dp[j]\) among the admissible ones.

Three indices start new (\(0\), \(1\), \(3\)) and five extend. Index \(3\) is the instructive one: two earlier values are admissible-looking neighbors in position but not in value, and the equal value \(1\) at index \(1\) is rejected because the comparison is strict, which is what makes the subsequence increasing rather than non-decreasing. Index \(6\) shows that extending is not the same as improving: \(a[6] = 2\) extends to length \(2\), well below the \(4\) already found, yet it is worth recording, because index \(7\) later scans it. Finally, note that \(dp[7] = 4\) does not come from \(dp[5] = 4\): \(9 \not< 6\), so the longest run through \(9\) is a dead end for \(6\). The answer is \(\max_i dp[i] = 4\), and it is attained twice. 

// Longest increasing subsequence. dp[i] = length of the longest strictly
// increasing subsequence ENDING AT i. Initializing to 1 is the start-new
// branch; the inner loop is the extend branch. Theta(n^2) time, Theta(n) space.
int lis(const vector<int>& a) {
    int n = a.size(), best = 0;
    vector<int> dp(n, 1), from(n, -1);              // from[i]: predecessor index
    for (int i = 0; i < n; i++) {
        for (int j = 0; j < i; j++)
            if (a[j] < a[i] && dp[j] + 1 > dp[i]) { // strict: increasing
                dp[i] = dp[j] + 1;                  // extend the run ending at j
                from[i] = j;
            }
        best = max(best, dp[i]);                    // answer lives anywhere
    }
    return best;                                    // 0 on an empty array
}

Why “ending at \(i\)” rather than “within the first \(i\) elements”? Because the recurrence must know whether the subsequence can be extended by \(a[i]\), and only the value it ends on decides that; a prefix-based state discards exactly the information the transition needs. This is the DP recipe’s advice (the Dynamic Programming Method handout) made concrete: when the recurrence needs a fact the state does not carry, redefine (or extend) the state. The double loop is \(\Theta(n^2)\); a refinement that keeps, for each length, the smallest possible tail value and binary-searches each element into place (“patience sorting”) achieves \(\Theta(n \log n)\), a nice marriage of DP thinking with the searching toolkit, worth knowing by name. LIS itself shows up as longest chains of nested boxes, compatible version upgrades, and one-axis scheduling.

3. Exercises (with solutions)

  1. Count the monotone (right/down) paths across a \(3\times 3\) grid when the center cell is blocked. Show the filled table.
    solution Sum-of-neighbors with the blocked cell forced to \(0\): 
       1  1  1
   1  0  1
   1  1  2
    The corner counts \(2\) paths (down the left edge then across, or across the top then down the right edge), versus \(6\) unblocked (§1). Every path through the center (\(6 - 2 = 4\) of them) is erased by that single \(0\), because the zero propagates through every sum that would have used it.
  2. Matrices \(A\ (5{\times}10)\), \(B\ (10{\times}2)\), \(C\ (2{\times}20)\). Compute the scalar-multiplication cost of both parenthesizations of \(ABC\) and verify that the interval-DP recurrence of §1 picks the cheaper one.
    solution \((AB)C\): \(AB\) costs \(5 \cdot 10 \cdot 2 = 100\) and yields \(5{\times}2\); times \(C\) costs \(5 \cdot 2 \cdot 20 = 200\); total \(300\). \(A(BC)\): \(BC\) costs \(10 \cdot 2 \cdot 20 = 400\) and yields \(10{\times}20\); times \(A\) costs \(5 \cdot 10 \cdot 20 = 1000\); total \(1400\). The DP: \(dp[1][2] = 100\), \(dp[2][3] = 400\) (adjacent pairs have one order), and \(dp[1][3] = \min(k{=}1:\; 0 + 400 + 1000,\;\; k{=}2:\; 100 + 0 + 200) = \min(1400, 300) = 300\), split \(k = 2\): multiply \(AB\) first. A \(4.7\times\) cost gap on three small matrices; on long chains the gap grows unboundedly, which is why the \(\Theta(n^3)\) DP pays.
  3. Coin change, DP-style: with coin values \(\{1, 3, 4\}\), let \(dp[a]\) be the minimum number of coins summing to amount \(a\). Write the recurrence, fill \(dp[0..6]\), and show that greedy (largest coin first) is beaten at \(a = 6\).
    solution Recurrence (case on the last coin used): \(dp[0] = 0\) and \(dp[a] = 1 + \min\{\,dp[a - c] : c \in \{1,3,4\},\, c \le a\,\}\). Filling upward: \(dp[1] = 1\) (coin \(1\)); \(dp[2] = 2\) (\(1{+}1\)); \(dp[3] = 1\) (coin \(3\)); \(dp[4] = 1\) (coin \(4\)); \(dp[5] = 2\) (\(4{+}1\) or \(1{+}4\)); \(dp[6] = 2\) via \(dp[3] + 1\): two \(3\)-coins. So \(dp[0..6] = 0, 1, 2, 1, 1, 2, 2\). Greedy at \(a = 6\) takes \(4\), then must cover \(2\) with \(1 + 1\): three coins against DP’s two, the same \(\{1,3,4\}\) counterexample that sank greedy in the Greedy Method handout, now actually solved. Cost: \(n\) states \(\times\) \(O(1)\) transition (three coins) \(= \Theta(n)\).
  4. Coins \(\{1, 4, 5\}\), amount \(8\). What does greedy (largest-coin-first) produce? Fill \(\mathit{dp}[0..8]\) and give the optimal count.
    solution Greedy: \(5\), then three \(1\)s: four coins. The DP table: 
      a:      0  1  2  3  4  5  6  7  8
  dp[a]:  0  1  2  3  1  1  2  3  2
    \(\mathit{dp}[8]\) tries last coins \(1\) (\(1 + dp[7] = 4\)), \(4\) (\(1 + dp[4] = 2\)), and \(5\) (\(1 + dp[3] = 4\)): the optimum is \(2\), namely \(4 + 4\). Greedy’s first grab of the \(5\) leaves the amount \(3\), reachable only by ones, the standard non-canonical-coin-system failure, and the DP examines all last coins instead of committing.
  5. Compute the LIS length of \([10, 9, 2, 5, 3, 7, 101, 18]\), showing the \(dp\) array. Then explain concretely what breaks if the state is defined as “\(dp[i]\) = LIS length within the first \(i\) elements” instead of “ending at \(i\).”
    solution 
      a[i]:   10   9   2   5   3   7  101  18
  dp[i]:   1   1   1   2   2   3    4   4
    The maximum is \(4\), achieved by \(2, 5, 7, 101\) (or \(2, 3, 7, 18\), or \(2, 5, 7, 18\)). With the prefix state, consider extending by the next element: knowing only “the first \(6\) elements contain an increasing subsequence of length \(3\)” does not say whether that subsequence ends below \(101\) or below \(18\); the recurrence cannot decide extendability, because the state discarded the ending value. “Ending at \(i\)” carries exactly the needed fact (the last value is \(a[i]\)) at the price of taking a final max over all \(i\). When a recurrence will not close, enrich the state, the first line of the capstone checklist (the Dynamic Programming Method handout).
