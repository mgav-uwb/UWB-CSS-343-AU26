0/1 Knapsack

In 1978 Ralph Merkle and Martin Hellman built a public-key cryptosystem on the knapsack problem. Adi Shamir broke it in 1982. A. Shamir, “A Polynomial Time Algorithm for Breaking the Basic Merkle-Hellman Cryptosystem,” FOCS 1982

The DP recipe (define the subproblem, write the recurrence off the last decision, pin the base cases, fill in dependency order, read the answer cell) is the Dynamic Programming Method handout. This handout runs it on a problem where greedy fails outright (the Greedy Method handout): the 0/1 knapsack, whose take-or-skip table also exposes the subtle notion of pseudo-polynomial time.

1. The 0/1 knapsack problem

Definition (0/1 knapsack) Given \(n\) items, each with a value \(v_i\) and a weight \(w_i\), and a knapsack of capacity \(W\): choose a subset of items of maximum total value whose total weight is at most \(W\). Each item is taken whole or not at all; that all-or-nothing choice is the “0/1.”

The running example, four items and capacity \(W = 5\):

itemABCD
value \(v_i\)3456
weight \(w_i\)2345

Which subset fits and is worth the most? Contrast this with the fractional knapsack of the Greedy Method handout, where items could be cut and greedy-by-ratio was provably optimal. Making the items indivisible breaks the greedy argument completely:

Example (greedy fails) Capacity \(W = 6\), three items: \(P\) (value \(5\), weight \(4\), ratio \(1.25\)), \(Q\) (value \(3\), weight \(3\), ratio \(1.00\)), \(R\) (value \(3\), weight \(3\), ratio \(1.00\)). Greedy takes the best-ratio item \(P\) first, and then only \(2\) units of capacity remain, into which nothing fits, for a total of \(5\). The optimum is \(Q + R\): weight \(6\), value \(6\). One high-ratio item blocks two jointly better ones. The best choice for any one item depends on the remaining capacity and on all the other items, so no single choice can be committed to greedily: both including and excluding each item must be considered. (On the A–D set above, greedy happens to get lucky; one passing test is not a proof, which is why this counterexample matters.)

Trying everything naively is hopeless: \(n\) items form \(2^n\) subsets, and for \(n = 40\) that is \(2^{40} \approx 1.1 \times 10^{12}\), a trillion subsets. DP replaces the enumeration with a table of \(n \cdot W\) cells: for \(n = 40\) and \(W = 1000\), forty thousand cells. From \(10^{12}\) to \(4 \times 10^4\) is the same exponential-to-polynomial collapse as memoized Fibonacci, now on a real optimization problem (with one caveat about that \(W\), the subject of §2).

The subproblem and the recurrence

Definition (knapsack table) Let \(K[i][w]\) be the maximum value achievable using only the first \(i\) items within weight capacity \(w\). The last-decision question (take item \(i\) or not?) gives the recurrence \[ K[i][w] = \max\bigl(\; \underbrace{K[i-1][w]}_{\text{skip item } i},\;\; \underbrace{v_i + K[i-1][w - w_i]}_{\text{take item } i \text{ (only if } w_i \le w\text{)}} \;\bigr), \] with base cases \(K[0][w] = 0\) (no items, no value) and \(K[i][0] = 0\) (no capacity, nothing fits). The answer is \(K[n][W]\).

The state is two-dimensional (how many items have been considered, and how much capacity remains), exactly the “add a dimension when the recurrence needs information the state lacks” move of the DP recipe: the value of taking an item cannot be judged without knowing the capacity left for the rest. Skipping item \(i\) keeps the best of the first \(i-1\) items at the same capacity (the cell directly above); taking it earns \(v_i\) plus the best the earlier items can do in the reduced capacity \(w - w_i\) (one row up, \(w_i\) columns left). The guard \(w_i \le w\) is the only wrinkle this recurrence adds over LCS: an item that does not fit cannot be taken.

The indexing pitfall In the recurrence, “item \(i\)” is 1-based: \(K[i][w]\) covers items \(1\) through \(i\), and row \(0\) is the empty set. A 0-based C++ vector of items therefore reads value[i-1] and weight[i-1] inside the row-\(i\) loop (or carries a dummy slot \(0\), as the code below does). This off-by-one, and its twin at the base-case edges, is the single most common knapsack bug: write row \(0\) and column \(0\) first, then the double loop never reads an uninitialized or misaligned cell.
Example (one cell, both branches) Compute \(K[2][5]\) (items A and B available, capacity \(5\); B has value \(4\), weight \(3\)): \[ \begin{aligned} \text{skip B:}\quad K[1][5] &= 3 &&\text{(just A)}\\ \text{take B:}\quad 4 + K[1][5-3] &= 4 + K[1][2] = 4 + 3 = 7\\ K[2][5] &= \max(3, 7) = 7 &&\text{take both A and B} \end{aligned} \] Taking B adds its value to the best use of the two units of capacity that remain for the earlier items: \(K[1][2] = 3\), item A alone (weights \(2 + 3 = 5\) exactly fill the sack). Every cell of the table is this one computation. One more, at a tighter capacity: \(K[3][4]\) (items A–C, capacity \(4\); C has value \(5\), weight \(4\)). Skip C: \(K[2][4] = 4\) (B alone; A\(+\)B weigh \(5\), too much for capacity \(4\)). Take C: \(5 + K[2][0] = 5 + 0 = 5\), C using the whole capacity. \(K[3][4] = \max(4, 5) = 5\): C alone beats B alone at capacity \(4\).
Example (one whole row, every branch) Row \(+\)C (item C, value \(5\), weight \(4\)) filled left to right, given the row above it, \(K[2][0..5] = 0, 0, 3, 4, 4, 7\). The recurrence has three possible outcomes at a cell, and this single row shows all of them:

  • Does not fit (\(w < 4\)): the take branch is never evaluated, the guard skips it, and the cell copies the row above unchanged. Four cells of this row are pure copies.
  • Fits and take wins (\(w = 4\)): C alone (\(5\)) beats the best of A and B at capacity \(4\) (\(4\), which is B alone, since A\(+\)B weighs \(5\)).
  • Fits and skip wins (\(w = 5\)): taking C consumes \(4\) of the \(5\) units and leaves \(1\), into which nothing fits, for \(5\); skipping keeps A\(+\)B at \(7\).
The fourth outcome, a tie, needs a little more capacity. Widen the same instance to \(W = 7\) and look at \(K[4][7]\), with row \(+\)C now reading \(K[3][0..7] = 0, 0, 3, 4, 5, 7, 8, 9\): \[ \begin{aligned} \text{skip D:}\quad K[3][7] &= 9 &&\text{(B + C, weight 7)}\\ \text{take D:}\quad 6 + K[3][7-5] &= 6 + K[3][2] = 6 + 3 = 9 &&\text{(A + D, weight 7)}\\ K[4][7] &= \max(9, 9) = 9 &&\text{both choices optimal} \end{aligned} \] All four outcomes, cell by cell: Because max keeps the skip value on a tie, the cell equals the one above it, and the traceback below reports D as skipped and returns \(\{\text{B}, \text{C}\}\). The equally optimal \(\{\text{A}, \text{D}\}\) is simply the branch the tie-break did not take; either answer is correct, and only one is reported.

The code

// Tabulated 0/1 knapsack. value[i], weight[i] describe item i (1-based, with a
// dummy slot 0). K[i][w] = best value using items 1..i within capacity w.
// Theta(nW) time and space.
int knapsack(int n, int W, const vector<int>& value, const vector<int>& weight,
             vector<vector<int>>& K) {
    K.assign(n + 1, vector<int>(W + 1, 0));           // row 0: no items -> 0
    for (int i = 1; i <= n; i++)
        for (int w = 0; w <= W; w++) {
            K[i][w] = K[i-1][w];                      // skip item i
            if (weight[i] <= w)                       // does it fit?
                K[i][w] = max(K[i][w],
                              value[i] + K[i-1][w - weight[i]]);   // take it
        }
    return K[n][W];                                   // the optimal value
}

// Traceback: recover WHICH items achieve K[n][W]. If a cell differs from the
// cell directly above, item i was taken; drop its weight and continue. O(n).
vector<int> knapsackItems(int n, int W, const vector<int>& weight,
                          const vector<vector<int>>& K) {
    vector<int> taken;
    int w = W;
    for (int i = n; i >= 1; i--)
        if (K[i][w] != K[i-1][w]) {                   // value changed: taken
            taken.push_back(i);
            w -= weight[i];
        }
    reverse(taken.begin(), taken.end());              // forward order
    return taken;
}

// with a dummy slot 0). K[i][w] = best value using items 1..i within
// capacity w. Theta(nW) time and space.
static int knapsack(int n, int W, int[] value, int[] weight, int[][] K) {

                    value[i] + K[i-1][w - weight[i]]);   // take it
        }

}

            taken.add(i);

        }

}
# Tabulated 0/1 knapsack. value[i], weight[i] describe item i (1-based lists
# with a dummy slot 0). K[i][w] = best value using items 1..i within
# capacity w. Theta(nW) time and space. Returns the full table.
def knapsack(n, W, value, weight):
    K = [[0] * (W + 1) for _ in range(n + 1)]     # row 0: no items -> 0
    for i in range(1, n + 1):
        for w in range(W + 1):
            K[i][w] = K[i - 1][w]                 # skip item i
            if weight[i] <= w:                    # does it fit?
                K[i][w] = max(K[i][w],
                              value[i] + K[i - 1][w - weight[i]])   # take it
    return K                                      # K[n][W] is the optimum

# Traceback: recover WHICH items achieve K[n][W]. If a cell differs from the
# cell directly above, item i was taken; drop its weight and continue. O(n).
def knapsack_items(n, W, weight, K):
    taken, w = [], W
    for i in range(n, 0, -1):
        if K[i][w] != K[i - 1][w]:                # value changed: taken
            taken.append(i)
            w -= weight[i]
    return taken[::-1]                            # forward order
// Tabulated 0/1 knapsack. value[i], weight[i] describe item i (1-based slices
// with a dummy slot 0). k[i][w] = best value using items 1..=i within
// capacity w. Theta(nW) time and space. Returns the full table.
fn knapsack(n: usize, cap: usize, value: &[i64], weight: &[usize]) -> Vec<Vec<i64>> {
    let mut k = vec![vec![0i64; cap + 1]; n + 1];     // row 0: no items -> 0
    for i in 1..=n {
        for w in 0..=cap {
            k[i][w] = k[i - 1][w];                    // skip item i
            if weight[i] <= w {                       // does it fit?
                k[i][w] = k[i][w].max(value[i] + k[i - 1][w - weight[i]]);
            }
        }
    }
    k                                                 // k[n][cap] is the optimum
}

// Traceback: recover WHICH items achieve k[n][cap]. If a cell differs from
// the cell directly above, item i was taken; drop its weight. O(n).
fn knapsack_items(n: usize, cap: usize, weight: &[usize], k: &[Vec<i64>]) -> Vec<usize> {
    let mut taken = Vec::new();
    let mut w = cap;
    for i in (1..=n).rev() {
        if k[i][w] != k[i - 1][w] {                   // value changed: taken
            taken.push(i);
            w -= weight[i];
        }
    }
    taken.reverse();                                  // forward order
    taken
}

The traceback deserves a word here (its general pattern is the Traceback & Space-Saving handout). \(K[n][W]\) is only the optimal value; to know which items achieve it, walk from the bottom-right upward, one item per step. If a cell equals the cell directly above, skipping item \(i\) was (one) optimal choice (taking it changed nothing), so the item was not needed; if the values differ, the item was taken: record it and reduce the remaining capacity by its weight. On the table above:

1\(K[4][5] = 7 = K[3][5]\)D skipped\(w = 5\)
2\(K[3][5] = 7 = K[2][5]\)C skipped\(w = 5\)
3\(K[2][5] = 7 \ne K[1][5] = 3\)B taken\(w = 5 - 3 = 2\)
4\(K[1][2] = 3 \ne K[0][2] = 0\)A taken\(w = 2 - 2 = 0\)

The walk ends in row \(0\) with items \(\{\text{A}, \text{B}\}\), value \(7\).

Proposition (knapsack cost) The table has \((n+1)(W+1)\) cells, each filled in \(O(1)\), so the DP runs in \(\Theta(nW)\) time and space; the traceback adds \(O(n)\). (Space drops to \(\Theta(W)\) with the rolling array of the Traceback & Space-Saving handout, if only the value is needed.)
The knapsack family Small changes to the transition cover a whole family of problems. In the 0/1 version, the take branch reads row \(i-1\): item \(i\), once used, is gone. In the unbounded version (unlimited copies of each item), the take branch reads row \(i\) itself, \(K[i][w] = \max(K[i-1][w],\; v_i + K[i][w-w_i])\), so an item can be taken again. A bounded version (at most \(k\) copies) loops over the count. Coin change (the DP Patterns handout) is unbounded knapsack in disguise, minimizing the number of coins instead of maximizing value. One mental model, a one-line tweak per variant, and the Traceback & Space-Saving handout shows the same 0/1-versus-unbounded switch hiding inside a loop direction.

To watch a greedy rule actually lose, run 1/6, 2/10, 3/12 -> 5: densities \(6, 5, 4\), so taking the densest item first yields \(16\), while the optimum is \(22\).

2. Pseudo-polynomial time

\(\Theta(nW)\) looks polynomial: two variables, multiplied. But look at what the two variables are. The \(n\) counts items: an input with more items is physically longer. The \(W\), though, is not a count of anything in the input; it is the numeric value of a single number that the input spells in binary.

Definition (pseudo-polynomial) An algorithm runs in pseudo-polynomial time if its running time is polynomial in the numeric value of the input’s numbers but not in the size (bit-length) of the input. Knapsack’s \(\Theta(nW)\) is the standard example.
Proposition (the bit-length argument) \(\Theta(nW)\) is exponential in the size of the encoded input.
Why. The capacity \(W\) occupies \(b = \lceil \log_2(W{+}1) \rceil\) bits of input (\(W = 1{,}000{,}000\) is written in just \(20\) bits, since \(2^{20} = 1{,}048{,}576\)), yet the DP builds a table with \(W + 1\) columns: a million columns conjured from twenty bits. In general a \(b\)-bit capacity can be as large as \(2^b - 1\), so the running time is \[ \Theta(nW) = \Theta\!\bigl(n \cdot 2^{\,b}\bigr), \] exponential in the bit-length \(b\). The everyday symptom: appending one \(0\) bit to \(W\), one more input character, doubles the running time. A truly polynomial algorithm would have to run in time polynomial in \(n\) and \(\log W\). ∎
Example (the same instance, rescaled) The A–D instance measured its weights in whole units: weights \(2, 3, 4, 5\) and \(W = 5\), a table of \(6\) columns and \(5\) rows (row \(0\) included), \(30\) cells. Measure the identical sack in tenths of a unit, then in thousandths, and nothing about the problem changes: the optimum is still A\(+\)B at value \(7\), the same two items. Only the table changes.

Three extra digits written into the input bought a table about \(1000 \approx 2^{10}\) times larger, matching the \(10\) extra bits (\(3 \to 13\)). The work tracks the numeric value of \(W\), while the input grew by a handful of characters, and the answer never moved. Padding \(W\) with one more bit doubles the table again, and again.

The contrast with edit distance (the Edit Distance handout) makes the distinction sharp. Its \(\Theta(mn)\) bound is truly polynomial, because \(m\) and \(n\) are the lengths of the two input strings: the table grows with the physical size of the input, not with the value of a number inside it. Knapsack’s table has a dimension proportional to a value, and values grow exponentially faster than their encodings.

No contradiction with NP-hardness The 0/1 knapsack problem is NP-hard (NP: nondeterministic polynomial time): among the problems for which no polynomial-time algorithm is known, and none is expected. The \(\Theta(nW)\) DP does not contradict that: it is efficient when the capacity is numerically modest, and exponential (in the input size) when \(W\) is astronomically large, exactly the regime the hardness lives in. In practice this makes the DP a genuinely useful algorithm: capacities in real scheduling, budgeting, and cargo problems are usually small enough that \(nW\) is tiny. Recognizing a pseudo-polynomial bound (asking “is this variable a count or a value?”) is a standard exam and interview point.

3. Exercises (with solutions)

  1. Items X (value \(4\), weight \(3\)), Y (value \(5\), weight \(4\)), Z (value \(7\), weight \(5\)); capacity \(W = 7\). Fill the knapsack table \(K[0..3][0..7]\), state the optimal value and (by traceback) the items taken, and show that greedy-by-ratio fails on this instance.
    solution \(K[3][7] = 9\). Traceback: \(K[3][7] = 9 = K[2][7]\) → Z skipped; \(K[2][7] = 9 \ne K[1][7] = 4\) → Y taken (\(w = 7-4 = 3\)); \(K[1][3] = 4 \ne K[0][3] = 0\) → X taken (\(w = 0\)). Items \(\{X, Y\}\): weight \(7\), value \(9\). Greedy by ratio: Z has the best ratio (\(7/5 = 1.40\) versus \(4/3 \approx 1.33\) and \(5/4 = 1.25\)), so greedy takes Z first, leaving capacity \(2\) into which nothing fits: total \(7 < 9\). The same “one blocker beats two partners” failure as §1.
  2. A friend argues: “\(\Theta(nW)\) is a polynomial in two variables, so the knapsack DP is a polynomial-time algorithm, so knapsack cannot be NP-hard.” Locate the error precisely, using the case \(W = 2^{100}\).
    solution “Polynomial time” means polynomial in the input size: the number of bits needed to write the input down. The capacity \(W = 2^{100}\) is written in only \(101\) bits, yet \(\Theta(nW) = \Theta(n \cdot 2^{100})\) table cells would be needed, astronomically exponential in those \(101\) bits. In general a \(b\)-bit capacity permits \(W\) up to \(2^b - 1\), making the DP \(\Theta(n \cdot 2^b)\): each additional input bit doubles the work. That is pseudo-polynomial (polynomial in the value \(W\), exponential in the size \(\log_2 W\)), so there is no contradiction with NP-hardness. (Contrast edit distance: its \(m\) and \(n\) are string lengths, actual input size, so \(\Theta(mn)\) is genuinely polynomial.)
