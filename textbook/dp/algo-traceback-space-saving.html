Traceback & Space-Saving

Daniel Hirschberg showed in 1975 that a longest common subsequence, not just its length, can be found in linear space and quadratic time, by divide and conquer. D. S. Hirschberg, “A Linear Space Algorithm for Computing Maximal Common Subsequences,” CACM 18(6), 1975

A filled DP table stores optimal values; applications usually want the solution itself, and memory is often the binding constraint. This handout states in general the two techniques that every optimization DP of the problem handouts (Rod Cutting, Longest Common Subsequence, 0/1 Knapsack, Edit Distance, and DP Patterns) used piecemeal: the traceback and the rolling array.

1. Traceback and space-saving

Two techniques appeared in every problem of the DP handouts; they deserve their general statements, because they apply to every optimization DP you will ever write.

The traceback, in general

Pattern (traceback) A filled DP table stores optimal values; to recover the optimal solution:
  1. start at the answer cell;
  2. determine which neighbor (and which decision) produced this cell’s value, by comparing against each candidate of the recurrence;
  3. record the decision and move to that neighbor;
  4. stop at a base case; reverse the recorded decisions.
Cost: \(O(\text{path length})\). Either store the winning choice per cell while filling (extra memory, trivial walk) or recompute it during the walk (no memory, a few comparisons per step); the knapsack and edit-distance code of the 0/1 Knapsack and Edit Distance handouts both recompute.
Example (following the arrows, step by step)

Take the longest common subsequence of \(A =\) HEAP and \(B =\) HELP. Filling \(L[i][j]\) (the length of the LCS of the first \(i\) and first \(j\) characters) also records, per cell, which candidate won: ↖ for a match taken on the diagonal, ↑ for “the cell above was at least as good,” ← for the cell to the left. Row and column \(0\) are base cells and carry no arrow.

The walk starts at the answer cell \(L[4][4] = 3\) and stops when either index hits \(0\). Each step is shown twice over: the arrow that was stored, and the comparison that recomputes the same decision from the values alone, which is what code that stores no arrows does.

stepat\(L\)chars recomputed testarrowmove to output so far
1(4,4)3 P = P match, and \(3 = L[3][3] + 1\) ↖(3,3) P
2(3,3)2 A ≠ L \(L[2][3] = 2 = L[3][3]\), up explains it ↑(2,3) P
3(2,3)2 E ≠ L \(L[1][3] = 1 \ne 2\), so not up; \(L[2][2] = 2\) ←(2,2) P
4(2,2)2 E = E match, and \(2 = L[1][1] + 1\) ↖(1,1) EP
5(1,1)1 H = H match, and \(1 = L[0][0] + 1\) ↖(0,0) HEP
6(0,0)0 – base cell reached, stop –– HEP

Five steps, three of them emitting a character: HEP, of length \(3 = L[4][4]\), so the walk and the value agree. Three details generalize. A diagonal step is the only one that outputs anything; the other two just reposition, which is why the walk can be longer than the solution it produces. The path is monotone (every step decreases \(i + j\) by \(1\) or \(2\)), so it visits at most \(m + n\) cells: the \(O(\text{path length})\) claim of the pattern. And it visits cells scattered across every row, here rows \(4, 3, 2, 1\), which is the fact the rolling array collides with. Output is built here by prepending, the equivalent of collecting backwards and reversing at the end.

The Rod Cutting and Longest Common Subsequence handouts traced cuts and characters; the 0/1 Knapsack handout traced items (the equal-vs-different test against the cell above), the Edit Distance handout an edit script (which of three neighbors explains the value), and the DP Patterns handout the grid path. Five problems, one pattern, and one universal skeleton around it: 

  1. allocate the table; set the BASE cells
  2. loop over states in dependency ORDER
  3. each cell = combine(smaller cells)        // the recurrence
  4. read the ANSWER cell
  5. (optional) TRACE BACK for the solution

Every DP in these handouts (Fibonacci, rod cutting, LCS, knapsack, edit distance, grids, intervals, coin change, LIS) is this five-line skeleton with a different state and combine step. The scaffolding never changes; only the recurrence does. That is what makes DP one technique rather than a zoo of tricks.

Space-saving: the rolling array

Look back at the knapsack and edit-distance recurrences: row \(i\) reads only row \(i-1\) (and, to its left, row \(i\) itself). Rows older than the previous one are dead weight, so keep two rows and swap them, or for knapsack even one row updated in place, cutting space from \(\Theta(mn)\) or \(\Theta(nW)\) to \(\Theta(n)\) or \(\Theta(W)\): 

// 0/1 knapsack value in Theta(W) space: ONE row, updated RIGHT-TO-LEFT so that
// K[w - weight[i]] still holds the previous row's value (item i not yet used).
// Iterating forward instead would let item i be taken again -- that variant is
// exactly the UNBOUNDED knapsack. No table survives, so no traceback.
int knapsackValue(int n, int W, const vector<int>& value,
                  const vector<int>& weight) {
    vector<int> K(W + 1, 0);                          // row 0: no items
    for (int i = 1; i <= n; i++)
        for (int w = W; w >= weight[i]; w--)          // BACKWARD: 0/1
            K[w] = max(K[w], value[i] + K[w - weight[i]]);
    return K[W];
}

// Edit-distance value in Theta(n) space: keep TWO rows, the previous and the
// current, swapping after each row. Same fill, same answer -- no traceback.
int editDistanceValue(const string& a, const string& b) {
    int m = a.size(), n = b.size();
    vector<int> prev(n + 1), cur(n + 1);
    for (int j = 0; j <= n; j++) prev[j] = j;         // row 0: insert all of b
    for (int i = 1; i <= m; i++) {
        cur[0] = i;                                   // column 0: delete all
        for (int j = 1; j <= n; j++)
            cur[j] = (a[i-1] == b[j-1])
                       ? prev[j-1]                    // match: free diagonal
                       : 1 + min({prev[j],            // delete
                                  cur[j-1],           // insert
                                  prev[j-1]});        // replace
        swap(prev, cur);                              // this row becomes "previous"
    }
    return prev[n];                                   // the last computed row
}
// 0/1 knapsack value in Theta(W) space: ONE row, updated RIGHT-TO-LEFT so
// K[w - weight[i]] still holds the previous row's value (item i not yet
// used). Iterating forward would let item i be taken again -- that variant
// is exactly the UNBOUNDED knapsack. No table survives, so no traceback.
static int knapsackValue(int n, int W, int[] value, int[] weight) {
    int[] K = new int[W + 1];                     // row 0: no items
    for (int i = 1; i <= n; i++)
        for (int w = W; w >= weight[i]; w--)      // BACKWARD: 0/1
            K[w] = Math.max(K[w], value[i] + K[w - weight[i]]);
    return K[W];
}

// Edit-distance value in Theta(n) space: keep TWO rows, previous and
// current, swapping after each row. Same fill, same answer -- no traceback.
static int editDistanceValue(String a, String b) {
    int m = a.length(), n = b.length();
    int[] prev = new int[n + 1], cur = new int[n + 1];
    for (int j = 0; j <= n; j++) prev[j] = j;     // row 0: insert all of b
    for (int i = 1; i <= m; i++) {
        cur[0] = i;                               // column 0: delete all
        for (int j = 1; j <= n; j++)
            cur[j] = (a.charAt(i-1) == b.charAt(j-1))
                       ? prev[j-1]                          // match
                       : 1 + Math.min(prev[j],              // delete
                             Math.min(cur[j-1],             // insert
                                      prev[j-1]));          // replace
        int[] t = prev; prev = cur; cur = t;      // rows swap roles
    }
    return prev[n];                               // the last computed row
}
# 0/1 knapsack value in Theta(W) space: ONE row, updated RIGHT-TO-LEFT so
# K[w - weight[i]] still holds the previous row's value (item i not yet
# used). Iterating forward instead would let item i be taken again -- that
# variant is exactly the UNBOUNDED knapsack. No table, so no traceback.
def knapsack_value(n, W, value, weight):
    K = [0] * (W + 1)                             # row 0: no items
    for i in range(1, n + 1):
        for w in range(W, weight[i] - 1, -1):     # BACKWARD: 0/1
            K[w] = max(K[w], value[i] + K[w - weight[i]])
    return K[W]

# Edit-distance value in Theta(n) space: keep TWO rows, previous and current,
# swapping after each row. Same fill, same answer -- no traceback.
def edit_distance_value(a, b):
    m, n = len(a), len(b)
    prev = list(range(n + 1))                     # row 0: insert all of b
    for i in range(1, m + 1):
        cur = [i] + [0] * n                       # column 0: delete all
        for j in range(1, n + 1):
            if a[i - 1] == b[j - 1]:
                cur[j] = prev[j - 1]              # match: free diagonal
            else:
                cur[j] = 1 + min(prev[j],         # delete
                                 cur[j - 1],      # insert
                                 prev[j - 1])     # replace
        prev = cur                                # this row becomes "previous"
    return prev[n]                                # the last computed row
// 0/1 knapsack value in Theta(W) space: ONE row, updated RIGHT-TO-LEFT so
// k[w - weight[i]] still holds the previous row's value (item i not yet
// used). Iterating forward would let item i be taken again -- that variant
// is exactly the UNBOUNDED knapsack. No table survives, so no traceback.
fn knapsack_value(n: usize, cap: usize, value: &[i64], weight: &[usize]) -> i64 {
    let mut k = vec![0i64; cap + 1];                  // row 0: no items
    for i in 1..=n {
        for w in (weight[i]..=cap).rev() {            // BACKWARD: 0/1
            k[w] = k[w].max(value[i] + k[w - weight[i]]);
        }
    }
    k[cap]
}

// Edit-distance value in Theta(n) space: keep TWO rows, previous and current,
// swapping after each row. Same fill, same answer -- no traceback.
fn edit_distance_value(a: &[u8], b: &[u8]) -> usize {
    let (m, n) = (a.len(), b.len());
    let mut prev: Vec<usize> = (0..=n).collect();     // row 0: insert all of b
    let mut cur = vec![0usize; n + 1];
    for i in 1..=m {
        cur[0] = i;                                   // column 0: delete all
        for j in 1..=n {
            cur[j] = if a[i - 1] == b[j - 1] {
                prev[j - 1]                           // match: free diagonal
            } else {
                1 + prev[j]                           // delete
                    .min(cur[j - 1])                  // insert
                    .min(prev[j - 1])                 // replace
            };
        }
        std::mem::swap(&mut prev, &mut cur);          // rows swap roles
    }
    prev[n]                                           // the last computed row
}

Example (two rows on the table just traced)

Run the two-row fill on the very LCS instance of the traceback above, \(A =\) HEAP, \(B =\) HELP. Each row is computed from the previous one exactly as before; the difference is only that the finished row is then dropped.

after“”HELPmemory holds
init (row 0) 00000 row 0
\(i=1\) (H) 01111 rows 0, 1
\(i=2\) (E) 01222 rows 1, 2 (row 0 overwritten)
\(i=3\) (A) 01222 rows 2, 3 (row 1 overwritten)
\(i=4\) (P) 01223 rows 3, 4 (row 2 overwritten)

Every number matches the corresponding row of the full table, and the answer \(3\) is identical; the \(5 \times 5 = 25\) stored integers have become \(2 \times 5 = 10\), and for \(m\) rows the saving is the whole factor of \(m\). What is gone is the walk. The traceback above needed \(L[2][2]\) and \(L[1][1]\), both in rows the fill has since reused, so from the surviving rows \(3\) and \(4\) the letters E and H cannot be recovered. The length survives because it lives in one cell; the subsequence does not, because it lives in the whole table.

Example (one row in place, sweeping backward)

Knapsack does better still, because each row reads only cells at smaller capacities in the row above: one array, updated in place. Take capacity \(W = 6\) and three items, \((v, w) = (3, 2)\), \((4, 3)\), \((5, 4)\). Sweeping \(w\) downward, the row after item \(i\) is exactly row \(i\) of the full \((n{+}1) \times (W{+}1)\) table.

\(w\)0123456
initial row 0000000
after item 1 (3, 2) 0033333
after item 2 (4, 3) 0034477
after item 3 (5, 4) 0034578

The answer \(8\) is items \(1\) and \(3\), weight \(2 + 4 = 6\), value \(3 + 5 = 8\). Watch the inner sweep for item \(2\), starting from \([0, 0, 3, 3, 3, 3, 3]\) and running \(w = 6, 5, 4, 3\): 

  w=6:  max( K[6]=3,  4 + K[3]=3 )  =  max(3, 7)  =  7
  w=5:  max( K[5]=3,  4 + K[2]=3 )  =  max(3, 7)  =  7
  w=4:  max( K[4]=3,  4 + K[1]=0 )  =  max(3, 4)  =  4
  w=3:  max( K[3]=3,  4 + K[0]=0 )  =  max(3, 4)  =  4
                                    →  [0, 0, 3, 4, 4, 7, 7]

At \(w = 6\) the read of \(K[3]\) returns \(3\), the value from before item \(2\) was considered, because \(w = 3\) is written last. Sweep the same item forward instead, \(w = 3, 4, 5, 6\), and \(K[3]\) becomes \(4\) first, so \(w = 6\) reads \(4 + K[3] = 4 + 4 = 8\) and the row ends \([0, 0, 3, 4, 4, 7, 8]\): item \(2\) packed twice, weight \(3 + 3 = 6\), value \(4 + 4 = 8\). One item, two copies, from reversing a loop.

The loop direction encodes the variant In the one-row knapsack, the backward sweep is not a stylistic choice; it is the 0/1 semantics. Going right-to-left, \(K[w - w_i]\) has not yet been touched this pass, so it still holds the previous item-row’s value: item \(i\) cannot combine with itself. Flip the loop forward and \(K[w - w_i]\) may already include item \(i\), which is precisely the unbounded knapsack. Smallest possible demonstration: a single item of value \(3\), weight \(2\), capacity \(4\). Backward the row ends \([0, 0, 3, 3, 3]\), the item once, value \(3\); forward it ends \([0, 0, 3, 3, 6]\), the item twice, value \(6\). One character of code, a different problem. (A favorite interview probe, for exactly that reason.)

Value or solution: decide up front

you needkeepspace

The rolling array destroys the very cells the traceback walks: a genuine functionality trade, not a free optimization. State which side of it an application needs before writing the fill loop. And if recursion feels more natural than loops, the other implementation style (memoization; the Dynamic Programming Method handout) still applies here: memoize the knapsack recurrence top-down, knap(i, w) checking a \((n{+}1)\times(W{+}1)\) cache before recursing on skip and (if it fits) take, and you get the same \(\Theta(nW)\) bound while computing only the cells actually reachable from \((n, W)\), which can be far fewer. Tabulation’s reward is the rolling row; memoization’s is writing exactly the recurrence and no fill-order reasoning. Both are “the DP.”

Enrichment: both at once (Hirschberg) Remarkably, the trade can be beaten for the string DPs. Hirschberg’s algorithm recovers the full LCS or edit solution in linear space by composing DP with divide-and-conquer (the Divide & Conquer handout’s paradigm): run the two-row fill forward over the top half of the table and backward over the bottom half to find where the optimal path crosses the middle row (linear space suffices for values), then recurse on the two halves the crossing splits off. Total time stays \(\Theta(mn)\) (the half-tables form a geometric series), space stays \(\Theta(n)\), and the full alignment comes out. This is how genome-scale sequence aligners run in memory that the full table could never fit. Not examinable, but a beautiful example of two paradigms composing.

2. Exercises (with solutions)

  1. Below is the filled LCS table for \(A =\) STACK and \(B =\) TRACKS, with the winning choice stored per cell. Walk the traceback from the answer cell and give the subsequence. How many steps does the walk take, and how many of them emit a character? 
              ""    T     R     A     C     K     S
    ""     0     0     0     0     0     0     0
    S      0   ↑0    ↑0    ↑0    ↑0    ↑0    ↖1
    T      0   ↖1    ←1    ←1    ←1    ←1    ↑1
    A      0   ↑1    ↑1    ↖2    ←2    ←2    ←2
    C      0   ↑1    ↑1    ↑2    ↖3    ←3    ←3
    K      0   ↑1    ↑1    ↑2    ↑3    ↖4    ←4
    solution Start at \(L[5][6] = 4\). 
      (5,6) ←  no output      → (5,5)
  (5,5) ↖  emit K         → (4,4)
  (4,4) ↖  emit C         → (3,3)
  (3,3) ↖  emit A         → (2,2)
  (2,2) ←  no output      → (2,1)
  (2,1) ↖  emit T         → (1,0)   column 0: stop
    Six steps, four of them emitting, giving TACK of length \(4 = L[5][6]\). Two observations. The walk stops on reaching column \(0\), not on reaching \((0,0)\): either index hitting a base edge ends it, and here row \(1\) is never entered. And the match of S at \(L[1][6]\), a perfectly real ↖ in the table, is not on the path: using it would force abandoning TACK, since S occurs before the others in \(A\) but after them in \(B\). A stored arrow records what this cell chose, not what is globally reachable, which is exactly why the traceback must be a walk and not a scan.
  2. Space optimization, carefully. (a) The two-row LCS trick keeps only the current and previous rows. What is its space, and what capability is lost? (b) Can rod cutting’s \(\mathrm{best}[]\) be similarly reduced to \(O(1)\) space, as Fibonacci’s was? Justify from the recurrences.
    solution (a) Two rows of the shorter dimension: \(\Theta(\min(m,n))\), with time still \(\Theta(mn)\). Lost: the traceback: recovering the subsequence needs cells from every row, which have been overwritten; only the length survives. (b) No. Fibonacci’s recurrence reaches back a fixed distance (\(\mathrm{fib}(i)\) needs only \(i{-}1\) and \(i{-}2\)), so a two-cell window suffices. Rod cutting’s \(\mathrm{best}[\ell] = \max_i(\mathrm{price}[i] + \mathrm{best}[\ell - i])\) reaches back to every smaller index, all the way to \(\mathrm{best}[0]\), so all \(\ell\) earlier cells are live at every step: \(\Theta(n)\) space is inherent to this recurrence. The lesson: the space optimization is a property of the dependency pattern, not of DP in general; read it off the recurrence.
  3. A classmate “simplifies” the one-row knapsack of §1 by iterating \(w\) from weight[i] up to \(W\). The code runs and returns plausible numbers. What does it actually compute? Demonstrate on a single item of value \(3\), weight \(2\), with \(W = 4\).
    solution It computes the unbounded knapsack. Sweeping forward, \(K[w - w_i]\) may already have been updated this same pass, so it can already include item \(i\); the item combines with itself. On the single item: forward, \(K[2] = \max(0, 3 + K[0]) = 3\), then \(K[4] = \max(0, 3 + K[2]) = 6\), the item taken twice; final row \([0, 0, 3, 3, 6]\). Backward, \(K[4]\) is computed first from the untouched \(K[2] = 0\), giving \(3\); final row \([0, 0, 3, 3, 3]\), the correct 0/1 answer. The bug is nasty precisely because nothing crashes: the code solves a different problem correctly.
