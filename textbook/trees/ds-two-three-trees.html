2-3 Trees

John Hopcroft invented 2-3 trees in 1970 but did not publish them; they first appeared in print in a 1974 textbook. A. V. Aho, J. E. Hopcroft and J. D. Ullman, The Design and Analysis of Computer Algorithms, 1974

The AVL tree won a \(\Theta(\log n)\) guarantee for the binary search tree by keeping it nearly balanced: every node’s balance factor pinned to \(\{-1,0,+1\}\), and any violation repaired by a rotation. That is one strategy, not the only one. The 2-3 tree reaches the same guarantee by a completely different mechanism: let a node hold one or two keys, keep every leaf at the same depth, and grow the tree upward by splitting. The red-black BST is how real code implements this idea, and B-trees are how databases scale it to disk; all three share one move: split a full node and send its middle key up.

1. From rotations to fatter nodes

The AVL tree (the AVL Trees handout) keeps a binary tree balanced: one invariant (balance factor \(\in\{-1,0,+1\}\)), restored after each update by rotations, buying a height of at most \(1.44\log_2 n\), a guarantee. It works, but the rotations are fiddly: four cases on insert (LL, RR, LR, RL), and a deletion can cascade rotations all the way up the path. AVL fixes imbalance after it happens. What if a tree could be built so that imbalance never happens at all?

The shift is to allow a node to hold more than one key and have more than two children. Then a new key can be absorbed into an existing node rather than grown onto a lopsided path, and balance becomes a property we get by construction instead of one we repair.

Definition (2-3 tree) A 2-3 tree is a search tree in which every internal node is one of two kinds. A 2-node holds one key and has two children (an ordinary BST node). A 3-node holds two keys \(a \lt c\) and has three children: the subtree of keys \(\lt a\), the subtree of keys strictly between \(a\) and \(c\), and the subtree of keys \(\gt c\). Every leaf is required to lie at the same depth.

A 3-node is the genuinely new thing: two keys guarding three doors. Reading one just extends the BST rule: instead of “left or right,” it is “left, middle, or right” depending on how the search key compares to the two stored keys.

In code

One node type serves both kinds: room for two keys and three children, and a count that says which kind the node is. One spare key slot and one spare child pointer give a node room to hold the temporary 4-node an insertion creates just before it splits (§3). The keys stay sorted, so child[i] holds the keys between key[i-1] and key[i]: an insertion shifts every larger key one slot right, together with the child pointer to its right. A temporary 4-node is therefore key[0] < key[1] < key[2] over child[0..3], and its middle key is key[1]. The split sends key[1] up; key[0] keeps child[0] and child[1], and key[2] takes child[2] and child[3]. Search descends one node per level, comparing against at most two keys.

    int     n;              // keys in use: 1 = a 2-node, 2 = a 3-node

};

bool TwoThreeTree::contains(int key) const {
    Node23* h = root;
    while (h != nullptr) {
        int i = 0;
        while (i < h->n && key > h->key[i]) i++;    // first key >= the target
        if (i < h->n && key == h->key[i]) return true;
        h = h->child[i];                              // the door: child i
    }
    return false;
}

impl TwoThreeTree {

            h = &node.child[i];

        false
    }

Invariant (perfect balance) A 2-3 tree keeps every leaf at the same depth, at all times: no “\(\pm 1\) slack” as in AVL. Consequently its height \(h\) satisfies \(\log_3(n+1) - 1 \le h \le \log_2(n+1) - 1\), so a 2-3 tree is \(\Theta(\log n)\) tall, guaranteed, for any sequence of insertions.
Proof (of the height bounds). Every leaf is at depth \(h\), so every node above depth \(h\) has all its two or three children, and level \(d \le h\) holds between \(2^d\) nodes (all 2-nodes) and \(3^d\) nodes (all 3-nodes), each with one or two keys. Summing over the levels, the number of keys satisfies \[ 2^{h+1} - 1 \;\le\; n \;\le\; 2 \cdot \frac{3^{h+1} - 1}{2} \;=\; 3^{h+1} - 1. \] The left inequality gives \(h \le \log_2(n+1) - 1\) (the all-2-node tree is the tallest), the right one \(h \ge \log_3(n+1) - 1\) (the all-3-node tree is the shortest). Both bounds are \(\Theta(\log n)\). ∎

This is a stronger balance condition than AVL’s, and insertion keeps it without a rotation (§3), because a 2-3 tree grows at the root, not the leaves. A BST adds a new leaf, so one side can sink deeper and the tree tilts; a 2-3 tree pushes growth upward, adding a level at the very top, which lowers every leaf by one simultaneously. The “same depth” invariant is preserved by construction, never patched.

A family, not one tree Sedgewick & Wayne (§3.3) treat the 2-3 tree chiefly as the explanation of the red-black BST, which stores a 2-3 tree in the binary nodes of a BST and, in its classic form, is the balanced tree real libraries ship. Everything in this family (2-3, red-black, B-trees) is the one mechanism “split a full node, promote its middle key,” tuned to a different node width and a different level of the memory hierarchy.

2. Searching a 2-3 tree

Search is the easy half, and it is essentially BST search with one more door to choose from at a 3-node. Compare the target against the key(s) in the current node and descend into the one child whose key range contains it; stop when you match a stored key or fall off at a leaf.

Search cost is one comparison group per level, so it is \(\Theta(h) = \Theta(\log n)\). The catch versus a plain BST is that a 3-node may cost two key comparisons rather than one; the win is not raw comparisons but that balance is automatic and stays that way under updates, which is the subject of the next two sections.

3. Insertion: split and promote

Search down for the new key as usual; since it is not present, the search ends at a leaf. We insert there, but never as a new, deeper leaf (that would break “all leaves same depth”). Instead we absorb the key into the leaf. Two cases follow from whether that leaf has room.

Case 1. Into a 2-node: just grow it

A 2-node has a free slot, so it simply becomes a 3-node. Nothing moves and no height changes: inserting \(15\) into the leaf \([10]\) yields \([10\,|\,15]\). Half of all leaf insertions are this trivial.

Case 2. Into a 3-node: it overflows, so split

A 3-node is already full. Adding a key makes a momentary 4-node (three keys), which the tree does not allow, so we split it: the middle of the three keys moves up into the parent, and the node breaks into two 2-nodes holding the smaller and the larger key. The middle is the only choice that preserves order: everything below it goes left, everything above it goes right, and it becomes their guard in the parent.

Because the promoted key joins the parent, the parent may itself overflow, split, and promote again: a cascade that can ripple to the root. This is the crux of the whole design:

Proposition (growth is only at the root) A 2-3 tree gains height only when the root splits: the promoted middle key becomes a brand-new root with the two halves as its children. Since the new level is added at the top, every leaf drops one level together, so all leaves remain at a common depth. This is the only way a 2-3 tree grows taller, and it needs no rotation.
Proof. A split at a non-root node moves one key up but leaves the number of levels below unchanged and touches no leaf’s depth. The only split with nowhere to promote is a split of the root; there we create a new root whose two children are the halves, adding exactly one level above all existing nodes. Every root-to-leaf path lengthens by one, so if the leaves were at a common depth before, they are at a common (one greater) depth after. Any other insertion (Case 1, or a split that stops below the root) leaves all leaf depths unchanged. By induction the invariant holds after every insertion. ∎
Example (a worked insertion sequence) Insert \(50, 30, 70, 10, 20\) into an empty 2-3 tree: The two splits show both cases: \(70\) splits a leaf whose promotion creates the very first second level, and \(20\) splits a leaf and promotes into a root that had room, widening it to \([20\,|\,50]\). All three leaves finish at depth 1.
Example (a cascade to a new root) Insert \(25\) into a tree whose root is already full: One insertion, two splits: the leaf splits (promoting \(20\)), the root then splits (promoting \(30\) into a new root), and the tree grows from two levels to three, every leaf still landing at depth 2. Note that \([40\,|\,50]\) and \([70\,|\,80]\) never moved: only the path from the changed leaf up to the root was touched, which is why an insertion is \(\Theta(\log n)\) even when the tree “grew.”

In every case the cost is a search down (\(\Theta(\log n)\)) plus at most one split per level on the way back up, each split being \(O(1)\) pointer work. Insertion is \(\Theta(\log n)\), and we never wrote a rotation. This split-and-promote rule is exactly what recurs, wider, in B-trees (the B-Trees & B+ Trees handout), and, encoded with a color bit, in red-black trees (the Red-Black Trees handout).

4. Deletion: borrow and merge

Deletion is the mirror image of insertion: merge and demote in place of split and promote. There is more casework but no new idea, and it rests on the same discipline: act only at a leaf.

Step 1: get down to a leaf. If the key sits in an internal node, swap it with its in-order predecessor (the rightmost key of its left subtree, always in a leaf), and delete that copy instead. Removal therefore always happens at a leaf.

Predecessor or successor The in-order successor (the leftmost key of the subtree to the key’s right, also always in a leaf) works equally well. The predecessor and the successor are the key’s two neighbors in sorted order, so either one can take its place without breaking the order, and the rest of the delete (remove from a leaf, then borrow or merge) is the same. The two choices remove from different leaves, so the repairs that follow can differ and so can the final trees; both are valid 2-3 trees. The Hibbard delete of Trees & Binary Search Trees uses the successor. This chapter, the 2-3 demo and the red-black delete of the Red-Black Trees handout use the predecessor, so the 2-3 tree and its red-black encoding make the same changes step for step.

Step 2: fix underflow. Removing a key from a leaf that held only one key leaves it empty (an underflow). Two repairs, chosen by what the siblings can spare:

  • Borrow if a sibling has two keys to spare: rotate a key through the parent. Deleting \(10\) from \([10]\) under a parent \([30]\) whose other child \([40\,|\,50]\) is a 3-node, the parent’s \(30\) drops into the empty node and the sibling’s \(40\) rises to replace it: a single, local move, and the tree’s shape above is untouched.
  • Merge if every sibling is already at the minimum (one key): pull the parent’s separating key down and fuse it with a sibling into a single 3-node. The parent loses a key, which may underflow the parent in turn, cascading upward. If the merge empties the root, the root’s only child becomes the new root and the tree shrinks a level, the exact mirror of a root split.
Example (borrow left, borrow right, merge) The three leaf repairs on one small tree, each deleting \(40\) from the shape shown. Which repair fires is decided entirely by what the siblings hold.
  • Borrow from the left. The left sibling \([10\,|\,20]\) is a 3-node and can spare a key: the parent’s separator \(30\) drops into the empty leaf and the sibling’s largest key \(20\) rises to replace it. In-order \(10, 20, 30, 60, 70, 80\): still sorted, every leaf still at depth 1, nothing above moved.
  • Borrow from the right. The left sibling \([10]\) is at the minimum; the right sibling \([70\,|\,80]\) is not. The parent’s other separator \(60\) drops into the empty leaf and the right sibling’s smallest key \(70\) rises. In-order \(10, 30, 60, 70, 80\).
  • Merge. Both siblings hold one key each, so there is nothing to borrow. The separator \(30\) comes down and fuses with the left sibling into the 3-node \([10\,|\,30]\). The parent loses a key, but it was a 3-node, so it survives as a 2-node and the cascade stops there: the tree keeps its height. In-order \(10, 30, 60, 80\).
Borrow is always preferred when it is available: it is purely local (only the underflowing leaf, one sibling, and one parent key change) and it can never propagate, because the parent keeps the same number of keys. Only a merge takes a key away from the parent, and only a merge can therefore cascade.
Example (a merge that cascades and shrinks the root) The mirror of the root split. Start from a tree of height \(2\) made entirely of 2-nodes, the sparsest 2-3 tree there is, and delete \(10\).
  1. The leaf \([10]\) empties; its only sibling \([40]\) holds one key, so merge: the separator \(30\) comes down and fuses into \([30\,|\,40]\). The node that held \(30\) is now empty, so the underflow has moved up one level.
  2. That empty internal node’s sibling \([70]\) is also at the minimum, so merge again: the root’s \(50\) comes down and fuses, producing \([50\,|\,70]\) with the three children \([30\,|\,40]\), \([60]\), and \([80]\).
  3. The root is now empty. Its only child becomes the new root, and every leaf is at depth 1.
One deletion, two merges, and the tree lost a level. Height falls only here, at the root, exactly as it rises only at the root during insertion, and every leaf drops one level together so the common-depth invariant survives. In-order before and after: \(10,30,40,50,60,70,80\) and \(30,40,50,60,70,80\).
Example (deleting a key that sits in an internal node) Step 1 of the recipe, made concrete. Delete \(30\), a separator in the root, from the tree of the first example. The in-order predecessor of \(30\) is the rightmost key of the subtree just left of it: the \(20\) in the leaf \([10\,|\,20]\). Copy \(20\) up over the \(30\), then delete the leaf’s copy of \(20\). That leaf was a 3-node, so it drops to \([10]\) without underflowing and no repair is needed; in-order \(10, 20, 40, 60, 70, 80\): \(30\) is gone and the order is intact. Had that leaf been the 2-node \([20]\) instead, removing the copy would have emptied it, and one of the three leaf repairs above would have followed. The successor works the same way from the other side. The successor of \(30\) is \(40\), the leftmost key of the subtree just right of it. Copy \(40\) up over the \(30\), then delete the leaf’s copy: the leaf \([40]\) empties, and its left sibling \([10\,|\,20]\) can spare a key, so borrow: \(40\) drops back into the empty leaf and \(20\) rises to replace it. The result is the tree the predecessor gave, one repair later. Every deletion reduces to this: reach a leaf, remove there, then borrow or merge upward.

Both moves are \(O(1)\), applied along a single root-to-leaf path, so deletion is \(\Theta(\log n)\) like insertion. The red-black encoding of the Red-Black Trees handout keeps this case analysis (which sibling, which side, cascading merges) and stores the tree in binary nodes, each case a few rotations and recolorings. Insertion and deletion repair here on the way back up, after the change; in a tree whose nodes have room for it, the 2-3-4 tree, both repairs can run on the way down instead (Top-Down Balanced Trees).

5. Exercises (with solutions)

  1. Insert \(60, 20, 80, 10, 40, 50\), in that order, into an initially empty 2-3 tree. Draw the final tree and give every leaf’s depth.
    solution \(60 \to [60]\); \(20 \to [20\,|\,60]\); \(80 \to [20\,|\,60\,|\,80]\) overflows, promote \(60\) to root \([60]\) over leaves \([20]\) and \([80]\). \(10 \to [10\,|\,20]\). \(40\): descend to leaf \([10\,|\,20]\), overflow \([10\,|\,20\,|\,40]\), promote \(20\) into the root, which becomes \([20\,|\,60]\); its children are \([10], [40], [80]\). \(50\): \(20 \lt 50 \lt 60\) so descend to the middle child \([40]\), a 2-node, giving \([40\,|\,50]\). Final: All three leaves are at depth 1.
  2. Explain, in your own words, why a 2-3 tree grows only at the root and why that single fact keeps all leaves at the same depth, and contrast it with why a plain BST can become unbalanced.
    solution A split promotes its middle key to the parent, which either has room (the split stops) or overflows and splits in turn. The only split with nowhere to promote is a split of the root, which manufactures a new root one level above everything else. Adding a level at the top lengthens every root-to-leaf path by exactly one, so a common leaf depth stays common. A BST, by contrast, only ever adds a new leaf, deepening one path while leaving the others untouched; repeated one-sided inserts then tilt it toward a chain of height \(n-1\). Grow-up preserves balance; grow-down does not.
  3. Take the tree built in exercise 1, root \([20\,|\,60]\) over the leaves \([10]\), \([40\,|\,50]\), \([80]\). Delete \(10\), then delete \(40\) from the result. Name the repair used at each step and draw both trees.
    solution Delete 10. The leaf \([10]\) empties. It has no left sibling, and its right sibling \([40\,|\,50]\) is a 3-node, so borrow right: the parent’s separator \(20\) drops into the empty leaf and the sibling’s smallest key \(40\) rises to replace it. Delete 40. Now \(40\) sits in an internal node, so first swap in its in-order predecessor, the rightmost key to its left, which is \(20\); the root becomes \([20\,|\,60]\) and the leaf \([20]\) must give up its copy, emptying it. Its only sibling on that side, \([50]\), holds one key, so no borrow is possible: merge, pulling the separator \(20\) down to fuse into \([20\,|\,50]\). The root loses \(20\) and becomes the 2-node \([60]\). In-order is \(20,50,60,80\), and both leaves are still at depth 1.
  4. In a 2-3 tree of height \(h\), what is the largest number of splits a single insertion can cause, and the largest number of merges a single deletion can cause? Why can a borrow never cascade, while a merge can?
    solution A root-to-leaf path holds \(h+1\) nodes. An insertion can split every one of them, at most \(h+1\) splits, the last being the root split that adds a level. A deletion can merge at every level above the leaf, at most \(h\) merges, the last of which may empty the root and remove a level. A borrow moves one key from a sibling into the underflowing node through the parent and hands the parent a replacement separator in the same motion, so the parent’s key count is unchanged and no node above can underflow: the repair stops immediately. A merge instead pulls a separator out of the parent, so the parent loses a key and may itself fall to zero, passing the same problem up one level.
