Red-Black Trees

Leonidas Guibas and Robert Sedgewick named red-black trees in 1978. Sedgewick has said they chose red because it was the color that printed best on the laser printer they had at Xerox PARC. L. J. Guibas and R. Sedgewick, “A Dichromatic Framework for Balanced Trees,” FOCS 1978

The AVL tree keeps a binary search tree balanced with rotations; the 2-3 tree reaches the same \(\Theta(\log n)\) guarantee by splitting full nodes and promoting their middle keys, but it is awkward to code directly. The red-black BST closes that gap: an ordinary binary search tree with one colour bit per link that encodes a 2-3 tree exactly, inheriting its balance while keeping a single node type. It is the balanced tree real libraries ship.

1. Red-black BSTs: a 2-3 tree in binary

The 2-3 tree is elegant but painful to implement: two node types, split logic, promotion, new roots: many cases and much pointer surgery. In real code we would rather have one node type. The idea, due to Sedgewick, is to represent a 2-3 tree as an ordinary binary tree, using a single colour bit on each link to remember where the 3-nodes were.

Definition (left-leaning red-black BST) A left-leaning red-black BST is a BST whose links are coloured red or black so that: (1) red links lean left (no right-leaning red link); (2) no node has two red links in a row; and (3) black balance holds: every root-to-null path crosses the same number of black links. By convention a node’s stored colour is the colour of the link to its parent, and the root link is black.

A red link is the “glue” inside a 3-node. A 3-node \([a\,|\,c]\) becomes two BST nodes joined by a red link; a 2-node is a plain black-linked node. Read a red link as “these two nodes are really one 3-node,” and the three invariants become the 2-3 rules in disguise: “no two reds in a row” is “no node has a third key” (the 4-node we must split), and “equal black-height” is “all 2-3 leaves at the same depth.”

2. The three restoring moves

Insertion is a normal BST insert with the new link coloured red (a new key always tries to join an existing node as a 3-node), followed by a walk back up applying whichever of three constant-time fix-ups restores the invariants: 

  right child red, left child black   →  rotateLeft
  left red AND its left child red     →  rotateRight
  both children red                   →  flipColors

rotateLeft and rotateRight are the order-preserving pointer surgery of the AVL Trees handout, with one extra line to carry the colour; flipColors is the encoding of a 2-3 split. A node with two red children is a temporary 4-node, and flipping all three colours pushes the middle key up (the node turns red, “joining its parent”) while its two children become independent black 2-nodes: precisely “promote the middle and split,” expressed in colour. If the parent now has two reds of its own, the flip cascades upward exactly as the 2-3 split did. 

// Left-leaning red-black BST: the three constant-time moves that maintain a
// 2-3 tree's shape. A node's `red` flag = the colour of the link to its PARENT;
// a null link counts as black.
struct Node { int key; Node *left = nullptr, *right = nullptr; bool red = true; };

bool isRed(Node* h) { return h && h->red; }    // null links are black

Node* rotateLeft(Node* h) {        // h's right link leans red; lean it left
    Node* x = h->right;
    h->right = x->left;
    x->left  = h;
    x->red = h->red;               // x inherits h's colour
    h->red = true;                 // h is now glued under x by a red link
    return x;                      // x is the new subtree root
}

Node* rotateRight(Node* h) {       // mirror image of rotateLeft
    Node* x = h->left;
    h->left  = x->right;
    x->right = h;
    x->red = h->red;
    h->red = true;
    return x;
}

void flipColors(Node* h) {         // two red children = a temporary 4-node
    h->red        = !h->red;       // push the middle key UP (h "promotes")
    h->left->red  = !h->left->red; // the two children become black 2-nodes
    h->right->red = !h->right->red;
}
// Left-leaning red-black BST: the three constant-time moves. A node's `red`
// flag = the colour of the link to its PARENT; a null link counts as black.
static class Node {
    int key; Node left, right; boolean red = true;
    Node(int k) { key = k; }
}

static boolean isRed(Node h) { return h != null && h.red; }

static Node rotateLeft(Node h) {      // right link leans red -> lean it left
    Node x = h.right;
    h.right = x.left;
    x.left  = h;
    x.red = h.red;                     // x inherits h's colour
    h.red = true;                      // h is now glued under x by a red link
    return x;
}

static Node rotateRight(Node h) {     // mirror image of rotateLeft
    Node x = h.left;
    h.left  = x.right;
    x.right = h;
    x.red = h.red;
    h.red = true;
    return x;
}

    h.red       = !h.red;              // push the middle key UP (h "promotes")
    h.left.red  = !h.left.red;         // children become black 2-nodes
    h.right.red = !h.right.red;
}
# Left-leaning red-black BST: the three constant-time moves. A node's `red`
# flag = the colour of the link to its PARENT; a missing link counts as black.
class Node:
    def __init__(self, key):
        self.key = key
        self.left = self.right = None
        self.red = True

def is_red(h):                       # None links are black
    return h is not None and h.red

def rotate_left(h):                  # right link leans red -> lean it left
    x = h.right
    h.right = x.left
    x.left = h
    x.red, h.red = h.red, True       # x inherits h's colour; h turns red
    return x                         # x is the new subtree root

def rotate_right(h):                 # mirror image of rotate_left
    x = h.left
    h.left = x.right
    x.right = h
    x.red, h.red = h.red, True
    return x

def flip_colors(h):                  # two red children = a temporary 4-node
    h.red = not h.red                # push the middle key UP (h "promotes")
    h.left.red = not h.left.red      # children become black 2-nodes
    h.right.red = not h.right.red
// Left-leaning red-black BST moves. `red` = colour of the link to the PARENT;
// a None link counts as black. Children are Option<Box<Node>>, so we take/put
// the boxes to move subtrees around without aliasing.
type Link = Option<Box<Node>>;
struct Node { key: i32, left: Link, right: Link, red: bool }

fn is_red(h: &Link) -> bool { h.as_ref().map_or(false, |n| n.red) }

fn rotate_left(mut h: Box<Node>) -> Box<Node> {   // right link leans red
    let mut x = h.right.take().unwrap();
    h.right = x.left.take();
    x.red = h.red;                 // x inherits h's colour
    h.red = true;                  // h is now glued under x by a red link
    x.left = Some(h);
    x                              // x is the new subtree root
}

fn rotate_right(mut h: Box<Node>) -> Box<Node> {  // mirror image
    let mut x = h.left.take().unwrap();
    h.left = x.right.take();
    x.red = h.red;
    h.red = true;
    x.right = Some(h);
    x
}

fn flip_colors(h: &mut Box<Node>) {               // two red children = 4-node
    h.red = !h.red;                               // push the middle key up
    if let Some(l) = h.left.as_mut() { l.red = !l.red; }
    if let Some(r) = h.right.as_mut() { r.red = !r.red; }
}

Only nodes move in a rotation; the in-order sequence is unchanged, exactly as for the rotations of the AVL Trees handout. “Left-leaning” is what keeps the case count at three rather than the classic red-black tree’s six (Sedgewick’s simplification), and it is why the whole of insertion is BST-insert plus these three \(O(1)\) moves applied bottom-up.

Insertion: BST insert, then the three moves

Search ignores colours entirely: a red-black BST is a binary search tree, so get is the unchanged descent of the Trees & Binary Search Trees handout, a hit on an equal key and a miss when it falls off a null link. Insertion is that same descent, a new node attached by a red link, and then the three moves tested in a fixed order at every node on the way back up. 

// LLRB insert: an ordinary BST insert whose new link is RED, then the three
// moves tested in this order at every node on the way back up. The order
// matters: leaning left first turns the other two tests into simple ones.
Node* fixUp(Node* h) {
    if (isRed(h->right) && !isRed(h->left))     h = rotateLeft(h);   // lean left
    if (isRed(h->left) && isRed(h->left->left)) h = rotateRight(h);  // two reds
    if (isRed(h->left) && isRed(h->right))      flipColors(h);       // 4-node
    return h;
}
Node* put(Node* h, int key) {
    if (!h) return new Node{key};              // new node: its link is red
    if      (key < h->key) h->left  = put(h->left,  key);
    else if (key > h->key) h->right = put(h->right, key);
    return fixUp(h);                           // restore the three invariants
}
void insert(Node*& root, int key) {
    root = put(root, key);
    root->red = false;                         // the root link is always black
}

    return h;
}

# LLRB insert: an ordinary BST insert whose new link is RED, then the three
# moves tested in this order at every node on the way back up.
def fix_up(h):
    if is_red(h.right) and not is_red(h.left):
        h = rotate_left(h)                     # lean the red link left
    if is_red(h.left) and is_red(h.left.left):
        h = rotate_right(h)                    # two reds in a row
    if is_red(h.left) and is_red(h.right):
        flip_colors(h)                         # split the temporary 4-node
    return h

def put(h, key):
    if h is None:
        return Node(key)                       # new node: its link is red
    if key < h.key:
        h.left = put(h.left, key)
    elif key > h.key:
        h.right = put(h.right, key)
    return fix_up(h)                           # restore the three invariants

def insert(root, key):
    root = put(root, key)
    root.red = False                           # the root link is always black
    return root
// LLRB insert over owned links. take() moves a child out so it can be rotated
// and put back; the three moves are tested in the same fixed order.
fn fix_up(mut h: Box<Node>) -> Box<Node> {
    if is_red(&h.right) && !is_red(&h.left) { h = rotate_left(h); }
    if is_red(&h.left) && is_red(&h.left.as_ref().unwrap().left) {
        h = rotate_right(h);
    }
    if is_red(&h.left) && is_red(&h.right) { flip_colors(&mut h); }
    h
}
fn put(h: Link, key: i32) -> Box<Node> {
    let mut n = match h {
        None => return Box::new(                // new node: its link is red
            Node { key, left: None, right: None, red: true }),
        Some(n) => n,
    };
    if      key < n.key { n.left  = Some(put(n.left.take(),  key)); }
    else if key > n.key { n.right = Some(put(n.right.take(), key)); }
    fix_up(n)
}
fn insert(root: Link, key: i32) -> Link {
    let mut r = put(root, key);
    r.red = false;                             // the root link is always black
    Some(r)
}

Three tests, in that order, at every node on the path. Everything below is a trace of which of them fire, and when.

Example (each of the three moves, from one 3-node) Start each time from the same two keys, the 3-node \([30\,|\,50]\), which in this encoding is \(50\) black at the root with a red left link to \(30\). Where the new key falls relative to those two decides the fix-up, and the three possibilities are exactly the three moves. Write \(x\)B and \(x\)R for a node reached by a black or a red link. 
  start:  50B          new key 70 (LARGER than both)
         /             70 attaches as 50’s red right child, so 50 now has
      30R              two red children: a temporary 4-node [30|50|70].
                       Test 1 fails (the left child is red too), test 2 fails
                       (30 has no left child), test 3 fires:

    flipColors(50)  →  50 turns red, 30 and 70 turn black; the root link is
                        then forced black again:      50B(30B, 70B)

  start:  50B          new key 10 (SMALLER than both)
         /             10 attaches as 30’s red left child: two red links in a
      30R              row, 50-30 and 30-10. At node 30 nothing fires. At 50,
                       test 1 fails, test 2 fires (left red, its left red):

    rotateRight(50) →  30 rises with red children 10 and 50, which is again a
    flipColors(30)      4-node, so test 3 fires:      30B(10B, 50B)

  start:  50B          new key 40 (BETWEEN them)
         /             40 attaches as 30’s red right child. At node 30 test 1
      30R              fires (red right, black left):

    rotateLeft(30)  →  now 50 has red left 40 whose left 30 is red, so at 50
    rotateRight(50)     test 2 fires, and the result has two red children:
    flipColors(40)                                    40B(30B, 50B)
All three land on the same shape a 2-3 tree would: the middle of the three keys black at the top with the other two as black children, which is the split of a 4-node with its middle key promoted. In-order is \(30,50,70\), \(10,30,50\), and \(30,40,50\) respectively, and every root-to-null path crosses two black links in all three results.

The moves are applied at every node of the path, so a fix-up at one level can create work for the level above it: a flipColors turns its node red, and that red link may now lean the wrong way at the parent. That is the red-black spelling of a 2-3 split cascading upward.

Every root-to-null path keeps the same number of black links, and the tree never exceeds \(2\log_2 n\) tall no matter the insertion order. (The demo’s Delete button works too; deletion is the same three moves applied both on the way down (borrowing a red onto a black-linked child before descending) and on the way back up, which is why it is roughly twice the casework of insert yet uses no new primitive.)

3. Why the height is \(\Theta(\log n)\)

Theorem (red-black height) A red-black BST on \(n\) keys has height at most \(2\log_2 n\), so search, insert, and delete are \(\Theta(\log n)\) for any insertion order.
Proof. Let \(b\) be the number of black links on a root-to-null path, the same on every path by black balance (invariant 3). Collapse each red link into its parent: two nodes glued by a red link merge into one 2-3 node, recovering the very 2-3 tree this encoding came from. The black links are exactly that 2-3 tree’s edges, so \(b\) equals the 2-3 tree’s height, which by the height bounds in the 2-3 Trees handout is at most \(\log_2 n\); hence \(b \le \log_2 n\). Now count all links on a path. Between any two black links invariant 2 permits at most one red (two in a row is the violation flipColors removes), so the total number of links is at most \(2b\). Therefore the height is at most \(2b \le 2\log_2 n\). ∎

The bound is looser than AVL’s \(1.44\log_2 n\) (a red-black tree can be up to twice as tall) but still \(\Theta(\log n)\), and it is reached with far fewer restructuring operations per update. That trade is why a red-black BST, being just one node type plus one colour bit, is the balanced tree real libraries ship: C++’s std::map and std::set, Java’s TreeMap and TreeSet, and the Linux kernel’s scheduler among them.

The correspondence is the whole point “2-3 trees are balanced” (the 2-3 Trees handout) and “red-black trees are \(\Theta(\log n)\)” (here) are the same fact, seen through the collapse-the-red-links map. This is Sedgewick & Wayne’s central insight: do not analyse the red-black tree directly: recognise it as a 2-3 tree in a costume and inherit everything already proved. Cormen et al. develop the classic (not-left-leaning) red-black tree from five colour axioms instead; the two agree on the \(\Theta(\log n)\) guarantee and differ mainly in how many cases the code must handle.

4. Exercises (with solutions)

  1. Convert the 2-3 tree whose root is the 3-node \([40\,|\,80]\) with children \([20], [60], [100]\) into a left-leaning red-black BST. Give each node’s colour and its parent link.
    solution The root 3-node \([40\,|\,80]\) becomes \(80\) (black, since it is the root) with a red left link to \(40\). The three subtrees hang under the two keys by range: \(20\) (\(\lt 40\)) is \(40\)’s left child, \(60\) (\(40\!-\!80\)) is \(40\)’s right child, and \(100\) (\(\gt 80\)) is \(80\)’s right child; all three are black. In-order \(20,40,60,80,100\) matches the 2-3 tree, and collapsing the one red link \(40\!-\!80\) recovers the original 3-node.
  2. Prove that a left-leaning red-black BST on \(n\) keys has height at most \(2\log_2 n\), using the correspondence with 2-3 trees.
    solution Let \(b\) be the number of black links on any root-to-null path; black balance makes \(b\) the same on every path. Collapsing each red link into its parent merges each red-glued pair into one 2-3 node and turns the black links into the edges of a 2-3 tree, so \(b\) equals that 2-3 tree’s height, which is at most \(\log_2 n\) (the all-2-nodes worst case; see the 2-3 Trees handout); thus \(b \le \log_2 n\). Between two consecutive black links at most one red link can appear (invariant 2 forbids two reds in a row), so a path has at most \(2b\) links total. Hence height \(\le 2b \le 2\log_2 n\).
  3. Insert the keys \(S, E, A, R, C\), in that order, into an empty left-leaning red-black BST. List the moves each insertion fires and draw the final tree with its link colours.
    solution S: the root, black. E: \(E \lt S\), so a red left link; it leans left, there are no two reds in a row and no two red children, so no move fires. A: \(A \lt E\), a red left link under \(E\), giving the two reds in a row \(S\!-\!E\) and \(E\!-\!A\). Nothing fires at \(E\); at \(S\) the second test fires, rotateRight(S), lifting \(E\) with red children \(A\) and \(S\), which the third test then splits, flipColors(E). The tree is \(E\) black with black children \(A\) and \(S\). R: \(R \lt S\), a red left link under \(S\); it already leans left, so no move. C: \(C \gt A\), a red right link under \(A\), so the first test fires, rotateLeft(A), leaving \(C\) black in \(A\)’s place with \(A\) as its red left child. 
                E (black root)
           /            \
        C (black)      S (black)
       /              /
     A (RED)        R (RED)
    In-order is \(A,C,E,R,S\); every root-to-null path crosses two black links; and collapsing the two red links recovers the 2-3 tree with root \([E]\) over the 3-nodes \([A\,|\,C]\) and \([R\,|\,S]\).
  4. Show that flipColors and the two rotations all preserve black balance, so an insertion can never break invariant 3.
    solution flipColors turns the two child links from red to black and the node’s own parent link from black to red. Any root-to-null path through this node uses the parent link and exactly one of the two child links, so it loses one black link at the top and gains one just below: the count is unchanged, and paths that avoid the node are untouched. For a rotation, the two nodes involved exchange colours (\(x\) inherits \(h\)’s colour and \(h\) becomes red), and the subtree that changes parent moves across a link of the same colour it had before, so every path through the subtree still crosses the same number of black links. Since the new link of an insertion is red, it adds no black link anywhere either, which is why black balance is the one invariant an insertion never has to repair.
