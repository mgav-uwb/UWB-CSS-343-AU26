Red-Black Trees

Leonidas Guibas and Robert Sedgewick named red-black trees in 1978. Sedgewick has said they chose red because it was the color that printed best on the laser printer they had at Xerox PARC. L. J. Guibas and R. Sedgewick, “A Dichromatic Framework for Balanced Trees,” FOCS 1978

The AVL tree keeps a binary search tree (BST) balanced with rotations; the 2-3 tree reaches the same \(\Theta(\log n)\) guarantee by splitting full nodes and promoting their middle keys, but it is awkward to code directly. The red-black BST closes that gap: an ordinary binary search tree with one color bit per node that encodes a 2-3 tree exactly, inheriting its balance while keeping a single node type. It is the balanced tree real libraries ship.

1. A 2-3 tree in binary

The 2-3 tree is simple to describe and awkward to implement: two node types, splits that create nodes, promotions, new roots. A red-black BST stores the same tree with one node type, the binary node of a BST, plus one bit per node that records which binary nodes belong to the same 2-3 node.

One 2-3 node at a time

  • A 2-node \([a]\) becomes one node \(a\); the 2-node’s two subtrees become \(a\)’s two children.
  • A 3-node \([a\,|\,b]\) becomes two nodes joined by a red link: \(b\), with \(a\) as its left child. The 3-node’s three subtrees hang under the two keys by key range: keys below \(a\) under \(a\)’s left, keys between \(a\) and \(b\) under \(a\)’s right, keys above \(b\) under \(b\)’s right.

Every other link is black. The bit is stored in the child: a node is red when the link from its parent is red, so a red node is the smaller key of a 3-node, glued to the larger one. The root has no parent link and is black.

Left or right

Nothing forces the red link to the left. A 3-node \([a\,|\,b]\) can just as well become \(a\) with \(b\) as its red right child, the three subtrees under \(a\)’s left, \(b\)’s left and \(b\)’s right. That right-leaning encoding is also a binary search tree with the same keys in the same order, and it puts the same black links on every path. What matters is choosing one side for every 3-node: then each 2-3 tree has exactly one encoding, and the repairs of sections 5 and 6 handle one shape of 3-node instead of two. This chapter, following Sedgewick, uses the left-leaning encoding. A right-leaning red-black BST is its mirror image, with every rule and every repair mirrored left for right.

Other red-black trees The red-black tree as Guibas and Sedgewick introduced it, and as Cormen et al. present it, lets red links lean either way and lets a black node have two red children: it encodes a 2-3-4 tree, whose nodes hold up to three keys. Its rules are stated for colored nodes and its repairs are organized by the colors of a node’s relatives rather than by 2-3 nodes; the height bound and the costs are the same.

The rules

Definition (left-leaning red-black BST) A left-leaning red-black BST is a BST whose links are colored red or black (each node stores the color of the link from its parent) so that:
  1. the root is black;
  2. red links lean left: a red node is a left child;
  3. no node has two red links: a red node has no red child, and no node has two red children;
  4. black balance: every path from the root to a null link crosses the same number of black links.

Each rule is a 2-3 fact. Rules 2 and 3 say that each 2-3 node is a 2-node or a left-leaning 3-node: a 4-node \([a\,|\,b\,|\,c]\) would need two red links at one node. Rule 4 says that the 2-3 leaves are all at one depth: the black links are exactly the 2-3 tree’s edges, so a path crosses one black link per 2-3 level.

Whole trees, both ways

Encoding a whole 2-3 tree applies the node rule to every node, from the root down. Decoding collapses every red link into its parent, which recovers each 2-3 node and so the whole tree.

Example (a three-level 2-3 tree, encoded and decoded) The 2-3 tree has root \([40]\), children \([20]\) and \([60\,|\,80]\), and leaves \([10], [30]\) under \([20]\) and \([50], [70], [90\,|\,95]\) under \([60\,|\,80]\). From the top:
  1. \([40]\), a 2-node: the black root \(40\).
  2. \([20]\), a 2-node: a black node \(20\), the root’s left child.
  3. \([60\,|\,80]\), a 3-node: \(80\), black, the root’s right child, with \(60\) as its red left child.
  4. \([10]\) and \([30]\): black children of \(20\).
  5. \([50]\) and \([70]\): black children of \(60\) (keys below \(60\), and keys between \(60\) and \(80\)).
  6. \([90\,|\,95]\): \(95\), black, \(80\)’s right child, with \(90\) as its red left child.
Decoding reads the encoding the other way: \(40\), \(20\), \(10\), \(30\), \(50\) and \(70\) have no red child, so each is a 2-node; \(80\) with its red child \(60\) is \([60\,|\,80]\), and \(95\) with \(90\) is \([90\,|\,95]\). Every path from the root crosses three black links, counting the root’s, one per 2-3 level.

2. The data structure

A red-black BST is one node type, a BST node with one extra bit, and a tree object that owns the root. Search is the BST search unchanged; insert and delete are the BST operations followed by repairs. 

// One node per key. `red` is the color of the link from the parent: a red
// node is glued to its parent as one 2-3 node (the smaller key of a 3-node).
struct RBNode {
    int     key;
    RBNode* left  = nullptr;
    RBNode* right = nullptr;
    bool    red   = true;          // a new node joins its parent's 2-3 node
    explicit RBNode(int k) : key(k) {}
};

// a null link is black
bool isRed(const RBNode* h) { return h != nullptr && h->red; }

    RBNode* h = root;

        if (key == h->key) return true;
        h = (key < h->key) ? h->left : h->right;

            h = if key < n.key { &n.left } else { &n.right };

    // remove(key): BST delete, then repair (section 6)

A new node starts red (section 3 says why). isRed treats a null link as black, so a rule can be tested at a node without first checking that its children exist.

3. Insertion: what can break

An insert begins as a plain BST insert: search for the key, and attach a new node where the search falls off the tree. The new node is colored red.

Why red. A new black node would add a black link to the paths through it and to no other path, breaking black balance (rule 4) on every insert. A red node adds no black link anywhere, so rule 4 holds; what a red node can break is one of the rules about red links (1, 2 or 3). In 2-3 terms a red node is a key that joins its parent’s 2-3 node, which is where a 2-3 insert puts a new key.

Which rule breaks depends on where the new node lands: in a 2-node or a 3-node, and below, between or above its keys. In 2-3 terms there are only two outcomes: a 2-node becomes a 3-node, or a 3-node becomes a 4-node, which a 2-3 tree does not allow.

Two more violations arise later, during repairs, never from the attach itself. Splitting a 4-node (section 5) sends its middle key up into the parent’s 2-3 node by a red link, and that red link lands in one of the same five places one level up. A split at the top leaves the root red, breaking rule 1.

4. Deletion: what can break

A delete also begins as a plain BST delete, in two steps.

Step 1: bring the key to the bottom. If the key’s node has two children, swap the key with its in-order predecessor, the largest key in its left subtree (go left once, then right to the end). No key lies between a key and its predecessor, so after the swap the only key out of order is the one being deleted, now in the predecessor’s old node, which has no right child. The in-order successor, the smallest key in the right subtree, works equally well, mirrored. This chapter uses the predecessor, as the 2-3 delete does, so the red-black delete and the 2-3 delete stay in step and end with the same 2-3 tree.

Step 2: remove it. The node now holding the key has at most one child, and in a left-leaning red-black BST that leaves three kinds of node. (A node with only a right child cannot occur: that child’s link would be red and lean right, breaking rule 2, or black and add a black link on one side only, breaking rule 4.)

  • A red leaf, the smaller key of a 3-node at the bottom of the 2-3 tree. Remove it: only a red link goes, so every path keeps its black links. No violation.
  • A black node with one child. The child is a red leaf, and the two are a 3-node at the bottom. The child takes the node’s place and turns black, so the paths through it cross the same black links as before. No violation.
  • A black leaf, a 2-node at the bottom. Removing it removes a black link from the paths through it, which now cross one black link fewer than every other path. Violation: black balance (rule 4).

The violation has a place: the spot where the black leaf was. The figures and the demos draw an empty node there. It stands for the missing black link (counted as one black link, it balances every path again), and in the 2-3 tree it is exactly the empty node a 2-3 delete leaves when a leaf loses its only key. The repair depends on the empty node’s surroundings in the 2-3 tree: its parent is a 2-node or a 3-node, the empty node is the parent’s left, middle or right child, and a sibling next to it is a 2-node or a 3-node. In the red-black BST the five positions look like this:

a 3-nodeevery one is a 2-nodemerge: the parent’s key comes down and joins a sibling in one 3-nodedone: the parent becomes a 2-node
a 2-nodeis a 2-nodemergethe parent is empty now: the missing black moves up one level

An empty middle child has a sibling on each side: the 2-3 delete borrows from the left one if it can, then from the right one, and otherwise merges with the left one. A merge under a 2-node parent is the only case that moves the empty node up, so the repair makes at most one change per level of the tree.

5. Fixing an insert

Each insert violation has its own fix, a constant-time change to a few links or colors at the node where the violation is:

  • a red link leans right: rotateLeft;
  • two reds in a row, both leaning left: rotateRight;
  • two red children: flipColors;
  • a red root: recolor it black.

Rotations: a red link turned the other way

rotateLeft and rotateRight are the order-preserving pointer surgery of the AVL Trees handout with one extra line to carry the color: the node that rises takes the old top’s color, and the node that drops turns red. Turned on a red link, a rotation changes how a 2-3 node is drawn and nothing else: rotateLeft turns a 3-node leaning right into one leaning left, and rotateRight turns a 4-node drawn as two reds in a row into one drawn as a node with two red children.

flipColors: the 2-3 split

A node with two red children is a 4-node. flipColors makes both children black and the node red: the two children become separate 2-nodes, and the middle key joins its parent’s 2-3 node by a red link. That is the 2-3 split, promote the middle key, expressed in color. The red link it sends up can break a rule one level up, and the same fixes apply there, just as a 2-3 split can overflow the parent. 

// Left-leaning red-black BST: the three constant-time moves (RBNode and isRed
// are defined with the tree class).
RBNode* rotateLeft(RBNode* h) {        // h's right link leans red; lean it left
    RBNode* x = h->right;
    h->right = x->left;
    x->left  = h;
    x->red = h->red;               // x inherits h's color
    h->red = true;                 // h is now glued under x by a red link
    return x;                      // x is the new subtree root
}

RBNode* rotateRight(RBNode* h) {       // mirror image of rotateLeft
    RBNode* x = h->left;
    h->left  = x->right;
    x->right = h;
    x->red = h->red;
    h->red = true;
    return x;
}

void flipColors(RBNode* h) {         // two red children = a temporary 4-node
    h->red        = !h->red;       // push the middle key UP (h "promotes")
    h->left->red  = !h->left->red; // the two children become black 2-nodes
    h->right->red = !h->right->red;
}

# are defined with the tree class).
def rotate_left(h):                  # right link leans red -> lean it left
    x = h.right
    h.right = x.left
    x.left = h
    x.red, h.red = h.red, True       # x inherits h's color; h turns red
    return x                         # x is the new subtree root

def rotate_right(h):                 # mirror image of rotate_left
    x = h.left
    h.left = x.right
    x.right = h
    x.red, h.red = h.red, True
    return x

def flip_colors(h):                  # two red children = a temporary 4-node
    h.red = not h.red                # push the middle key UP (h "promotes")
    h.left.red = not h.left.red      # children become black 2-nodes
    h.right.red = not h.right.red
// Left-leaning red-black BST: the three moves (RBNode, Link and is_red are
// defined with the tree type). Children are Option<Box<RBNode>>, so we
// take/put the boxes to move subtrees around without aliasing.
fn rotate_left(mut h: Box<RBNode>) -> Box<RBNode> {   // right link leans red
    let mut x = h.right.take().unwrap();
    h.right = x.left.take();
    x.red = h.red;                 // x inherits h's color
    h.red = true;                  // h is now glued under x by a red link
    x.left = Some(h);
    x                              // x is the new subtree root
}

fn rotate_right(mut h: Box<RBNode>) -> Box<RBNode> {  // mirror image
    let mut x = h.left.take().unwrap();
    h.left = x.right.take();
    x.red = h.red;
    h.red = true;
    x.right = Some(h);
    x
}

fn flip_colors(h: &mut Box<RBNode>) {               // two red children = 4-node
    h.red = !h.red;                               // push the middle key up
    if let Some(l) = h.left.as_mut() { l.red = !l.red; }
    if let Some(r) = h.right.as_mut() { r.red = !r.red; }
}

Insert, assembled

Search ignores colors entirely: a red-black BST is a binary search tree, so search is the unchanged descent of the Trees & Binary Search Trees handout. Insertion is that same descent, a new node attached by a red link, and then the three tests below at every node on the way back up, in a fixed order, followed by recoloring the root black. 

// LLRB insert: an ordinary BST insert whose new link is RED, then the three
// moves tested in this order at every node on the way back up. The order
// matters: leaning left first turns the other two tests into simple ones.
RBNode* fixUp(RBNode* h) {
    if (isRed(h->right) && !isRed(h->left))     h = rotateLeft(h);   // lean left
    if (isRed(h->left) && isRed(h->left->left)) h = rotateRight(h);  // two reds
    if (isRed(h->left) && isRed(h->right))      flipColors(h);       // 4-node
    return h;
}
RBNode* put(RBNode* h, int key) {
    if (!h) return new RBNode{key};              // new node: its link is red
    if      (key < h->key) h->left  = put(h->left,  key);
    else if (key > h->key) h->right = put(h->right, key);
    return fixUp(h);                           // restore the three invariants
}
void RedBlackTree::insert(int key) {
    root = put(root, key);
    root->red = false;                         // the root link is always black
}

// LLRB insert over owned links. take() moves a child out so it can be rotated
// and put back; the three moves are tested in the same fixed order.
fn fix_up(mut h: Box<RBNode>) -> Box<RBNode> {
    if is_red(&h.right) && !is_red(&h.left) { h = rotate_left(h); }
    if is_red(&h.left) && is_red(&h.left.as_ref().unwrap().left) {
        h = rotate_right(h);
    }
    if is_red(&h.left) && is_red(&h.right) { flip_colors(&mut h); }
    h
}
fn put(h: Link, key: i32) -> Box<RBNode> {
    let mut n = match h {
        None => return Box::new(                // new node: its link is red
            RBNode { key, left: None, right: None, red: true }),
        Some(n) => n,
    };
    if      key < n.key { n.left  = Some(put(n.left.take(),  key)); }
    else if key > n.key { n.right = Some(put(n.right.take(), key)); }
    fix_up(n)
}
impl RedBlackTree {
    fn insert(&mut self, key: i32) {
        let mut r = put(self.root.take(), key);
        r.red = false;                         // the root link is always black
        self.root = Some(r);
    }
}

Three tests, in that order, at every node on the path; each fires only on the violation it fixes. Everything below is a trace of which of them fire, and when.

Example (the three 3-node violations, fixed) Start each time from the 3-node \([30\,|\,50]\): \(50\) black at the root with a red left link to \(30\). Where the new key falls relative to those two decides which tests fire.
  • 70, larger than both, attaches as \(50\)’s red right child, so \(50\) has two red children (the 4-node \([30\,|\,50\,|\,70]\)): test 3 fires, flipColors(50).
  • 10, smaller than both, attaches as \(30\)’s red left child: two red links in a row. Nothing fires at \(30\); at \(50\) test 2 fires, rotateRight(50), and the result has two red children, so test 3 fires at \(30\).
  • 40, between them, attaches as \(30\)’s red right child: test 1 fires at \(30\), rotateLeft(30), which makes two reds in a row at \(50\), so test 2 fires, rotateRight(50), and then test 3 at \(40\).

The moves are applied at every node of the path, so a fix-up at one level can create work for the level above it: a flipColors turns its node red, and that red link may now lean the wrong way at the parent. That is the red-black spelling of a 2-3 split cascading upward.

6. Fixing a delete

The missing black is repaired the way a 2-3 delete repairs an empty node, one level at a time, and each 2-3 repair is a few rotations and recolorings in the red-black BST.

  • Merge, when every sibling next to the empty node is a 2-node. The parent’s key comes down and joins the sibling. In red-black terms a merge is a recolor: the sibling turns red, joining the parent key’s node, and the parent’s key, if it was red (part of a 3-node), turns black, leaving the parent’s node. If the merged 3-node leans right, rotateLeft fixes it, the same fix as for an insert. Under a 3-node parent the repair ends there. Under a 2-node parent the parent has lost its only key: the empty node is now above the merged node, and the repair repeats one level up.
  • Borrow, when a sibling next to the empty node is a 3-node. The parent’s key comes down into the empty node and the sibling’s nearer key goes up into its place. In red-black terms, one to three rotations bring the sibling’s key into the parent’s position, and a recolor makes its two neighbors black 2-nodes. The empty node is filled and the repair ends.
  • At the root, the empty node above the root is dropped: every path misses the same black link, so black balance holds, and the tree is one level shorter.

Example (a merge, then a borrow one level up) Delete \(10\) from the 2-3 tree with root \([40]\), children \([20]\) and \([60\,|\,80]\), and leaves \([10], [30]\) and \([50], [70], [90]\). In the red-black BST, \(40\) is the black root; \(20\) is black with black children \(10\) and \(30\); \(80\) is black with \(60\) as its red left child (over \(50\) and \(70\)) and \(90\) as its black right child.
  1. The search reaches \(10\), a black leaf. Removing it leaves the empty node as \(20\)’s left child: black balance is broken.
  2. The empty node’s parent \([20]\) is a 2-node and its sibling \([30]\) is a 2-node: merge. Recolor \(30\) red; the 3-node \([20\,|\,30]\) now leans right, so rotateLeft(20) makes \(30\) black with \(20\) its red left child. \([20]\) gave up its only key, so the empty node is now \(40\)’s left child, above \([20\,|\,30]\).
  3. Its parent \([40]\) is a 2-node and its sibling \([60\,|\,80]\) is a 3-node: borrow. rotateRight(80) brings \(60\) up inside the sibling, rotateLeft(40) lifts \(60\) into \(40\)’s place with \(40\) below it, and recoloring \(40\) and \(80\) black puts \(40\) where the empty node was.
The result: \(60\) black at the root; \(40\) black with children \(30\) (black, with \(20\) its red left child) and \(50\); \(80\) black with children \(70\) and \(90\). In 2-3 terms, \([60]\) over \([40]\) (over \([20\,|\,30]\) and \([50]\)) and \([80]\) (over \([70]\) and \([90]\)), exactly what the 2-3 delete gives.

Every case is a constant number of moves at one level, and the empty node climbs only through merges under 2-node parents, so the repair costs \(O(\log n)\) on top of the \(\Theta(\log n)\) search: delete, like insert, is \(\Theta(\log n)\).

Top-down delete Sedgewick’s published left-leaning delete works top-down instead: on the way down it merges or borrows before stepping into a 2-node (its helpers are named moveRedLeft and moveRedRight), so the key it removes is never a black leaf and no black link goes missing. It performs the same 2-3 merges and borrows, ahead of time, and restores the left-leaning shape on the way back up.

7. Why the height is \(\Theta(\log n)\)

Theorem (red-black height) A red-black BST on \(n\) keys has height at most \(2\log_2 n\), so search, insert, and delete are \(\Theta(\log n)\) for any insertion order.
Proof. Let \(b\) be the number of black links on a root-to-null path, the same on every path by black balance (invariant 3). Collapse each red link into its parent: two nodes glued by a red link merge into one 2-3 node, recovering the very 2-3 tree this encoding came from. The black links are exactly that 2-3 tree’s edges, so \(b\) equals the 2-3 tree’s height, which by the height bounds in the 2-3 Trees handout is at most \(\log_2 n\); hence \(b \le \log_2 n\). Now count all links on a path. Between any two black links invariant 2 permits at most one red (two in a row is the violation flipColors removes), so the total number of links is at most \(2b\). Therefore the height is at most \(2b \le 2\log_2 n\). ∎

The bound is looser than AVL’s \(1.44\log_2 n\) (a red-black tree can be up to twice as tall) but still \(\Theta(\log n)\), and it is reached with far fewer restructuring operations per update. That trade is why a red-black BST, being just one node type plus one color bit, is the balanced tree real libraries ship: C++’s std::map and std::set, Java’s TreeMap and TreeSet, and the Linux kernel’s scheduler among them.

The correspondence is the whole point “2-3 trees are balanced” (the 2-3 Trees handout) and “red-black trees are \(\Theta(\log n)\)” (here) are the same fact, seen through the collapse-the-red-links map. This is Sedgewick & Wayne’s central insight: do not analyse the red-black tree directly: recognise it as a 2-3 tree in a costume and inherit everything already proved. Cormen et al. develop the classic (not-left-leaning) red-black tree from five color axioms instead; the two agree on the \(\Theta(\log n)\) guarantee and differ mainly in how many cases the code must handle.

8. Exercises (with solutions)

  1. Convert the 2-3 tree whose root is the 3-node \([40\,|\,80]\) with children \([20], [60], [100]\) into a left-leaning red-black BST. Give each node’s color and its parent link.
    solution The root 3-node \([40\,|\,80]\) becomes \(80\) (black, since it is the root) with a red left link to \(40\). The three subtrees hang under the two keys by range: \(20\) (\(\lt 40\)) is \(40\)’s left child, \(60\) (\(40\!-\!80\)) is \(40\)’s right child, and \(100\) (\(\gt 80\)) is \(80\)’s right child; all three are black. In-order \(20,40,60,80,100\) matches the 2-3 tree, and collapsing the one red link \(40\!-\!80\) recovers the original 3-node.
  2. Prove that a left-leaning red-black BST on \(n\) keys has height at most \(2\log_2 n\), using the correspondence with 2-3 trees.
    solution Let \(b\) be the number of black links on any root-to-null path; black balance makes \(b\) the same on every path. Collapsing each red link into its parent merges each red-glued pair into one 2-3 node and turns the black links into the edges of a 2-3 tree, so \(b\) equals that 2-3 tree’s height, which is at most \(\log_2 n\) (the all-2-nodes worst case; see the 2-3 Trees handout); thus \(b \le \log_2 n\). Between two consecutive black links at most one red link can appear (invariant 2 forbids two reds in a row), so a path has at most \(2b\) links total. Hence height \(\le 2b \le 2\log_2 n\).
  3. Insert the keys \(S, E, A, R, C\), in that order, into an empty left-leaning red-black BST. List the moves each insertion fires and draw the final tree with its link colors.
    solution S: the root, black. E: \(E \lt S\), so a red left link; it leans left, there are no two reds in a row and no two red children, so no move fires. A: \(A \lt E\), a red left link under \(E\), giving the two reds in a row \(S\!-\!E\) and \(E\!-\!A\). Nothing fires at \(E\); at \(S\) the second test fires, rotateRight(S), lifting \(E\) with red children \(A\) and \(S\), which the third test then splits, flipColors(E). The tree is \(E\) black with black children \(A\) and \(S\). R: \(R \lt S\), a red left link under \(S\); it already leans left, so no move. C: \(C \gt A\), a red right link under \(A\), so the first test fires, rotateLeft(A), leaving \(C\) black in \(A\)’s place with \(A\) as its red left child. 
                E (black root)
           /            \
        C (black)      S (black)
       /              /
     A (RED)        R (RED)
    In-order is \(A,C,E,R,S\); every root-to-null path crosses two black links; and collapsing the two red links recovers the 2-3 tree with root \([E]\) over the 3-nodes \([A\,|\,C]\) and \([R\,|\,S]\).
  4. Show that flipColors and the two rotations all preserve black balance, so an insertion can never break invariant 3.
    solution flipColors turns the two child links from red to black and the node’s own parent link from black to red. Any root-to-null path through this node uses the parent link and exactly one of the two child links, so it loses one black link at the top and gains one just below: the count is unchanged, and paths that avoid the node are untouched. For a rotation, the two nodes involved exchange colors (\(x\) inherits \(h\)’s color and \(h\) becomes red), and the subtree that changes parent moves across a link of the same color it had before, so every path through the subtree still crosses the same number of black links. Since the new link of an insertion is red, it adds no black link anywhere either, which is why black balance is the one invariant an insertion never has to repair.
  5. Insert \(10, 20, 30, 40, 50\) in that order into an empty left-leaning red-black BST (the last tree of the ascending figure), then delete \(40\). List the steps of the deletion and give the final tree. What does the deletion do in the 2-3 tree?
    solution The tree is \(40\) black at the root with a red left child \(20\); \(20\) has black children \(10\) and \(30\); \(50\) is the root’s black right child. \(40\) has two children, so it swaps with its in-order predecessor \(30\) (one step left to \(20\), then right to \(30\)): \(30\) is now at the root, and \(40\) sits where \(30\) was, a black leaf. Removing it leaves the empty node as \(20\)’s right child, and black balance is broken. The empty node’s parent is the 3-node \([20\,|\,30]\) (\(20\) red, \(30\) black) and the empty node is its middle child; both siblings, \([10]\) and \([50]\), are 2-nodes, so the repair is a merge with the left one: recolor \(20\) black and \(10\) red. The result is \(30\) black at the root, \(20\) black as its left child with \(10\) its red left child, and \(50\) black as its right child. In the 2-3 tree, \([20\,|\,40]\) over \([10], [30], [50]\) loses the internal key \(40\): its predecessor \(30\) takes its place, the leaf \([30]\) empties, and since neither sibling can spare a key it merges with \([10]\) and the key \(20\) from the parent, giving \([30]\) over \([10\,|\,20]\) and \([50]\).
  6. Encode the 2-3 tree with root \([40]\) and leaves \([20\,|\,30]\) and \([60]\) as a left-leaning red-black BST. Then, each time starting from that tree, insert \(35\), \(10\) and \(50\). For each insert, say where the new red node lands, which rule it breaks, and which fixes run.
    solution The encoding: \(40\) black at the root, \(30\) black as its left child with \(20\) its red left child, \(60\) black as its right child.
    • 35 lands above both keys of the 3-node \([20\,|\,30]\), as \(30\)’s red right child: \(30\) has two red children, the 4-node \([20\,|\,30\,|\,35]\) (rule 3). flipColors(30) splits it: \(20\) and \(35\) turn black and \(30\) joins \([40]\) as its red left child, the 3-node \([30\,|\,40]\), which breaks no rule.
    • 10 lands below both keys, as \(20\)’s red left child: two reds in a row, \(30\) to \(20\) to \(10\) (rule 3). rotateRight(30) lifts \(20\) with red children \(10\) and \(30\), and flipColors(20) splits that 4-node: \(20\) joins \([40]\) as \([20\,|\,40]\).
    • 50 lands below the key of the 2-node \([60]\), as its red left child: the 3-node \([50\,|\,60]\), leaning left. No rule breaks and no fix runs.
  7. Encode the 2-3 tree with root \([30\,|\,60]\) and leaves \([10]\), \([40]\) and \([70]\), then delete \(10\). Where is the empty node, which repair applies, and which red-black moves carry it out?
    solution The encoding: \(60\) black at the root, \(30\) its red left child with black children \(10\) and \(40\), and \(70\) black as the root’s right child. \(10\) is a black leaf, so removing it leaves the empty node as \(30\)’s left child: the left child of the 3-node \([30\,|\,60]\). Its sibling, the middle child \([40]\), is a 2-node, so the repair is a merge: \(30\) comes down and joins \(40\), and the parent keeps \(60\). In red-black terms: recolor \(30\) black and \(40\) red, which leaves a red link leaning right, then rotateLeft(30). The result is \(60\) black at the root, \(40\) black as its left child with \(30\) its red left child, and \(70\): the 2-3 tree \([60]\) over \([30\,|\,40]\) and \([70]\).
