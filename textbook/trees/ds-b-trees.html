B-Trees & B+ Trees

Rudolf Bayer and Edward McCreight invented B-trees at Boeing Scientific Research Labs in 1970. They never explained what the B stands for. R. Bayer and E. McCreight, Acta Informatica 1, 1972; D. Comer, “The Ubiquitous B-Tree,” Computing Surveys 11(2), 1979

A 2-3 tree keeps every leaf at the same depth by splitting a full node and promoting its middle key, and that mechanism, unlike the rotations of the AVL tree, does not care how wide a node is. A B-tree widens the node deliberately: size it to a disk block, and the tree becomes shallow enough that a lookup costs a handful of block reads. That is the structure underneath essentially every database and filesystem, and this handout closes by comparing the balanced search trees and when to reach for each.

1. B-trees: sized for the disk

A 2-3 node holds one or two keys. Why stop at two? A B-tree of order \(M\) lets each node hold up to \(M-1\) keys (and thus up to \(M\) children), keeps every leaf at the same depth, and splits a node the moment it reaches \(M\) keys: the identical split-and-promote, just with a wider node. A 2-3 tree is exactly a B-tree of order 3.

Definition (B-tree of order \(M\)) A search tree in which every node holds a sorted array of at most \(M-1\) keys and at most \(M\) child pointers, every non-root node has at least \(\lceil M/2 \rceil\) children (so at least \(\lceil M/2\rceil - 1\) keys), the root has at least two children unless it is a leaf, and all leaves lie at the same depth. The “at least half full” lower bound is what bounds the height at \(\log_{\lceil M/2\rceil} n\) and keeps the tree shallow.

The reason to want fat nodes is not comparison count: it is the disk. Reading from disk or SSD is not \(\approx 1\times\) the cost of a memory access; it is \(\approx 10^5\times\) slower, and it arrives a whole block (page) at a time. So the cost that matters is the number of node accesses = disk reads, not the number of comparisons.

Size a node to fill exactly one block, and each node holds hundreds of keys, so the tree is only a few levels deep. One block read brings a whole key array into memory, where a single in-RAM binary search picks the child: one disk read per level, and the height is \(\log_M n\).

Example (searching across the separators) Search in a node is a scan of its sorted key array, and the keys act as separators: with keys \(k_1 \lt \cdots \lt k_{m}\) and children \(c_0, \ldots, c_{m}\), child \(c_i\) holds exactly the keys between \(k_i\) and \(k_{i+1}\). Three searches on the tree above, whose root is \([30\,|\,60]\) over the leaves \([10\,|\,20]\), \([40\,|\,50]\), and \([70\,|\,80\,|\,90]\).
  • Search 50. Read the root \([30\,|\,60]\): \(30 \lt 50 \lt 60\), so \(50\) belongs between the two separators; follow the middle child. Read \([40\,|\,50]\): \(50\) is present. A hit, 2 node reads.
  • Search 65. Read the root: \(65 \gt 60\), past the last separator; follow the right child. Read \([70\,|\,80\,|\,90]\): \(65\) is smaller than every key there and the node is a leaf. A miss, 2 node reads.
  • Search 30. Read the root: \(30\) equals the first separator, so the search stops at the root. A hit, 1 node read: a key stored in an internal node is found without reaching a leaf.
Each search reads one node per level, one disk block per level, no matter how many keys that block holds. The hit at \(30\) is worth noticing: in a plain B-tree records sit in internal nodes too, so a lookup may finish early, whereas the B+ tree of §2 always walks all the way down to a leaf.

In code

A node is a sorted key array, a child array one longer, and a count; it is the 2-3 tree’s node at width \(M\), sized so that one node fills one disk block. As in the 2-3 node, one spare key slot holds the overflow of an insertion until the node splits; the keys stay sorted, so the overflowed node’s middle key is key[(M-1)/2] (integer division), the key the split promotes. Search scans (or binary-searches) the keys of a node already in memory and follows one child: one block read per level. 

// the order (a disk-sized node: M in the hundreds)
const int M = 5;

struct BTreeNode {
    // keys in use: ceil(M/2) - 1 to M - 1 (the root: 1 to M - 1)
    int        n;
    int        key[M];         // sorted; an M-th key only mid-insert
    BTreeNode* child[M + 1];   // n + 1 children; none in a leaf
    bool       leaf;
};

class BTree {
public:
    bool contains(int key) const;  // one node (one block read) per level
    void insert(int key);          // add in a leaf, split full nodes upward
    void remove(int key);          // remove, then borrow or merge upward
private:
    BTreeNode* root = nullptr;
};

bool BTree::contains(int key) const {
    BTreeNode* h = root;
    while (h != nullptr) {
        int i = 0;
        while (i < h->n && key > h->key[i]) i++;   // first key >= the target
        if (i < h->n && key == h->key[i]) return true;
        if (h->leaf) return false;
        h = h->child[i];                             // read the next block
    }
    return false;
}

Example (a B-tree split, \(M=5\)) Insert \(55\) into the full leaf \([60\,|\,70\,|\,80\,|\,90]\) under the root \([30]\): Split at \(M\) keys, promote the middle, and two half-full nodes remain: the same rule as a 2-3 split, only the threshold (5 keys instead of 3) and the halves (two keys each instead of one) differ. A root split still grows the height by one, at the top.
Example (building the tree above, key by key, \(M=5\)) Insert \(10, 20, \ldots, 90\) into an empty order-5 B-tree. A node overflows at \(M = 5\) keys and promotes the third of the five.
Proposition (few disk reads) A B-tree of order \(M\) on \(n\) keys has height at most \(\log_{\lceil M/2\rceil} n\), so a lookup costs \(O(\log_M n)\) disk reads.
Proof. Write \(t = \lceil M/2\rceil\). The root holds at least one key and has at least two children; every other node has at least \(t\) children and so at least \(t - 1\) keys. Depth \(d \ge 1\) therefore holds at least \(2t^{d-1}\) nodes, and a tree of height \(h\) holds at least \[ n \;\ge\; 1 + (t-1)\sum_{d=1}^{h} 2t^{d-1} \;=\; 1 + 2(t^h - 1) \;=\; 2t^h - 1 \] keys. Solving for \(h\) gives \(h \le \log_t \frac{n+1}{2} \le \log_t n\). Each level costs exactly one node access (one block read); the in-node binary search is free once the block is in RAM. ∎

The contrast with a binary tree is the whole argument for B-trees. A balanced binary tree over \(10^9\) keys is about \(\log_2 10^9 \approx 30\) levels: up to 30 disk reads, roughly \(0.3\) s on a spinning disk. The same keys in an order-1000 B-tree take 3 reads, roughly \(30\) ms: the branching factor does all the work. In RAM, 30 versus 3 comparisons is nothing; against the disk it is the difference between a snappy query and a slow one. The lesson is to match the node size to the unit of I/O; historically the original motivation (Bayer & McCreight, 1972).

Splitting on the way down At an even order, a B-tree can instead split every full node on the way down, before it overflows, and borrow or merge before entering a node at its minimum, so that an update never climbs back up: one pass, and fewer locks when many updates share the tree. The Top-Down Balanced Trees chapter covers it and compares it with the bottom-up repairs here.

2. B+ trees: values in the leaves

Databases use a variant, the B+ tree, that pushes all values down to the leaves. Internal nodes hold only keys (pure routing information); every value lives in a leaf, and the leaves are linked into a sorted list. Value-free internal nodes fan out even wider (each block routes to more children), so the tree is even shorter, and the linked leaves make range scans a single descent followed by a walk along the chain.

In code, a B+ node is a B-tree node whose fields depend on its kind: a router node holds keys and children only, and a leaf holds keys with their records and a pointer to the next leaf, the link that makes the leaves one sorted list. 

struct BPlusNode {
    bool       leaf;
    int        n;              // keys in use
    int        key[M];         // routers, or a leaf's keys (one spare slot)
    BPlusNode* child[M + 1];   // router only: n + 1 children
    Record*    rec[M];         // leaf only: rec[i] is key[i]'s record
    BPlusNode* next;           // leaf only: the next leaf in key order, or null
};
static class BPlusNode {
    boolean leaf;
    int n;                             // keys in use
    int[] key = new int[M];            // routers or leaf keys (one spare slot)
    BPlusNode[] child = new BPlusNode[M + 1];   // router only: n + 1 children
    Record[] rec = new Record[M];      // leaf only: rec[i] is key[i]'s record
    BPlusNode next;                    // leaf only: the next leaf, or null
}
class BPlusNode:
    def __init__(self, leaf):
        self.leaf = leaf
        self.n = 0                    # keys in use
        self.key = [0] * M            # routers, or a leaf's keys (one spare slot)
        self.child = [None] * (M + 1) # router only: n + 1 children
        self.rec = [None] * M         # leaf only: rec[i] is key[i]'s record
        self.next = None              # leaf only: the next leaf, or None
// The nodes live in one Vec and a link is an index into it: a leaf is
// reached both from its parent and from the leaf before it.
struct BPlusNode {
    leaf: bool,
    n: usize,                    // keys in use
    key: [i32; M],               // routers, or a leaf's keys (one spare slot)
    child: [usize; M + 1],       // router only: n + 1 children
    rec: [Option<Record>; M],    // leaf only: rec[i] is key[i]'s record
    next: Option<usize>,         // leaf only: the next leaf in key order, or None
}

Definition (routing in a B+ tree) At a router node with routers \(s_1 \lt s_2 \lt \cdots \lt s_m\), a key \(k\) follows child \(i\), where \(i\) is the number of routers \(\le k\): child \(0\) if \(k \lt s_1\), child \(i\) if \(s_i \le k \lt s_{i+1}\), child \(m\) if \(k \ge s_m\). Less goes left; equal goes right. Every key in a subtree is at least the router to its left and less than the router to its right, and a router is a copy of the first key of the subtree to its right at the time it was made.

In the index above, a search for \(30\) reads the router \([30\,|\,60]\), finds \(30 \le 30 \lt 60\) and follows child \(1\) to the leaf \([30\,|\,45]\). The router \(30\) does not end the search: it carries no record, so every search ends in a leaf.

A key appears twice because of how routers are made:

  • a leaf split copies: a full leaf splits into two, and the new right leaf’s first key is copied up as a router while it stays in the leaf with its record (a borrow between two leaves likewise rewrites the router between them to a copy of the right leaf’s new first key);
  • a router split moves: a full router node splits around its middle router, which goes up and is gone from the node below, exactly as in a B-tree; a router needs no copy, so no new duplicate appears;
  • a delete leaves routers alone unless leaves borrow or merge: once its key is deleted a router may match no key in the tree, and it still separates its two sides correctly.
Example (one key copied up, then moved up) Insert \(50\) into the order-3 index above (a node holds at most 2 keys).
  1. \(50\) descends: at the routers \([30\,|\,60]\), \(30 \le 50 \lt 60\), so it takes child 1, the leaf \([30\,|\,45]\), which becomes \([30\,|\,45\,|\,50]\): three keys, so it splits.
  2. Leaf split: \([30\,|\,45]\) and \([50]\), linked into the chain; \(50\) is copied up, and the router node becomes \([30\,|\,50\,|\,60]\): three routers, so it splits.
  3. Router split: \([30]\) and \([60]\); \(50\) moves up into a new root.
Now \(50\) is the root’s router and a key in its leaf, and \(30\) and \(60\) are routers and leaf keys as well. Deleting \(30\) next turns its leaf into \([45]\) (still at least one key, so no repair) and leaves the router \(30\) in place, a correct separator that is no longer a key.

Because the leaves form a sorted linked list, a range query such as SELECT * WHERE age BETWEEN 20 AND 40 descends once to find \(20\), then follows leaf links until it passes \(40\). ORDER BY, BETWEEN, and pagination are all just sequential leaf walks, which is why B+ trees, not plain B-trees, index essentially every relational database and back most modern filesystems (NTFS, ext4, APFS).

Example (a range scan along the leaf chain) Run BETWEEN 20 AND 40 against the index drawn above: the router \([30\,|\,60]\) over the linked leaves \([10\,|\,20] \to [30\,|\,45] \to [60\,|\,90]\).
  1. Descend for the low end, \(20\): read the routers \([30\,|\,60]\); \(20 \lt 30\), so follow the left child. Read the leaf \([10\,|\,20]\) and position on \(20\). The descent does not stop at a router: \(30\) appears upstairs as a separator, but its record lives in a leaf, so every search reaches a leaf. That is the B+ rule.
  2. Scan this leaf from that position: \(20\) is in range, emit it. The leaf ends, so follow its next-leaf link.
  3. Read \([30\,|\,45]\): \(30\) is in range, emit it; \(45 \gt 40\), out of range, stop.
The result \(20, 30\) costs one descent (2 node reads) plus one extra leaf read, and no internal node is ever revisited. A plain B-tree answers the same query by walking the tree itself, returning to internal nodes between leaves; the linked leaves replace that wandering with a sequential read, which is also exactly what a disk is fastest at. Extending the range to \(90\) would simply continue the walk into \([60\,|\,90]\), one more leaf read, with no extra descent.

Choosing the order \(M\) The order is dictated by hardware, not taste: pick \(M\) so a node fills one block. With a \(4096\)-byte block, \(8\)-byte keys, and \(8\)-byte pointers, an internal node needs about \(M\cdot 8 + (M-1)\cdot 8 \approx 4096\), giving \(M \approx 256\). Then three full levels hold \((1 + 256 + 256^2) \times 255 = 256^3 - 1 \approx 16.8\) million keys in three reads; at \(M = 1000\), three full levels hold \(1000^3 - 1\), about a billion. Those figures assume full nodes, though. The order property only guarantees half-full, and the root is exempt even from that: right after any root split the new root holds a single key. Counting the guaranteed minimum (\(\lceil M/2\rceil\) children) instead of the maximum gives far fewer keys at the same depth, but because capacity grows exponentially in the fan-out, one extra disk read makes it up. “A few disk reads for the largest real datasets” is the sound takeaway (Open Data Structures, Morin, Ch. 14); just do not quote the best case as if it were the guarantee.

3. One goal, several tools

The AVL tree, the red-black BST, the 2-3 tree, and the B-tree all deliver \(\Theta(\log n)\) search, insert, and delete. They differ in the mechanism that keeps them balanced and in which level of the memory hierarchy they optimise for.

plain BSTnothingup to \(n-1\)keys arrive randomly

The choice between AVL and red-black is a choice of constant, not of asymptotic class. AVL keeps a tighter tree (height \(1.44\log_2 n\) versus \(2\log_2 n\)), so it searches a little faster, and it does at most one rotation per insertion; but a deletion can rotate at every level. Red-black does slightly more work per insertion yet keeps deletion to \(O(1)\) rotations (recolours may cascade, but they are cheaper than rotations). So AVL optimises the search and wins when reads dominate; red-black optimises the update and wins when writes dominate, which is why a general-purpose library map is red-black.

4. Exercises (with solutions)

  1. Start from the order-5 B-tree with root \([30\,|\,60]\) over the leaves \([10\,|\,20]\), \([40\,|\,50]\), and \([70\,|\,80\,|\,90]\). Insert \(45\), then \(55\), then \(35\). Which node splits, which key is promoted, and what is the tree at the end? How many more insertions could the root absorb before it too must split?
    solution \(45\) and \(55\) both fall between the separators \(30\) and \(60\) and join the middle leaf, giving \([40\,|\,45\,|\,50]\) and then \([40\,|\,45\,|\,50\,|\,55]\): four keys, full but legal, since a node overflows only at \(M = 5\). \(35\) lands in that same leaf, making the five keys \([35\,|\,40\,|\,45\,|\,50\,|\,55]\), so the leaf splits and its middle key \(45\) is promoted: The root now holds three keys, so it can accept one more promoted key (reaching the legal maximum of four) and splits on the next one, which would lift a new root above it and take the tree to height 2. Every leaf is still at the same depth, as it is after every insertion.
  2. A B-tree has order \(M = 256\) and three levels (so a lookup is three disk reads). Assuming every node is full, how many keys can it hold? Repeat for order \(M\) and \(h\) levels in general.
    solution A full node has \(M\) children and \(M-1\) keys. With \(h\) levels the number of nodes is \(1 + M + M^2 + \dots + M^{h-1} = (M^h - 1)/(M - 1)\), and each holds \(M-1\) keys, for a total of \(M^h - 1\) keys. For \(M = 256\), \(h = 3\): \(256^3 - 1 \approx 1.67 \times 10^7\), about 16.7 million keys in three reads. (This is the best case; the order property only guarantees half-full nodes, so the guaranteed capacity at three levels is far smaller, but one more level restores “millions.”)
  3. Why do databases prefer B+ trees over plain B-trees for queries such as SELECT * WHERE age BETWEEN 20 AND 40?
    solution In a B+ tree all records live in the leaves, and the leaves are linked into a sorted list. A range query descends once to the first key in range, then walks the leaf chain sequentially until it leaves the range: no re-traversal of the tree. In a plain B-tree records sit at every level, so a range scan must wander up and down the tree, revisiting internal nodes. B+ trees also keep internal nodes value-free, so each block routes to more children (higher fan-out, shorter tree). The cost is that some keys appear twice (as a router and in a leaf), a small price for cheap range and ordered scans.
  4. For each situation, name the balanced search tree you would reach for: (a) an in-memory dictionary that is queried far more often than it is updated; (b) the general-purpose ordered map in a standard library; (c) an index for a database table on disk that must support ordered range scans.
    solution (a) an AVL tree: its tighter height (\(1.44\log_2 n\)) makes reads fastest. (b) a red-black BST: fewer rotations per update suit a mix of inserts and erases, which is why std::map/TreeMap use it. (c) a B+ tree: wide nodes minimise disk reads and the linked leaves make range scans a single descent plus a leaf walk. All three are \(\Theta(\log n)\); the machine and the workload decide.
  5. True or false, with justification: “AVL, red-black, 2-3, and B-trees all guarantee \(\Theta(\log n)\) search regardless of the order the keys are inserted.”
    solution True. Each maintains a height bound that is \(\Theta(\log n)\) under every insertion order: AVL keeps \(h \le 1.44\log_2 n\) via the balance-factor invariant; red-black keeps \(h \le 2\log_2 n\) via black balance and the no-double-red rule; a 2-3 tree keeps \(\log_3(n+1) - 1 \le h \le \log_2(n+1) - 1\) by perfect balance; and a B-tree of order \(M\) keeps \(h \le \log_{\lceil M/2\rceil} n\) by the half-full rule. Search visits one node per level, so it is \(\Theta(h) = \Theta(\log n)\) in every case. (A plain BST would make the claim false: adversarial inserts give height \(n-1\), which is exactly the problem these structures were built to solve.)
