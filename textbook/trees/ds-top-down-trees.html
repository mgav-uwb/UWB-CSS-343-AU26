Top-Down Balanced Trees

…new algorithms which perform the update and rebalancing in one pass, on the way down towards a leaf. L. J. Guibas and R. Sedgewick, “A Dichromatic Framework for Balanced Trees,” FOCS 1978 (abstract)

The 2-3 tree, the red-black BST and the B-tree all repair bottom-up: an update changes the bottom of the tree first (a key goes into a leaf, or comes out of one), and the repair then climbs back up the search path as far as the change propagates. A top-down algorithm repairs in the opposite order. On the way down it fixes every node that could pass a repair upward, before entering it, so the change at the bottom breaks nothing and the algorithm never climbs back.

1. Two orders of repair

A bottom-up insert adds the key to a leaf. If the leaf overflows, it splits and its middle key moves up into the parent, which may overflow and split in turn. The repair climbs until it reaches a node with room, or splits the root. To climb, the algorithm needs the path it came down: the recursion’s call stack, a stack of nodes, or parent pointers.

A top-down insert splits a full node before entering it, while its parent, already made non-full, has room for the middle key. When the search reaches the leaf, the leaf has room. A top-down delete gives every node it is about to enter a key to spare, so removing a key at the bottom cannot leave a node too small. In both directions the idea is the same:

Definition (safe node) A node is safe for an insert if it is not full, and safe for a delete if it holds more than the minimum number of keys. A split or a merge below a safe node stops there: the node absorbs the key it gains or loses. A top-down algorithm makes each node on the search path safe before it descends from that node.

The examples in §1–§4 use the 2-3-4 tree: a node holds one, two or three keys (a 2-node, 3-node or 4-node) and every leaf is at the same depth. It is the B-tree of order 4, and §2 shows why the 2-3 tree cannot be used instead.

The two final trees differ. The shape of a balanced tree depends on the algorithm that built it, not only on its keys, and both algorithms keep every leaf at one depth.

2. Room to repair early

A top-down insert splits a node that is full, before it overflows. A top-down delete merges a node that holds the minimum, before it underflows. Both need a node size that leaves room.

Proposition (room to split and merge early) In a tree whose nodes other than the root hold between \(a\) and \(b\) keys, a full node can be split around one of its keys into two legal nodes, and two siblings holding \(a\) keys each can be merged with their separator into one legal node, exactly when \(b \ge 2a + 1\).
Proof. A split of a full node sends one of its \(b\) keys up and leaves \(b - 1\) keys for the two halves, each of which needs at least \(a\): possible exactly when \(b - 1 \ge 2a\). A merge makes a node of \(a + 1 + a = 2a + 1\) keys, legal exactly when \(2a + 1 \le b\). Both conditions are \(b \ge 2a + 1\). ∎

A 2-3 tree has \(a = 1\) and \(b = 2\): \(2 \lt 3\), so it fails. That is why its insert must let a node overflow to three keys before splitting it, and why its delete must let a node empty before merging it: the repair can only come after the change. A 2-3-4 tree has \(a = 1\) and \(b = 3\), which meets the bound exactly. A B-tree of order \(M\) has \(a = \lceil M/2 \rceil - 1\) and \(b = M - 1\):

For even \(M = 2t\), \(a = t - 1\) and \(b = 2t - 1 = 2a + 1\): the bound holds. For odd \(M = 2t + 1\), \(a = t\) and \(b = 2t \lt 2a + 1\): it fails. Top-down repair needs an even order.

Minimum degree Cormen, Leiserson, Rivest and Stein’s Introduction to Algorithms (CLRS) defines a B-tree by its minimum degree \(t \ge 2\): every node other than the root holds between \(t - 1\) and \(2t - 1\) keys. That allows only even orders, \(M = 2t\), which is what its one-pass insert and delete need; \(t = 2\) is the 2-3-4 tree. The B-Trees & B+ Trees chapter allows any order, and repairs bottom-up.

3. Top-down insertion

The rule: before entering a node, split it if it is full. The root has no parent to receive its middle key, so a full root splits under a new, empty root that takes the middle key; this is the only way the tree grows taller, and it lowers every leaf by one level together, as in the 2-3 tree.

Proposition (a split never cascades) In a top-down insert, every node the search stands on is not full. So the parent of every split has room for the middle key, the leaf the search ends at has room for the new key, and the insert makes at most one split per level and never returns to a node it has left.
Proof. The search starts at the root, which is not full: a full root was split first, leaving a new root with one key. Suppose the search stands on a node \(x\) that is not full and is about to enter its child \(c\). If \(c\) is not full, the search enters a node that is not full. If \(c\) is full, it splits; \(x\), not full, takes the middle key, and each half of \(c\) keeps one key, so the half the search enters is not full. By induction every node on the path is not full, including each split’s parent and the final leaf. ∎

In code

A node is a sorted key array with one slot to spare, a child array, and a count, as in the 2-3 node, but at most three keys are ever in use: a node never overflows. 

struct Node234 {
    int      n = 0;               // keys in use: 1, 2 or 3
    int      key[3] = {};         // sorted
    Node234* child[4] = {};       // n + 1 children, all null in a leaf
};

bool isLeaf(const Node234* h) { return h->child[0] == nullptr; }

class Tree234 {
public:
    void insert(int key);         // split full nodes on the way down
    void remove(int key);         // fix 2-nodes on the way down
private:
    Node234* root = nullptr;
};

// x->child[i] is full (3 keys). Its middle key moves up into x, which is not
// full; the child keeps key[0], and a new node takes key[2].
void splitChild(Node234* x, int i) {
    Node234* c = x->child[i];
    Node234* right = new Node234();
    right->n = 1;
    right->key[0] = c->key[2];
    right->child[0] = c->child[2];
    right->child[1] = c->child[3];
    for (int j = x->n; j > i; j--) {             // open slot i in x
        x->key[j] = x->key[j - 1];
        x->child[j + 1] = x->child[j];
    }
    x->key[i] = c->key[1];                       // the middle key moves up
    x->child[i + 1] = right;
    x->n++;
    c->n = 1;
    c->child[2] = nullptr;
    c->child[3] = nullptr;
}

void Tree234::insert(int key) {
    if (root == nullptr) {
        root = new Node234();
        root->n = 1;
        root->key[0] = key;
        return;
    }
    if (root->n == 3) {                          // a full root: split it first
        Node234* top = new Node234();            // no keys yet, one child
        top->child[0] = root;
        splitChild(top, 0);                      // the tree grows one level
        root = top;
    }
    Node234* x = root;
    while (true) {
        int i = 0;
        while (i < x->n && key > x->key[i]) i++;
        if (i < x->n && key == x->key[i]) return;    // already present
        if (isLeaf(x)) {                         // not full: room for the key
            for (int j = x->n; j > i; j--) x->key[j] = x->key[j - 1];
            x->key[i] = key;
            x->n++;
            return;
        }
        if (x->child[i]->n == 3) {               // full: split before entering
            splitChild(x, i);
            if (key == x->key[i]) return;        // the key that moved up
            if (key > x->key[i]) i++;
        }
        x = x->child[i];
    }
}

// x.child[i] is full (3 keys). Its middle key moves up into x, which is not
// full; the child keeps key[0], and a new node takes key[2].
fn split_child(x: &mut Node234, i: usize) {
    let c = x.child[i].as_mut().unwrap();
    let mut right = Node234::new();
    right.n = 1;
    right.key[0] = c.key[2];
    right.child[0] = c.child[2].take();
    right.child[1] = c.child[3].take();
    let middle = c.key[1];
    c.n = 1;
    for j in (i + 1..=x.n).rev() {      // open slot i in x
        x.key[j] = x.key[j - 1];
        x.child[j + 1] = x.child[j].take();
    }
    x.key[i] = middle;                  // the middle key moves up
    x.child[i + 1] = Some(right);
    x.n += 1;
}

impl Tree234 {
    fn insert(&mut self, key: i32) {    // split full nodes on the way down
        if self.root.is_none() {
            let mut r = Node234::new();
            r.n = 1;
            r.key[0] = key;
            self.root = Some(r);
            return;
        }
        if self.root.as_ref().unwrap().n == 3 {     // a full root: split it first
            let mut top = Node234::new();            // no keys yet, one child
            top.child[0] = self.root.take();
            split_child(&mut top, 0);                // the tree grows one level
            self.root = Some(top);
        }
        let mut x = self.root.as_mut().unwrap();
        loop {
            let mut i = 0;
            while i < x.n && key > x.key[i] { i += 1; }
            if i < x.n && key == x.key[i] { return; }       // already present
            // not full: room for the key
            if x.is_leaf() {
                for j in (i + 1..=x.n).rev() { x.key[j] = x.key[j - 1]; }
                x.key[i] = key;
                x.n += 1;
                return;
            }
            // full: split before entering
            if x.child[i].as_ref().unwrap().n == 3 {
                split_child(x, i);
                // the key that moved up
                if key == x.key[i] { return; }
                if key > x.key[i] { i += 1; }
            }
            x = x.child[i].as_mut().unwrap();
        }
    }
    // remove(key): fix 2-nodes on the way down
}

A key that is already in the tree still pays for the splits above it; they leave a valid tree.

The cost: splits that were not needed

Every full node on the path splits, whether or not the new key would have reached it. A bottom-up insert splits only nodes that actually overflow.

Both inserts cost \(\Theta(\log n)\): one descent, and at most one split per level. What differs is which splits happen, and therefore the shape of the tree afterwards.

4. Top-down deletion

The rule: never enter a 2-node, except at the root. Before the search steps into a child that holds one key, it gives that child a second key:

  • Borrow if an adjacent sibling holds two or more keys: the separator between them comes down into the child, and the sibling’s nearest key goes up to replace it (the left sibling is tried first).
  • Merge otherwise: the child, the separator and a sibling become one 4-node. The parent loses a key, which it can afford: the descent gave it at least two, unless it is the root. A root with one key whose two children are both 2-nodes merges with them into one 4-node, and the tree becomes one level shorter before the descent starts.

A key found in an internal node cannot be removed there, since its node would lose a child. As in the bottom-up delete, a neighbor in sorted order replaces it, chosen so that the search still never enters a 2-node:

  • if the child before the key holds two or more keys, the key’s predecessor (the largest key in that subtree) replaces it, and the search goes on into that child to delete the predecessor;
  • otherwise, if the child after the key holds two or more keys, the successor replaces it, and the search goes into that child;
  • otherwise both children are 2-nodes: they merge with the key between them into one 4-node, and the search goes into it, still looking for the key.
Proposition (a delete never comes back up) In a top-down delete, every node the search stands on, other than the root, holds at least two keys. So the key is finally removed from a leaf that keeps at least one key, or from the root, and no repair is needed below or above it.
Proof. Each node the search enters below the root either held two or more keys already, or was just given a second key by a borrow (two keys) or a merge (three keys); in the internal-key cases the child entered holds two or more keys, or is the 4-node of a merge. A borrow takes a key from a sibling that had two or more, and a merge takes one from the parent, which had two or more or is the root (a root left with no keys is replaced by its one child). No node on the path or beside it is left below its minimum. ∎

In code

// x->child[i] + x->key[i] + x->child[i + 1] become one node, x->child[i].
void merge(Node234* x, int i) {
    Node234* a = x->child[i];
    Node234* b = x->child[i + 1];
    a->key[a->n] = x->key[i];                    // the separator comes down
    for (int j = 0; j < b->n; j++) a->key[a->n + 1 + j] = b->key[j];
    for (int j = 0; j <= b->n; j++) a->child[a->n + 1 + j] = b->child[j];
    a->n += 1 + b->n;
    for (int j = i; j < x->n - 1; j++) {         // close the gap in x
        x->key[j] = x->key[j + 1];
        x->child[j + 1] = x->child[j + 2];
    }
    x->child[x->n] = nullptr;
    x->n--;
    delete b;
}

// The left sibling lends: x->key[i - 1] comes down into the front of
// child i, and the sibling's largest key goes up in its place.
void borrowFromLeft(Node234* x, int i) {
    Node234* c = x->child[i];
    Node234* left = x->child[i - 1];
    for (int j = c->n; j > 0; j--) c->key[j] = c->key[j - 1];
    for (int j = c->n + 1; j > 0; j--) c->child[j] = c->child[j - 1];
    c->key[0] = x->key[i - 1];
    c->child[0] = left->child[left->n];
    c->n++;
    x->key[i - 1] = left->key[left->n - 1];
    left->child[left->n] = nullptr;
    left->n--;
}

// The right sibling lends: x->key[i] comes down onto the end of child i,
// and the sibling's smallest key goes up in its place.
void borrowFromRight(Node234* x, int i) {
    Node234* c = x->child[i];
    Node234* right = x->child[i + 1];
    c->key[c->n] = x->key[i];
    c->child[c->n + 1] = right->child[0];
    c->n++;
    x->key[i] = right->key[0];
    for (int j = 0; j < right->n - 1; j++) right->key[j] = right->key[j + 1];
    for (int j = 0; j < right->n; j++) right->child[j] = right->child[j + 1];
    right->child[right->n] = nullptr;
    right->n--;
}

// x->child[i] is a 2-node. Give it a second key before the search enters:
// borrow if a sibling can spare a key, else merge. Returns the child to enter.
int fixChild(Node234* x, int i) {
    Node234* left  = (i > 0)    ? x->child[i - 1] : nullptr;
    Node234* right = (i < x->n) ? x->child[i + 1] : nullptr;
    if (left != nullptr && left->n >= 2)   { borrowFromLeft(x, i);  return i; }
    if (right != nullptr && right->n >= 2) { borrowFromRight(x, i); return i; }
    if (left != nullptr) { merge(x, i - 1); return i - 1; }
    merge(x, i);
    return i;
}

int maxKey(Node234* h) {
    while (!isLeaf(h)) h = h->child[h->n];
    return h->key[h->n - 1];
}

int minKey(Node234* h) {
    while (!isLeaf(h)) h = h->child[0];
    return h->key[0];
}

void Tree234::remove(int key) {
    Node234* x = root;
    while (x != nullptr) {
        int i = 0;
        while (i < x->n && key > x->key[i]) i++;
        bool here = (i < x->n && key == x->key[i]);
        if (isLeaf(x)) {                         // 2+ keys, or the root
            if (!here) return;                   // not in the tree
            for (int j = i; j < x->n - 1; j++) x->key[j] = x->key[j + 1];
            x->n--;
            if (x->n == 0) {                     // the root held the last key
                delete x;
                root = nullptr;
            }
            return;
        }
        if (here) {                              // a key in an internal node
            if (x->child[i]->n >= 2) {           // the left side can spare one
                key = maxKey(x->child[i]);       // the predecessor replaces it,
                x->key[i] = key;                 // then goes from the leaf
            } else if (x->child[i + 1]->n >= 2) {
                key = minKey(x->child[i + 1]);   // the successor, mirrored
                x->key[i] = key;
                i++;
            } else {
                merge(x, i);                     // the key comes down
            }
        } else if (x->child[i]->n == 1) {
            i = fixChild(x, i);
        }
        Node234* next = x->child[i];
        if (x == root && x->n == 0) {            // a merge took the root's key
            delete x;
            root = next;                         // one level shorter
        }
        x = next;
    }
}

    }

    // x.child[i] is a 2-node. Give it a second key before the search enters:
    // borrow if a sibling can spare a key, else merge. Returns the child to enter.
    static int fixChild(Node234 x, int i) {
        Node234 left  = (i > 0)   ? x.child[i - 1] : null;
        Node234 right = (i < x.n) ? x.child[i + 1] : null;
        if (left != null && left.n >= 2)   { borrowFromLeft(x, i);  return i; }
        if (right != null && right.n >= 2) { borrowFromRight(x, i); return i; }
        if (left != null) { merge(x, i - 1); return i - 1; }
        merge(x, i);
        return i;
    }

    static int maxKey(Node234 h) {
        while (!isLeaf(h)) h = h.child[h.n];
        return h.key[h.n - 1];
    }

    static int minKey(Node234 h) {
        while (!isLeaf(h)) h = h.child[0];
        return h.key[0];

    b = x.child[i + 1]

fn merge(x: &mut Node234, i: usize) {
    let mut b = x.child[i + 1].take().unwrap();
    let sep = x.key[i];
    let a = x.child[i].as_mut().unwrap();
    a.key[a.n] = sep;                            // the separator comes down
    for j in 0..b.n { a.key[a.n + 1 + j] = b.key[j]; }
    for j in 0..=b.n { a.child[a.n + 1 + j] = b.child[j].take(); }
    a.n += 1 + b.n;
    for j in i..x.n - 1 {                        // close the gap in x
        x.key[j] = x.key[j + 1];
        x.child[j + 1] = x.child[j + 2].take();
    }
    x.n -= 1;
}

// The left sibling lends: x.key[i - 1] comes down into the front of
// child i, and the sibling's largest key goes up in its place.
fn borrow_from_left(x: &mut Node234, i: usize) {
    let (lo, hi) = x.child.split_at_mut(i);
    let left = lo[i - 1].as_mut().unwrap();
    let c = hi[0].as_mut().unwrap();
    for j in (1..=c.n).rev() { c.key[j] = c.key[j - 1]; }
    for j in (1..=c.n + 1).rev() { c.child[j] = c.child[j - 1].take(); }
    c.key[0] = x.key[i - 1];
    c.child[0] = left.child[left.n].take();
    c.n += 1;
    x.key[i - 1] = left.key[left.n - 1];
    left.n -= 1;
}

// The right sibling lends: x.key[i] comes down onto the end of child i,
// and the sibling's smallest key goes up in its place.
fn borrow_from_right(x: &mut Node234, i: usize) {
    let (lo, hi) = x.child.split_at_mut(i + 1);
    let c = lo[i].as_mut().unwrap();
    let right = hi[0].as_mut().unwrap();
    c.key[c.n] = x.key[i];
    c.child[c.n + 1] = right.child[0].take();

    for j in 0..right.n { right.child[j] = right.child[j + 1].take(); }
    right.n -= 1;
}

// x.child[i] is a 2-node. Give it a second key before the search enters:
// borrow if a sibling can spare a key, else merge. Returns the child to enter.
fn fix_child(x: &mut Node234, i: usize) -> usize {
    let left_n = if i > 0 { x.child[i - 1].as_ref().unwrap().n } else { 0 };
    let right_n = if i < x.n { x.child[i + 1].as_ref().unwrap().n } else { 0 };
    if left_n >= 2 { borrow_from_left(x, i); return i; }
    if right_n >= 2 { borrow_from_right(x, i); return i; }
    if i > 0 { merge(x, i - 1); return i - 1; }
    merge(x, i);
    i
}

// One step down from x, which holds two or more keys or is the root.
fn remove_from(x: &mut Node234, mut key: i32) {
    let mut i = 0;
    while i < x.n && key > x.key[i] { i += 1; }
    let here = i < x.n && key == x.key[i];
    if x.is_leaf() {                                // 2+ keys, or the root
        if !here { return; }                        // not in the tree
        for j in i..x.n - 1 { x.key[j] = x.key[j + 1]; }
        x.n -= 1;
        return;
    }
    if here {                                       // a key in an internal node
        if x.child[i].as_ref().unwrap().n >= 2 {    // the left side can spare one
            // the predecessor replaces it, then goes from the leaf
            key = max_key(x.child[i].as_ref().unwrap());
            x.key[i] = key;
        } else if x.child[i + 1].as_ref().unwrap().n >= 2 {
            // the successor, mirrored
            key = min_key(x.child[i + 1].as_ref().unwrap());
            x.key[i] = key;
            i += 1;
        } else {
            merge(x, i);                            // the key comes down
        }
    } else if x.child[i].as_ref().unwrap().n == 1 {
        i = fix_child(x, i);
    }
    remove_from(x.child[i].as_mut().unwrap(), key);
}

5. B-trees: one pass, few locks

Both algorithms work unchanged at any even order \(M = 2t\). A full node holds \(2t - 1\) keys and splits around key[t-1] into two nodes of \(t - 1\) keys, the minimum. A child with the minimum \(t - 1\) keys gets one more before the search enters it, by a borrow or by a merge into \((t - 1) + 1 + (t - 1) = 2t - 1\) keys, a full but legal node.

On disk, where each node is one block (the B-Trees & B+ Trees chapter), the top-down algorithms have two practical properties:

  • One pass. Each node on the path is read once, from the root down, and written at most once. The algorithm never returns to a node it has left, so it does not need to keep the path. A bottom-up insert that keeps the path in memory also reads each node once; the difference is that it may have to write nodes it left behind.
  • Few locks. When several transactions update one tree at once, each must lock the nodes it may change. Below a safe node, no split or merge can climb past it, so the locks above it can be released. Bayer and Schkolnick (1977) built locking protocols on this observation. A top-down update makes every node safe before descending, so it needs to hold locks only on a node and its child (and the new sibling during a split); a bottom-up update keeps locks on every node below the last safe node on its path.
Another route to concurrency Lehman and Yao (1981) gave each B-tree node a link to its right sibling. A search that arrives at a node just split can follow the link to find the keys that moved, so updates can split bottom-up while holding very few locks. PostgreSQL’s B-tree indexes implement their algorithm.

6. Red-black trees

2-3-4 trees in red and black

In the red-black BST a node with two red children is a temporary 4-node, split by flipColors as soon as it forms. If 4-nodes are allowed to stay, the same encoding stores a 2-3-4 tree: a 4-node is a black node with two red children, and a 3-node is a black node with one red child, on the left in a left-leaning red-black (LLRB) tree. The red-black trees of Guibas and Sedgewick’s 1978 paper encode 2-3-4 trees this way, and the new algorithms it introduced work top-down.

Insert: one line moves

The LLRB insert of the red-black chapter (put, with fixUp) flips colors last, on the way back up, after the rotations. Moving that one test to the start of the function, before the comparison, splits every 4-node on the search path on the way down, the top-down rule of §3:

Sedgewick (2008) put it this way: “the left-leaning versions of 2-3 trees and top-down 2-3-4 trees differ in the position of one line of code.” With the flip first, a 4-node splits only when a later search passes through it, so 4-nodes survive between inserts and the tree is a 2-3-4 tree. With the flip last, a 4-node splits on the way up from the insert that made it, and the tree is a 2-3 tree.

Either way the LLRB insert is recursive and rotates on the way back up, so even the flip-first version makes two passes. An insert can also do its rotations on the way down if it keeps pointers to the last few nodes of the path; that makes it one pass, at the price of more cases.

Sedgewick’s delete

Sedgewick’s LLRB delete (2008; also the delete in Sedgewick and Wayne’s Algorithms, 4th edition) applies the top-down rule to the 2-3 tree: “we perform rotations and color flips on the way down the search path to ensure that the search does not end on a 2-node, so that we can just delete the node at the bottom.” On the way down it keeps the current node or its left child red, so the current 2-3 node always has a key to spare. To start, the root is colored red if both its links are black.

  • moveRedLeft(h): the search is about to go left into a 2-node. flipColors(h) brings h’s key down into one temporary 4-node with both children: a merge. If the right sibling is a 3-node, that would make four keys, so two rotations and a second flip turn the merge into a borrow.
  • moveRedRight(h): the mirror image, going right. Because red links lean left, its borrow needs one rotation.
  • Going right past a red left link, rotateRight first moves the red link onto the search path.
  • A key with two children is replaced by its successor, the minimum of its right subtree, which deleteMin removes by the same rules. The red-black chapter uses the predecessor; either works.

A 2-3 tree has no room for an early merge (§2), so the temporary 4-nodes the descent makes are allowed only on the search path, and fixUp, the insert’s three tests, splits them on the way back up. The delete repairs in both directions: two passes.

            h = move_red_left(h)
        h.left = delete(h.left, key)
    else:
        if is_red(h.left):
            h = rotate_right(h)        # red onto the path
        if key == h.key and h.right is None:
            return None
        if not is_red(h.right) and not is_red(h.right.left):
            h = move_red_right(h)
        if key == h.key:               # two children
            h.key = min_key(h.right)   # the successor
            h.right = delete_min(h.right)
        else:
            h.right = delete(h.right, key)
    return fix_up(h)                   # back up

def remove(self, key):                 # a RedBlackTree method
    if not self.contains(key):
        return                         # delete assumes the key is there
    if not is_red(self.root.left) and not is_red(self.root.right):
        self.root.red = True           # h or h.left red at the top
    self.root = delete(self.root, key)
    if self.root is not None:
        self.root.red = False
// h.left is a 2-node. Merge it with h's key and h.right into one temporary
// 4-node; if h.right is a 3-node, turn the merge into a borrow.
fn move_red_left(mut h: Box<RBNode>) -> Box<RBNode> {
    flip_colors(&mut h);
    if is_red(&h.right.as_ref().unwrap().left) {
        h.right = Some(rotate_right(h.right.take().unwrap()));
        h = rotate_left(h);
        flip_colors(&mut h);
    }
    h
}

// The mirror, for h.right. Red links lean left, so one rotation does.
fn move_red_right(mut h: Box<RBNode>) -> Box<RBNode> {
    flip_colors(&mut h);
    if is_red(&h.left.as_ref().unwrap().left) {
        h = rotate_right(h);
        flip_colors(&mut h);
    }
    h
}

fn delete_min(mut h: Box<RBNode>) -> Link {
    if h.left.is_none() { return None; }
    if !is_red(&h.left) && !is_red(&h.left.as_ref().unwrap().left) {
        h = move_red_left(h);
    }
    h.left = delete_min(h.left.take().unwrap());
    Some(fix_up(h))
}

fn min_key(h: &RBNode) -> i32 {
    let mut h = h;
    while let Some(l) = &h.left { h = l; }
    h.key
}

// key is in the tree. On the way down, h or h.left is red.
fn del(mut h: Box<RBNode>, key: i32) -> Link {
    if key < h.key {
        if !is_red(&h.left) && !is_red(&h.left.as_ref().unwrap().left) {
            h = move_red_left(h);
        }
        h.left = del(h.left.take().unwrap(), key);
    } else {
        // red onto the path
        if is_red(&h.left) { h = rotate_right(h); }
        if key == h.key && h.right.is_none() { return None; }
        if !is_red(&h.right) && !is_red(&h.right.as_ref().unwrap().left) {
            h = move_red_right(h);
        }
        if key == h.key {                                         // two children
            h.key = min_key(h.right.as_ref().unwrap());           // the successor
            h.right = delete_min(h.right.take().unwrap());
        } else {
            h.right = del(h.right.take().unwrap(), key);
        }
    }
    Some(fix_up(h))                                               // back up
}

impl RedBlackTree {
    fn remove(&mut self, key: i32) {
        if !self.contains(key) { return; }          // del assumes the key is there
        let mut root = self.root.take().unwrap();
        if !is_red(&root.left) && !is_red(&root.right) {
            root.red = true;                        // h or h.left red at the top
        }
        self.root = del(root, key);
        if let Some(r) = self.root.as_mut() { r.red = false; }
    }
}

7. Bottom-up or top-down

bottom-uptop-down
passesdown, then up as far as the repair climbsone (the LLRB versions: down and up)
splits and mergesonly where a node overflows or emptiesat every unsafe node on the path, needed or not
node sizesany: 2-3 trees, any order \(M\)\(b \ge 2a + 1\) (§2): 2-3-4 trees, even \(M\)
the pathkept for the climb back (stack, recursion or parent pointers)not needed
locks, concurrent updatesevery node below the last safe onea node and its child
cost per operation\(\Theta(\log n)\)\(\Theta(\log n)\)

Both keep every leaf at one depth, so both guarantee \(\Theta(\log n)\) height. The bottom-up red-black algorithms of CLRS do at most two rotations per insert and three per delete; the C++ and Java standard libraries (libstdc++’s std::map, Java’s TreeMap) use them, with parent pointers for the climb. A top-down algorithm can rotate, split or merge at every level. The top-down algorithms matter most where one pass and short-held locks pay for the extra restructuring: B-trees updated by many transactions at once.

8. Exercises (with solutions)

  1. Insert \(10, 20, 30, 40, 50, 60, 70, 80, 90\), in that order, into an empty 2-3-4 tree, first top-down, then bottom-up. Give each final tree and its height.
    solution Top-down: inserting \(40\) splits the full root \([10\,|\,20\,|\,30]\) first (\(20\) up), then \(40\) joins \([30]\). \(60\) splits the full leaf \([30\,|\,40\,|\,50]\) on the way down (\(40\) up), \(80\) splits \([50\,|\,60\,|\,70]\) (\(60\) up), and \(90\) meets the full root \([20\,|\,40\,|\,60]\) and splits it (\(40\) up into a new root) before joining \([70\,|\,80]\). Bottom-up, each leaf splits only when it overflows to four keys, and the root never does: \(40\) overflows \([10\,|\,20\,|\,30]\) (\(20\) up), \(60\) overflows \([30\,|\,40\,|\,50]\) (\(40\) up), \(80\) overflows \([50\,|\,60\,|\,70]\) (\(60\) up), and \(90\) fits. The top-down tree has height 2 and the bottom-up tree height 1: the top-down insert of \(90\) split the full root although the leaf it reached had room.
  2. Explain why a 2-3 tree cannot be updated top-down in one pass.
    solution A top-down insert must split a full node before it overflows, and a full 2-3 node has two keys: there is no middle key to send up that leaves two non-empty halves. A top-down delete must merge a 2-node before entering it, and a 2-node, its separator and a 2-node sibling make three keys, more than a 2-3 node holds. In the terms of §2, \(a = 1\) and \(b = 2 \lt 2a + 1\). The LLRB delete gets around this by letting temporary 4-nodes exist on the search path, which it must then split on the way back up: two passes.
  3. Give the minimum and maximum number of keys in a non-root node of a B-tree of order 7 and of order 8. Which of the two can use the top-down insert and delete?
    solution Order 7: between \(\lceil 7/2 \rceil - 1 = 3\) and \(6\) keys. A full node of 6 keys leaves 5 for its two halves, so one gets at most 2, below the minimum; two minimal siblings and their separator make 7 keys, one too many. Order 8: between 3 and 7 keys; a full node of 7 splits into 3, 1 up, 3, and a merge makes \(3 + 1 + 3 = 7\). Only order 8 works, as for every even order (\(t = 4\) in CLRS’s terms).
  4. Delete \(10\) top-down from the 2-3-4 tree with root \([40]\), children \([20]\) and \([60]\), and leaves \([10], [30], [50], [70]\). Name each repair. Does the bottom-up delete give the same tree?
    solution The root holds one key and both its children are 2-nodes, so they merge into the root \([20\,|\,40\,|\,60]\) before the descent: one level shorter. The search goes to \([10]\), a 2-node whose only sibling \([30]\) is also a 2-node, so \([10]\), the separator \(20\) and \([30]\) merge into \([10\,|\,20\,|\,30]\). Then \(10\) comes out of that leaf. The bottom-up delete reaches the same tree in the other order: the leaf empties, merges with \([30]\) and \(20\), which empties \([20]\); that node merges with \([60]\) and \(40\), which empties the root, and the root’s one child becomes the root.
  5. In the left-leaning insert, which line decides whether the tree is a 2-3 tree or a 2-3-4 tree, and why does its position decide it?
    solution The color flip, if (isRed(h->left) && isRed(h->right)) flipColors(h);. At the start of the function it splits a 4-node only when a later insert passes through it on the way down, so 4-nodes stay in the tree between inserts: a 2-3-4 tree. At the end, after the rotations, it splits a 4-node on the way up from the insert that created it, so no 4-node outlasts an insert: a 2-3 tree.
  6. In the red-leaf example of §6, the top-down delete of \(5\) changed the root from \(40\) to \(60\). Why, when \(5\) sat in a 3-node?
    solution The descent decides at each level from what it sees there. At \(40\) it is about to enter \(20\), a 2-node, and its rule forbids entering a 2-node, so moveRedLeft(40) runs before the search knows what lies below \(20\). The sibling \(80\) is in the 3-node \([60\,|\,80]\), so the move is a borrow: \(40\) comes down beside \(20\) and \(60\) goes up into the root. The fix-ups on the way back up do not undo a borrow; they only split temporary 4-nodes and lean red links left.
