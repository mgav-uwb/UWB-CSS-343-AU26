Kruskal’s Algorithm

Joseph Kruskal published his algorithm in 1956 in a three-page note whose title also mentions the traveling salesman problem. J. B. Kruskal, “On the Shortest Spanning Subtree of a Graph and the Traveling Salesman Problem,” Proc. AMS 7(1), 1956

Kruskal’s algorithm computes a minimum spanning tree as a sort followed by a near-linear pass. Its cycle test is exactly a union-find query, and every edge it accepts is licensed by the cut property of the Minimum Spanning Trees handout; this handout supplies the algorithm, the trace, and the analysis.

1. Cheapest edge first

Kruskal’s algorithm considers edges from cheapest to most expensive and accepts each one that connects two so-far-separate pieces, skipping any edge whose endpoints are already connected (it would close a cycle). After \(V-1\) acceptances the tree spans everything.

The one non-trivial step is the test “would this edge form a cycle?”, which is exactly “are its endpoints already in the same component?”, a union-find query. The Union-Find handout builds the structure that makes each check near-constant. 

// Kruskal: sort edges cheapest-first, then add each edge whose endpoints are not
// yet connected (union-find is the cycle check). Stop after V-1 edges.
struct Edge { int u, v; long w; };

vector<Edge> kruskal(int V, vector<Edge> edges) {
    sort(edges.begin(), edges.end(),
         [](const Edge& a, const Edge& b) { return a.w < b.w; });
    UF uf(V);                                    // from union-find.cpp
    vector<Edge> mst;
    for (const Edge& e : edges) {
        if (uf.connected(e.u, e.v)) continue;    // cycle: skip (cycle property)
        mst.push_back(e);                        // safe: take it (cut property)
        uf.unite(e.u, e.v);
        if ((int)mst.size() == V - 1) break;     // spanning tree complete
    }
    return mst;
}
// Kruskal: sort edges cheapest-first, then add each edge whose endpoints are not
// yet connected. Stop after V-1 edges.
class Edge {
    int u, v; long w;
    Edge(int u, int v, long w) { this.u = u; this.v = v; this.w = w; }
}

List<Edge> kruskal(int V, List<Edge> edges) {
    edges.sort((a, b) -> Long.compare(a.w, b.w));
    UF uf = new UF(V);                           // from union-find.java
    List<Edge> mst = new ArrayList<>();
    for (Edge e : edges) {
        if (uf.connected(e.u, e.v)) continue;    // cycle: skip (cycle property)
        mst.add(e);                              // safe: take it (cut property)
        uf.unite(e.u, e.v);
        if (mst.size() == V - 1) break;          // spanning tree complete
    }

# Kruskal: sort edges cheapest-first, then add each edge whose endpoints are not
# yet connected. Each edge is a tuple (w, u, v). Stop after V-1 edges.
def kruskal(V, edges):
    uf = UF(V)                               # from union-find.py
    mst = []
    for w, u, v in sorted(edges):            # sorts by weight (first tuple field)
        if uf.connected(u, v):               # cycle: skip (cycle property)
            continue
        mst.append((w, u, v))                # safe: take it (cut property)
        uf.unite(u, v)
        if len(mst) == V - 1:                # spanning tree complete
            break
    return mst
// Kruskal: sort edges cheapest-first, then add each edge whose endpoints are not
// yet connected. Each edge is (weight, u, v). Stop after V-1 edges.
fn kruskal(v: usize, mut edges: Vec<(i64, usize, usize)>)
    -> Vec<(i64, usize, usize)>
{
    edges.sort();                            // tuples sort by weight first
    let mut uf = UF::new(v);                 // from union-find.rs
    let mut mst = Vec::new();
    for (w, a, b) in edges {
        if uf.connected(a, b) { continue; }  // cycle: skip (cycle property)
        mst.push((w, a, b));                 // safe: take it (cut property)
        uf.unite(a, b);
        if mst.len() == v - 1 { break; }     // spanning tree complete
    }
    mst
}

Kruskal maintains a forest that merges: it starts with \(V\) one-vertex trees, and every accepted edge fuses two of them, so the graph goes from \(V\) components down to \(1\) over exactly \(V-1\) acceptances. That forest is the union-find structure: each unite a merge, each connected a “same tree?” question.

The cases the loop can take

The body of the loop is small, so the whole algorithm is four branches. Every one of them shows up in the traces of §2:

  1. Accept. connected(u,v) is false, so the edge joins two different components and is taken. The merge comes in three flavors, and the run below has all three: two singletons fuse (\(1\text{-}2\)), a singleton joins a bigger component (\(4\text{-}5\)), or two multi-vertex components fuse (\(1\text{-}3\)).
  2. Reject by cycle. connected(u,v) is true: the endpoints already share a component, so the edge would close a cycle and is skipped (\(0\text{-}3\) and \(2\text{-}3\) below).
  3. Early stop. The acceptance that brings the count to \(V-1\) breaks the loop, leaving the remaining, heavier, edges unexamined.
  4. Edges exhausted first. On a disconnected graph the loop runs out of edges before reaching \(V-1\) acceptances; what comes out is a minimum spanning forest, one minimum tree per connected component.

2. The run on the running graph

The trace below uses the running graph of the Minimum Spanning Trees handout: eight vertices, eleven edges with all-distinct weights, and a unique MST of total weight \(31\).

Example (the full run) On the running graph, edges sorted ascending (all weights distinct): The skips are the algorithm. When \(0\text{-}3\) is examined, \(0\) and \(3\) already share a component (through \(0\text{-}1\), \(1\text{-}2\), \(1\text{-}3\)), so it is rejected by the cycle property; likewise \(2\text{-}3\). The early stop at seven edges means the two heaviest edges (\(11\) and \(20\)) are never even looked at. Total weight \(31\).
(Note \(1\text{-}2\) and \(3\text{-}4\), the two lightest edges, are accepted first even though they lie in different parts of the graph; Kruskal grows several fragments at once, unlike Prim.)

The same run, seen as the union-find forest coalescing: the real state the algorithm maintains. Each accepted edge (green) is a connected(u,v) query that returned false, followed by a unite that merges two components; each skip (gray) is a query that returned true. The component count falls from \(8\) to \(1\) over exactly seven merges.

Example (the fourth branch: a disconnected graph) The run above ended by the break at \(V-1\) edges. The other exit is running out of edges, which happens exactly when the graph is disconnected. Take five vertices and four edges: The loop never breaks; it falls out the bottom. With \(3\) accepted edges for \(5\) vertices, the result is not a spanning tree but a minimum spanning forest: the MST of \(\{0,1,2\}\) (weight \(3\)) plus the MST of \(\{3,4\}\) (weight \(3\)), total \(6\). Since a disconnected graph has no spanning tree at all, that is the correct answer, and it comes out of the same loop with no extra code. The count of accepted edges reports the structure: \(V - |{\rm accepted}| = 5 - 3 = 2\) is the number of connected components.

3. Correctness and cost

Proposition (Kruskal is correct) Every edge Kruskal accepts is a minimum crossing edge of some cut, hence in an MST by the cut property; so Kruskal outputs an MST.
Proof. Suppose Kruskal accepts \(e = (u,v)\), and let \(C\) be \(u\)’s component at that moment. Since \(u\) and \(v\) were not yet connected, \(v \notin C\), so \(e\) crosses the cut \((C, \text{rest})\). We claim \(e\) is a lightest crossing edge. Any crossing edge \(f\) with \(w(f) < w(e)\) would have been processed earlier (edges come in weight order), and by then it was either accepted or skipped, and in both cases its two endpoints ended up in the same component. But a crossing edge has one endpoint in \(C\) and one outside, i.e. in different components, a contradiction. So no lighter crossing edge exists; \(e\) is a minimum crossing edge and, by the cut property, safe. Accepting \(V-1\) safe edges yields a spanning tree that is an MST. ∎
Proposition (Kruskal cost) Kruskal runs in \(O(E\log E) = O(E\log V)\) time.
Proof. Sorting the \(E\) edges costs \(O(E\log E)\). The single pass performs \(O(E)\) union-find operations, each near-constant, for \(O(E\,\alpha(V))\) total. The sort dominates, and since \(E \le V^2\), \(\log E \le \log V^2 = 2\log V\), so \(O(E\log E) = O(E\log V)\). ∎

Kruskal is, in one phrase, a sort followed by a near-linear pass. If the edges arrive already sorted (or the weights are small integers that admit radix sort), it approaches linear time, a reason to reach for it on sparse graphs and pre-sorted input.

4. Exercises (with solutions)

  1. In Kruskal on the running graph, the edge \(0\text{-}3\) (weight \(6\)) is skipped. Name the cycle it would have closed and the two MST properties that justify skipping it.
    solution By the time \(0\text{-}3\) is examined, \(0\) and \(3\) are already connected through \(0\text{-}1\), \(1\text{-}3\), so adding \(0\text{-}3\) would close the cycle \(0\text{-}1\text{-}3\text{-}0\). It is safe to skip by the cycle property: among the cycle’s edges (\(0\text{-}1{=}4\), \(1\text{-}3{=}5\), \(0\text{-}3{=}6\)) it is the heaviest, so it is in no MST. Equivalently, the union-find query connected(0,3) returns true, which is Kruskal’s implementation of the same test.
  2. You are handed the edges of a large sparse graph already sorted by weight, and told weights are small integers. Which MST algorithm do you choose, and what is its running time here?
    solution Kruskal. Its only expensive step is the sort, and the input is already sorted (or radix-sortable in \(O(E)\) for small integer weights), so the algorithm reduces to a single near-linear union-find pass: \(O(E\,\alpha(V)) \approx O(E)\). Prim would still pay the heap’s \(\log V\) factor per edge, so on pre-sorted sparse input Kruskal is the better fit.
  3. Run Kruskal on the four-cycle \(a\text{-}b,\ b\text{-}c,\ c\text{-}d,\ d\text{-}a\) with every weight equal to \(1\). Which edges are accepted, which are skipped, and does the answer depend on how the sort breaks the ties?
    solution The sort may present the four tied edges in any order. Whatever that order, the first three examined are all accepted: three edges of a four-cycle never close a cycle. At the third acceptance the count reaches \(V-1 = 3\) and the loop breaks, so the fourth edge is never even examined (had it been, it would have been skipped as a cycle). So the output edge set does depend on the tie-breaking, four different answers are possible, but every one has weight \(3\). That is the equality case of the cut property: with ties, a lightest crossing edge is in some MST, not necessarily in every one, and all MSTs still share the same total weight.
  4. Show that the number of edges Kruskal accepts is always \(V - c\), where \(c\) is the number of connected components of the input graph. What does this give you if you run Kruskal purely to count components?
    solution The union-find structure starts with \(V\) components. A skip changes nothing; an acceptance merges two components into one, dropping the count by exactly \(1\). So after \(k\) acceptances the count is \(V - k\). The loop stops in one of two ways. If it breaks at \(k = V-1\), the count is \(1\) and the graph is connected, so \(c = 1 = V - k\). If instead the edge list is exhausted, every edge has been examined, so two vertices share a union-find component exactly when the graph connects them; the union-find components are then the graph’s connected components and \(V - k = c\). Either way \(k = V - c\). Run with all weights equal and you have a connected-components algorithm: the accepted edges form a spanning forest, and \(V\) minus their number is the component count.
