Prim’s Algorithm

Data Structures & Algorithms. Algorithm (greedy).
Prim’s minimum-spanning-tree algorithm: grow one tree from a start vertex, always by the lightest edge leaving it, kept in a min-heap with lazy deletion of stale entries. A full trace on the running graph, the \(O(E\log V)\) analysis and the array variant for dense graphs, and the comparison with Dijkstra’s shortest-path tree, which the smallest triangle separates. With the demo and exercises.

Prim’s algorithm grows a minimum spanning tree outward from a start vertex, always adding the lightest edge that leaves the tree, found with the binary heap of Heaps, Priority Queues & Heapsort. Its correctness is immediate from the cut property of the Minimum Spanning Trees handout: the growing tree versus everything else is a cut, and Prim takes that cut’s minimum crossing edge by construction.

1. Growing one tree

Prim’s algorithm grows a single tree from a start vertex, repeatedly adding the lightest edge that leaves the tree to a vertex not yet in it. Unlike Kruskal, its correctness needs no separate argument: the growing tree versus everything else is a cut, and Prim takes that cut’s minimum crossing edge by construction: safe by the cut property at every step.

To find the lightest crossing edge quickly, keep the candidate crossing edges in a min-heap (the binary heap again). When a vertex joins the tree, push its edges to outside vertices; to grow, pop the cheapest edge and use it if it still leads outside, discarding stale entries whose far endpoint has since joined, the same lazy-deletion trick as Dijkstra. 

// Lazy Prim: grow one tree from s. A min-heap holds candidate crossing edges
// keyed by weight; pop the lightest, skip it if it now leads back into the tree,
// otherwise take it. adj[u] = u's weighted edges. Returns the MST total weight.
struct Edge { int to; long w; };

long prim(int V, vector<vector<Edge>>& adj, int s) {
    vector<bool> inTree(V, false);
    priority_queue<pair<long,int>, vector<pair<long,int>>,
                   greater<>> pq;                 // min-heap keyed by edge weight
    long total = 0; int picked = 0;
    inTree[s] = true;
    for (Edge e : adj[s]) pq.push({e.w, e.to});   // edges leaving the start
    while (picked < V - 1 && !pq.empty()) {
        auto [w, u] = pq.top(); pq.pop();
        if (inTree[u]) continue;                  // stale: both ends already in
        inTree[u] = true; total += w; picked++;   // take the crossing edge
        for (Edge e : adj[u])
            if (!inTree[e.to]) pq.push({e.w, e.to});
    }
    return total;
}
// Lazy Prim: grow one tree from s. Min-heap of {weight, vertex}; skip stale pops.
// adj.get(u) = u's weighted edges. Returns the MST total weight.
long prim(int V, List<List<Edge>> adj, int s) {
    boolean[] inTree = new boolean[V];
    PriorityQueue<long[]> pq =
        new PriorityQueue<>((a, b) -> Long.compare(a[0], b[0]));  // by weight
    long total = 0; int picked = 0;
    inTree[s] = true;
    for (Edge e : adj.get(s)) pq.add(new long[]{e.w, e.to});
    while (picked < V - 1 && !pq.isEmpty()) {
        long[] top = pq.poll();
        long w = top[0]; int u = (int) top[1];
        if (inTree[u]) continue;                  // stale: both ends already in
        inTree[u] = true; total += w; picked++;   // take the crossing edge
        for (Edge e : adj.get(u))
            if (!inTree[e.to]) pq.add(new long[]{e.w, e.to});
    }
    return total;
}
import heapq

# Lazy Prim: grow one tree from s. Min-heap of (weight, vertex); skip stale pops.
# adj[u] is a list of (v, w) pairs, as in the weighted graph type. Returns the
# MST total weight.
def prim(V, adj, s):
    in_tree = [False] * V
    total, picked = 0, 0
    in_tree[s] = True
    pq = [(w, v) for v, w in adj[s]]          # edges leaving the start
    heapq.heapify(pq)
    while picked < V - 1 and pq:
        w, u = heapq.heappop(pq)
        if in_tree[u]:                        # stale: both ends already in
            continue
        in_tree[u] = True                     # take the crossing edge
        total += w
        picked += 1
        for v, wt in adj[u]:
            if not in_tree[v]:
                heapq.heappush(pq, (wt, v))
    return total
use std::collections::BinaryHeap;
use std::cmp::Reverse;

// Lazy Prim from s. adj[u] holds (v, weight) pairs. Reverse turns the max-heap
// into a min-heap on weight; skip stale pops. Returns the MST total weight.
fn prim(n: usize, adj: &Vec<Vec<(usize, i64)>>, s: usize) -> i64 {
    let mut in_tree = vec![false; n];
    let mut pq = BinaryHeap::new();
    let (mut total, mut picked) = (0i64, 0usize);
    in_tree[s] = true;
    for &(v, w) in &adj[s] { pq.push(Reverse((w, v))); }
    while picked < n - 1 {
        let Some(Reverse((w, u))) = pq.pop() else { break };
        if in_tree[u] { continue; }           // stale: both ends already in
        in_tree[u] = true;                    // take the crossing edge
        total += w;
        picked += 1;
        for &(v, wt) in &adj[u] {
            if !in_tree[v] { pq.push(Reverse((wt, v))); }
        }
    }
    total
}

The cases the loop can take

The loop body is a pop and a test, so the algorithm has few branches. All of them appear in the traces of §2 and §3:

  1. Fresh pop: take the edge. The popped entry’s far endpoint \(u\) is still outside the tree, so the entry is the lightest crossing edge; \(u\) joins the tree, the weight is added to the total, and \(u\)’s edges to outside vertices are pushed.
  2. Stale pop: skip. \(u\) joined the tree after this entry was pushed, so the entry now points inside the tree and no longer crosses the cut. It is discarded and the loop pops again, with no other effect. This is lazy deletion: rather than hunt down and remove the obsolete entry when \(u\) joins, the algorithm lets it sit in the heap and recognizes it on the way out.
  3. A vertex’s key improves. An outside vertex can sit in the heap several times at several weights, one entry per tree vertex that can reach it. The smallest of them is popped first, so the vertex enters the tree by its cheapest crossing edge and the rest of its entries become stale. The array variant of §3 makes this explicit as an overwrite of key[v], which has its own two cases: the new crossing edge is cheaper than the recorded one (update) or it is not (leave it alone).
  4. Termination. The loop stops when \(V-1\) edges have been taken, typically leaving entries unpopped in the heap. If instead the heap empties first, the graph is disconnected: no spanning tree exists, and what has been built is the MST of the start vertex’s component.

2. The run on the running graph

The trace below uses the running graph of the Minimum Spanning Trees handout: eight vertices, eleven edges with all-distinct weights, and a unique MST of total weight \(31\).

Example (Prim from 0) 
  tree {0}          cheapest leaving edge  0-1 (4)  → add 1   total  4
  tree {0,1}        1-2 (1)                        → add 2   total  5
  tree {0,1,2}      1-3 (5)                        → add 3   total 10
  tree {0,1,2,3}    3-4 (2)                        → add 4   total 12
  tree +4           4-5 (3)                        → add 5   total 15
  tree +5           4-7 (7)                        → add 7   total 22
  tree +7           5-6 (9)                        → add 6   total 31
Prim adds vertices in the order \(1,2,3,4,5,7,6\) (different from Kruskal’s edge order, which took the two lightest edges \(1\text{-}2\) and \(3\text{-}4\) first), yet the final edge set and the total, \(31\), are identical. Watch the expensive edges \(0\text{-}3\,(6)\) and \(0\text{-}5\,(20)\) keep losing to cheaper options until the tree is complete and they are never used.

That summary hides the structure the algorithm actually runs on. Here is the same run at the level of the heap, one row per pop. An entry is written \((w, u)\): weight \(w\), far endpoint \(u\). The “from” column names the tree vertex that pushed the entry, which an implementation that must return the edges (rather than only the total) stores alongside.

Three entries for vertex \(3\) coexisted in the heap at once, \((5,3)\), \((6,3)\), \((8,3)\), one per tree vertex able to reach it. The heap pops the cheapest first, so \(3\) joins by \(1\text{-}3\,(5)\), and the other two are then stale by definition. That is how the lazy version does a key decrease: it never edits an entry, it just lets the ordering of the heap pick the smallest and throws the rest away on the way out. The price is a heap holding up to \(E\) entries instead of \(V\), which costs a constant factor in space and \(\log E \le 2\log V\) per operation in time.

3. Cost, and a queue-free variant

The lazy version pushes each edge onto the heap at most twice (once from each endpoint), and each heap operation is \(O(\log E)\), so Prim runs in \(O(E\log E) = O(E\log V)\) with a binary heap, the same bound as Kruskal.

A queue-free Prim, \(O(V^2)\) As with Dijkstra, dropping the heap gives an array version: keep key[v], the weight of \(v\)’s cheapest connection to the tree, and each of \(V\) rounds scans for the minimum-key outside vertex in \(O(V)\), then updates its neighbors. That is \(O(V^2)\), no heap, and on a dense graph (\(E = \Theta(V^2)\)) it matches or beats the heap version: the same dense-versus-sparse trade seen in the graph representations and Dijkstra handouts.
Example (the array variant, key by key) The array version keeps one number per outside vertex, key[v] = the weight of the cheapest edge now joining \(v\) to the tree, and \(\infty\) if no such edge exists yet. Each round takes the outside vertex of smallest key, then updates its outside neighbors. The same run from \(0\), with the keys of the vertices still outside the tree:

The edges used are \(0\text{-}1,\ 1\text{-}2,\ 1\text{-}3,\ 3\text{-}4,\ 4\text{-}5,\ 4\text{-}7,\ 5\text{-}6\), summing to \(4+1+5+2+3+7+9 = 31\): the same tree the heap version built. The two improvements at round \(5\) are the whole point of the array variant: where the lazy heap leaves \((20,5)\) and \((11,7)\) lying around to be discarded later, the array overwrites them on the spot, so it never holds more than \(V\) numbers. It pays for that with an \(O(V)\) scan per round instead of an \(O(\log V)\) pop.

4. Prim and Dijkstra

Prim grows a tree from a source with a priority queue, and so does Dijkstra (Dijkstra’s Algorithm); the two are the same skeleton, differing only in the key they minimize.

Prim (MST)Dijkstra (shortest paths)
priority-queue keyedge weight \(w\)distance \(\texttt{dist}[u] + w\)
minimizesthe single connecting edgethe total distance from the source
resultcheapest spanning treecheapest paths from the source

Because the keys differ, the trees can differ, and the smallest example proves it.

Example (MST \(\ne\) shortest-path tree) The triangle \(0\text{-}1\,(2)\), \(1\text{-}2\,(2)\), \(0\text{-}2\,(3)\): 
  MST:  keep 0-1 and 1-2      total weight 4   (drop the 3-edge)
  SPT from 0:  keep 0-1, 0-2  dist[1]=2, dist[2]=3

  in the MST, the route 0→2 costs 2+2 = 4, not the shortest 3;
  the SPT's total weight is 2+3 = 5, not the minimum 4.
The MST minimizes total edge weight (\(4 < 5\)); the shortest-path tree minimizes each vertex’s distance from the source (the direct \(0\text{-}2\) at \(3\) beats the MST’s \(4\)-cost detour). Neither tree does the other’s job. (On the eight-vertex running graph the two happen to coincide, which is exactly why this three-vertex triangle is the example to remember: it separates the concepts even when larger graphs do not.)

5. Exercises (with solutions)

  1. Run Prim from vertex \(6\) on the running graph. Do you get the same tree as Prim from \(0\)? Why should you expect that?
    solution Yes: the same seven edges, total \(31\). From \(6\), Prim first takes \(5\text{-}6\,(9)\), then \(4\text{-}5\,(3)\), \(3\text{-}4\,(2)\), then \(1\text{-}3\,(5)\), \(1\text{-}2\,(1)\), \(0\text{-}1\,(4)\), and \(4\text{-}7\,(7)\), assembling the identical edge set in a different order. Because all weights are distinct, the MST is unique (Minimum Spanning Trees), so every correct MST algorithm and every start vertex must produce that one tree.
  2. Give a weighted graph on which Prim’s MST and Dijkstra’s shortest-path tree from the same source are different, and state each tree.
    solution The triangle \(0\text{-}1\,(2)\), \(1\text{-}2\,(2)\), \(0\text{-}2\,(3)\). The MST is \(\{0\text{-}1, 1\text{-}2\}\) (total weight \(4\), dropping the weight-\(3\) edge). Dijkstra from \(0\) keeps \(\{0\text{-}1, 0\text{-}2\}\), reaching \(2\) by the direct edge at distance \(3\) rather than the \(4\)-cost path through \(1\). The two trees share \(0\text{-}1\) but differ on the second edge, because Prim minimizes the connecting edge’s weight while Dijkstra minimizes total distance from the source.
  3. The heap trace of §2 made nine pops on a graph with \(11\) edges: seven takes, two stale skips, two entries never popped. Bound the number of entries the heap can ever hold and the number of pops a run can make, and say what each of the two stale pops cost.
    solution An entry for edge \(u\text{-}v\) is pushed only when one endpoint joins the tree while the other is still outside. Once either endpoint is in the tree, the guard if (!inTree[e.to]) blocks a second push when the other joins, so this code pushes each edge at most once: at most \(E\) entries pushed, hence at most \(E\) pops. (Without that guard the bound is two pushes per edge, still \(O(E)\).) Exactly \(V-1\) pops are takes on a connected graph, so at most \(E - (V-1)\) are stale, here at most \(11 - 7 = 4\) and in fact \(2\). A stale pop costs one \(O(\log E)\) pop plus one array test, and nothing else: no push, no change to the tree or the total. Since \(\log E \le 2 \log V\), the run is \(O(E \log V)\) whether or not stale entries pile up.
  4. Run lazy Prim from \(0\) on the graph \(V = 5\) with edges \(0\text{-}1\,(1)\), \(1\text{-}2\,(2)\), \(0\text{-}2\,(4)\), \(3\text{-}4\,(3)\). Which loop exit fires, and what does the algorithm return?
    solution The heap starts as \((1,1), (4,2)\). Pop \((1,1)\): take \(0\text{-}1\), total \(1\), push \((2,2)\). Pop \((2,2)\): take \(1\text{-}2\), total \(3\), nothing to push. Pop \((4,2)\): stale, \(2\) is already in the tree. The heap is now empty with only \(2\) edges taken, short of \(V - 1 = 4\), so the loop exits on pq.empty() rather than on the edge count. What comes back is the MST of \(0\)’s component \(\{0,1,2\}\), weight \(3\); vertices \(3\) and \(4\) are never reached, because Prim can only grow across edges and no edge leaves the component. This is the one place Prim and Kruskal genuinely differ in output: Kruskal sees every edge and returns a spanning forest of the whole graph, while Prim stays inside the component it started in.
