Computer Systems Primer

“We are therefore forced to recognize the possibility of constructing a hierarchy of memories, each of which has greater capacity than the preceding but which is less quickly accessible.” Arthur Burks, Herman Goldstine and John von Neumann, Preliminary Discussion of the Logical Design of an Electronic Computing Instrument, 1946

The analysis chapters of this book count operations and treat every operation as costing the same. That model is the right first approximation: it predicts orders of growth correctly and it is the language every later chapter uses. It also leaves out the single largest effect on the running time of real data structures: where the data is when the processor needs it. Two loops that perform exactly the same additions can differ in speed by a factor of fifty. This chapter explains why, and introduces the operating system and compiler behaviour that also shows up in every timing experiment.

The measurements Every number labelled measured in this chapter comes from three short C++ programs (latency.cpp, locality.cpp, optimize.cpp) run on a 2019 laptop: an Intel Core i9-9980HK at 2.4 GHz with a 32 KiB level-1 data cache and a 256 KiB level-2 cache per core, a 16 MiB level-3 cache shared by its 8 cores, and 32 GiB of main memory. Other machines give different numbers with the same shape. (KiB, MiB and GiB are \(2^{10}\), \(2^{20}\) and \(2^{30}\) bytes.)

1. The processor

A compiled program is a sequence of machine instructions: load a value from memory into a register, add two registers, compare, jump to another instruction, store a register to memory. A register is one of a few dozen storage slots inside the processor itself; arithmetic happens only on registers. The processor steps through instructions to the beat of a clock; at 2.4 GHz one clock cycle lasts \(1 / (2.4 \times 10^9)\) s, about 0.42 ns.

A modern processor completes several simple instructions per cycle. It does so by working on many instructions at once: while one is being decoded, another is executing and a third is writing its result (pipelining), and independent instructions run side by side. It also guesses which way each branch will go and runs ahead along the guess (branch prediction), discarding the work if the guess was wrong. All of this depends on the next instructions having their inputs ready. An instruction that waits for a value from main memory stalls everything that depends on it, and as the next section shows, that wait can last hundreds of cycles.

A core is one complete processor; the laptop above has 8, each able to run its own sequence of instructions. A single-threaded program, which is every program in this book, uses one core at a time.

2. The memory hierarchy

No single memory technology is large, fast and cheap at once. Computers therefore use a hierarchy: a small, fast memory close to the processor, backed by successively larger, slower ones. Data the program is using right now is kept near the top; everything else lives lower down and is brought up when needed.

The processor-memory gap

These ratios have not always been so large. In the early 1980s a main-memory access took roughly as long as an instruction, and counting instructions was a good model of running time. Since then processors have become faster by a factor of thousands, mostly through higher clock rates and many instructions per cycle, while the time to fetch one value from DRAM has improved by perhaps a factor of ten. On the laptop above, one main-memory read costs about \(100 / 0.42 \approx 240\) clock cycles, time in which the processor could have completed several hundred instructions. Caches exist to hide this gap, and they succeed only when the program’s accesses cooperate.

3. Caches and locality

Definition (cache, cache line) A cache keeps copies of recently used parts of main memory. Memory moves between DRAM and the caches in fixed blocks called cache lines, 64 bytes on current processors. A read that finds its line in a cache is a hit; one that does not is a miss, and fetches the whole line from the level below.

Because a miss brings in 64 bytes, not just the 4 bytes of one int, the next 15 ints of an array arrive for free. Caches work well for programs that have locality:

Definition (locality) Spatial locality: after accessing an address, the program soon accesses nearby addresses (scanning an array). Temporal locality: after accessing an address, the program soon accesses the same address again (a loop counter, the top levels of a tree).

The processor also watches the pattern of misses. When it sees addresses increasing by a fixed step, it fetches the following lines before they are requested (prefetching), so a sequential scan rarely waits for memory at all. A sequence of addresses with no pattern defeats both the cache line and the prefetcher.

Same additions, different order

locality.cpp runs two experiments. In each, both versions perform exactly the same additions on exactly the same values; only the order of the memory accesses differs. 

// m is an 8192 x 8192 matrix of int (256 MiB), stored row by row
for (r = 0; r < n; r++) for (c = 0; c < n; c++) sum += m[r * n + c];   // by rows
for (c = 0; c < n; c++) for (r = 0; r < n; r++) sum += m[r * n + c];   // by columns

By rows, consecutive reads are adjacent in memory: one miss per 16 ints, and the prefetcher hides most of those. By columns, consecutive reads are \(8192 \times 4 = 32{,}768\) bytes apart, so every read touches a different line, and by the time the loop returns to a line for the next column the line has long since been evicted. The second experiment walks a linked list of 16,777,216 nodes twice: once with the nodes laid out in memory in list order, and once with the same nodes linked in a shuffled order.

The scattered list costs about 110 ns per node, the main-memory latency of section 2: each p = p->next is a dependent read of an unpredictable address. A list built by inserting nodes in random order, or a tree after many insertions and deletions, has exactly this layout.

What this means for data structures

None of this changes an order of growth. Both matrix loops are \(\Theta(n^2)\) and both list walks are \(\Theta(N)\). It changes the constant factor, by a factor of forty or fifty here, and that is enough to reverse comparisons between algorithms of the same order:

4. Counting memory transfers: the external-memory model

When transfers between levels dominate the running time, the right cost model counts transfers rather than operations. The external-memory model (Aggarwal and Vitter, 1988) was stated for a disk below main memory, and it applies equally to main memory below a cache.

Definition (external-memory model) A fast memory of \(M\) items sits above an unbounded slow memory. Data moves between them in blocks of \(B\) consecutive items. Computation on items already in fast memory is free; the cost of an algorithm is the number of block transfers.

Two results show the model at work. Scanning \(N\) consecutive items costs \(\lceil N / B \rceil\) transfers, not \(N\). Searching a sorted array by binary search costs about \(\log_2(N/B)\) transfers, because each probe lands in a new block until the remaining range fits in one block. A search tree whose nodes each hold about \(B\) keys has height about \(\log_B N\), and a search reads one block per level:

\[ \log_B N = \frac{\log_2 N}{\log_2 B}. \]

For \(N = 10^9\) keys and blocks of \(B = 1000\) keys, binary search needs about \(\log_2(10^6) \approx 20\) transfers while the B-tree needs \(\log_{1000} 10^9 = 3\). When a transfer is a disk read of several milliseconds, that is the difference between a tenth of a second and about fifteen milliseconds, and it is why databases and file systems are built on B-trees. Algorithms designed to perform well for every \(B\) and \(M\) at once, without knowing them, are called cache-oblivious.

The external-memory model does not replace the operation-counting model of Analysis of Algorithms: Time; it is a second cost model, chosen when memory transfers are the expensive operation. Choosing what to count is part of every analysis.

5. The operating system

The operating system (OS) is the program that manages the hardware on behalf of every other program: it decides which program runs on which core, gives each program its memory, and performs input and output (I/O) for them.

Definition (process) A process is a running program: its machine code, its memory, its open files, and the current state of its registers. Each process has its own address space, the range of memory addresses it can use, and cannot read or write another process’s memory.

Within its address space, a C++ process’s memory is laid out in regions with different lifetimes:

The stack has a fixed maximum size, commonly 8 MiB for the main thread on Linux and macOS (the shell command ulimit -s shows it in KiB). A recursion that goes too deep exhausts it, and the process is stopped with a stack overflow, usually reported as a segmentation fault. A recursive function with a 100-byte frame can recurse about 80,000 levels deep; a recursion on a linked list of a million nodes cannot. The Recursion chapter shows how to convert such recursions into loops.

Multitasking

A laptop runs hundreds of processes on 8 cores. The OS scheduler gives each runnable process a time slice, typically a few milliseconds, then stops it and runs another. Switching between processes, a context switch, saves one process’s registers and restores another’s. It costs microseconds directly, and more indirectly, because the incoming process finds the caches full of the outgoing one’s data. Switching happens often enough that every program appears to run continuously.

System calls and I/O

A process cannot touch a disk, a network or the screen itself. It asks the OS through a system call, which transfers control into the OS and back, at a cost of hundreds of nanoseconds or more before any data moves. This is why output is buffered: cout collects characters in memory and passes them to the OS in large pieces. endl writes a newline and forces the buffer out, so when output goes to a file or another program, a loop that prints a million lines with endl makes about a million system calls where "\n" makes a few hundred. (Output to a terminal is flushed at every newline either way.)

6. Virtual memory, paging and swap

The addresses a program uses are not the physical addresses of memory chips. They are virtual addresses, translated by the hardware on every access.

Definition (virtual memory, page) Virtual memory divides each address space into fixed-size pages, 4 KiB on most systems, and keeps a page table per process mapping each virtual page to a physical page frame or marking it as not present. A small cache of recent translations, the TLB (translation lookaside buffer), makes most translations free.

Translation is what gives each process its own address space: the same virtual address in two processes maps to different physical memory. It also lets the OS hand out memory lazily. When a program allocates a large array, the OS only records that those pages may be used; it supplies a physical page the first time each page is touched. That first touch is a page fault: the hardware finds no translation, the OS allocates and zeroes a page, updates the table, and resumes the program. A program that allocates 256 MiB and then fills it pays 65,536 such faults, one per page, on the first pass and none afterwards. This is one reason a timing experiment should not time the first pass over freshly allocated memory.

An array much larger than the TLB covers (the TLB holds on the order of a thousand translations, a few MiB of 4 KiB pages) also pays a translation miss on random accesses. That is the early rise in the latency figure of section 2, before the L3 cache is full.

Swap and thrashing

When the processes running together ask for more memory than the machine has, the OS moves pages that have not been used recently out to a reserved area of the disk, the swap space, and marks them not present. Touching a swapped-out page causes a page fault that reads it back from disk, at SSD or disk latency: tens of microseconds to milliseconds, thousands to tens of thousands of times a main-memory access. A program whose working set (the memory it uses repeatedly) fits in physical memory hardly notices swap. One whose working set does not fit spends nearly all its time waiting for pages, a condition called thrashing, in which it can run hundreds of times slower than its operation count suggests. For data structures this is the space analysis of Space Complexity with a cliff in it: a structure 10% too large for memory is not 10% slower. What the cliff does to an order of growth, and to a doubling experiment that crosses it, is worked out in Algorithms on Real Machines.

7. The compiler

g++ prog.cpp -o prog runs four programs in turn:

  1. the preprocessor pastes in every #included file and expands macros, producing one large source file;
  2. the compiler proper parses that file, checks types, optimizes, and generates assembly code for the target processor;
  3. the assembler turns assembly into an object file of machine code with unresolved references to functions defined elsewhere;
  4. the linker combines object files and libraries into one executable, resolving each reference to the function’s address.

The division explains two kinds of error message. A compile error names a line of your source. A linker error, such as undefined reference to 'IntList::~IntList()', means every file compiled but some function was declared (usually in a header) and never defined, or its file was not given to the linker.

Optimization

By default (-O0) the compiler translates each statement directly, keeping every variable in memory, so that a debugger can show them. With -O2 it keeps values in registers, moves computations out of loops, replaces calls to small functions by their bodies (inlining), and removes work whose result is never used. The program’s output is the same; its running time is not.

The last row is not a fast loop: at -O2 the compiler proved that the loop has no effect on the program’s output and deleted it. Any timing experiment must use what it computes (print it, return it, add it to something printed), or it may be timing nothing.

Undefined behaviour

The C++ standard leaves some operations undefined: reading outside an array, using an object after its lifetime, reading an uninitialized variable, overflowing a signed integer. The optimizer is allowed to assume they never happen. A loop that relies on signed overflow to terminate, or a check placed after a null dereference, may be removed entirely at -O2, so a program with undefined behaviour can work at -O0 and fail at -O2, or work on one compiler and fail on another. The tools of C++ for Data Structures, section 8 (warnings, sanitizers, Valgrind) find most of these errors.

Different machines, different compilers

“It works on my laptop” often means it works with that compiler and that library. macOS installs Apple’s clang under the name g++, with a different standard library from Linux’s GNU g++. The two give some library types different sizes (sizeof(std::string) is 24 bytes with Apple’s library and 32 with GNU’s) and implement the random number distributions differently, so the same seed can give different sequences. Code meant to run elsewhere should be compiled and tested there.

8. Consequences for measuring programs

The doubling experiments of Analysis of Algorithms: Time measure running time; everything above affects the measurement.

  • Count operations when you can. An operation count is exact and the same on every machine; a time is neither.
  • Compile with optimization (-O2), since that is how programs are run, and use every result, so that the optimizer cannot delete the work.
  • Time enough work. A run of a few milliseconds is dominated by timer resolution, page faults on first touch and cache warm-up. Repeat short runs and report the median.
  • Expect noise. Other processes share the cores and the caches, and the processor changes its clock rate with temperature and load. Ratios between runs on the same machine are more reliable than absolute times.
  • Watch for a change of level. A doubling ratio that jumps when the data outgrows a cache, or memory, is the hierarchy, not the algorithm.

9. Exercises (with solutions)

  1. A cache line is 64 bytes. A loop reads every element of an array of \(10^6\) doubles in order. About how many cache misses occur, ignoring prefetching? How many if it reads every 8th element?
    solution A line holds \(64 / 8 = 8\) doubles, so the full scan touches \(10^6 / 8 = 125{,}000\) lines: about 125,000 misses. Reading every 8th element touches the same 125,000 lines, one element from each, so it takes about as many misses while doing one eighth of the additions. Its running time is close to that of the full scan.
  2. Explain why summing a row-major matrix by columns is slow, and give a loop order for computing the sum of each column that is fast.
    solution Down a column, consecutive elements are a full row apart in memory, so each read is in a different cache line, and the line is evicted before the next column returns to it. To compute column sums quickly, keep an array colSum[c] and loop by rows: for r: for c: colSum[c] += m[r*n + c];. The matrix is now read sequentially, and the \(n\) partial sums stay in cache.
  3. In the external-memory model with \(B = 512\) items per block, how many transfers does a scan of \(N = 2^{30}\) items cost? A binary search? A search in a tree with 512 keys per node?
    solution Scan: \(2^{30} / 2^9 = 2^{21} = 2{,}097{,}152\) transfers. Binary search: about \(\log_2(N/B) = 30 - 9 = 21\) transfers. Tree with fan-out 512: height about \(\log_{512} 2^{30} = 30/9 \approx 3.3\), so 4 transfers.
  4. A recursive function on a linked list uses a 64-byte stack frame per call. With an 8 MiB stack, what is the longest list it can process?
    solution \(8 \times 2^{20} / 64 = 131{,}072\) nodes, slightly fewer in practice because main and the runtime use part of the stack. A list of a million nodes overflows the stack; an iterative version uses constant stack space.
  5. A student times for (i = 0; i < n; i++) x += i; at -O2, never uses x, and finds the time does not grow with n. What happened?
    solution The loop has no effect on the program’s output, so the optimizer removed it. The measured time is the cost of reading the clock twice. Printing x after the timing restores the loop.
  6. A program allocates a 2 GiB table, fills it once, then performs random lookups. On a machine with 4 GiB of memory and other programs running it is extremely slow; on a machine with 32 GiB it is fast. Explain.
    solution On the small machine the table and the other programs do not all fit in physical memory, so the OS swaps pages of the table to disk, and random lookups keep faulting them back in at disk latency, thousands of times slower than a memory access: thrashing. On the large machine the whole table stays resident and each lookup costs one main-memory access.
  7. Why can printing a million lines with endl be much slower than with "\n"?
    solution endl flushes the output buffer after every line, and each flush is a system call. "\n" leaves the characters in the buffer, which is passed to the OS only when it fills, so a million lines become a few hundred system calls. (This holds when output goes to a file or a pipe; a terminal is flushed at every newline.)
  8. Linear probing and separate chaining both search a hash table in expected constant time. Using sections 3 and 4, explain why linear probing is usually faster on modern hardware at moderate load.
    solution A linear-probing search reads a run of adjacent slots in one array, usually within one or two cache lines. A chaining search reads the bucket array and then follows a pointer to each node of the chain, and nodes allocated separately are scattered in memory, so each step can be a cache miss. In the external-memory view, probing costs about one block transfer per search and chaining about one per chain node.
