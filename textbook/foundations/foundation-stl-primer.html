STL Primer

Alexander Stepanov and Meng Lee wrote the Standard Template Library at Hewlett-Packard; in July 1994 the C++ standards committee voted it into the draft standard. B. Stroustrup, “Evolving a language in and for the real world: C++ 1991–2006,” HOPL III, 2007

Most chapters of this text build a data structure from nodes and arrays, and then use the standard library’s version of it in later code: Dijkstra’s algorithm takes its heap from std::priority_queue, breadth-first search its queue from std::queue, Huffman coding its code table from std::map. This primer covers each library structure and algorithm that the chapters and lecture slides use: its header, what it is underneath, the calls the code makes and what they cost, and the mistake it invites. Each section ends with the chapters whose code uses it.

Every code block below is copied from code/stl/primer.cpp, which checks every value a comment states. The code follows the conventions of this text: using namespace std;, named functions and comparison structs rather than lambdas, and declared types rather than auto. The mechanisms underneath (templates, references, the heap) are in C++ for Data Structures.

1. Ranges and iterators

A library algorithm does not take a container; it takes a range: two iterators, one at the first element and one one past the last. An iterator is a position in a container; for a vector it behaves like a pointer into the array. The range \([\text{first}, \text{last})\) is half-open, so v.begin() and v.end() together name every element, v.end() - v.begin() is the size, and an empty range has first == last. end() is never dereferenced: there is no element there. 

vector<int> v = {7, 3, 9, 4, 1};
sort(v.begin(), v.begin() + 3);   // sorts v[0..3): 3 7 9 4 1

The range-based for loop walks the same range, from begin() up to but not including end(): 

for (const int& x : v) sum += x;  // visits begin() up to, not including, end()
Pitfall An iterator can be invalidated by a change to its container. A push_back that makes a vector reallocate moves every element, and every iterator, pointer and reference into the old array then dangles. Take iterators after the container stops growing.

2. vector and string

vector<T> (<vector>) is a dynamic array: the elements sit contiguously in one heap block, and when the block is full push_back allocates one twice as large and moves the elements over. The occasional move is paid for by the cheap appends before it, so an append costs \(O(1)\) amortized; the Amortized Analysis chapter proves it. A vector keeps its size (elements in use) apart from its capacity (elements allocated). 

vector<int> dist;
dist.assign(5, INT_MAX);          // five elements, each INT_MAX
dist.push_back(0);                // amortized O(1): size 6
dist.resize(3);                   // keeps the first three
int last = dist.back();           // INT_MAX

string (<string>) is a vector of char with text operations added. Appending is amortized \(O(1)\) per character; substr and + build a new string, so they cost the length of the result. 

string path = "10";
path += "1";                      // "101": amortized O(1) per character
string tail = path.substr(1);     // "01": a copy, O(length)
Pitfall v[i] does not check \(i\): an index past the end reads or writes whatever memory is there, which is undefined behaviour, and the program may run on with corrupted data. Use at while debugging, or compile with the address sanitizer.

Every chapter’s code uses vector; assign or resize appear in: 0/1 Knapsack, Dijkstra’s Algorithm, Edit Distance, Hashing, Longest Common Subsequence, Matrix-Chain Multiplication, Maximum Flow & Minimum Cut, Regular Expressions & Automata, Rod Cutting.

3. pair

pair<A, B> (<utility>) holds two values named first and second. Pairs compare lexicographically: by first, and by second when the firsts are equal. That order is why a heap of (distance, vertex) pairs pops the nearest vertex first. 

pair<int, int> e = {4, 2};        // (weight, vertex)
int w = e.first, u = e.second;    // 4, 2
bool before = pair<int, int>{4, 2} < pair<int, int>{4, 7};   // true
Pitfall first and second say nothing about what they hold, and a pair of two ints accepts them in either order. The code in this text prefers a small struct with named fields, such as struct Entry { long dist; int vertex; }; in Dijkstra’s Algorithm, and writes its order out in a comparison struct.

Used in: Context-Free Grammars & Parsing, Interval Scheduling, P, NP & Reductions, Space Complexity, Treaps, Tries & Ternary Search Trees, Turing Machines & Computability.

4. stack

stack<T> (<stack>) is last in, first out: it adds and removes at one end, the top. It is an adapter: a thin wrapper that exposes only the top of another container (a deque by default). The call stack of a recursion is the same structure, which is why an explicit stack turns a recursion into a loop. 

stack<int> st;
st.push(1); st.push(2); st.push(3);
int t = st.top();                 // 3: the last one pushed
st.pop();                         // removes the 3; returns nothing
calldoescost
push(x)put \(x\) on top\(O(1)\) amortized
top()the top element, left in place\(O(1)\)
pop()remove the top element\(O(1)\)
size(), empty()how many; none?\(O(1)\)
Pitfall pop() returns nothing: read top() first, then pop. top() and pop() on an empty stack are undefined behaviour, so a loop tests !st.empty() before each one.

Used in: Depth-First Search, Recursion & Induction.

5. queue

queue<T> (<queue>) is first in, first out: push adds at the back, front and pop work at the front. Like stack it is an adapter over a deque. Breadth-first search keeps its frontier in one: the vertices come out in the order they were found, which is the order of their distance from the start. 

queue<int> q;
q.push(1); q.push(2); q.push(3);
int f = q.front();                // 1: the first one pushed
q.pop();                          // removes the 1; returns nothing
calldoescost
push(x)add \(x\) at the back\(O(1)\) amortized
front(), back()the first and the last element, left in place\(O(1)\)
pop()remove the front element\(O(1)\)
size(), empty()how many; none?\(O(1)\)
Pitfall As with stack, pop() returns nothing and front() on an empty queue is undefined behaviour. A queue cannot be searched or indexed; a search that also needs “is \(v\) waiting?” keeps a separate visited array.

Used in: Breadth-First Search, Maximum Flow & Minimum Cut, Space Complexity, Topological Sort.

6. list

list<T> (<list>) is a doubly linked list: each element is a separate heap node with links to its neighbours. Inserting or removing at a known position is \(O(1)\), and it never moves the other elements, so iterators to them stay valid. There is no indexing: reaching the \(i\)-th element walks \(i\) links. 

list<int> chain = {4, 9};
chain.push_front(1);              // 1 4 9: O(1)
chain.remove(4);                  // 1 9: O(n) to find, O(1) to unlink
calldoescost
push_front(x), push_back(x)add at either end\(O(1)\)
insert(it, x), erase(it)add before, or remove at, an iterator\(O(1)\)
remove(x)remove every element equal to \(x\)\(O(n)\)
front(), back(), size()the ends; how many\(O(1)\)
Pitfall The nodes are scattered in memory, so walking a list misses the cache far more often than walking a vector, and at the same order of growth the vector is usually several times faster. A list pays off only when elements are inserted and removed in the middle while iterators to the others must stay valid. It also cannot be passed to sort; it has its own member sort().

Used in: Hashing.

7. priority_queue

priority_queue<T, Container, Compare> (<queue>) is a binary heap stored in a vector, the structure built in Heaps & Priority Queues. top() is the element that is largest under the comparison, which by default is <, so the plain form is a max-heap. To pop the smallest first, pass a comparison that answers “is a greater than b?”: 

struct Greater {                      // reverses the comparison
    bool operator()(int a, int b) const { return a > b; }
};
priority_queue<int> maxPQ;                          // the largest on top
for (int x : {5, 1, 8, 3, 9, 2}) maxPQ.push(x);
int top = maxPQ.top();                              // 9
priority_queue<int, vector<int>, Greater> minPQ;    // the smallest on top
for (int x : {5, 1, 8, 3, 9, 2}) minPQ.push(x);
int low = minPQ.top();                              // 1

The three template arguments are the element type, the container the heap lives in (always vector<T> here), and the comparison. The library’s own greater<int> (<functional>) does what Greater does; this text writes the comparison out so that its rule, including how ties are broken, is on the page. The heaps of Dijkstra, Prim and Huffman are written this way.

calldoescost
push(x)insert \(x\): append, then swim it up\(O(\log n)\)
top()the top element, left in place\(O(1)\)
pop()remove the top: move the last element to the root, then sink it\(O(\log n)\)
size(), empty()how many; none?\(O(1)\)
Pitfall The direction trips everyone once: the comparison names what goes below, so a > b produces a min-heap. There is no decrease-key and no way to look inside, so an algorithm that would lower a key (Dijkstra, Prim) pushes a new entry instead and skips the stale one when it surfaces. top() and pop() on an empty queue are undefined behaviour.

Used in: Dijkstra’s Algorithm, Heaps & Priority Queues, Huffman Coding, Interval Scheduling, Prim’s Algorithm.

8. map and set

map<K, V> (<map>) stores key → value pairs sorted by key, in a balanced search tree; in the common libraries it is the red-black tree of Red-Black Trees. Every lookup, insertion and removal is \(O(\log n)\), and a loop over a map visits the keys in increasing order. set<K> (<set>) is the same tree with keys and no values. The key type needs <. 

map<char, string> code;
code['f'] = "0";                  // insert
code['a'] = "1100";
bool has = code.count('z') == 1;  // false
string w = code['z'];             // "", and 'z' is now a key
for (const pair<const char, string>& kv : code)
    keys += kv.first;             // "afz": sorted by key
bool found = code.find('q') != code.end();   // false, and nothing inserted
set<int> seen = {5, 1, 8};
seen.insert(1);                   // already there: no change
bool in = seen.count(8) == 1;     // true
calldoescost
m[k] = vinsert \(k\), or overwrite its value\(O(\log n)\)
m[k]\(k\)’s value; a missing \(k\) is inserted with a default value\(O(\log n)\)
m.count(k)1 if \(k\) is a key, else 0\(O(\log n)\)
m.find(k)an iterator to \(k\), or m.end(); inserts nothing\(O(\log n)\)
m.erase(k)remove \(k\)\(O(\log n)\)
s.insert(k), s.count(k)add \(k\) (no effect if present); is \(k\) in?\(O(\log n)\)
m.lower_bound(k)the first key \(\ge k\): an ordered query a hash table cannot answer\(O(\log n)\)
Pitfall Reading m[k] never fails: a missing key is inserted with a default value ("", 0, nullptr) and that value is returned. A test written as if (m[k] == ...) therefore grows the map. To ask whether a key is present, use count or find; adaptive Huffman’s update asks count before it reads leafOf[s] for exactly this reason.

Used in: Context-Free Grammars & Parsing, Huffman Coding, Regular Expressions & Automata, The Dynamic Programming Method, Tries & Ternary Search Trees, Turing Machines & Computability.

9. unordered_map and unordered_set

unordered_map<K, V> (<unordered_map>) has the same calls as map but is a hash table with separate chaining, the structure of Hashing. A call costs \(O(1)\) on average and \(O(n)\) in the worst case, and the keys come out of a loop in no particular order. When the load factor (keys per bucket) passes its maximum, 1 by default, the table about doubles its buckets and rehashes. unordered_set<K> is the set version. The key type needs std::hash and ==. 

unordered_map<string, int> index;
index["the"] = 0;                 // average O(1)
index["cat"] = 1;
bool has = index.count("dog") == 1;   // false
unordered_set<int> visited = {3, 7};
visited.insert(3);                // already there: no change
needusewhy
lookups only, as fast as possibleunordered_map\(O(1)\) average
keys in order, ranges, smallest key \(\ge k\)mapsorted; \(O(\log n)\) guaranteed
a bound that holds on every inputmapa hash table’s worst case is \(O(n)\)
Pitfall The iteration order is unspecified and changes when the table grows, so output that loops over an unordered_map can differ between runs, libraries and input sizes. Growing also invalidates every iterator. The [] trap of map applies here too.

Used in: Hashing, LZW Compression.

10. hash

hash<T> (<functional>) is the function object an unordered_map uses to turn a key into a size_t. Construct one and call it; a table of \(M\) slots then reduces the result with % M: 

size_t h = hash<string>()("cat");     // the value depends on the library
size_t bucket = h % 13;               // one of 13 slots
Pitfall The standard fixes only that equal keys hash equally within one run. The values themselves differ between libraries (and for integers are often the integer itself), so a program must not print them or store them as data. std::hash is not a cryptographic hash, and an adversary who knows it can choose keys that collide.

Used in: Hashing.

11. sort and stable_sort

sort(first, last) (<algorithm>) sorts a range in place with <, in \(O(n \log n)\) comparisons on every input. It is introsort: quicksort that switches to heapsort when the recursion grows too deep, as described in Quicksort. A third argument replaces <: a function that answers “does a go before b?” 

struct Edge { int u, v, w; };

bool lighter(const Edge& a, const Edge& b) {
    return a.w < b.w;                 // strict: false when the weights tie
}
vector<Edge> edges = {{0, 1, 4}, {1, 2, 1}, {0, 2, 4}};
stable_sort(edges.begin(), edges.end(), lighter);   // 1-2, then 0-1, 0-2

sort may put equal elements in any order: the two weight-4 edges above can come out either way round. stable_sort keeps equal elements in their input order, which is what makes radix-style multi-pass sorting and “sort by finish, ties by index” work; it is a mergesort, \(O(n \log n)\) with a buffer of up to \(n\) elements (\(O(n \log^2 n)\) when no buffer can be allocated).

Pitfall The comparison must be strict: it answers false for equal elements. A comparison written with <= breaks the assumptions sort relies on, and the result is undefined behaviour, which in practice can be a crash rather than a wrong order. sort needs random-access iterators, so it works on vector, string and arrays but not on list.

Used in: Analysis of Algorithms: Time, Interval Scheduling, Kruskal’s Algorithm, Suffix Arrays.

12. swap, min, max, reverse, iota, abs

A few small functions appear throughout the chapters’ code. All are in <algorithm> except iota (<numeric>) and abs (<cstdlib>). 

int a = 3, b = 8;
swap(a, b);                           // a = 8, b = 3
int hi = max(a, b), lo = min(a, b);   // 8, 3
vector<int> path = {3, 2, 0};
reverse(path.begin(), path.end());    // 0 2 3
vector<int> idx(5);
iota(idx.begin(), idx.end(), 0);      // 0 1 2 3 4
int d = abs(-7);                      // 7
calldoescosttypical use
swap(a, b)exchange two values\(O(1)\)heaps, sorting, union by size
min(a, b), max(a, b)the smaller or larger; min({a, b, c}) takes a list\(O(1)\)DP recurrences, tree heights
reverse(first, last)reverse a range in place\(O(n)\)a path or traceback collected backwards
iota(first, last, x)fill with \(x, x+1, x+2, \ldots\)\(O(n)\)a vector of indices to sort
abs(x)\(\lvert x \rvert\)\(O(1)\)balance factors, differences
Pitfall min and max need both arguments of the same type: max(1, 2L) does not compile, and max(x, 0) with a long x needs 0L. A path built by following parent links from the end comes out backwards; one reverse at the end is \(O(n)\), while inserting each step at the front of a vector would be \(O(n^2)\).

Used in: 0/1 Knapsack, Amortized Analysis, AVL Trees, Count-Min Sketch, DP Patterns: Grid, Interval, Coin Change & LIS, Edit Distance, Elementary Sorts, Heaps & Priority Queues, Heapsort, Huffman Coding, Longest Common Subsequence, Maximum Flow & Minimum Cut, Quicksort, Suffix Arrays, Topological Sort, Traceback & Space-Saving, Union-Find.

13. INT_MAX and numeric_limits

Shortest-path and DP code needs a value that stands for “infinity” or “nothing yet”. <climits> names the extremes of the built-in types (INT_MAX, INT_MIN, LONG_MAX); <limits> gives the same for any type as numeric_limits<T>::max(). 

int INF = INT_MAX;                       // 2147483647: "no path yet"
long big = numeric_limits<long>::max();  // 9223372036854775807 (64-bit)
vector<int> dist = {7, INF};
int w = 5;
if (dist[1] != INF && dist[1] + w < dist[0])   // test INF before adding
    dist[0] = dist[1] + w;
Pitfall INT_MAX + 1 overflows, which for a signed integer is undefined behaviour; in practice it wraps to a large negative number, and a relaxation then “improves” a distance to something negative. Test for the sentinel before adding to it, as above, or keep distances in a wider type such as long.

Used in: Bellman-Ford, Dijkstra’s Algorithm, Interval Scheduling, Matrix-Chain Multiplication, Maximum Flow & Minimum Cut, The Floyd–Warshall Algorithm.

16. Exercises (with solutions)

  1. After stack<int> s; queue<int> q; and pushing 4, 1, 3 into both, and into a priority_queue<int> p, what does each return from its first top() or front()? And from a priority_queue with the Greater comparison?
    solution The stack gives 3 (the last pushed), the queue 4 (the first pushed), the default priority_queue 4 (the largest), and the one with Greater 1 (the smallest).
  2. This loop is meant to print and empty a stack. What is wrong with it? 
    while (!st.empty()) cout << st.pop() << " ";
    solution It does not compile: pop() returns void. Read the top, then remove it: while (!st.empty()) { cout << st.top() << " "; st.pop(); }.
  3. A program counts words with map<string, int> freq; and freq[w]++;. Why does this work for a word seen for the first time? A later function reports whether a word was seen with return freq[w] > 0;. What does that function do to the map, and how should it be written?
    solution freq[w] on a new word inserts it with the value 0, and ++ makes it 1. The same insertion happens in the query: every unseen word asked about is added with count 0, so the map grows and a later loop over it prints words that never occurred. Write return freq.count(w) == 1;, which inserts nothing.
  4. Write a comparison struct for a priority_queue of struct Entry { long dist; int vertex; }; that pops the smallest dist first and, on equal distances, the smaller vertex.
    solution The struct answers “does a go below b?”, which is “is a greater?”: 
    struct Greater {
    bool operator()(const Entry& a, const Entry& b) const {
        if (a.dist != b.dist) return a.dist > b.dist;
        return a.vertex > b.vertex;
    }
};
    Declared as priority_queue<Entry, vector<Entry>, Greater> pq;.
  5. Why is bool atMost(int a, int b) { return a <= b; } wrong as the comparison for sort, and what does sort(v.begin() + 1, v.end() - 1) sort?
    solution sort requires a strict comparison, false for equal elements; atMost(x, x) is true, which is undefined behaviour and can make sort read past the end of the range. Use a < b. The second call sorts every element except the first and the last: the range starts one after begin() and stops one before end().
  6. Choose a container for each and give the cost of its main operation: (a) word counts printed in alphabetical order; (b) a membership test that must be as fast as possible; (c) the next event by time in a simulation; (d) an undo history.
    solution (a) map<string, int>: \(O(\log n)\) per update, and the loop over it is already alphabetical. (b) unordered_set: \(O(1)\) average per test. (c) priority_queue with a comparison that puts the earliest time on top: \(O(\log n)\) per push and pop. (d) stack: \(O(1)\) per push and pop, and the most recent action comes off first.
  7. A shortest-path program sets dist[v] = INT_MAX for every unreached vertex and relaxes with if (dist[u] + w < dist[v]) dist[v] = dist[u] + w;. What goes wrong, and on which vertices?
    solution When u is itself unreached, dist[u] + w is INT_MAX + w, which overflows (undefined behaviour; in practice a large negative number), so the test succeeds and v gets a negative distance. Test dist[u] != INT_MAX first, as in section 13, or only relax edges out of vertices taken from the queue, which are always reached.
