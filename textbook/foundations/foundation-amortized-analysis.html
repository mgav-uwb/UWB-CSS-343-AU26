Amortized Analysis

Data Structures & Algorithms. Foundation.
How to bound the cost of a sequence of operations when individual operations are occasionally expensive. The precise difference between a worst-case bound per operation and an amortized bound; the three standard methods (aggregate, accounting, potential), each defined and each worked in full on the doubling dynamic array; the binary counter as a second complete example; where the course text already relies on amortized bounds; exercises with solutions.

A dynamic array almost always appends in constant time, but once in a while an append must copy the entire array first. A worst-case bound per operation must charge every append for that copy: \(\Theta(n)\) each. Yet a run of \(N\) appends demonstrably performs fewer than \(3N\) element writes in total. The per-operation worst case is correct and useless; the quantity that matches reality is the cost of the whole sequence. Amortized analysis makes that quantity precise, and gives three interchangeable techniques for computing it: add everything up (aggregate), prepay with credits (accounting), or measure stored work with a function of the state (potential).

1. Worst case per operation versus amortized

The cost of an operation is measured in a fixed cost model, as in the Analysis of Algorithms: Time reading; in this handout the basic operation is an element write (for arrays) or a bit flip (for counters). Two different guarantees can then be stated about an operation that is executed many times.

Definition (worst-case cost per operation) An operation has worst-case cost \(f(n)\) if every single execution of it, from every reachable state of size \(n\), costs at most \(f(n)\). The bound must hold for each execution in isolation.
Definition (amortized cost) Fix a data structure and its operations. An assignment of an amortized cost \(\hat c_i\) to the \(i\)-th operation is valid if for every sequence of \(N\) operations starting from the initial state, the actual costs \(c_i\) satisfy \[ \sum_{i=1}^{N} c_i \;\le\; \sum_{i=1}^{N} \hat c_i . \] We then say the operation runs in amortized \(O(\hat c)\) time. The inequality must hold for every prefix of every sequence, not merely in the limit.

The two guarantees differ in scope. A worst-case bound per operation controls each execution separately; an amortized bound controls only the running total, and permits an individual operation to be expensive provided enough cheap operations precede it. Every worst-case bound per operation is also a valid amortized bound (sum both sides), but not conversely: an amortized \(O(1)\) operation may occasionally cost \(\Theta(n)\).

Amortized is not average-case No probability is involved. An average-case bound assumes a distribution over inputs and can be violated by an unlucky input. An amortized bound is a worst-case statement about sequences: it holds for every sequence of operations, including the one an adversary picks. What is being averaged is the cost across the operations of one worst-case sequence, not across random inputs.

2. The running example: a doubling array

A dynamic array stores \(n\) elements in a contiguous block of capacity \(\mathrm{cap} \ge n\). Append writes into the next free slot; when the block is full (\(n = \mathrm{cap}\)), a new block of capacity \(\max(1,\,2\,\mathrm{cap})\) is allocated, all \(n\) elements are copied over, and the append proceeds. The array starts empty with capacity \(0\). The cost of one append is the number of element writes it performs: the copies (if any) plus \(1\) for the new element. 

// Doubling dynamic array. cost counts element writes: copies + the new write.
struct DynArray {
    vector<int> a;              // backing store; a.size() is the capacity
    int  n    = 0;              // elements in use
    long cost = 0;              // element writes (the cost model here)
    void append(int x) {
        if (n == (int)a.size()) {              // full: double, copy n elements
            vector<int> b(max(1, 2 * n));
            for (int i = 0; i < n; i++) { b[i] = a[i]; cost++; }
            a = move(b);
        }
        a[n++] = x; cost++;                    // the write itself
    }
};
// Doubling dynamic array. cost counts element writes: copies + the new write.
static class DynArray {
    int[] a = new int[0];       // backing store; a.length is the capacity
    int  n    = 0;              // elements in use
    long cost = 0;              // element writes (the cost model here)
    void append(int x) {
        if (n == a.length) {                   // full: double, copy n elements
            int[] b = new int[Math.max(1, 2 * n)];
            for (int i = 0; i < n; i++) { b[i] = a[i]; cost++; }
            a = b;
        }
        a[n++] = x; cost++;                    // the write itself
    }
}
# Doubling dynamic array. cost counts element writes: copies + the new write.
class DynArray:
    def __init__(self):
        self.a = []             # backing store; len(a) is the capacity
        self.n = 0              # elements in use
        self.cost = 0           # element writes (the cost model here)

    def append(self, x):
        if self.n == len(self.a):              # full: double, copy n elements
            b = [None] * max(1, 2 * self.n)
            for i in range(self.n):
                b[i] = self.a[i]
                self.cost += 1
            self.a = b
        self.a[self.n] = x                     # the write itself
        self.n += 1
        self.cost += 1
// Doubling dynamic array. cost counts element writes: copies + the new write.
struct DynArray { a: Vec<i64>, n: usize, cost: u64 }
impl DynArray {
    fn append(&mut self, x: i64) {
        if self.n == self.a.len() {            // full: double, copy n elements
            let mut b = vec![0; 1.max(2 * self.n)];
            for i in 0..self.n { b[i] = self.a[i]; self.cost += 1; }
            self.a = b;
        }
        self.a[self.n] = x; self.n += 1; self.cost += 1;  // the write itself
    }
}

The worst-case cost per append is easy and discouraging: the append that finds \(n = \mathrm{cap}\) copies all \(n\) elements, so a single append costs \(n + 1\) writes, which is \(\Theta(n)\). That bound is attained, so it cannot be improved per operation. The three methods below all prove the same sharper statement: the amortized cost of append is at most \(3\) writes.

One append sequence serves for all three analyses: \(N = 13\) appends into an initially empty array. Expansions occur on appends 1, 2, 3, 5, and 9, the appends that find the array full at sizes 0, 1, 2, 4, 8. (Every trace table in this handout was generated by executing the code above and printing the counters.)

3. Method 1: the aggregate method

Definition (aggregate method) Compute \(T(N)\), the maximum total cost of any sequence of \(N\) operations, directly, by summation. Then assign every operation the same amortized cost \(\hat c = T(N)/N\). Validity is immediate: the actual total is at most \(T(N) = N \cdot \hat c\).

The 13 appends perform \(13\) new-element writes plus \(1+2+4+8 = 15\) copies, \(28\) writes in total, an average of \(28/13 \approx 2.15\) per append. Extending the same sequence to \(N = 17\) picks up the expansion at size 16: copies \(1+2+4+8+16 = 31\), total \(17 + 31 = 48\) writes, average \(48/17 \approx 2.82\). The average creeps toward \(3\) right after an expansion and drifts down between expansions, but never reaches \(3\). That is the general fact:

Theorem (aggregate bound for doubling) Starting from an empty array of capacity \(0\), any sequence of \(N \ge 1\) appends performs fewer than \(3N\) element writes. Hence append runs in amortized \(O(1)\), with amortized cost at most \(3\) writes.
Proof. Each append writes its own element once: \(N\) writes. Copies occur only during expansions, and the expansion triggered when the array holds \(m\) elements copies exactly \(m\) elements. Expansions are triggered precisely at the sizes \(m = 0, 1, 2, 4, \ldots, 2^j, \ldots\); during \(N\) appends the largest size at which an expansion can trigger is at most \(N-1\). Writing \(J = \lfloor \lg (N-1) \rfloor\) (for \(N \ge 2\)), the total number of copies is at most \[ \sum_{j=0}^{J} 2^{\,j} \;=\; 2^{\,J+1} - 1 \;\le\; 2(N-1) - 1 \;\lt\; 2N, \] using \(2^{J} \le N-1\). For \(N = 1\) there are no copies. Total writes \(\lt N + 2N = 3N\). ∎

The aggregate method is the bluntest of the three: it produces one uniform amortized cost for all operations and gives no way to charge different operation types differently. Its strength is that nothing needs to be invented; the sum is computed and divided. When operations of several kinds interact (as in the multipop stack of exercise 3), the other two methods are usually easier to apply.

4. Method 2: the accounting (banker’s) method

Definition (accounting method) Charge each operation a fixed amortized price \(\hat c_i\), possibly different per operation type. The operation pays its actual cost \(c_i\) from the charge; any surplus \(\hat c_i - c_i\) is deposited as credit in a bank (often attached to specific parts of the structure), and any deficit is withdrawn from the bank. The assignment is valid provided the bank balance never goes negative, for then over every prefix \(\sum c_i \le \sum \hat c_i\).

For the doubling array, charge 3 writes per append and spend them as follows:

  • \(1\) write pays for writing the new element itself;
  • \(1\) credit is stored on the new element, prepaying the copy that will move it during the next expansion;
  • \(1\) credit is stored on one veteran element in the older half of the array, an element that was copied by the previous expansion and whose own credit is therefore already spent.

After an expansion to capacity \(2m\), the next \(m\) appends fill the top half; each deposits \(2\) credits, one for itself and one for one of the \(m\) veterans in the bottom half. When the array reaches size \(2m\) and the next expansion must copy \(2m\) elements, every element holds exactly one credit, and the \(2m\) credits pay for the \(2m\) copies. The balance never goes negative, which is what validates the charge of \(3\). The pattern in the last column is exact and worth proving: the balance returns to precisely \(3\) after every expansion.

Claim (bank balance) Immediately after any append that triggered an expansion, the bank balance is exactly \(3\). Consequently the balance is never negative.
Proof. By induction over expansions. Append 1 (capacity \(0 \to 1\)) costs \(1\) and leaves balance \(2\); append 2 (capacity \(1 \to 2\)) costs \(2\) and leaves \(2 + 3 - 2 = 3\), the base case. Suppose the balance is \(3\) just after the expansion to capacity \(2m\), at which point the array holds \(m + 1\) elements. The next \(m - 1\) appends are cheap (cost \(1\), deposit \(2\)), so the balance grows to \(3 + 2(m-1) = 2m + 1\) as the array fills to \(2m\). The following append triggers the expansion to \(4m\), costing \(2m + 1\) writes, and leaves \((2m + 1) + 3 - (2m + 1) = 3\). Between those two moments the balance only grows, so it stays positive throughout. ∎

In the table: after the expansion to capacity 8 (append 5, \(m = 4\)), the balance climbs \(5, 7, 9 = 2m + 1\) over appends 6-8, and append 9, which costs exactly \(2m + 1 = 9\), drops it back to \(3\).

5. Method 3: the potential method

The accounting method stores prepaid work as credits scattered over the structure. The potential method stores the same information as a single number computed from the state itself: no bookkeeping travels with the data; the state is the bank.

Definition (potential method) Choose a potential function \(\Phi\) mapping each reachable state \(D\) to a real number, with \(\Phi(D_0) = 0\) for the initial state and \(\Phi(D) \ge 0\) for every reachable state. Define the amortized cost of the \(i\)-th operation, which takes state \(D_{i-1}\) to \(D_i\) at actual cost \(c_i\), as \[ \hat c_i \;=\; c_i + \Phi(D_i) - \Phi(D_{i-1}). \]
Lemma (validity of the potential method) With \(\Phi\) as above, \(\sum_{i=1}^{N} c_i \le \sum_{i=1}^{N} \hat c_i\) for every sequence of \(N\) operations, so the \(\hat c_i\) are valid amortized costs.
Proof. The sum telescopes: \[ \sum_{i=1}^{N} \hat c_i = \sum_{i=1}^{N} \bigl( c_i + \Phi(D_i) - \Phi(D_{i-1}) \bigr) = \Phi(D_N) - \Phi(D_0) + \sum_{i=1}^{N} c_i \;\ge\; \sum_{i=1}^{N} c_i, \] since \(\Phi(D_N) \ge 0 = \Phi(D_0)\). ∎

Intuitively, \(\Phi\) is stored work: a cheap operation that pushes the structure toward its next expensive moment raises \(\Phi\) (amortized cost above actual), and the expensive operation releases the stored potential (\(\Delta\Phi\) large and negative), cancelling its actual cost. For the doubling array, take \[ \Phi \;=\; 2n - \mathrm{cap}. \] \(\Phi = 0\) for the initial empty state, and \(\Phi \ge 0\) always, because a doubling array is at least half full: right after an expansion \(n = \tfrac{\mathrm{cap}}{2} + 1\), and appends only increase \(n\). Two cases, plus the special first append:

  • Append without expansion. Actual cost \(1\); \(n\) rises by 1, \(\mathrm{cap}\) unchanged, so \(\Delta\Phi = 2\). Amortized \(= 1 + 2 = 3\).
  • Append with expansion at \(n = \mathrm{cap} = m \ge 1\). Actual cost \(m + 1\). Before: \(\Phi = 2m - m = m\). After: \(n = m+1\), \(\mathrm{cap} = 2m\), so \(\Phi = 2(m+1) - 2m = 2\), giving \(\Delta\Phi = 2 - m\). Amortized \(= (m + 1) + (2 - m) = 3\).
  • First append (capacity \(0 \to 1\)). Actual cost \(1\); \(\Phi: 0 \to 2\cdot 1 - 1 = 1\). Amortized \(= 1 + 1 = 2\).

Every append has amortized cost at most \(3\), reproving the theorem of the aggregate section without summing anything. The same 13-append sequence, with \(\Phi\) computed at every step:

The three methods are one argument The bank balance of the accounting table and the potential column differ by a bookkeeping constant: compare bank \(2, 3, 3, 5, 3, 5, 7, 9, 3, \ldots\) with \(\Phi\)-after \(1, 2, 2, 4, 2, 4, 6, 8, 2, \ldots\). A credit scheme is a potential function (the total credit in the bank), and a potential function is a credit scheme with the ledger replaced by a formula. The aggregate method is the same sum with the intermediate balance never written down. Choosing among them is a matter of which is easiest to state for the structure at hand.

6. Second example: the binary counter

A \(k\)-bit binary counter supports one operation, increment, whose cost is the number of bit flips it performs. Increment clears the trailing block of 1 bits and sets the first 0 bit: 

// Binary counter as a bit array, bit[0] least significant.
// cost counts bit flips: the trailing 1s cleared, plus the one bit set.
void increment(vector<int>& bit, long& cost) {
    size_t i = 0;
    while (i < bit.size() && bit[i] == 1) {
        bit[i] = 0; cost++; i++;         // clear a trailing 1
    }
    if (i < bit.size()) { bit[i] = 1; cost++; }   // set the first 0
}
// Binary counter as a bit array, bit[0] least significant.
// cost counts bit flips: the trailing 1s cleared, plus the one bit set.
static long increment(int[] bit, long cost) {
    int i = 0;
    while (i < bit.length && bit[i] == 1) {
        bit[i] = 0; cost++; i++;         // clear a trailing 1
    }
    if (i < bit.length) { bit[i] = 1; cost++; }   // set the first 0
    return cost;
}
# Binary counter as a bit list, bit[0] least significant.
# cost counts bit flips: the trailing 1s cleared, plus the one bit set.
def increment(bit, cost):
    i = 0
    while i < len(bit) and bit[i] == 1:
        bit[i] = 0; cost += 1; i += 1    # clear a trailing 1
    if i < len(bit):
        bit[i] = 1; cost += 1            # set the first 0
    return cost
// Binary counter as a bit vector, bit[0] least significant.
// cost counts bit flips: the trailing 1s cleared, plus the one bit set.
fn increment(bit: &mut [u8], cost: &mut u64) {
    let mut i = 0;
    while i < bit.len() && bit[i] == 1 {
        bit[i] = 0; *cost += 1; i += 1;  // clear a trailing 1
    }
    if i < bit.len() { bit[i] = 1; *cost += 1; }  // set the first 0
}

All three methods, briefly, on this table:

  • Aggregate. Count flips per bit position instead of per increment. Bit \(j\) flips exactly \(\lfloor n / 2^{\,j} \rfloor\) times during \(n\) increments (it flips on every \(2^{\,j}\)-th increment). For \(n = 16\): bit 0 flips 16 times, bit 1 flips 8, then 4, 2, 1; total \(16+8+4+2+1 = 31\), matching the cumulative column. In general \[ \sum_{j \ge 0} \Bigl\lfloor \frac{n}{2^{\,j}} \Bigr\rfloor \;\lt\; n \sum_{j \ge 0} 2^{-j} \;=\; 2n, \] so \(n\) increments cost fewer than \(2n\) flips: amortized cost below \(2\).
  • Accounting. Charge \(2\) per increment: \(1\) pays the single \(0 \to 1\) flip the increment performs, and \(1\) is left as a coin on that freshly set bit. Invariant: every 1 bit carries one coin (induction: increments preserve it). Each \(1 \to 0\) flip is paid by the coin on the bit being cleared, so the clearing loop is free at the counter and the balance (the number of 1 bits) never goes negative.
  • Potential. \(\Phi = \) number of 1 bits; \(\Phi(D_0) = 0\), \(\Phi \ge 0\). An increment with \(t\) trailing 1s costs \(t + 1\) and changes \(\Phi\) by \(1 - t\) (it clears \(t\) ones and sets one). Amortized \(= (t+1) + (1-t) = 2\), for every increment; the table confirms it row by row. Cumulative check: amortized total \(32\), actual total \(31\), difference \(1 = \Phi(D_{16})\).
When amortized bounds do not apply An amortized bound covers sequences from the initial state of the structure. It says nothing about the cost of one operation performed on an adversarially prepared state in isolation, and it can fail entirely when an added operation lets an adversary undo the progress the potential measures: adding decrement to the counter destroys the amortized \(O(1)\) bound (exercise 4), and shrinking the array too eagerly destroys the append bound (exercise 5). A latency-critical system may also care that the occasional \(\Theta(n)\) append happens at all, even though the average is constant; amortized bounds say nothing about the spike, only about the total.

7. Where the course text uses amortized bounds

Two handouts in this catalog state amortized results whose proofs are instances of the methods above. The Union-Find reading proves near-constant cost for find and union with path compression and union by size: the compression step can be expensive on one call, but it flattens the tree and thereby prepays future calls; the resulting bound of \(O(\alpha(N))\) amortized per operation (with \(\alpha\) the inverse Ackermann function) is a genuine amortized statement, not a per-operation one. The Hashing reading keeps a hash table’s load factor bounded by resizing to a larger table and rehashing every key; its proposition that inserts remain amortized \(\Theta(1)\) is exactly the doubling-array argument of this handout with “copy an element” replaced by “rehash a key.” The same doubling argument is what standard library growable arrays (C++ vector, Java ArrayList, Python list) rely on for constant amortized append. The surrounding machinery, cost models and order-of-growth notation, is developed in Analysis of Algorithms: Time and Asymptotic Notation.

8. Exercises (with solutions)

  1. Tripling. Change the growth rule to \(\mathrm{cap} \to \max(1,\,3\,\mathrm{cap})\). Find a potential function that yields a constant amortized cost for append, and state the constant.
    solution Take \(\Phi = \tfrac{3n - \mathrm{cap}}{2}\). Initially \(\Phi = 0\), and \(\Phi \ge 0\) because a tripling array is always at least one-third full. Append without expansion: cost \(1\), \(\Delta\Phi = \tfrac32\), amortized \(\tfrac52\). Append with expansion at \(n = \mathrm{cap} = m\): cost \(m + 1\); before, \(\Phi = \tfrac{3m - m}{2} = m\); after, \(\Phi = \tfrac{3(m+1) - 3m}{2} = \tfrac32\); amortized \(= (m+1) + \tfrac32 - m = \tfrac52\). (First append: cost 1, \(\Phi: 0 \to 1\), amortized \(2\).) So the amortized cost is \(\tfrac52\) writes: a bigger growth factor copies less often, at the price of more slack space. (Numerically: over all \(N \le 5000\) the worst average cost is \(2.499\ldots\), and the per-operation amortized costs computed from this \(\Phi\) are exactly \(2\) and \(2.5\).)
  2. Additive growth fails. Change the growth rule to \(\mathrm{cap} \to \mathrm{cap} + 1\). Compute the exact total cost of \(N\) appends and conclude the amortized cost per append.
    solution Now every append finds the array full and copies all \(n\) existing elements. Append \(i\) costs \((i - 1) + 1 = i\) writes, so the total is \[ \sum_{i=1}^{N} i \;=\; N + \frac{N(N-1)}{2}, \] counting the \(N\) fresh writes plus \(0+1+\cdots+(N-1)\) copies. For \(N = 16\) that is \(16 + 120 = 136\) writes (verified by running the code), against \(43\) for doubling (\(16 + 1 + 2 + 4 + 8 + \ldots\): the doubling total for 16 appends is \(16 + 15 = 31\) writes before the expansion at size 16, 47 with it at \(N = 17\)). The total is \(\Theta(N^2)\), so the amortized cost is \(\Theta(N)\): no constant amortized bound exists. Growing by any fixed increment gives the same \(\Theta(N)\) amortized cost; a constant amortized cost requires growing by a constant factor.
  3. Multipop stack. A stack supports push (cost 1), pop (cost 1), and multipop(k), which pops \(\min(k, \text{size})\) elements at cost equal to the number popped (at least 1). Show that all three run in amortized \(O(1)\), by the accounting method and by a potential function.
    solution Accounting. Charge push 2: one pays the push, one coin stays on the pushed element. Charge pop and multipop 1 each: every element removed pays for its own removal with the coin it carries, and the charged 1 covers the case of popping from an empty (or exhausted) stack. Every element on the stack carries one coin (invariant, by induction), so the bank never goes negative; a multipop that removes \(m\) elements costs \(m\) but withdraws \(m\) prepaid coins. Potential. \(\Phi = \) stack size; \(\Phi(D_0) = 0\), \(\Phi \ge 0\). Push: \(1 + 1 = 2\). Pop: \(1 - 1 = 0\), plus the constant, at most \(1\). Multipop removing \(m\): cost \(\max(m,1)\), \(\Delta\Phi = -m\), amortized \(\le 1\). So any \(n\) operations cost at most \(2n\) (verified over random operation sequences). The aggregate view: each element is pushed once and popped at most once, so total cost \(\le 2 \cdot \#\text{pushes} + \#\text{ops}\).
  4. Decrement breaks the counter. Add a decrement operation (subtract 1, cost = bit flips) to the binary counter. Exhibit a sequence of \(n\) operations on a \(k\)-bit counter that costs \(\Theta(nk)\), and explain why no potential function can restore an amortized \(O(1)\) bound.
    solution Bring the counter to \(2^k - 1 = 0111\ldots1\) and then alternate increment, decrement, increment, decrement, \(\ldots\). Each increment carries through \(k\) trailing ones (\(0111\ldots1 \to 1000\ldots0\), \(k+1\) flips) and each decrement borrows through \(k\) trailing zeros (\(1000\ldots0 \to 0111\ldots1\), \(k+1\) flips). For \(k = 10\), running this oscillation for 1000 operations gives an average of exactly \(11 = k+1\) flips per operation (verified). No potential function helps: the state returns to \(0111\ldots1\) after every increment-decrement pair, so over the pair \(\Delta\Phi = 0\) and the amortized cost of the pair equals its actual cost, \(2(k+1)\). Any valid amortized costs must therefore average at least \(k + 1\) per operation on this sequence; amortization cannot beat a sequence that keeps revisiting the same expensive state.
  5. Shrinking too eagerly. To avoid wasting space, suppose the array also supports remove (delete the last element, cost 1) and halves its capacity, copying the \(n\) survivors, as soon as \(n\) drops to \(\mathrm{cap}/2\). Exhibit a sequence on which append and remove cost \(\Theta(n)\) amortized, and state the standard fix.
    solution Fill the array so that \(n = \mathrm{cap} = 8\), then alternate append, remove, append, remove, \(\ldots\). The append expands to capacity 16 (9 writes); the remove drops \(n\) back to \(8 = 16/2\) and immediately shrinks, copying 8 elements (9 writes with the deletion). Every operation in the oscillation costs 9; around \(n = 16\) every operation costs 17, around \(n = 32\) it costs 33 (all verified by running the rule): \(\Theta(n)\) per operation with no cheap operations in between, so the amortized cost is \(\Theta(n)\). The fix is to leave a gap between the triggers: double when full, but halve only when \(n\) drops to \(\mathrm{cap}/4\). Then after any resize the array is exactly half full, and \(\Theta(n)\) operations must intervene before either trigger can fire again; the potential \(\Phi = |2n - \mathrm{cap}|\) gives constant amortized cost for both operations. (Numerically, random append/remove sequences under the quarter rule average about \(1.04\) writes per operation.)
  6. Reading the bank. For the doubling array with the 3-per-append charge, give closed forms, in terms of the current size \(n\) and capacity, for the bank balance at every moment after the second append, and check them against the table of the accounting section.
    solution From the claim proved in the accounting section, the balance is exactly \(3\) immediately after each expansion, when \(n = \tfrac{\mathrm{cap}}{2} + 1\). Each subsequent cheap append adds \(2\), so while \(\tfrac{\mathrm{cap}}{2} \lt n \le \mathrm{cap}\) the balance is \[ 3 + 2\Bigl(n - \frac{\mathrm{cap}}{2} - 1\Bigr) \;=\; 2n - \mathrm{cap} + 1 \;=\; \Phi + 1, \] one more than the potential of the potential section. Check against the table: after append 4 (\(n=4\), cap 4): \(8 - 4 + 1 = 5\); after append 8 (\(n=8\), cap 8): \(16 - 8 + 1 = 9\); after append 13 (\(n=13\), cap 16): \(26 - 16 + 1 = 11\). All match. The constant \(1\) is the surplus deposited by the very first append, which cost \(1\) against a charge of \(3\) but raised \(\Phi\) by only \(1\).
