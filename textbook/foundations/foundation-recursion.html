Recursion & Induction

ALGOL 60 was among the first programming languages to allow recursive procedures. Edsger Dijkstra showed the same year how a stack of activation records implements them, the mechanism every C++ call still uses. E. W. Dijkstra, “Recursive Programming,” Numerische Mathematik 2, 1960

A recursive procedure solves a problem by calling itself on a smaller instance of the same problem. That one idea carries most of this course: the tree operations, the divide-and-conquer sorts, the graph traversals, and the dynamic-programming recurrences are all written recursively first and analysed recursively afterwards. Two questions follow immediately, and this handout answers both. Why does a recursive procedure terminate and return the right answer? The answer is induction, the proof technique that is the mirror image of recursion. What does it cost? The answer is a recurrence, an equation that describes a function’s cost in terms of itself, and which is solved by the same unrolling that the recursion performs.

1. Base case and recursive case

A recursive definition has exactly two obligations. It must say what the answer is for inputs small enough to answer outright, and it must say how to build the answer for a larger input from answers to strictly smaller inputs. The factorial function is the standard first example: \[ n! \;=\; \begin{cases} 1 & \text{if } n \le 1 \quad \text{(base case)}\\[2pt] n \cdot (n-1)! & \text{if } n \gt 1 \quad \text{(recursive case)} \end{cases} \]

Definition (base case, recursive case, recursion invariant) The base case of a recursive procedure is an input it answers without calling itself. The recursive case answers an input by combining results of calls on other inputs. Those calls must satisfy a progress measure: a quantity that is a non-negative integer, is strictly smaller in every recursive call than in the current call, and reaches a base case when it can shrink no further. For fact(n) the measure is \(n\) itself.

The two obligations divide the work of proving a recursive procedure correct into two matching parts, which is precisely what induction (§4) formalises: the base case of the proof handles the base case of the code, and the inductive step handles the recursive case, granting itself the assumption that the recursive calls already work. That assumption is not optimism. It is what induction licenses.

The one rule of writing recursive code Write the recursive call assuming it already returns the correct answer for its smaller input, then check only two things: that the base case is right, and that the progress measure strictly decreases. Do not attempt to trace the call chain in your head; the whole point of the technique is that you do not have to. The traces in this handout exist to make the machinery visible once, not to be the way you reason day to day. 
// Factorial and a recursive sum: one base case, one recursive case each.
long fact(int n) {
    if (n <= 1) return 1;              // BASE CASE: answered outright
    return n * fact(n - 1);            // RECURSIVE CASE: n strictly decreases
}

// sum(n) = n + (n-1) + ... + 1, and sum(0) = 0.
long sum(int n) {
    if (n == 0) return 0;              // BASE CASE
    return n + sum(n - 1);             // RECURSIVE CASE
}
// Factorial and a recursive sum: one base case, one recursive case each.

2. The call stack, frame by frame

A recursive call is an ordinary function call, and the machine implements it the ordinary way: it pushes a stack frame holding the call’s parameters, its local variables, and the address to return to. The frame stays live for as long as the call is unfinished, which for recursion means while its own recursive call is running. Frames therefore accumulate on the way down and are released, innermost first, on the way back up.

Definition (stack frame, recursion depth) A stack frame (activation record) is the block of stack memory belonging to one in-progress call. The recursion depth is the largest number of frames of the recursive procedure that are live at the same instant.

Here is every push and pop of fact(4), eight events in the order the machine performs them. Read the top half downward (the descent to the base case) and the bottom half upward (the multiplications, which all happen on the way out).

Three facts are visible in the table and worth naming. First, the base case is reached once, at step 4, and it is the only step that produces a value without a multiplication. Second, every multiplication happens after the recursive call returns: the expression n * fact(n - 1) cannot be evaluated until the call finishes, which is exactly why the frame must stay live. Third, the peak depth is 4, one frame per level, so fact(n) holds \(n\) frames at its deepest point.

Frames are not free. Recursion depth is the auxiliary space of a recursive procedure, so fact(n) costs \(\Theta(n)\) stack space to produce one number, and a recursion over a structure costs as much stack as the structure is deep. The Space Complexity handout develops that accounting, including what happens when the depth exceeds the (bounded) stack region; §8 below returns to the crash.

3. Structural recursion on trees

Recursion on an integer shrinks a number. Structural recursion shrinks a structure, and it is the reason tree code is short. A binary tree is itself defined recursively: a tree is either empty, or a node holding a key together with two subtrees. A function over a tree is written by answering the same two obligations against that definition: what is the answer for the empty tree, and how is the answer for a node assembled from the answers for its two subtrees.

Definition (structural recursion) A structurally recursive function on an inductively defined type gives one case per constructor of the type, and recurses only on the immediate substructures of its argument. For binary trees: a case for the empty tree (the base case), and a case for a node that calls itself on left and right. The progress measure is the number of nodes, which strictly decreases in each call, so termination is automatic. 
struct Node { int key; Node* left; Node* right; };

// Empty tree has 0 nodes; a node has 1 plus what its two subtrees have.
int size(Node* t) {
    if (t == nullptr) return 0;                         // base case
    return 1 + size(t->left) + size(t->right);          // combine
}

// In-order: left subtree, this key, right subtree. On a BST this is sorted.
void inorder(Node* t, std::vector<int>& out) {
    if (t == nullptr) return;                           // base case
    inorder(t->left, out);
    out.push_back(t->key);                              // visit
    inorder(t->right, out);
}
class Node { int key; Node left, right; }

// Empty tree has 0 nodes; a node has 1 plus what its two subtrees have.
static int size(Node t) {
    if (t == null) return 0;                            // base case
    return 1 + size(t.left) + size(t.right);            // combine
}

// In-order: left subtree, this key, right subtree. On a BST this is sorted.
static void inorder(Node t, List<Integer> out) {
    if (t == null) return;                              // base case
    inorder(t.left, out);
    out.add(t.key);                                     // visit
    inorder(t.right, out);
}
class Node:
    def __init__(self, key):
        self.key, self.left, self.right = key, None, None

struct Node { key: i32, left: Link, right: Link }
type Link = Option<Box<Node>>;

// Empty tree has 0 nodes; a node has 1 plus what its two subtrees have.
fn size(t: &Link) -> usize {
    match t {
        None => 0,                                      // base case
        Some(n) => 1 + size(&n.left) + size(&n.right),  // combine
    }
}

// In-order: left subtree, this key, right subtree. On a BST this is sorted.
fn inorder(t: &Link, out: &mut Vec<i32>) {
    if let Some(n) = t {
        inorder(&n.left, out);
        out.push(n.key);                                // visit
        inorder(&n.right, out);
    }
}

4. Mathematical induction

Induction proves a statement about every natural number by proving two smaller statements, in the same shape as a base case and a recursive case.

Principle (mathematical induction) Let \(P(n)\) be a statement about the natural number \(n\), and let \(n_0\) be an integer. If
(base) \(P(n_0)\) holds, and
(step) for every \(n \gt n_0\), \(P(n-1)\) implies \(P(n)\),
then \(P(n)\) holds for every \(n \ge n_0\).
Why it is sound. Suppose the two hypotheses hold but \(P(m)\) fails for some \(m \ge n_0\). Then the set of counterexamples \(S = \{m \ge n_0 : P(m) \text{ is false}\}\) is a non-empty set of integers bounded below by \(n_0\), so by the well-ordering principle it has a least element \(k\). Since \(P(n_0)\) holds, \(k \gt n_0\), so \(k - 1 \ge n_0\), and by minimality of \(k\) the statement \(P(k-1)\) holds. The step then gives \(P(k)\), contradicting \(k \in S\). Hence \(S\) is empty. ∎

The assumption \(P(n-1)\) used inside the step is the inductive hypothesis. Naming it explicitly, and saying exactly where it is used, is what distinguishes a proof from a plausible story.

A summation identity

Theorem 1 For every integer \(n \ge 0\), \(\displaystyle\sum_{k=1}^{n} k = \frac{n(n+1)}{2}\).
Proof. By induction on \(n\), with \(P(n)\) the equation \(\sum_{k=1}^{n} k = n(n+1)/2\).
Base (\(n = 0\)). The empty sum is \(0\), and \(0 \cdot 1 / 2 = 0\). So \(P(0)\) holds.
Step. Let \(n \ge 1\) and assume \(P(n-1)\), that is \(\sum_{k=1}^{n-1} k = (n-1)n/2\). Split the last term off the sum and apply that hypothesis: \[ \sum_{k=1}^{n} k \;=\; \Bigl(\sum_{k=1}^{n-1} k\Bigr) + n \;\overset{\text{IH}}{=}\; \frac{(n-1)n}{2} + n \;=\; \frac{(n-1)n + 2n}{2} \;=\; \frac{n(n-1+2)}{2} \;=\; \frac{n(n+1)}{2}, \] which is \(P(n)\). By induction \(P(n)\) holds for all \(n \ge 0\). ∎

The step used the hypothesis at exactly one place, marked IH. Every honest inductive proof can point at that place. This identity is not an ornament: it is the closed form for the \(1 + 2 + \cdots + n\) comparison count of the quadratic sorts and of the \(\Theta(n^2)\) loop patterns counted in Analysis of Algorithms: Time.

Correctness of a recursive procedure

The same machinery proves code correct. The claim to prove is a specification: for every input in the domain, the call returns the stated value (and terminates).

Theorem 2 (correctness of sum) For every integer \(n \ge 0\), the call sum(n) from §1 terminates and returns \(n(n+1)/2\).
Proof. By induction on \(n\).
Base (\(n = 0\)). The test n == 0 succeeds, so the call returns \(0\) without recursing. It terminates, and \(0 = 0 \cdot 1/2\), as claimed.
Step. Let \(n \ge 1\) and assume the claim for \(n-1\): sum(n-1) terminates and returns \((n-1)n/2\). Executing sum(n), the test n == 0 fails, so the code evaluates n + sum(n - 1). Its argument \(n-1\) is \(\ge 0\), so the hypothesis applies: the inner call terminates with value \((n-1)n/2\), hence sum(n) terminates and returns \[ n + \frac{(n-1)n}{2} \;=\; \frac{2n + n^2 - n}{2} \;=\; \frac{n^2+n}{2} \;=\; \frac{n(n+1)}{2}. \] By induction the claim holds for every \(n \ge 0\). ∎

Notice the exact correspondence: the proof’s base case argues about the code’s base case, and the proof’s step argues about the code’s recursive case, using the hypothesis precisely where the code makes the recursive call. Termination came along for free because the argument \(n\) is a non-negative integer that strictly decreases: that is the progress measure of §1 doing its job, and it is the part a proof must never skip.

5. Strong induction and structural induction

Ordinary induction hands the step exactly one assumption, \(P(n-1)\). That is enough when the code recurses on \(n-1\). It is not enough when the code recurses on \(\lfloor n/2 \rfloor\), or on two subtrees of unknown sizes: the hypothesis available is about the wrong instance. Strong induction fixes this by granting the step all the smaller cases.

Principle (strong induction) Let \(P(n)\) be a statement about the natural number \(n\). If for every \(n \ge n_0\), \[ \bigl(P(m) \text{ holds for all } n_0 \le m \lt n\bigr) \;\Longrightarrow\; P(n), \] then \(P(n)\) holds for every \(n \ge n_0\).
Why it is sound. The same well-ordering argument. If the set \(S\) of counterexamples \(\ge n_0\) were non-empty it would have a least element \(k\); by minimality every \(m\) with \(n_0 \le m \lt k\) satisfies \(P(m)\), so the hypothesis yields \(P(k)\), a contradiction. (No separate base case is stated because at \(n = n_0\) the assumption is vacuous, so the implication is the base case. In practice one still writes the base case out, because that is where the vacuous assumption forces an outright argument.) ∎

Strong induction is what divide-and-conquer proofs need. A procedure that splits its input in half appeals to a claim about size \(\lfloor n/2 \rfloor\), which ordinary induction never offers when \(n \gt 2\). A procedure that recurses on two subtrees appeals to claims about two sizes that are only known to be smaller than \(n\), not to be \(n-1\). Both are handled at once by assuming everything below \(n\).

A worked proof: fast exponentiation

Fast exponentiation (also called exponentiation by squaring) computes \(x^n\) with about \(\log_2 n\) multiplications instead of \(n\), by squaring the result for the halved exponent: 

  long power(long x, int n) {
      if (n == 0) return 1;                 // base case
      long h = power(x, n / 2);             // integer division: floor(n/2)
      if (n % 2 == 0) return h * h;         // even: x^n = (x^(n/2))^2
      return h * h * x;                     // odd: x^n = (x^floor(n/2))^2 * x
  }
Theorem 3 (correctness of power) For every integer \(n \ge 0\) and every \(x\), power(x, n) terminates and returns \(x^n\).
Proof. By strong induction on \(n\). Assume the claim for every \(m\) with \(0 \le m \lt n\).
Base (\(n = 0\)). The first test succeeds and the call returns \(1 = x^0\), with no recursion.
Step (\(n \ge 1\)). Let \(h = \lfloor n/2 \rfloor\). Then \(0 \le h \lt n\) (for \(n \ge 1\), \(\lfloor n/2 \rfloor \le n/2 \lt n\)), so the inductive hypothesis applies to \(h\): the recursive call terminates and returns \(x^{h}\). Two cases remain, exactly the two the code distinguishes.
Case \(n\) even. Then \(n = 2h\), and the code returns \(x^{h} \cdot x^{h} = x^{2h} = x^{n}\).
Case \(n\) odd. Then \(n = 2h+1\), and the code returns \(x^{h} \cdot x^{h} \cdot x = x^{2h+1} = x^{n}\). In both cases the returned value is \(x^n\) and the call terminates, because the single recursive call terminates by hypothesis. By strong induction the claim holds for all \(n \ge 0\). ∎

Structural induction on trees

For a recursively defined structure the same principle takes a form with no arithmetic in it: prove the claim for the empty tree, and prove it for a node assuming it for both subtrees. This is strong induction with the number of nodes as the measure, since both subtrees are strictly smaller than the whole.

Theorem 4 (null links) A binary tree with \(n \ge 0\) nodes has exactly \(n+1\) empty subtrees (null links).
Proof. By structural induction on the tree \(T\), with \(L(T)\) the number of empty subtrees and \(n(T)\) the number of nodes.
Base. \(T\) empty: \(n(T) = 0\) and \(T\) is itself one empty subtree, so \(L(T) = 1 = n(T) + 1\).
Step. \(T\) is a node with subtrees \(A\) and \(B\). Every empty subtree of \(T\) lies in \(A\) or in \(B\) and in exactly one of them, so \(L(T) = L(A) + L(B)\). Both \(A\) and \(B\) have fewer nodes than \(T\), so the hypothesis gives \(L(A) = n(A)+1\) and \(L(B) = n(B)+1\). Hence \[ L(T) = \bigl(n(A)+1\bigr) + \bigl(n(B)+1\bigr) = \bigl(n(A) + n(B) + 1\bigr) + 1 = n(T) + 1 , \] using \(n(T) = n(A)+n(B)+1\). By structural induction the claim holds for every binary tree. ∎

The \(n = 7\) tree of §3 therefore has 8 empty subtrees, which is exactly the 8 size(nil) calls counted in that trace, and 15 calls in total. The identity is why a null-checking recursion over a tree of \(n\) nodes makes \(2n+1\) calls, and it is the counting fact behind the space accounting of red-black and 2-3 trees.

6. Solving recurrences by unrolling

The cost of a recursive procedure is itself described recursively: the work at this call, plus the cost of the calls it makes. Such an equation is a recurrence, and solving it means finding a closed form.

Definition (recurrence, unrolling) A recurrence defines \(T(n)\), the cost on input size \(n\), in terms of \(T\) at smaller sizes together with a non-recursive term for the work done at the current call, plus a base value for the smallest size. Unrolling (also called the substitution or iteration method) solves it by repeatedly replacing \(T\) on the right-hand side with its own definition, spotting the pattern after \(i\) substitutions, choosing the \(i\) that reaches the base case, and summing.

Linear recursion: \(T(n) = T(n-1) + c\)

This is fact and sum: constant work per call, one call per level, with \(T(0) = 0\). Unroll it: \[ T(n) = T(n-1) + c = T(n-2) + 2c = T(n-3) + 3c = \cdots = T(n-i) + i\,c . \] The base case is reached when \(n - i = 0\), that is \(i = n\), giving \(T(n) = T(0) + nc = cn = \Theta(n)\). Reading the same equation as a depth rather than a count of operations gives the \(n\) frames of the §2 trace.

Halving: \(T(n) = T(n/2) + c\)

This is power, and binary search: one call on half the input, constant work per call, \(T(1) = 0\). Unroll: \[ T(n) = T(n/2) + c = T(n/4) + 2c = \cdots = T(n/2^i) + i\,c . \] The base is reached when \(n/2^i = 1\), that is \(i = \log_2 n\), so \(T(n) = c\log_2 n = \Theta(\log n)\). For \(n = 1024\) the unrolled count is exactly 10 levels, and for power(3, 13) the chain \(13 \to 6 \to 3 \to 1 \to 0\) is \(\lfloor \log_2 13 \rfloor + 2 = 5\) calls.

Divide and conquer: \(T(n) = 2T(n/2) + n\)

This is mergesort: two half-size calls plus linear merging work, with \(T(1) = 0\). Unrolling now produces a growing number of terms, so it is clearest to sum level by level. At level \(i\) there are \(2^i\) subproblems of size \(n/2^i\), each doing \(n/2^i\) units of work, for a level total of exactly \(n\): \[ T(n) = \underbrace{n}_{\text{level }0} + \underbrace{2 \cdot \tfrac n2}_{\text{level }1} + \underbrace{4 \cdot \tfrac n4}_{\text{level }2} + \cdots = \sum_{i=0}^{\log_2 n - 1} n \;=\; n \log_2 n . \] The recursion stops at level \(\log_2 n\), where the subproblems have size 1 and cost nothing, so there are \(\log_2 n\) levels each contributing \(n\): \(T(n) = \Theta(n \log n)\). At \(n = 8\) this is \(8 + 2\cdot 4 + 4 \cdot 2 = 24 = 8 \log_2 8\), and at \(n = 1024\) it is \(10{,}240\).

Branching without shrinking enough: \(T(n) = 2T(n-1) + 1\)

Two calls, each only one smaller. This is the Towers of Hanoi move count, with \(T(0) = 0\). Unroll: \[ T(n) = 2T(n-1) + 1 = 4T(n-2) + 2 + 1 = 8T(n-3) + 4 + 2 + 1 = 2^i T(n-i) + \sum_{j=0}^{i-1} 2^j . \] At \(i = n\) the first term is \(2^n T(0) = 0\) and the sum is the geometric series \(2^n - 1\), so \(T(n) = 2^n - 1 = \Theta(2^n)\). The move counts for \(n = 1,\dots,10\) are 1, 3, 7, 15, 31, 63, 127, 255, 511, 1023, which are \(2^n - 1\) exactly.

The third row deserves a note, because it is the one that surprises: two half-size calls with constant combining work is linear, not logarithmic. Summing by levels, level \(i\) has \(2^i\) calls each costing \(c\), so the total is \(c(1 + 2 + 4 + \cdots + n) = c(2n-1) = \Theta(n)\): the geometric series is dominated by its last term, the leaves. That is why size on a tree of \(n\) nodes costs \(\Theta(n)\) even though the tree is only \(\Theta(\log n)\) deep, as the 15-call count of §3 confirms.

Unrolling handles every recurrence in the table, but it becomes tedious once the split is uneven or the combining work is some \(n^k\). The master theorem packages the level-summing argument into a formula covering all recurrences of the form \(T(n) = aT(n/b) + f(n)\); it is stated and proved in The Divide-and-Conquer Method, alongside the recursion-tree picture that the level sums above are drawing informally.

7. Recursion to iteration: explicit stacks and tail calls

Any recursion can be rewritten as a loop, because the only thing the runtime adds is a stack. Converting by hand is worth doing when the recursion is too deep for the call stack, or when the language charges too much per call. There are two conversions, and which one applies depends on whether the procedure does any work after its recursive call returns.

Tail recursion

Definition (tail call, tail recursion) A call is a tail call if its result is returned immediately, with no further computation in the caller. A procedure is tail recursive if every recursive call it makes is a tail call. Since nothing in the frame is needed after such a call, the frame can be reused rather than stacked, turning the recursion into a loop that runs in \(\Theta(1)\) stack space (a transformation called tail-call optimisation).

sum(n) as written in §1 is not tail recursive: it computes n + sum(n - 1), so the addition waits for the call, and the frame must survive. Adding an accumulator parameter moves that pending work to before the call and makes it a tail call: 

  long sum(int n)              { return n == 0 ? 0 : n + sum(n - 1); }        // NOT tail: adds after
  long sumTail(int n, long a)  { return n == 0 ? a : sumTail(n - 1, a + n); } // tail: nothing after

  long sumLoop(int n) {                                // the same procedure as a loop
      long a = 0;
      while (n != 0) { a = a + n; n = n - 1; }         // parameters become variables
      return a;
  }

The rewrite is mechanical: the parameters of the tail-recursive version become the loop’s variables, the base-case test becomes the loop exit, and the arguments of the tail call become the assignments at the bottom of the body. All three return the same value on every input; the third uses one frame instead of \(n\).

Do not rely on the compiler for this C++ compilers usually perform tail-call optimisation at -O2, but the standard does not require it, so a tail-recursive C++ function may still consume \(\Theta(n)\) stack in a debug build. Java does not perform it at all, and CPython does not either: CPython’s default recursion limit is 1000 frames, so a plain recursive factorial raises RecursionError just short of \(n = 1000\). When depth is proportional to input size and the input can be large, convert to a loop yourself.

Non-tail recursion: carry the stack yourself

When work remains after the recursive call, as in tree traversal, the conversion needs an explicit stack that stores what the frames were storing. In-order traversal is the standard case: push nodes while walking left, then pop, visit, and turn right. 

// In-order traversal with an EXPLICIT stack: same output, no recursion.
// The stack holds the nodes whose key has not been visited yet.
void inorderIterative(Node* root, std::vector<int>& out) {
    std::stack<Node*> st;
    Node* cur = root;
    while (cur != nullptr || !st.empty()) {
        if (cur != nullptr) {
            st.push(cur);            // remember this node, its key is still owed
            cur = cur->left;         // ... after the whole left subtree
        } else {
            cur = st.top(); st.pop();
            out.push_back(cur->key); // visit
            cur = cur->right;        // then the right subtree
        }
    }
}

// Rust's ownership rules make raw parent pointers awkward).
fn inorder_iterative(arena: &[NodeA], root: Option<usize>) -> Vec<i32> {
    let (mut out, mut st, mut cur) = (Vec::new(), Vec::new(), root);
    while cur.is_some() || !st.is_empty() {
        if let Some(i) = cur {
            st.push(i);              // remember this node, its key is still owed
            cur = arena[i].left;     // ... after the whole left subtree
        } else {
            let i = st.pop().unwrap();
            out.push(arena[i].key);  // visit
            cur = arena[i].right;    // then the right subtree
        }
    }
    out
}

8. Four ways recursion goes wrong

(a) Missing base case

With no case that returns without recursing, the descent never stops. The frames accumulate until the stack region is exhausted and the program is killed by a stack overflow (a segmentation fault in C++, a StackOverflowError in Java, a RecursionError in Python). 

  long factBad(int n) {
      return n * factBad(n - 1);      // no base case: n goes 4, 3, 2, 1, 0, -1, -2, ...
  }

The subtler version has a base case that some inputs step over. if (n == 1) return 1; is fine for positive \(n\) and catastrophic for factBad(0), which descends through \(-1, -2, \dots\) and never tests true. Guard with \(\le\), not \(=\), so the base case catches everything at or below it.

(b) The argument does not decrease

A base case is useless if the recursive call fails to move toward it. The classic instance is an off-by-one in binary search, passing mid instead of mid - 1 or mid + 1: 

  int searchBad(int a[], int x, int lo, int hi) {
      if (lo > hi) return -1;
      int mid = (lo + hi) / 2;
      if (a[mid] == x) return mid;
      if (x < a[mid]) return searchBad(a, x, lo, mid);      // BUG: should be mid - 1
      return searchBad(a, x, mid, hi);                      // BUG: should be mid + 1
  }

Searching for 4 in {1, 3, 5, 7, 9} starting from \((lo,hi) = (0,4)\) produces the interval sequence \((0,4)\), \((0,2)\), \((1,2)\), \((1,2)\), \((1,2)\), forever: at \(lo = 1, hi = 2\) the midpoint is \(\lfloor 3/2 \rfloor = 1\), the key 4 exceeds \(a[1] = 3\), so \(lo\) is set to \(mid = 1\), which is where it already was. The interval stops shrinking, lo > hi is never reached, and the program overflows the stack. With mid - 1 and mid + 1 the interval loses at least the midpoint on every call, so its width is a genuine progress measure and the same search correctly returns \(-1\).

The check that catches both (a) and (b) Name the progress measure out loud, and confirm three things about it: it is a non-negative integer, it is strictly smaller in every recursive call, and the base case triggers whenever it can no longer shrink. factBad fails the third check, searchBad fails the second.

(c) Recomputation blowup

This failure produces correct answers, slowly enough to be useless. The textbook case is the Fibonacci recurrence transcribed directly into code: 

  long fib(int n) {
      if (n < 2) return n;                 // base cases: fib(0)=0, fib(1)=1
      return fib(n - 1) + fib(n - 2);      // two calls, each barely smaller
  }

The subproblems overlap: fib(5) calls fib(3) twice, fib(2) three times, and fib(1) five times, recomputing each from scratch. Let \(C(n)\) be the number of calls; then \(C(0) = C(1) = 1\) and \(C(n) = 1 + C(n-1) + C(n-2)\), whose solution is \(C(n) = 2F(n+1) - 1\) where \(F\) is Fibonacci itself. The call count therefore grows like the Fibonacci numbers, that is like \(\varphi^n\) with \(\varphi \approx 1.618\), which is exponential:

Adding a table of already-computed values (memoisation) collapses the count to \(2n - 1\) calls, because each of the \(n\) distinct subproblems is solved once and every later request is a table hit. The fix is not specific to Fibonacci: whenever a recursion revisits the same subproblem along different branches, storing subresults converts exponential time to the number of distinct subproblems. That observation is the whole content of The Dynamic Programming Method, which develops memoisation and its bottom-up counterpart systematically. Note the contrast with mergesort’s \(T(n) = 2T(n/2) + n\): two calls are not the problem, calls on overlapping subproblems are.

(d) Depth that exceeds the stack

The last failure is a correct, terminating recursion whose depth is simply too large. A traversal of a balanced tree of a million nodes is about 20 frames deep and safe; the same traversal of a tree that has degenerated into a chain of a million nodes is a million frames deep and crashes. So does a linear recursion over a long list. The remedies are the ones this handout has already covered: bound the depth by keeping the structure balanced (see AVL Trees), or move the stack off the call stack by hand (§7). The cost model for the frames themselves is in Space Complexity.

9. Where this sits

Recursion is the writing technique and induction is the proof technique for most of the catalog. The tree operations of Binary Search Trees and the balance arguments of AVL Trees are structural recursion and structural induction throughout. The Divide-and-Conquer Method generalises §6 into the master theorem and applies it to Mergesort and Quicksort. The Dynamic Programming Method is the systematic cure for §8(c). Depth-First Search is structural recursion over a graph, where the extra difficulty is that the structure has cycles, so a visited set replaces the automatic progress measure that trees provide.

On the analysis side, the recurrences of §6 are the cost equations whose solutions are expressed in the notation of Asymptotic Notation and measured in Analysis of Algorithms: Time; the frames of §2 are the stack term of Space Complexity. Induction also underlies arguments that are not about recursive code at all: the decision-tree bound of The Sorting Lower Bound and the potential arguments of Amortized Analysis are both inductions in disguise.

10. Exercises (with solutions)

  1. Write out the full push/pop trace of sum(3) for the sum of §1, giving the value each frame returns, and state the peak depth.
    solution Push sum(3) (depth 1), push sum(2) (depth 2), push sum(1) (depth 3), push sum(0) (depth 4, peak). Then pop sum(0) returning 0; pop sum(1) returning \(1 + 0 = 1\); pop sum(2) returning \(2 + 1 = 3\); pop sum(3) returning \(3 + 3 = 6\). Peak depth is \(n+1 = 4\) frames (one more than fact’s \(n\), because this base case is \(n = 0\) rather than \(n \le 1\)), and \(6 = 3\cdot 4/2\) agrees with Theorem 2. Every addition happens during the pops.
  2. Prove by induction that \(\sum_{k=0}^{n} 2^k = 2^{n+1} - 1\) for all \(n \ge 0\), and say where the identity is used in §6.
    solution Base (\(n=0\)). The left side is \(2^0 = 1\); the right side is \(2^1 - 1 = 1\). Step. Let \(n \ge 1\) and assume \(\sum_{k=0}^{n-1} 2^k = 2^{n} - 1\). Then \(\sum_{k=0}^{n} 2^k = \bigl(\sum_{k=0}^{n-1} 2^k\bigr) + 2^n \overset{\text{IH}}{=} (2^n - 1) + 2^n = 2\cdot 2^n - 1 = 2^{n+1}-1\). By induction the identity holds for all \(n \ge 0\). It is the geometric sum that closes the Hanoi unrolling (\(\sum_{j=0}^{n-1}2^j = 2^n - 1\)) and the level sum that makes \(T(n) = 2T(n/2) + c\) linear rather than logarithmic.
  3. Explain why Theorem 3 (correctness of power) cannot be proved by ordinary induction as stated, and identify the single line of the proof that needs the strong hypothesis.
    solution Ordinary induction supplies only \(P(n-1)\) in the step. The code recurses on \(\lfloor n/2 \rfloor\), which equals \(n-1\) only for \(n \in \{1, 2\}\); for \(n = 13\) the hypothesis on hand would concern 12 while the proof needs 6. The line that needs strong induction is “\(0 \le h \lt n\), so the inductive hypothesis applies to \(h\)”: it invokes \(P\) at an arbitrary smaller value, which only the strong form grants. (One can recover ordinary induction by restating the claim as \(Q(n) =\) “\(P(m)\) for all \(m \le n\)”, which is the standard way of showing the two principles have equal strength; that reformulation is itself the strong hypothesis in disguise.)
  4. Unroll \(T(n) = T(n-1) + n\) with \(T(0) = 0\) to a closed form, and name an algorithm with this cost.
    solution \(T(n) = T(n-1) + n = T(n-2) + (n-1) + n = \cdots = T(n-i) + \sum_{j=n-i+1}^{n} j\). Taking \(i = n\) reaches \(T(0) = 0\) and leaves \(T(n) = \sum_{j=1}^{n} j = n(n+1)/2\) by Theorem 1, so \(T(n) = \Theta(n^2)\). This is quicksort’s worst case, where each partition peels off a single element and leaves \(n-1\) behind, and it is also the comparison count of selection sort.
  5. The recursion \(T(n) = 2T(n/2) + c\) and the recursion \(T(n) = 2T(n/2) + n\) differ only in the work done per call, yet their solutions are \(\Theta(n)\) and \(\Theta(n\log n)\). Explain the difference by summing levels, and say which level dominates in each.
    solution Both recursion trees have \(\log_2 n\) levels, with \(2^i\) subproblems of size \(n/2^i\) at level \(i\). With combining work \(c\), level \(i\) costs \(c\,2^i\), so the level costs form a geometric series that doubles: the total \(c(2n-1)\) is dominated by the last level (the \(n\) leaves), giving \(\Theta(n)\). With combining work equal to the subproblem size, level \(i\) costs \(2^i \cdot n/2^i = n\), the same at every level, so no level dominates and the total is (number of levels) \(\times\, n = n\log_2 n\). Uniform level costs are the signature of the \(n\log n\) sorts; geometrically growing level costs are the signature of leaf-dominated linear traversals.
  6. Convert this recursion to a loop, and state the stack space of each version: int gcd(int a, int b) { return b == 0 ? a : gcd(b, a % b); }.
    solution Every recursive call is a tail call (its value is returned directly), so the conversion is the mechanical one of §7: parameters become variables, the base test becomes the loop exit, the call arguments become the updates. int gcd(int a, int b) { while (b != 0) { int t = a % b; a = b; b = t; } return a; }. The recursive version uses one frame per call, and the number of calls is \(O(\log(\min(a,b)))\) since the remainder at least halves every two steps, so its stack is \(O(\log \min(a,b))\); the loop uses \(\Theta(1)\). A compiler performing tail-call optimisation would produce the loop from the recursive source, but the standard does not require it.
  7. For the §3 tree, hand-execute the explicit-stack traversal but with the two branches of the if swapped (visit on push instead of on pop). What order comes out, and what has been computed?
    solution Appending the key at push time and still descending left gives 50, 30, 20, 40, 70, 60, 80: a pre-order traversal (node, then left subtree, then right subtree). Nothing else changes, because the stack still records the nodes whose right subtrees are owed. The lesson is that the three classic traversals differ only in when the visit happens relative to the two recursive calls: before both (pre-order), between them (in-order), after both (post-order). Only in-order yields sorted output on a binary search tree; the pre-order output above is not sorted.
  8. A student memoises fib and reports that fib(40) now returns instantly, then claims “memoisation makes any exponential recursion fast”. Give a recursion where memoisation does not help, and state the property that decides the matter.
    solution Towers of Hanoi: \(T(n) = 2T(n-1) + 1\) makes \(2^n - 1\) moves, and every call is on a distinct problem instance (a different disk count with a different peg assignment), so a table of subresults never scores a hit and the count is unchanged. The deciding property is overlapping subproblems: memoisation reduces the running time to (number of distinct subproblems) \(\times\) (work per subproblem). Fibonacci has \(n\) distinct subproblems reached exponentially often, so the win is from \(2F(n+1)-1\) calls down to \(2n-1\). Hanoi’s exponential count is the size of its output (it really must make \(2^n - 1\) moves), which no table can shrink. The same distinction separates the problems that The Dynamic Programming Method solves from those it does not.
