C++ for Data Structures

“C makes it easy to shoot yourself in the foot; C++ makes it harder, but when you do it blows your whole leg off.” Bjarne Stroustrup, who confirms the remark in his FAQ (“Did you really say that?”)

A linked list, a binary search tree, a hash table and a graph are all built from the same few C++ mechanisms: an object that refers to other objects through pointers, nodes allocated one at a time on the heap, and a class that is responsible for freeing them. When these mechanisms are misunderstood, the resulting bugs are not wrong answers but crashes, corrupted data and memory that is never returned, and they often appear far from the line that caused them. This chapter states each mechanism precisely, shows what goes wrong without it, and ends with the tools that detect the errors. The machine-level view of memory (caches, pages, the compiler) is in the companion Computer Systems Primer.

1. Objects, names and lifetimes

An object in C++ is a region of memory that holds a value of some type: an int, a double, a struct. A variable is a name for an object. Every object has a lifetime, the interval during which it exists, and using an object outside its lifetime is an error that the language does not catch for you.

Definition (storage duration) An automatic object is a local variable or parameter. It is created when execution reaches its declaration and destroyed when the enclosing block (the code between a pair of braces) ends. A dynamic object is created by new and lives until a matching delete, regardless of blocks. A static object (a global variable, or a local declared static) lives for the whole run of the program.

Automatic objects live in the function’s stack frame: when a function is called, a block of memory is reserved for its parameters and locals, and when it returns that block is released all at once. Dynamic objects live on the heap, a separate pool managed by the program at run time. The Space Complexity chapter counts the bytes in each; this chapter is about using them correctly. 

void f() {
    int a = 1;              // automatic: created here
    {
        int b = 2;          // automatic: created here
    }                       // b destroyed here
    int* p = new int(3);    // p is automatic; *p is dynamic
    delete p;               // *p destroyed here
}                           // a and p destroyed here

The pointer p and the integer it points to have different lifetimes. Destroying p at the closing brace does not destroy *p; without the delete, the integer would remain allocated with nothing left that knows its address. That situation, a memory leak, is the first of the errors this chapter teaches you to avoid.

2. References and pointers

C++ has two ways for one name to refer to an object that another name also refers to.

Definition (reference) A reference int& r = x; is another name for the existing object x. It must be initialized when it is declared, it always refers to the same object afterwards, and there is no null reference. Using r is using x.
Definition (pointer) A pointer int* p = &x; is an object whose value is the address of another object. &x takes the address of x; *p (dereferencing) is the object at that address. A pointer can be changed to point elsewhere, and it can hold the special value nullptr, which points to no object. 
int x = 10, y = 20;
int& r = x;      // r is x
int* p = &x;     // p holds x's address
r = 11;          // x is now 11
*p = 12;         // x is now 12
p = &y;          // p now points to y; x is unchanged
*p = 21;         // y is now 21
r = y;           // NOT a rebinding: copies y's value into x, so x is 21

The last line is a frequent source of confusion. A reference cannot be made to refer to a different object; assigning to it assigns to the object it already names. This is why data structures use pointers, not references, for links: a list node’s next must be able to change, and the last node needs a next that refers to nothing.

For a pointer to a struct, p->key is shorthand for (*p).key. Dereferencing nullptr, or a pointer whose object no longer exists, is undefined behaviour: the language makes no promise about what happens. The program may crash, may print a plausible wrong value, or may appear to work until the input changes. Every traversal of a linked structure therefore tests for nullptr before following a link.

3. Passing arguments and returning results

How a parameter is declared decides what the function receives, whether it can change the caller’s variable, and whether a copy is made. 

void byValue(int x)  { x = 99; }
void byRef(int& x)   { x = 99; }
void byPtr(int* x)   { *x = 99; }

int main() {
    int a = 1, b = 1, c = 1;
    byValue(a);
    byRef(b);
    byPtr(&c);
    cout << a << " " << b << " " << c << "\n";   // prints 1 99 99
}

The cost of a copy

Passing by value copies the whole argument. For an int that is free; for a vector of \(N\) elements it is \(N\) element copies and a heap allocation on every call. A function that sums a vector of 1000 elements whose element type counts its own copies shows the difference directly: 

long sumByValue(vector<Tracked> a)          { ... }   // 1000 element copies per call
long sumByConstRef(const vector<Tracked>& a) { ... }   // 0 copies

A function called once per element of a loop that copies an \(N\)-element argument turns a linear algorithm into a quadratic one without any change to its visible logic. The rule that follows is the default in this book:

Rule (choosing a parameter) Pass small values (int, double, a pointer) by value. Pass objects the function only reads (containers, strings, structs) by const reference. Pass by non-const reference when the function must change the caller’s object. Use a pointer when “no object” is a legal argument, as for the Node* of an empty subtree.

Returning results

A function may return a reference or a pointer only to an object that outlives the call. Returning the address of a local variable is the standard lifetime error: 

int* makeA() { int x = 7; return &x; }    // BUG: x dies at return
int* makeB() { return new int(7); }        // correct; the caller must delete

makeA returns a dangling pointer: the address of a stack slot that the next function call will reuse. Returning a large object by value, on the other hand, is not expensive in modern C++: the compiler constructs the result directly in the caller’s variable or moves it, so vector<int> build(int n) is the normal way to return a container.

4. The heap: new and delete

A data structure that grows while the program runs cannot keep its nodes in stack frames, because the frame disappears when the function that created the node returns. Nodes are therefore allocated on the heap. 

struct Node {
    int   key;
    Node* next;
    Node(int k, Node* n) : key(k), next(n) {}
};

Node* head = nullptr;
head = new Node(8, head);     // list: 8
head = new Node(5, head);     // list: 5 8
head = new Node(3, head);     // list: 3 5 8
head

new Node(3, head) allocates space for one Node on the heap, runs its constructor, and returns the address. The node lives until delete is applied to that address. An array allocated with new T[n] must be freed with delete[], not delete.

Definition (three heap errors) A memory leak: a heap object that is never deleted, usually because the last pointer to it was overwritten or went out of scope. A dangling pointer: a pointer to an object that has already been deleted (or to a dead local); using it is undefined behaviour. A double delete: deleting the same object twice, which corrupts the heap’s own bookkeeping and typically crashes later, at an unrelated allocation.

All three come from the same question left unanswered: which part of the program is responsible for deleting this object? The answer C++ programs give is ownership by a class.

5. Classes that own memory: the destructor

Definition (ownership, destructor) A class owns a heap object when it is the one place in the program responsible for deleting it. Its destructor, written ~ClassName(), runs automatically when an object of the class is destroyed (at the end of its block for an automatic object, at delete for a dynamic one) and is where the owned objects are freed. 
class IntList {
public:
    ~IntList() {
        while (head != nullptr) {
            Node* doomed = head;
            head = head->next;      // read next BEFORE deleting the node holding it
            delete doomed;
        }
    }
    void pushFront(int key) { head = new Node(key, head); }
private:
    Node* head = nullptr;
};

The order of the two middle lines matters. After delete doomed, the node no longer exists, so reading doomed->next would be a use of a dangling pointer. The loop saves the link first.

Tying the release of a resource to the destructor of the object that owns it is called RAII (Resource Acquisition Is Initialization). Its benefit is that cleanup cannot be forgotten: when an IntList goes out of scope, every node it owns is freed, whether the block ended normally, by an early return, or by an exception. The standard containers (vector, string, map) all work this way.

6. Copying: the Rule of Three

If a class declares no copy operations, the compiler writes them: the generated copy constructor and copy assignment copy each member in turn. For an IntList whose only member is head, that copies one pointer. 

{
    IntList a;                 // a owns 3 nodes
    a.pushFront(8); a.pushFront(5); a.pushFront(3);
    IntList b = a;             // generated copy: b.head == a.head
    b.setFirst(99);            // changes a's first node too
}                              // b's destructor frees the 3 nodes, then
                               // a's destructor walks and frees them again
Definition (shallow and deep copy) A shallow copy copies the pointers an object holds, so the original and the copy share the objects pointed to. A deep copy allocates new objects with the same values, so the copy owns objects of its own.

The shallow copy above has two symptoms. Changing b changes a, and at the end of the block both destructors delete the same three nodes: a double delete. A class that owns memory must therefore replace the generated copy operations.

Rule of Three If a class needs a user-written destructor, copy constructor, or copy assignment operator, it almost certainly needs all three. A destructor that frees owned memory means the generated (shallow) copies are wrong.

The copy constructor

The copy constructor builds a new object from an existing one. For a list it walks the source and appends a new node for each, keeping the order: 

IntList(const IntList& other) {
    Node* tail = nullptr;
    for (const Node* p = other.head; p != nullptr; p = p->next) {
        Node* n = new Node(p->key, nullptr);
        if (tail == nullptr) head = n;      // first node
        else                 tail->next = n; // append after the last
        tail = n;
    }
}

Building the copy with pushFront would be shorter and wrong: it reverses the list.

Copy assignment

Assignment c = a; differs from construction in one way: c already exists and already owns nodes. Assignment must free those first, then copy, and must survive being asked to assign an object to itself. 

IntList& operator=(const IntList& other) {
    if (this != &other) {        // self-assignment guard
        clear();                 // free the nodes this list owns
        copyFrom(other);         // then deep-copy, as the copy constructor does
    }
    return *this;                // allows c = b = a
}

Without the guard, c = c; would free c’s nodes and then try to copy from them. The return value *this lets assignments chain, as they do for built-in types. A program that builds a list, copies it, assigns over another and assigns a list to itself, counting nodes as they are created and destroyed, ends with exactly as many deletions as allocations: 

a: 3 -> 5 -> 8
after b = a; b.setFirst(99)
a: 3 -> 5 -> 8
b: 99 -> 5 -> 8
c: 3 -> 5 -> 8
live nodes inside the block: 9
live nodes after the block:  0
Beyond three C++11 added two more operations, the move constructor and move assignment, which transfer ownership from an object that is about to be destroyed instead of copying it (the Rule of Five). The opposite approach, the Rule of Zero, avoids writing any of the five by holding resources only through members that already manage themselves, such as vector or std::unique_ptr. Production code prefers the Rule of Zero; this book writes the Rule of Three out by hand because the data structures it studies are the kind of class that sits underneath those members.

7. Templates and the standard library

A template is code written once for any type. A function template states its type as a parameter, and the compiler generates a separate version for each type it is used with: 

template <class T>
T largest(const vector<T>& a) {      // a must be non-empty
    T best = a[0];
    for (const T& x : a) if (best < x) best = x;
    return best;
}
largest(vector<int>{3, 9, 4});         // 9
largest(vector<string>{"b", "c", "a"}); // "c"

The only requirement largest places on T is that it can be copied and compared with <. A class template such as template <class Key, class Value> class BST works the same way, and is how the symbol tables of this book are written.

The Standard Template Library (STL) provides the containers and algorithms used throughout:

A vector keeps its size (elements in use) separate from its capacity (elements allocated). push_back is constant time on average because the capacity doubles when it runs out, and the occasional full copy is paid for by the many cheap appends before it. A pointer or reference to an element can dangle after a push_back that reallocates, because the elements move to a new array. 

vector<int> v = {1, 2, 3};
int& first = v[0];
v.push_back(4);      // may reallocate: 'first' may now dangle

8. Finding memory errors

Memory errors rarely fail where they happen. A double delete corrupts the allocator, and the crash comes at some later, unrelated new; a leak produces no symptom at all until memory runs out. Three tools find these errors at the line that causes them.

toolhow to use itwhat it reports
compiler warningsg++ -std=c++17 -Wall -Wextrauninitialized variables, unused results, suspicious conversions, at compile time
sanitizersg++ -std=c++17 -g -fsanitize=address,undefined, then runuse after free, double delete, out-of-bounds access, signed overflow, leaks (on Linux), each with the line that caused it
Valgrindg++ -std=c++17 -g, then valgrind --leak-check=full ./prog (Linux)invalid reads and writes, uses of uninitialized values, and every leaked block with the line that allocated it

The -g flag stores the source line of every instruction in the program, which is what lets these tools name lines instead of addresses. A clean Valgrind run ends with 

All heap blocks were freed -- no leaks are possible
ERROR SUMMARY: 0 errors from 0 contexts

The shallow-copy program of section 6, run under the address sanitizer, stops inside the second destructor with a report that begins ERROR: AddressSanitizer: heap-use-after-free: before that destructor can delete a node a second time, it reads the node’s next field, and the node was already freed by the first destructor. The report gives three stack traces: the bad read, where the memory was freed, and where it was allocated. A program that runs correctly on one input is not thereby free of memory errors; running the tests under a sanitizer or Valgrind is part of testing.

9. Exercises (with solutions)

  1. What does this print? 
    void f(int a, int& b, int* c) { a++; b++; (*c)++; c = nullptr; }
int main() { int x = 1, y = 1, z = 1; f(x, y, &z); cout << x << y << z; }
    solution 122. a is a copy, so x stays 1. b is y, so y becomes 2. c holds the address of z, so (*c)++ makes z 2. Setting c to nullptr changes only the function’s own copy of the address.
  2. After int x = 5, y = 7; int& r = x; r = y; r = 9;, what are x and y?
    solution x is 9 and y is 7. r = y copies the value 7 into x; it does not make r refer to y. Then r = 9 sets x to 9.
  3. A function bool contains(vector<int> a, int key) scans for a key, and is called once for each of \(N\) keys against a vector of \(N\) elements. What is the total cost, and what one-character change fixes it?
    solution Each call copies the \(N\)-element vector (\(N\) element copies) and then scans it (up to \(N\) comparisons), so \(N\) calls cost on the order of \(N^2\) copies in addition to the scans. Declaring the parameter const vector<int>& a removes the copies. The scans remain quadratic in total, but the copying, which also allocates on every call, is gone.
  4. This destructor is wrong. Explain the error and fix it. 
    ~IntList() { for (Node* p = head; p != nullptr; p = p->next) delete p; }
    solution After delete p, the update p = p->next reads a field of a node that no longer exists: a use of a dangling pointer. Save the link first: while (head) { Node* d = head; head = head->next; delete d; }.
  5. A class Stack holds int* data allocated with new int[cap] and frees it in its destructor. It declares no copy constructor. What happens in { Stack s; Stack t = s; }?
    solution The generated copy constructor copies the pointer, so s and t share one array. At the closing brace t is destroyed first and frees the array, then s frees it again: a double delete. Any change through one of them in between would also be visible through the other.
  6. Write the copy assignment operator for the Stack of the previous exercise, which also has members int size and int cap.
    solution 
    Stack& operator=(const Stack& other) {
    if (this != &other) {
        delete[] data;
        cap = other.cap;
        size = other.size;
        data = new int[cap];
        for (int i = 0; i < size; i++) data[i] = other.data[i];
    }
    return *this;
}
    Note delete[], matching new int[cap].
  7. Why does this assignment operator fail on a = a;? 
    IntList& operator=(const IntList& other) { clear(); copyFrom(other); return *this; }
    solution When other is the same object as *this, clear() deletes every node, leaving head null, and copyFrom(other) then copies an empty list. The list silently becomes empty. (If clear did not reset head, copyFrom would read deleted nodes instead.) The guard if (this != &other) prevents both.
  8. vector<int> v(4); int* p = &v[0]; v.push_back(1); *p = 7; Is this correct?
    solution Not necessarily. If the push_back finds the capacity full (here the capacity is 4, so it is), the vector allocates a larger array, moves the elements, and frees the old one. p then points into freed memory, and *p = 7 is undefined behaviour. Take the pointer after the last operation that can grow the vector, or keep an index instead.
