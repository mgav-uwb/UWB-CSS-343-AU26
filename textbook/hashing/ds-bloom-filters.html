Bloom Filters

Burton Bloom’s 1970 paper motivated the filter with hyphenation: most words follow simple rules, and a compact filter in memory flags the few exceptions that need a lookup on disk. B. H. Bloom, “Space/Time Trade-offs in Hash Coding with Allowable Errors,” CACM 13(7), 1970

A hash table answers “is key \(x\) in the set?” exactly, but to do so it must store the keys: comparing is how it confirms a hit, so the keys themselves have to be there to compare against. That storage is the cost. A set of a billion 64-bit keys is at least 8 GB before any table overhead. A Bloom filter asks what happens if we throw the keys away and keep only a few hash bits per key. The answer: membership in about 10 bits per key, regardless of key size, at the price of a new kind of answer. The filter never says “yes”; it says definitely not or maybe, and the “maybe” is wrong a tunable percent of the time. This handout is about that contract: how the structure works, why one error direction is impossible, and how to compute and control the other.

1. Membership with one-sided error

The question a Bloom filter answers is the plain membership query: given a key \(x\), is \(x\) in the set \(S\) of keys inserted so far? What is new is the shape of the answer.

Definition (one-sided error) A membership structure has one-sided error when its two answers carry different guarantees:
  • “no” is certain: the key was never inserted (no false negatives);
  • “maybe” is probabilistic: the key was inserted, or the structure has confused it with the keys that were (a false positive, occurring with some probability \(p\)).
A Bloom filter delivers exactly this contract, with \(p\) set by how much space you give it.

An answer like that sounds weak until you notice how many systems ask membership questions where the two errors have wildly different prices, and the cheap error is exactly the one the filter permits. The pattern: a fast, small filter sits in front of a slow, exact store. A “no” from the filter skips the expensive step entirely and is always safe to trust; a “maybe” falls through to the exact check, which quietly absorbs the false positives.

  • A database in front of its disk. Log-structured storage engines (LevelDB, RocksDB, Cassandra, HBase) keep a Bloom filter in memory for each on-disk table file. A lookup consults the filters first; “definitely not here” skips the disk read. A false positive costs one wasted read; a false negative would lose data, and the filter cannot make one.
  • A browser in front of the network. A compact filter of known-malicious URL prefixes ships inside the browser. Most pages get “definitely not on the list” locally and load at once; the rare “maybe” triggers a round-trip to the real list.
  • A cache deciding what to admit. Admission policies ask “have I seen this item recently?” A filter answers in nanoseconds from a few megabytes; a stray “maybe” merely admits one item early.
  • A password checker in front of a blocklist. “Is this password on the leaked list?” A false positive asks a user to pick a different password; harmless. A false negative would wave a leaked password through; the filter cannot do it.

The common thread: the filter is worth it when a false positive costs a little extra work and a false negative would be a correctness bug. Where both answers must be exact (does this username exist? is this seat taken?) a Bloom filter is the wrong tool; use a hash table (Hashing) and pay for the keys.

2. The structure: \(m\) bits, \(k\) hash functions

Definition (Bloom filter) A Bloom filter is a bit array \(B[0..m-1]\), initially all \(0\), together with \(k\) hash functions \(g_0, g_1, \dots, g_{k-1}\), each mapping keys to positions \(\{0, \dots, m-1\}\). The operations:
  • insert(\(x\)): set the \(k\) bits \(B[g_0(x)], B[g_1(x)], \dots, B[g_{k-1}(x)]\) to \(1\).
  • query(\(x\)): if every one of those \(k\) bits is \(1\), answer “maybe”; if any is \(0\), answer “definitely not.”
There is no delete (§4).

That is the entire structure: no keys, no pointers, no buckets, just \(m\) bits and \(k\) ways of pointing into them. Each inserted key stamps its \(k\)-bit signature into the array; a query checks whether the signature is fully stamped. The two answers inherit their guarantees directly:

  • No false negatives. Inserting \(x\) sets all \(k\) of \(x\)’s bits, and no operation ever clears a bit, so if \(x\) was inserted its bits are all still \(1\) and every later query answers “maybe.” (This is a theorem, and its whole proof is the monotonicity of the bits; exercise 6 asks you to write it out.)
  • False positives possible. A key that was never inserted can find all \(k\) of its bits set anyway, each one turned on by some other key whose signature happens to overlap. The denser the array, the likelier the accident; §5 computes the probability.

The \(k\) hash functions must be deterministic, fast, and spread keys uniformly, the same requirements as for a hash table (Hashing covers them). In practice nobody implements \(k\) independent hashes; two suffice. Compute two base hashes \(h_1(x)\) and \(h_2(x)\) and derive the \(k\) positions by double hashing: \[ g_i(x) \;=\; \bigl(h_1(x) + i \cdot h_2(x)\bigr) \bmod m, \qquad i = 0, 1, \dots, k-1. \] This costs two hash evaluations instead of \(k\) and, for filter purposes, distributes as well as \(k\) independent hashes. 

// Bloom filter: m bits, k positions per key derived from two base
// hashes by double hashing: g_i(x) = (h1(x) + i*h2(x)) mod m.
struct BloomFilter {
    vector<bool> bits;                    // m bits, all initially false
    int m, k;
    BloomFilter(int m, int k) : bits(m, false), m(m), k(k) {}

    void insert(const Key& x) {
        size_t a = h1(x), b = h2(x);
        for (int i = 0; i < k; i++)
            bits[(a + i * b) % m] = true;   // set all k bits
    }
    bool query(const Key& x) const {        // false = DEFINITELY absent
        size_t a = h1(x), b = h2(x);
        for (int i = 0; i < k; i++)
            if (!bits[(a + i * b) % m])
                return false;               // one 0 bit proves absence
        return true;                        // "maybe": all k bits set
    }
};

# Bloom filter: m bits, k positions per key derived from two base
# hashes by double hashing: g_i(x) = (h1(x) + i*h2(x)) mod m.
class BloomFilter:
    def __init__(self, m, k):
        self.m, self.k = m, k
        self.bits = [False] * m           # m bits, all initially False

    def _positions(self, x):
        a, b = h1(x), h2(x)               # two base hashes
        return [(a + i * b) % self.m for i in range(self.k)]

    def insert(self, x):
        for p in self._positions(x):
            self.bits[p] = True           # set all k bits

    def query(self, x):                   # False = DEFINITELY absent
        return all(self.bits[p] for p in self._positions(x))
// Bloom filter: m bits, k positions per key derived from two base
// hashes by double hashing: g_i(x) = (h1(x) + i*h2(x)) mod m.
struct BloomFilter { bits: Vec<bool>, m: usize, k: usize }

impl BloomFilter {
    fn new(m: usize, k: usize) -> Self {
        BloomFilter { bits: vec![false; m], m, k }
    }
    fn insert(&mut self, x: &Key) {
        let (a, b) = (h1(x), h2(x));
        for i in 0..self.k {
            self.bits[(a + i * b) % self.m] = true;  // set all k bits
        }
    }
    fn query(&self, x: &Key) -> bool {    // false = DEFINITELY absent
        let (a, b) = (h1(x), h2(x));
        (0..self.k).all(|i| self.bits[(a + i * b) % self.m])
    }
}

3. A filter traced bit by bit

Take \(m = 16\) and \(k = 3\), with integer keys and the two base hashes

\[ h_1(x) = x \bmod 16, \qquad h_2(x) = 1 + (x \bmod 15), \]

so the three positions of key \(x\) are \(g_i(x) = (h_1(x) + i\,h_2(x)) \bmod 16\) for \(i = 0, 1, 2\). (The \(1 +\) keeps the stride \(h_2\) nonzero, so the three positions do not all coincide; exercise 3 pokes at the one remaining wrinkle.) We insert the three keys \(42, 77, 103\) and then run three queries.

Insert 42

\[ h_1(42) = 42 \bmod 16 = 10, \qquad h_2(42) = 1 + (42 \bmod 15) = 1 + 12 = 13 \] \[ \begin{aligned} g_0(42) &= (10 + 0 \cdot 13) \bmod 16 = 10 \\ g_1(42) &= (10 + 1 \cdot 13) \bmod 16 = 23 \bmod 16 = 7 \\ g_2(42) &= (10 + 2 \cdot 13) \bmod 16 = 36 \bmod 16 = 4 \end{aligned} \]

Insert 77

\[ h_1(77) = 77 \bmod 16 = 13, \qquad h_2(77) = 1 + (77 \bmod 15) = 1 + 2 = 3 \] \[ \begin{aligned} g_0(77) &= (13 + 0 \cdot 3) \bmod 16 = 13 \\ g_1(77) &= (13 + 1 \cdot 3) \bmod 16 = 16 \bmod 16 = 0 \\ g_2(77) &= (13 + 2 \cdot 3) \bmod 16 = 19 \bmod 16 = 3 \end{aligned} \]

Insert 103: setting a bit that is already set

\[ h_1(103) = 103 \bmod 16 = 7, \qquad h_2(103) = 1 + (103 \bmod 15) = 1 + 13 = 14 \] \[ \begin{aligned} g_0(103) &= (7 + 0 \cdot 14) \bmod 16 = 7 \\ g_1(103) &= (7 + 1 \cdot 14) \bmod 16 = 21 \bmod 16 = 5 \\ g_2(103) &= (7 + 2 \cdot 14) \bmod 16 = 35 \bmod 16 = 3 \end{aligned} \]

The third insert lands on two bits that other keys already set: bit \(7\) belongs to both \(42\) and \(103\) now, bit \(3\) to both \(77\) and \(103\). Setting an already-set bit changes nothing, and nothing records who set a bit or how many keys rely on it. That anonymity is what makes the filter small, and it is also, in §4, what makes deletion impossible. Nine stamped positions, two overlaps: \(7\) of the \(16\) bits are now \(1\).

Query 77: a true positive

Its positions, computed above, are \(g_0 = 13\), \(g_1 = 0\), \(g_2 = 3\).

Query 6: a true negative, decided in one probe

\[ h_1(6) = 6 \bmod 16 = 6, \qquad h_2(6) = 1 + (6 \bmod 15) = 1 + 6 = 7 \] \[ \begin{aligned} g_0(6) &= (6 + 0 \cdot 7) \bmod 16 = 6 \\ g_1(6) &= (6 + 1 \cdot 7) \bmod 16 = 13 \\ g_2(6) &= (6 + 2 \cdot 7) \bmod 16 = 20 \bmod 16 = 4 \end{aligned} \]

One zero bit is a proof: had \(6\) ever been inserted, bit \(6\) would be \(1\). The query never looks at positions \(13\) and \(4\) (both of which happen to be \(1\); it does not matter).

Query 20: a false positive, assembled from other keys’ bits

\[ h_1(20) = 20 \bmod 16 = 4, \qquad h_2(20) = 1 + (20 \bmod 15) = 1 + 5 = 6 \] \[ \begin{aligned} g_0(20) &= (4 + 0 \cdot 6) \bmod 16 = 4 \\ g_1(20) &= (4 + 1 \cdot 6) \bmod 16 = 10 \\ g_2(20) &= (4 + 2 \cdot 6) \bmod 16 = 16 \bmod 16 = 0 \end{aligned} \]

This is the false positive anatomized. No single inserted key covers \(20\)’s signature; the accident is a collage, two bits borrowed from \(42\) and one from \(77\). The filter cannot tell a signature stamped by one insert from one assembled by coincidence, because bits carry no owner. Nothing malfunctioned: every step followed the definition, and the definition simply permits this outcome. How often? For this filter, with \(7\) of \(16\) bits set, a uniformly hashed absent key is accepted with probability about \((7/16)^3 \approx 0.084\), and a sweep of all keys up to \(10^5\) confirms it: \(8.3\%\) of absent keys come back “maybe.” The general formula is next-but-one; deletion first.

4. Why deletion is impossible

The obvious delete would clear the key’s \(k\) bits. Watch it fail on the running filter. Delete \(103\) by clearing its positions \(7, 5, 3\):

Bits \(7\) and \(3\) were shared: \(42\) needs bit \(7\) and \(77\) needs bit \(3\), and clearing them manufactures two false negatives, the one error the structure promised never to make. The promise of §2 rested entirely on bits never being cleared; delete breaks exactly that. Nor is there a clever fix within the bit array: a bit does not record how many keys stamped it, so no local examination can tell a safe clear (no other key uses this bit) from a catastrophic one. Deletion does not merely cost extra here, as it did with open addressing’s tombstones in Hashing; it is unimplementable without changing the structure. A Bloom filter grows monotonically until it is thrown away and rebuilt, which is how the database engines of §1 use it: one filter per immutable file, discarded with the file.

The counting-filter fix Replace each bit with a small counter (4 bits is the customary width). Insert increments the key’s \(k\) counters; delete decrements them; query asks whether all \(k\) counters are nonzero. Now bit \(7\) in the trace above would hold the count \(2\) (stamped by \(42\) and \(103\)), and deleting \(103\) would decrement it to \(1\): still nonzero, and \(42\) survives. The costs: the array is \(4\times\) larger for the same \(m\), a counter can overflow (with 4 bits, \(16\) keys on one counter; rare under uniform hashing, and implementations pin an overflowed counter at its maximum, giving up its deletability rather than its correctness), and deleting a key that was never inserted silently corrupts the filter by driving someone else’s counters toward zero. One-sided error is only preserved when deletes are honest.

5. The false-positive probability

Insert \(n\) keys into \(m\) bits with \(k\) hashes and query an absent key. How likely is “maybe”? Assume uniform hashing: every hash position is uniform on \(\{0,\dots,m-1\}\) and independent across hashes and keys (the same idealization as for hash tables, and the same caveat: the analysis is only as good as the hash functions).

Proposition (false-positive rate) After \(n\) inserts, the probability that a fixed absent key queries as “maybe” is approximately \[ p \;\approx\; \Bigl(1 - e^{-kn/m}\Bigr)^{\!k}. \]
Derivation. The \(n\) inserts perform \(kn\) independent bit-settings in total. Fix one bit. A single setting misses it with probability \(1 - \frac1m\), so after all \(kn\) settings the bit is still \(0\) with probability \[ \Bigl(1 - \frac1m\Bigr)^{kn} = \Bigl[\Bigl(1 - \frac1m\Bigr)^{m}\Bigr]^{kn/m} \;\approx\; e^{-kn/m}, \] using \((1 - \frac1m)^m \to e^{-1}\), the same approximation that priced the birthday phenomenon in Hashing. So any fixed bit is \(1\) with probability about \(1 - e^{-kn/m}\). The absent key is accepted exactly when all \(k\) of its positions hold a \(1\); treating those \(k\) events as independent multiplies the probabilities and gives \(p \approx (1 - e^{-kn/m})^k\). ∎

Two approximations were waved in: \(e^{-kn/m}\) for the exact \((1-\frac1m)^{kn}\), and independence of the \(k\) “my bit is set” events (they are mildly correlated through the shared count of set bits). Both errors vanish as \(m\) grows and are already small at modest sizes; the exact analysis is graduate-level bookkeeping, and the formula above is the one everyone sizes filters with.

Sanity-check it against the traced filter: \(m = 16\), \(n = 3\), \(k = 3\), so \(kn/m = 9/16\) and \(e^{-9/16} \approx 0.5698\), giving \(p \approx (1 - 0.5698)^3 = (0.4302)^3 \approx 0.080\). The measured rate on the actual filter was \(0.083\): the formula is honest even at sixteen bits. Now read it as a design tool. The quantity that matters is \(m/n\), bits per key: fix the budget and every added key costs the same slice of it.

6. Choosing \(k\): the optimal number of hashes

Theorem (optimal \(k\)) For fixed \(m\) and \(n\), the false-positive rate \(p(k) = (1 - e^{-kn/m})^k\) is minimized at \[ k^\* \;=\; \frac{m}{n}\,\ln 2 \;\approx\; 0.693\,\frac mn, \] at which point each fraction \(e^{-k^\*n/m} = \tfrac12\) (the array is half zeros, half ones) and \[ p_{\min} \;=\; \Bigl(\tfrac12\Bigr)^{k^\*} \;=\; 2^{-\,(m/n)\ln 2} \;\approx\; (0.6185)^{\,m/n}. \]
Proof sketch. Write \(c = n/m\) and minimize \(\ln p(k) = k \ln\bigl(1 - e^{-ck}\bigr)\). Substitute \(u = e^{-ck}\), so \(k = -\frac{\ln u}{c}\) and \[ \ln p \;=\; -\frac1c\,\ln u \,\ln(1-u), \qquad 0 < u < 1. \] The function \(\ln u \ln(1-u)\) is symmetric under \(u \leftrightarrow 1-u\), positive on \((0,1)\), and vanishes at both endpoints; it attains its maximum at the fixed point of the symmetry, \(u = \tfrac12\) (differentiating and using the symmetry makes this precise: the derivative at \(u=\frac12\) is zero, and it is the only interior critical point). Maximizing \(\ln u\ln(1-u)\) minimizes \(\ln p\), so the optimum is \(e^{-ck} = \tfrac12\), that is, \(k^\* = \frac{\ln 2}{c} = \frac mn \ln 2\). Substituting back: each of the \(k^\*\) factors of \(p\) equals \(\tfrac12\). ∎

The half-full array is the memorable part: the optimal filter is the one whose bit array carries maximum entropy, one bit of information per bit of storage. Fuller wastes queries’ discriminating power; emptier wastes space. Since \(k\) must be an integer, round \(k^\*\) and take the neighbor with the smaller \(p\); the curve is flat near the optimum, so the rounding costs little (the table in §5 shows it: \(k = 3, 4, 5\) all land within \(7\%\) of each other around \(k^\* = \frac{16}{3}\ln 2 \approx 3.70\)). The working engineer’s summary: about 10 bits per key buys a 1% false-positive rate, with \(k = 7\) hashes, whatever the keys are and however large each one is. Sizing a filter runs the theorem in reverse: given \(n\) and a target \(p\), take \(m = -\,n \ln p / (\ln 2)^2\) and \(k = -\log_2 p\) (exercise 5 does one).

7. Cost, and where the trade is worth it

operationcostnotes
insert\(\Theta(k)\)two base hashes, \(k\) bit-sets; no resizing, no collisions to resolve
query\(O(k)\)exits at the first \(0\) bit; a “maybe” costs exactly \(k\) probes
deletenot supportedcounting filter: same costs, \(4\times\) the space
space\(m\) bits\(\approx 10\,n\) bits at \(p = 1\%\); independent of key size

The costs need almost no argument, which is itself the point: with \(k\) fixed by the design, insert and query are constant-time by construction, not in expectation. There are no collisions to resolve, because the structure never distinguishes keys well enough for distinctness to be an issue; “collisions” are not a failure mode but the accepted, priced-in source of false positives. Compare the ledger against the exact alternative:

hash setBloom filter
answersyes / no, both exactmaybe / no (only “no” exact)
space per keythe key itself + table overhead (a 64-bit key: \(\ge 64\) bits, typically \(2\)–\(4\times\) more)\(\approx 10\) bits at \(p=1\%\), any key size
lookup\(\Theta(1)\) expected\(\Theta(k)\) worst case
delete / iterate / retrieve keysyesno; keys are gone

For 64-bit keys at \(p = 1\%\) the filter is \(6\times\) smaller than even a zero-overhead array of the bare keys, and the ratio grows without bound for strings: a filter of million-character URLs costs the same \(10\) bits per URL as a filter of small integers, because no key material is stored at all. That is the trade in one sentence: space independent of key size, bought by accepting a tunable false-positive rate and giving up deletion, iteration, and the keys themselves. The systems in §1 are precisely the ones for which every clause of that sentence is acceptable, and the exact stores behind them absorb the rest.

8. Where this sits

The prerequisite is Hashing: hash-function quality, the uniform-hashing idealization, and the \((1-\frac1m)^{\cdot} \approx e^{-\cdot/m}\) approximation all come from there, and the Bloom filter is what remains of a hash table when the keys are deleted from the design. Where a problem needs exact answers with ordered queries, the balanced-tree handouts (for instance AVL Trees) occupy the opposite corner: maximum structure retained, maximum space paid. The Bloom filter is also the entry point to a family of sketches, small lossy summaries with quantified error: a companion handout on the count-min sketch applies the same “few hashes into a small array” recipe to frequency estimation (how many times has \(x\) appeared?) rather than membership.

9. Exercises (with solutions)

  1. Continue the traced filter of §3 (final bit array 1001110100100100, bits \(0,3,4,5,7,10,13\) set): insert the key \(12\). Compute \(h_1, h_2\), the three positions, and the resulting bit array.
    solution \(h_1(12) = 12\), \(h_2(12) = 1 + 12 = 13\). Positions: \(g_0 = 12\); \(g_1 = (12+13) \bmod 16 = 25 \bmod 16 = 9\); \(g_2 = (12+26) \bmod 16 = 38 \bmod 16 = 6\). All three bits were \(0\), so the insert sets three fresh bits and the array becomes 1001111101110100 (bits \(0,3,4,5,6,7,9,10,12,13\) set: ten of sixteen).
  2. In §3, the query for key \(6\) answered “definitely not.” Re-run that query after the insert of \(12\) from exercise 1. What happens, and what general fact about Bloom filters does the change illustrate?
    solution The positions of \(6\) are \([6, 13, 4]\). Bit \(6\) was the zero that proved absence; the insert of \(12\) set it. Now bit \(6 = 1\), bit \(13 = 1\) (from \(77\)), bit \(4 = 1\) (from \(42\)): all set, so the query answers “maybe,” a false positive. Nothing about \(6\) changed; the filter around it filled in. This is the general fact that the false-positive rate is not a constant of the structure but a function of \(n\): every insert can only raise it (bits only turn on), which is why \(p \approx (1-e^{-kn/m})^k\) contains \(n\), and why a filter sized for \(n\) keys degrades when fed more.
  3. Compute the three positions of the key \(37\) in the §3 filter. Something is off about them; identify it, explain which choice in the construction allows it, and determine whether it threatens the filter’s one-sided-error guarantee.
    solution \(h_1(37) = 37 \bmod 16 = 5\), \(h_2(37) = 1 + (37 \bmod 15) = 8\). Positions: \(g_0 = 5\), \(g_1 = 13\), \(g_2 = (5 + 16) \bmod 16 = 5\): the first and third coincide, because the stride \(8\) satisfies \(2 \cdot 8 \equiv 0 \pmod{16}\). The double-hashing scheme only guarantees distinct positions when the stride is coprime to \(m\); \(h_2 = 8\) shares the factor \(8\) with \(m = 16\). The guarantee survives: correctness (§2) needs only “insert sets bits, query checks the same bits, bits are never cleared,” none of which requires the positions to be distinct. The cost is statistical: key \(37\) effectively probes \(2\) distinct bits instead of \(3\), so this key is easier to falsely accept (and indeed bits \(5\) and \(13\) are both set, so \(37\) queries as “maybe” here). Real implementations pick \(m\) prime, or force \(h_2\) odd with \(m\) a power of two, to keep every stride coprime to \(m\).
  4. A colleague proposes deleting \(103\) from the §3 filter by clearing bits \(7, 5, 3\). List every key of the set \(\{42, 77\}\) that this breaks, exhibit the broken query step by step, and name the error class produced.
    solution Both break. Query \(42\): positions \([10, 7, 4]\); bit \(7\) was cleared, so the loop stops at \(i=1\) with “definitely not,” though \(42\) was inserted. Query \(77\): positions \([13, 0, 3]\); bits \(13\) and \(0\) pass, bit \(3\) was cleared: “definitely not,” also wrong. These are false negatives, the error class a Bloom filter is defined never to produce; the shared bits (\(7\) with \(42\), \(3\) with \(77\)) are invisible to the delete because bits carry no count. A counting filter stores that count and decrements instead of clearing: bit \(7\)’s counter would go \(2 \to 1\) and both queries survive.
  5. Size a filter: \(n = 1000\) keys, target false-positive rate \(p = 1\%\). Give \(m\) (in bits and bytes) and \(k\), and verify your \(p\) by plugging back into the formula. Then compare the space with a plain array of the raw keys, taking them as 64-bit integers.
    solution \(m = -n \ln p / (\ln 2)^2 = 1000 \times 4.605 / 0.4805 \approx 9585\) bits \(\approx 1.2\) KB; bits per key \(m/n \approx 9.59\). \(k = -\log_2 p = \log_2 100 \approx 6.64\), round to \(k = 7\). Check: \(p = (1 - e^{-7/9.585})^7 \approx (1 - e^{-0.730})^7 \approx 0.0100\). The raw keys alone occupy \(1000 \times 64 = 64{,}000\) bits \(= 8\) KB, so the filter is about \(6.7\times\) smaller than even a zero-overhead exact store, before any hash-table overhead, and the ratio would grow with longer keys.
  6. Prove the no-false-negatives guarantee: if insert(x) was executed, every later query(x) answers “maybe.” State exactly which property of the operation set the proof depends on, and exhibit the (already seen) operation that would destroy it.
    solution insert(x) sets \(B[g_i(x)] = 1\) for all \(i = 0,\dots,k-1\). The only operations are insert and query: query writes nothing, and insert only ever assigns \(1\). Hence the predicate “\(B[j] = 1\)” is monotone: once true it stays true forever. In particular each \(B[g_i(x)]\), true when insert(x) returns, is still true at any later query(x), whose all-bits-set test therefore passes and answers “maybe.” The proof uses nothing about the hash functions (not even determinism across different keys, only that \(x\)’s own positions are recomputed identically, which determinism supplies). The destroying operation is any bit-clearing delete, as in exercise 4: it breaks monotonicity, and the guarantee falls with it.
  7. Keep \(n = 3\) and \(k = 3\) but double the array to \(m = 32\). Compute the new predicted false-positive rate and compare with the \(m = 16\) value \(p \approx 0.080\). Doubling the space more than halved \(p\); explain the mechanism.
    solution \(kn/m = 9/32 = 0.281\), so \(p = (1 - e^{-0.281})^3 = (0.245)^3 \approx 0.0147\): doubling \(m\) cut \(p\) by a factor of \(5.4\), not \(2\). The mechanism is the exponent \(k\): halving the fill \(kn/m\) roughly halves the per-bit probability \(1 - e^{-kn/m}\) (from \(0.430\) to \(0.245\) here), and the false positive needs all three of its bits set, so the improvement compounds three times: \((0.57)^3 \approx 0.18 \approx 1/5.4\). Space works on \(p\) through a \(k\)-th power; that is the same compounding read in §6 as “every \(1.44\) bits per key halves \(p\)” at optimal \(k\).
  8. Two Bloom filters \(F_A\) and \(F_B\) use the same \(m\) and the same hash functions, built over key sets \(A\) and \(B\). Show that the bitwise OR of their arrays is exactly the filter that would have been built over \(A \cup B\). Then explain why the bitwise AND is not exactly the filter of \(A \cap B\) (which side of the equality fails, and what it costs).
    solution OR: bit \(j\) of the filter of \(A \cup B\) is \(1\) iff some key of \(A \cup B\) has a position at \(j\), iff some key of \(A\) does or some key of \(B\) does, iff bit \(j\) is \(1\) in \(F_A\) or in \(F_B\). The arrays are equal bit for bit (this is why the database engines of §1 can merge filters when they merge files). AND: one direction holds: every key of \(A \cap B\) was inserted into both, so its bits are set in both and survive the AND; the AND-filter never falsely rejects a member of the intersection. The failure is the other containment: a bit can be \(1\) in \(F_A\) because of a key \(a \in A\setminus B\) and \(1\) in \(F_B\) because of a different key \(b \in B\setminus A\), so the AND keeps a bit that no key of \(A \cap B\) set. The AND-array can therefore strictly contain the array of the true intersection filter, and its false-positive rate is correspondingly higher than a filter built from \(A \cap B\) directly. One-sided error is preserved; only the rate suffers.
