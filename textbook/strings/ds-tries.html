Tries & Ternary Search Trees

Edward Fredkin coined “trie” in 1960 from the middle of “retrieval.” He pronounced it like “tree”; most people now say “try” to tell the two apart. E. Fredkin, “Trie Memory,” CACM 3(9), 1960

Every symbol table so far has treated its keys as opaque: a binary search tree compares whole keys, a hash table hashes whole keys. This handout’s keys are strings, and strings have internal structure (characters) that both of those tools ignore. A trie stores keys by their character path, so a lookup costs the key’s length \(L\), no matter whether the table holds a hundred keys or a billion, and the structure answers prefix queries (“everything starting with sh”) that a hash table cannot approach. One idea runs through the whole handout: a string is not an opaque key, and the structures that look inside it win.

1. String keys: what comparing and hashing miss

Store \(n\) string keys, each of length up to \(L\), in the symbol tables of the earlier handouts and count the character work. A balanced binary search tree (BST, Trees & Binary Search Trees) does \(O(\log n)\) key comparisons per search, but each comparison walks the two strings character by character, up to \(L\) steps, so a search really costs \(O(L \log n)\). A hash table (Hashing) does better: the polynomial string hash reads every character once, so a lookup is \(\Theta(L)\), but the price of that speed is that hashing deliberately scatters the keys, so the table is unordered and completely blind to prefixes. Neither tool can answer “list every key starting with sh” without scanning everything.

structurework per searchtotal
balanced BST\(O(\log n)\) compares, each up to \(L\) characters\(O(L \log n)\)
hash table\(O(1)\) probes, but the hash reads the whole key\(\Theta(L)\); no order, no prefixes

Both treat a string as one atomic value. The trie’s idea is to stop doing that: use the characters themselves as the search path. The result is \(\Theta(L)\) search, matching the hash table’s bound, while keeping the keys ordered and physically grouped by shared prefix, which is exactly the property the prefix operations of §4 exploit. The Substring Search: The Problem & Baselines handout applies the same “look inside the string” principle to a different problem: finding a pattern inside a text.

2. R-way tries

Definition (trie) A trie (from retrieval; pronounced “try”) is a tree that stores string keys along paths of characters from the root: each edge is labeled with one character, and each node carries an is-word flag marking whether some stored key ends there. A key is present exactly when its character path exists and the node it ends on is word-marked: “ends on” meaning the node reached after the key’s last character, which is not necessarily a leaf. In an R-way trie each node holds an array of \(R\) child pointers, one per character of the alphabet (\(R = 26\) for lowercase letters, \(R = 256\) for bytes).

Keys that share a prefix share the corresponding nodes: storing she and sea creates one s node with two children, not two separate paths. Here is the trie holding \(\{\)she, sea, sells\(\}\):

Search and insert are the same walk

Search follows next[c] for each character of the key in turn. If a needed child is missing, the walk falls off the trie and the key is absent. If the walk survives to the end of the key, the key is present iff the node it ends on is word-marked: the path might exist only as a prefix of a longer key. Insert is the identical walk, except that it creates each missing node along the way and sets the is-word flag on the node the key ends on. Neither operation ever compares two keys; the structure has encoded all the comparisons. Following a character is a single array index (t = t->next[c]), so both operations cost \(\Theta(L)\) for a key of length \(L\), independent of \(n\). 

// R-way trie: each node has one child slot per alphabet character plus an
// is-word flag. Operations walk ONE character per step: Theta(L) for a key of
// length L, independent of how many keys are stored.
const int R = 26;                          // alphabet: lowercase a..z

struct Node {
    Node* next[R] = {};                    // one slot per possible character
    bool  isWord = false;
};

// search: follow next[c] for each character. Fall off -> absent; reach the
// end -> present iff the node it ENDS ON is word-marked (not necessarily a leaf).
bool search(Node* t, const string& key) {
    for (char ch : key) {
        int c = ch - 'a';
        if (!t->next[c]) return false;     // fell off: no such path
        t = t->next[c];
    }
    return t->isWord;                      // path exists: is it a word?
}

// insert: the same walk, creating only the MISSING nodes; mark the last one.
void insert(Node* t, const string& key) {
    for (char ch : key) {
        int c = ch - 'a';
        if (!t->next[c]) t->next[c] = new Node();   // create the missing suffix
        t = t->next[c];
    }
    t->isWord = true;                      // mark: a key ends here
}

// collect: emit every key stored in the subtree under t (DFS, in order).
void collect(Node* t, string& path, vector<string>& out) {
    if (t->isWord) out.push_back(path);    // a stored key ends here
    for (int c = 0; c < R; c++)
        if (t->next[c]) {
            path.push_back('a' + c);       // extend the path by this character
            collect(t->next[c], path, out);
            path.pop_back();
        }
}

// keysWithPrefix (autocomplete): walk down the prefix, then collect the
// subtree below it. Theta(prefix length + output size).
vector<string> keysWithPrefix(Node* t, const string& prefix) {
    for (char ch : prefix) {               // 1. walk down the prefix path
        if (!t->next[ch - 'a']) return {}; // no key has this prefix
        t = t->next[ch - 'a'];
    }
    vector<string> out;
    string path = prefix;
    collect(t, path, out);                 // 2. gather the whole subtree below
    return out;
}

// R-way trie: each node has one child slot per alphabet character plus an
// is-word flag. Operations walk ONE character per step: O(L) for a key of
// length L, independent of how many keys are stored.
const R: usize = 26;                       // alphabet: lowercase a..z

struct Node {
    next: Vec<Option<Box<Node>>>,          // one slot per possible character
    is_word: bool,
}

fn new_node() -> Box<Node> {
    Box::new(Node { next: (0..R).map(|_| None).collect(), is_word: false })
}

// search: follow next[c] for each character. Fall off -> absent; reach the
// end -> present iff the node it ENDS ON is word-marked (not necessarily a leaf).
fn search(mut t: &Node, key: &str) -> bool {
    for ch in key.bytes() {
        match &t.next[(ch - b'a') as usize] {
            None => return false,          // fell off: no such path
            Some(kid) => t = kid,
        }
    }
    t.is_word                              // path exists: is it a word?
}

// insert: the same walk, creating only the MISSING nodes; mark the last one.
fn insert(mut t: &mut Node, key: &str) {
    for ch in key.bytes() {
        let c = (ch - b'a') as usize;
        t = t.next[c].get_or_insert_with(new_node);   // create missing suffix
    }
    t.is_word = true;                      // mark: a key ends here
}

// collect: emit every key stored in the subtree under t (DFS, in order).
fn collect(t: &Node, path: &mut String, out: &mut Vec<String>) {
    if t.is_word {                         // a stored key ends here
        out.push(path.clone());
    }
    for c in 0..R {
        if let Some(kid) = &t.next[c] {
            path.push((b'a' + c as u8) as char);   // extend by this character
            collect(kid, path, out);
            path.pop();
        }
    }
}

// keysWithPrefix (autocomplete): walk down the prefix, then collect the
// subtree below it. O(prefix length + output size).
fn keys_with_prefix(mut t: &Node, prefix: &str) -> Vec<String> {
    for ch in prefix.bytes() {             // 1. walk down the prefix path
        match &t.next[(ch - b'a') as usize] {
            None => return vec![],         // no key has this prefix
            Some(kid) => t = kid,
        }
    }
    let mut out = Vec::new();
    collect(t, &mut prefix.to_string(), &mut out); // 2. gather the subtree
    out
}

Example (a worked search, and the is-word subtlety) Take the trie holding \(\{\)she, shell, shells\(\}\) and search for shell: shel is a perfectly good path (it lies on the way to shell and shells), but no stored key ends there, so the flag correctly rejects it. Returning “did I reach the end of the path” instead of isWord is the classic trie-implementation bug.

All three keys here lie on a single root-to-leaf path, which makes the converse just as visible: the nodes for she and shell are word-marked and have children. So the two facts are independent, and both matter:

  • a node on a path need not be a key: shel;
  • a key need not sit at a leaf: she, whose node has an l child.

That second one is why isWord is a stored bit rather than a computed test: if every key ended at a leaf you could just ask “does this node have no children?” and drop the flag. It also fixes the vocabulary: “the node the key ends on” is right, “the final node” or “the leaf” is not. Only one direction does hold unconditionally: every leaf is word-marked, since nothing but an inserted key would have created it.

And note the cost: five character steps for shell, whether the trie holds these three keys or three million: adding keys never slows a search, only longer keys do.

Example (a worked insert) Insert sea into a trie holding \(\{\)she, shell\(\}\): Insert allocates only the missing suffix of its key (here two nodes) and reuses every shared-prefix node already present. That reuse is what keeps a trie compact on dictionary-like key sets full of common prefixes, and it is why insert, like search, touches at most \(L\) nodes.

Between them, the two walks have five endings, and a correct implementation is one that produces the right answer in each. A search ends in one of three ways: it falls off at a missing child (absent), it survives to a node that is word-marked (present), or it survives to a node that is not word-marked (absent, the key is only a prefix of stored keys). An insert ends in one of two: the walk finds every node it needs and only sets a flag (the key is a prefix of a stored key, allocating nothing), or it falls off at some depth and creates a fresh branch from there down (allocating one node per remaining character, none of them shared). The table below plays all five out on the trie drawn above, \(\{\)she, sea, sells\(\}\):

The two rows worth staring at are the pair sell/shed. Searching for sell and inserting sell take the identical four steps and touch the identical four nodes; the only difference is that insert writes the flag the search read. And a search that falls off is cheaper than the key is long: cat costs one step, no matter how many keys the trie holds, which is why a miss on a random word is nearly free. After all three inserts the trie holds \(6\) keys in \(11\) nodes, and no node was ever copied or moved: shared prefixes are shared structure, not duplicated text.

The cost, and the catch

operationcost
search / insert / delete\(\Theta(L)\): the key’s length
search missoften \(< L\): the walk falls off at the first missing child
spaceup to \(\Theta(R \cdot N \cdot L)\) pointers for \(N\) keys

The headline is the first row: cost bounded by key length, independent of the number of keys. A miss is often cheaper still: searching a trie of English words for xylophone falls off at the first or second character. The catch is the third row: every R-way node reserves \(R\) child pointers whether it uses them or not, and deep in a trie most nodes have one or two children, leaving the other \(24\) (or \(254\)) slots null. For \(R = 256\) the waste dominates the data. Fixing that space cost without giving up the \(\Theta(L)\) walk is the subject of §3.

Deletion, and shared structure Deleting a key takes two steps: unmark the node it ends on (isWord = false), then prune bottom-up: a node with no children that is not itself a word is useless, so remove it and reconsider its parent, stopping at the first node still needed. The care is in the stopping: never remove a node shared by other keys. Deleting shell from \(\{\)shell, shells\(\}\) only clears a flag: every node on its path is still on shells’s path. This shared-structure trap is deletion’s version of the is-word subtlety. The pruning step is also what preserves the invariant noted above, that every leaf is word-marked: an unmarked childless node is precisely what pruning removes, so it never survives to become a leaf.
Example (three deletions, three stop conditions) Start from the trie holding \(\{\)she, shell, shells\(\}\), whose keys lie on one path of six nodes (s, h, e, l, l, s) with the 3rd, 5th and 6th word-marked. Delete all three keys, in this order, letting each deletion see the previous one’s result:

Each deletion stops for a different reason, and those are the only three reasons there are: the node still has children (other keys run through it), the node is itself a word (another key ends there), or the walk has reached the root, which is never removed. Note the order dependence in the last case: deleting shell frees five nodes only because she is already gone. Had the three deletions run in the reverse order, the same three keys would have been removed with the frees distributed differently (\(1\), then \(2\), then \(3\)), and the trie would be equally empty at the end. What is not order-dependent: no deletion ever removes a node another key needs, because both stop conditions are checked before the node is freed.

The first deletion is the case worth naming twice, because it looks like a bug and is not: deleting she changes exactly one bit and frees nothing. The key is gone (a search for it now reads an unmarked node and returns absent) while every node of its path survives, in service of the two longer keys.

You have already met a trie The Huffman code tree (Huffman Coding) is a binary trie over the alphabet \(\{0, 1\}\): each codeword is a root-to-leaf path of bits. Prefix-freeness (no codeword is a prefix of another) is precisely the statement that every “word” in that trie is a leaf, which is why decoding can walk bits until it hits a leaf and never needs a separator. 3. Saving space: compressed tries and TSTs

Two standard fixes attack the \(R\)-pointers-per-node cost from different directions: store fewer nodes, or store cheaper nodes.

Compressed tries (radix trees)

Deep in a trie, long runs of single-child nodes are common: the tail of any key that shares nothing beyond its prefix. A compressed trie (also radix tree) collapses every such chain into one edge labeled with the whole substring:

Nodes now exist only where keys branch or end. That is not a rule imposed from outside, it is forced: a node with one child and no key ending at it would have a chain through it, and the whole point is that such a chain gets merged into its parent edge. The consequence is the bound worth remembering: at most \(2n-1\) nodes for \(n\) keys, since a tree whose internal nodes all have at least two children has fewer internal nodes than leaves. The node count is governed by the number of keys, not by their length.

Two things the compression changes, and one name to keep straight
  • A search must match a whole edge label. In an R-way trie every step consumes exactly one character, so a miss shows up as a missing child. Here a miss can happen inside an edge: looking up shy above follows "sh", then finds an edge labelled "ore" whose first character already disagrees. Comparing only the first character of each label is the classic bug: it would accept shy as shore.
  • An insert may have to split an edge, which a plain trie never does. When the new key and an existing label agree on a proper prefix, that edge is cut at the divergence point, a new branch node goes in the middle, and the old child hangs off the remainder: exactly what happened to "she" when "shore" arrived. If the new key ends at the split, the new node is simply marked; no leaf is added.
  • The names. “Compressed trie” and “radix tree” are the same idea as above, over whatever alphabet you like. PATRICIA (Morrison, 1968; Practical Algorithm To Retrieve Information Coded In Alphanumeric) is the same compression applied to bit strings, where each node stores the bit index to test next rather than a substring. In modern usage the three names are thrown around interchangeably; what matters is the shared idea, path compression, and it is why these structures sit inside IP (Internet Protocol) routing tables and many key–value stores.

Search and insert, with the edge split written out. The two loops that matter are the whole-label comparison and the longest-common-prefix scan that decides where to cut: 

// Compressed trie (radix tree). A node exists only where keys BRANCH or END,
// so the node count is bounded by the number of KEYS, not by their length.
// Each edge carries a whole substring, filed under its first character.
struct RadNode {
    bool isWord = false;
    map<char, pair<string, RadNode*>> kids;    // first char -> (edge label, child)
};

RadNode* leaf() { RadNode* n = new RadNode(); n->isWord = true; return n; }

// Search must match a WHOLE edge label. Falling off mid-edge is a miss, which
// is the difference from an R-way trie: there, every step is one character.
bool search(RadNode* t, const string& key) {
    size_t i = 0;
    while (i < key.size()) {
        auto it = t->kids.find(key[i]);
        if (it == t->kids.end()) return false;
        const string& label = it->second.first;
        // a mismatch INSIDE an edge is a miss, not just a missing child
        if (key.compare(i, label.size(), label) != 0) return false;
        i += label.size();
        t = it->second.second;
    }
    return t->isWord;
}

// Insert walks the same way, but where the key and an edge label agree on only
// a PREFIX it must SPLIT that edge -- the one operation a plain trie never needs.
void insert(RadNode* t, const string& key, size_t i) {
    if (i == key.size()) { t->isWord = true; return; }
    char c = key[i];
    auto it = t->kids.find(c);
    if (it == t->kids.end()) {                           // no edge starts with c
        t->kids[c] = { key.substr(i), leaf() };
        return;
    }
    string label = it->second.first;
    RadNode* child = it->second.second;
    size_t j = 0;                                        // longest common prefix
    while (j < label.size() && i + j < key.size() && label[j] == key[i + j]) j++;
    // the whole label matched -- descend and keep going
    if (j == label.size()) { insert(child, key, i + j); return; }
    RadNode* mid = new RadNode();                        // SPLIT the edge at j
    t->kids[c] = { label.substr(0, j), mid };
    mid->kids[label[j]] = { label.substr(j), child };
    if (i + j == key.size()) mid->isWord = true;   // key ends AT the split
    else {
        mid->kids[key[i + j]] = { key.substr(i + j), leaf() };
    }
}
// Compressed trie (radix tree). A node exists only where keys BRANCH or END,
// so the node count is bounded by the number of KEYS, not by their length.
// Each edge carries a whole substring, filed under its first character.
static class RadNode {
    boolean isWord;
    // first char -> {edge label, child}
    TreeMap<Character, Object[]> kids = new TreeMap<>();
}

// Search must match a WHOLE edge label. Falling off mid-edge is a miss, which
// is the difference from an R-way trie: there, every step is one character.
static boolean search(RadNode t, String key) {
    int i = 0;
    while (i < key.length()) {
        Object[] e = t.kids.get(key.charAt(i));
        if (e == null) return false;
        String label = (String) e[0];
        if (i + label.length() > key.length()
            || !key.startsWith(label, i)) return false;  // mismatch INSIDE an edge
        i += label.length();
        t = (RadNode) e[1];
    }
    return t.isWord;
}

// Insert walks the same way, but where the key and an edge label agree on only
// a PREFIX it must SPLIT that edge -- the one operation a plain trie never needs.
static void insert(RadNode t, String key, int i) {
    if (i == key.length()) { t.isWord = true; return; }
    char c = key.charAt(i);
    Object[] e = t.kids.get(c);
    if (e == null) {                                     // no edge starts with c
        RadNode leaf = new RadNode(); leaf.isWord = true;
        t.kids.put(c, new Object[]{ key.substring(i), leaf });
        return;
    }
    String label = (String) e[0];
    RadNode child = (RadNode) e[1];
    int j = 0;                                           // longest common prefix
    while (j < label.length() && i + j < key.length()
           && label.charAt(j) == key.charAt(i + j)) j++;
    // the whole label matched -- descend and keep going
    if (j == label.length()) { insert(child, key, i + j); return; }
    RadNode mid = new RadNode();                         // SPLIT the edge at j
    t.kids.put(c, new Object[]{ label.substring(0, j), mid });
    mid.kids.put(label.charAt(j), new Object[]{ label.substring(j), child });
    if (i + j == key.length()) mid.isWord = true;  // key ends AT the split
    else {
        RadNode leaf = new RadNode(); leaf.isWord = true;
        mid.kids.put(key.charAt(i + j), new Object[]{key.substring(i + j), leaf});
    }
}

def search(t, key):
    i = 0
    while i < len(key):
        e = t.kids.get(key[i])
        if e is None: return False
        label, child = e
        if key[i:i + len(label)] != label: return False   # mismatch INSIDE an edge
        i += len(label)
        t = child
    return t.is_word

# Insert walks the same way, but where the key and an edge label agree on only
# a PREFIX it must SPLIT that edge -- the one operation a plain trie never needs.
def insert(t, key, i):
    if i == len(key): t.is_word = True; return
    c = key[i]
    if c not in t.kids:                                   # no edge starts with c
        leaf = RadNode(); leaf.is_word = True
        t.kids[c] = [key[i:], leaf]
        return
    label, child = t.kids[c]
    j = 0                                                 # longest common prefix
    while j < len(label) and i + j < len(key) and label[j] == key[i + j]: j += 1
    if j == len(label):                                   # whole label matched
        insert(child, key, i + j); return
    mid = RadNode()                                       # SPLIT the edge at j
    t.kids[c] = [label[:j], mid]
    mid.kids[label[j]] = [label[j:], child]
    if i + j == len(key): mid.is_word = True       # key ends AT the split
    else:
        leaf = RadNode(); leaf.is_word = True
        mid.kids[key[i + j]] = [key[i + j:], leaf]
// Compressed trie (radix tree). A node exists only where keys BRANCH or END,
// so the node count is bounded by the number of KEYS, not by their length.
// Each edge carries a whole substring, filed under its first character.
#[derive(Default)]
struct RadNode {
    is_word: bool,
    // first byte -> (edge label, child)
    kids: BTreeMap<u8, (String, Box<RadNode>)>,
}

// Search must match a WHOLE edge label. Falling off mid-edge is a miss, which
// is the difference from an R-way trie: there, every step is one character.
fn search(root: &RadNode, key: &str) -> bool {
    let (kb, mut t, mut i) = (key.as_bytes(), root, 0usize);
    while i < kb.len() {
        let e = match t.kids.get(&kb[i]) { Some(e) => e, None => return false };
        let lb = e.0.as_bytes();
        // a mismatch INSIDE an edge is a miss, not just a missing child
        if i + lb.len() > kb.len() || &kb[i..i + lb.len()] != lb {
            return false;
        }
        i += lb.len();
        t = &e.1;
    }
    t.is_word
}

// Insert walks the same way, but where the key and an edge label agree on only
// a PREFIX it must SPLIT that edge -- the one operation a plain trie never needs.
fn insert(t: &mut RadNode, key: &str, i: usize) {
    let kb = key.as_bytes();
    if i == kb.len() { t.is_word = true; return; }
    let c = kb[i];
    if !t.kids.contains_key(&c) {                        // no edge starts with c
        let leaf = Box::new(RadNode { is_word: true, ..Default::default() });
        t.kids.insert(c, (key[i..].to_string(), leaf));
        return;
    }
    let label = t.kids[&c].0.clone();
    let lb = label.as_bytes();
    let mut j = 0usize;                                  // longest common prefix
    while j < lb.len() && i + j < kb.len() && lb[j] == kb[i + j] { j += 1; }
    if j == lb.len() {                                   // whole label matched
        insert(&mut t.kids.get_mut(&c).unwrap().1, key, i + j);
        return;
    }
    let (_, child) = t.kids.remove(&c).unwrap();         // SPLIT the edge at j
    let mut mid = Box::new(RadNode::default());
    mid.kids.insert(lb[j], (label[j..].to_string(), child));
    if i + j == kb.len() { mid.is_word = true; }   // key ends AT the split
    else {
        let leaf = Box::new(RadNode { is_word: true, ..Default::default() });
        mid.kids.insert(kb[i + j], (key[i + j..].to_string(), leaf));
    }
    t.kids.insert(c, (label[..j].to_string(), mid));
}

Ternary search tries

Definition (ternary search trie) A ternary search trie (TST) replaces each R-way node’s child array with a small binary search tree over only the characters actually used at that position. Each node of that BST stores one character \(c\) and three links: left (query character \(< c\)), right (\(> c\)), and mid (\(= c\); advance to the key’s next character), plus the usual is-word flag.
Is it a binary search tree or a ternary tree? Both, at different levels, and the two answers do not compete. Structurally a TST is one ternary tree: all three links point to another node of the same kind, which is exactly what “ternary” names. The BST language describes what two of those links do, not a different kind of object. Read the links by what they change:
  • left/right: keep the character position fixed, searching among the characters used there. That little BST is what replaces the array.
  • mid: advances one position. It points at the root of the next position’s BST, so the following characters hang under it.

So the array lookup becomes two steps: BST-search on left/right for \(c\), then follow that node’s mid. That pair is what next[c] used to do in one array index, and only mid consumes a character. Keep the two axes apart and everything about TSTs follows: within one character position you are in a BST; crossing to the next position you are in a trie. Hence ternary search trie: “ternary” counts a node’s links, it does not describe the search over the characters at a position.

One more granularity trap: a single R-way node does not become a single TST node. It becomes a whole little BST, with one TST node per character actually used at that position: \(k\) characters used means \(k\) nodes of three pointers each, in place of one array of \(R\).

// Ternary search trie. ONE character per node and three links, so a node is
// three pointers instead of an R-slot array. left/right search among the
// characters used at THIS position (that is the little BST); mid ADVANCES one
// position, landing on the root of the next position's BST -- which is where
// the following characters live. Only mid consumes a character.
struct TstNode {
    char c;
    TstNode *left, *mid, *right;
    bool isWord;
    TstNode(char ch) : c(ch), left(0), mid(0), right(0), isWord(false) {}
};

// put -- the same walk as get, creating what is missing. Keys are non-empty.
TstNode* put(TstNode* x, const string& key, size_t d) {
    char c = key[d];
    if (!x) x = new TstNode(c);
    if      (c < x->c)            x->left  = put(x->left,  key, d);
    else if (c > x->c)            x->right = put(x->right, key, d);
    else if (d + 1 < key.size())  x->mid   = put(x->mid,   key, d + 1);
    else                         x->isWord = true;      // the node the key ends on
    return x;
}

bool get(TstNode* x, const string& key) {
    size_t d = 0;
    while (x) {
        char c = key[d];
        if      (c < x->c)           x = x->left;        // still position d
        else if (c > x->c)           x = x->right;       // still position d
        else if (d + 1 < key.size()) { x = x->mid; d++; }// the only character step
        else return x->isWord;      // path exists -- but does a key END here?
    }
    return false;                   // fell off the tree
}

# Ternary search trie. ONE character per node and three links, so a node is
# three pointers instead of an R-slot array. left/right search among the
# characters used at THIS position (that is the little BST); mid ADVANCES one
# position, landing on the root of the next position's BST -- which is where
# the following characters live. Only mid consumes a character.
class TstNode:
    def __init__(self, c):
        self.c = c
        self.left = self.mid = self.right = None
        self.is_word = False

# put -- the same walk as get, creating what is missing. Keys are non-empty.
def put(x, key, d):

// Ternary search trie. ONE character per node and three links, so a node is
// three pointers instead of an R-slot array. left/right search among the
// characters used at THIS position (that is the little BST); mid ADVANCES one
// position, landing on the root of the next position's BST -- which is where
// the following characters live. Only mid consumes a character.
struct TstNode {
    c: u8,
    left: Option<Box<TstNode>>,
    mid: Option<Box<TstNode>>,
    right: Option<Box<TstNode>>,
    is_word: bool,
}

impl TstNode {
    fn new(c: u8) -> Self {
        TstNode { c, left: None, mid: None, right: None, is_word: false }
    }
}

// put -- the same walk as get, creating what is missing. Keys are non-empty.
fn put(x: Option<Box<TstNode>>, key: &[u8], d: usize) -> Option<Box<TstNode>> {
    let c = key[d];
    let mut n = x.unwrap_or_else(|| Box::new(TstNode::new(c)));
    if c < n.c            { n.left  = put(n.left.take(),  key, d); }
    else if c > n.c       { n.right = put(n.right.take(), key, d); }
    else if d + 1 < key.len() { n.mid = put(n.mid.take(), key, d + 1); }
    else                 { n.is_word = true; }          // the node the key ends on
    Some(n)
}

fn get(root: &Option<Box<TstNode>>, key: &[u8]) -> bool {
    let (mut x, mut d) = (root, 0usize);
    while let Some(n) = x {
        let c = key[d];
        if c < n.c            { x = &n.left; }            // still position d
        else if c > n.c       { x = &n.right; }           // still position d
        else if d + 1 < key.len() { x = &n.mid; d += 1; } // the only char step
        else { return n.is_word; }  // path exists -- but does a key END here?
    }
    false                           // fell off the tree
}

A lookup, at each position of the key, walks left/right links to find the current character among the node’s siblings (a little BST search over the characters used there) and only on an exact character match descends mid and advances the query. Only mid edges consume characters, and the key takes \(L\) of them; each is preceded by an \(O(\log R)\) sibling search. Worst case \(\Theta(L \log R)\), and in practice close to \(\Theta(L)\), because most nodes have very few children. In exchange, a node is three pointers instead of \(R\): no null-slot waste at all. TSTs are Sedgewick’s default string symbol table: trie-like speed at BST-like space, the practical choice once the alphabet is large.

Five visits for three characters.

The two failing endings are the R-way trie’s, unchanged. shel walks four mid steps and stops on the l at \(d = 3\): the path exists, the node is not word-marked, so absent. sup matches s, takes mid to \(d = 1\), and there u \(>\) h asks for a right link that is null: the walk falls off after two node visits, without reading the key’s third character. As in the R-way trie, a miss usually costs less than a hit.

This extends the hash-versus-tree decision of Hashing with a third column. A hash table also reads all \(L\) characters (to hash them) and remains the simplest choice for plain membership. The trie’s unique powers are the two things hashing destroys by design: order, and prefix locality. If the workload ever asks “what starts with…” or “what is the longest stored prefix of…” (the operations of the next section), the trie is the only tool on the table that answers without a full scan.

4. Prefix operations: autocomplete and longest-prefix

The trie’s structure already groups keys by shared prefix: all keys with prefix \(P\) are exactly the subtree under \(P\)’s node. No extra index, no sorting: the tree is the prefix index. Two operations fall out of that observation for free, and they are the reason to choose a trie at all.

keysWithPrefix: autocomplete

To find every key starting with a prefix: walk the trie down the prefix path, then collect every word-marked node in the subtree below, by depth-first traversal (the keysWithPrefix/collect pair in §2’s code). In a hash table the keys sharing a prefix are scattered across buckets with no way to enumerate them short of scanning every key; in the trie they are literally one subtree.

Example (keysWithPrefix, worked) Trie holding \(\{\)she, shell, shells, sea\(\}\); query prefix she: The cost is \(\Theta(\text{prefix length} + \text{output size})\): the walk touches three nodes, and the collection touches only the keys that actually share the prefix. That output-sensitivity is why autocomplete feels instant even over huge dictionaries.

longestPrefixOf

The mirror-image query: the longest stored key that is a prefix of the query. Walk the query string down the trie, remembering the most recent word-marked node passed; when the walk falls off or the query ends, the last remembered word is the answer: a single \(\Theta(L)\) descent.

Example (longestPrefixOf, worked) Keys \(\{\)she, shells\(\}\); query shellsort: This is exactly IP longest-prefix match: a router stores network prefixes in a (Patricia) trie, walks a destination address bit by bit, and forwards along the most specific (longest) matching prefix it passed. It is also how word segmenters and lexers peel the longest recognized token off the front of the input.

From prefix queries to real autocomplete

Production autocomplete is keysWithPrefix plus a ranking: store a weight (frequency, recency) at each word-marked node, and while collecting the subtree keep only the top few completions by weight: a small heap (Heaps & Priority Queues) does it in one pass. That is why suggestions arrive curated rather than alphabetical: the trie supplies the candidate set in \(\Theta(\text{prefix} + \text{output})\), and the weights supply the intelligence. The branching structure supports approximate matching too: a wildcard character (c?t) means “try every child at this position,” and a bounded edit-distance search (“did you mean?”) explores paths within an edit budget: the same tree, searched more forgivingly.

5. Exercises (with solutions)

  1. Insert to, tea, ten into an empty R-way trie. How many nodes does it have (besides the root)? Which are word-marked? Is a search for te successful?
    solution Five nodes: t with children o and e, and e with children a and n (paths t–o, t–e–a, t–e–n). The three word-marked nodes are the ends o, a, n; t and e are shared, unmarked path nodes. Searching te walks a perfectly valid path, but its final node is not word-marked, so the search correctly fails: a reachable path is not a stored key.
  2. A trie holds \(\{\)to, tea, ted, ten, in, inn\(\}\). Compute keysWithPrefix("te") and longestPrefixOf("innards"), and state each operation’s cost in general.
    solution keysWithPrefix("te"): walk t–e, then collect the subtree: \(\{\)tea, ted, ten\(\}\) (neither to nor the in branch is visited). Cost: \(\Theta(\text{prefix length} + \text{output size})\). longestPrefixOf("innards"): walk i → n (passing the word in, remember it) → n (passing inn, remember it; longer) → a has no child → stop and return the last word passed: inn. Cost: one descent, \(\Theta(\text{query length})\) at most.
  3. From a trie holding \(\{\)she, shell, shells\(\}\), delete shell, then delete shells. Describe exactly what each deletion changes.
    solution Deleting shell only clears the is-word flag on its final l node: that node still has a child (the s of shells), so nothing can be pruned: every node on the path is still shared. Deleting shells then unmarks its final s node and prunes bottom-up: the s (childless, unmarked) goes, then the second l (now childless, and its mark was cleared by the first deletion), then the first l (childless, unmarked), three nodes removed, and pruning stops at e, which is word-marked (she survives). Forgetting the stop condition and pruning into shared/marked nodes is the classic deletion bug. You can run this pair live in the trie demo: build she, shell, shells, then Delete shell and shells in that order: the free counter reads \(0\), then \(3\).
