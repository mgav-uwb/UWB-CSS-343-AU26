Substring Search: The Problem & Baselines

Data Structures & Algorithms. Foundation.
Finding a pattern inside a text: the substring-search problem, and the brute-force baseline with its quadratic worst case unrolled alignment by alignment. Closes with the family table, naming Knuth–Morris–Pratt, Boyer–Moore and Rabin–Karp (each covered in its own handout), and the toolkit for choosing among them. With two worked traces, full implementations, and exercises.

A trie (Tries & Ternary Search Trees) exploits the character structure of string keys; substring search applies the same look-inside-the-string principle to a different problem: finding a pattern inside a text. This handout states the problem and works the brute-force baseline, locating the waste in it; the fast searchers, Knuth–Morris–Pratt, Boyer–Moore and Rabin–Karp, each have a handout of their own.

1. The problem, and brute force

Definition (substring search) Given a text of length \(n\) and a pattern of length \(m\) (usually \(m \ll n\)), find the index of the first occurrence of the pattern as a contiguous substring of the text (or report that none exists).

This is text.indexOf(pattern), grep, find-in-editor, DNA motif search: one of the most-executed operations in computing. The running example: 

  text:     A B A B A B C A B A B A B C A B      (n = 16)
  pattern:      A B A B C                        (m = 5)
  → first match at index 2   (text[2..6] = ABABC)

Brute force: try every alignment

The obvious algorithm tries the pattern at every start position \(i = 0, 1, \dots, n-m\): compare left to right, and on any mismatch slide the pattern by one and restart the comparison. 

// Brute-force substring search: try the pattern at EVERY start position; on a
// mismatch, slide by ONE and restart the comparison. Worst case Theta(nm):
// text characters get re-examined after a partial match.
int bruteSearch(const string& t, const string& p) {
    int n = t.size(), m = p.size();
    for (int i = 0; i <= n - m; i++) {     // each start position
        int j = 0;
        while (j < m && t[i + j] == p[j]) j++;   // compare left to right
        if (j == m) return i;              // all m matched: found at i
    }
    return -1;                             // no occurrence
}
// Brute-force substring search: try the pattern at EVERY start position; on a
// mismatch, slide by ONE and restart the comparison. Worst case Theta(nm):
// text characters get re-examined after a partial match.
static int bruteSearch(String t, String p) {
    int n = t.length(), m = p.length();
    for (int i = 0; i <= n - m; i++) {     // each start position
        int j = 0;
        while (j < m && t.charAt(i + j) == p.charAt(j)) j++;  // left to right
        if (j == m) return i;              // all m matched: found at i
    }
    return -1;                             // no occurrence
}
# Brute-force substring search: try the pattern at EVERY start position; on a
# mismatch, slide by ONE and restart the comparison. Worst case Theta(nm):
# text characters get re-examined after a partial match.
def brute_search(t, p):
    n, m = len(t), len(p)
    for i in range(n - m + 1):             # each start position
        j = 0
        while j < m and t[i + j] == p[j]:  # compare left to right
            j += 1
        if j == m:                         # all m matched: found at i
            return i
    return -1                              # no occurrence
// Brute-force substring search: try the pattern at EVERY start position; on a
// mismatch, slide by ONE and restart the comparison. Worst case O(nm):
// text characters get re-examined after a partial match.
fn brute_search(t: &str, p: &str) -> i32 {
    let (t, p) = (t.as_bytes(), p.as_bytes());
    let (n, m) = (t.len(), p.len());
    if m > n { return -1; }
    for i in 0..=(n - m) {                 // each start position
        let mut j = 0;
        while j < m && t[i + j] == p[j] { j += 1; }   // compare left to right
        if j == m { return i as i32; }     // all m matched: found at i
    }
    -1                                     // no occurrence
}

Example (brute force, worked) Search for ABABC in ABCABABC. Each row is one alignment of the pattern; green cells are compared-and-matched, the amber cell is the comparison that failed:
text →ABCABABCcompares
shift 0 ABABC3
shift 1 ABABC1
shift 2 ABABC1
shift 3 ABABC5
Shift 0 matches AB, then A falls on the text’s C; shifts 1 and 2 die on their first comparison; shift 3 matches all five: found at index \(3\), \(10\) comparisons in all. Note the waste at shift 0 → 1: having matched AB, brute force forgets it and re-reads text[1] from scratch.
Proposition (brute-force cost) Brute force makes at most \((n-m+1)\,m = \Theta(nm)\) character comparisons, and the bound is achieved: on text \(\texttt{AA}\cdots\texttt{A}\) (all \(n\) characters A) with pattern \(\texttt{AA}\cdots\texttt{AB}\) (\(m-1\) As then a B), every one of the \(n-m+1\) alignments matches \(m-1\) characters before failing on the last, costing \(m\) comparisons each.
Example (the worst case, unrolled) The bound is easiest to believe when every alignment is written out. Text AAAAAAAAAAAB (\(n = 12\): eleven As then a B) and pattern AAAB (\(m = 4\)). Colours as above: green matched, amber mismatched.
text →AAAAAAAAAAABcmptotal
shift 0AAAB44
shift 1AAAB48
shift 2AAAB412
shift 3AAAB416
shift 4AAAB420
shift 5AAAB424
shift 6AAAB428
shift 7AAAB432

Every alignment except the last matches three As and then fails, its B landing on one of the text’s As: four comparisons to advance one position. Shift 8 matches all four: found at index \(8\), after \((n-m+1)\,m = 9 \times 4 = 36\) comparisons for a twelve-character text. Nothing about the text changes between alignments, and brute force rediscovers that fact nine times.

The deep inefficiency is not the sliding but the re-examining: after a partial match, brute force throws away everything it learned about the text and reads the same characters again. Knuth–Morris–Pratt’s insight is that a partial match already tells you exactly how far the pattern can safely jump.

When brute force is the right call Do not over-engineer. On typical natural-language text, a mismatch occurs within the first character or two of most alignments, so brute force runs nearly linearly, which is why simple library find routines are essentially brute force (or Boyer–Moore) and are fine in practice. Reach for the fancier algorithms when the input is long and repetitive (DNA, binary data), adversarial, streamed, or searched so often that pattern preprocessing amortizes. Match the tool to the workload.

2. Rabin–Karp: hashing the windows

One more classic belongs with the baselines, and it is Hashing applied to substrings. Rabin–Karp hashes the pattern once, then slides a length-\(m\) window across the text carrying a rolling hash that updates in \(O(1)\) per shift, so all \(n-m+1\) windows are fingerprinted in \(\Theta(n)\) rather than \(\Theta(nm)\); characters are compared only where a window’s hash equals the pattern’s, since equal hashes do not prove equal strings. That gives \(\Theta(n+m)\) expected time, and one property no other family member has: hash many patterns into a set and a single pass finds them all. Rabin–Karp has the rolling update derived and traced, the Monte Carlo and Las Vegas variants, and the collision analysis.

3. The wider family, and the string toolkit

Two algorithms sharpen the baselines into the standard tools, and each has a handout of its own. Knuth–Morris–Pratt precomputes the pattern’s self-overlap structure (its failure function) so that a mismatch never sends the text pointer backward: \(\Theta(n+m)\), guaranteed, on every input, and the scan runs happily on a stream it cannot rewind. Boyer–Moore compares each alignment right to left and uses the mismatched text character to leap ahead, typically examining fewer than \(n\) characters. The family in one table:

algorithmpreprocesssearchidea
brute forcenone\(\Theta(nm)\) worsttry every alignment

Boyer–Moore\(\Theta(m+R)\)sublinear typicalright-to-left compare; skip on the bad character

The common thread: every fast searcher preprocesses the pattern (failure function, skip tables, hash) and then reads the huge text once (or less). The asymmetry is the point: \(m\) is small and the pattern is reused, so work invested there is amortized across the \(n\)-character scan; it is the same precompute-to-answer-fast principle as a hash table’s function or a dynamic-programming table, applied to search.

These algorithms are among the most-run code on Earth: every search box and spell-checker (tries), every router forwarding decision (longest-prefix match), every grep and find-in-file (Boyer–Moore), every genome alignment and packet-inspecting firewall (huge repetitive texts, where the linear guarantee is the difference between feasible and not), every compiler’s lexer (tries and automata over tokens). And the string handouts share one lesson: a string is not an opaque key. Its characters gave the trie a search cost independent of \(n\); its self-overlaps gave KMP a scan that never backs up. Regular Expressions & Automata pushes the second idea to its natural limit: from searching for one fixed string to matching a whole language of them: regular expressions, and the finite automata that run them, starting from exactly the DFA that KMP already built for a one-string language.

4. Exercises (with solutions)

  1. Exactly how many character comparisons does brute force make searching for \(\texttt{A}^{m-1}\texttt{B}\) (that is, \(m-1\) As then B) in the text \(\texttt{A}^{n-1}\texttt{B}\)? Evaluate at \(n = 12\), \(m = 4\), and compare with KMP’s guarantee.
    solution Every alignment \(i = 0, \dots, n-m\) compares \(m-1\) matching As and then one more character (a mismatching A under B at every alignment except the last, where the B matches and the search ends): \(m\) comparisons per alignment, \((n-m+1)\,m\) in all. At \(n = 12, m = 4\): \(9 \times 4 = 36\) comparisons, matching at index \(8\), the race demo’s adversarial pair. KMP’s scan is bounded by \(2n\) (each comparison either advances \(i\) or strictly increases the alignment \(i - j\)); on this instance it makes \(20\).
  2. A firewall must scan an unbounded, non-seekable network stream for a fixed 64-byte signature, with a hard guarantee that scanning keeps up with line rate. Which algorithm fits, and why do the other three family members fail at least one requirement?
    solution KMP. Its text pointer never decreases, so it reads each streamed byte exactly once with \(O(1)\) work amortized (at most \(2n\) comparisons total) and \(\Theta(m)\) memory for the failure function: both requirements met. Brute force re-examines earlier text characters after a partial match (needs buffering and loses the linear guarantee: \(\Theta(nm)\) on repetitive traffic). Boyer–Moore compares right to left inside a sliding window, so it needs an \(m\)-byte lookahead buffer (workable), but its bad-character heuristic alone has a \(\Theta(nm)\) worst case: an adversary can craft traffic that breaks the line-rate guarantee. Rabin–Karp streams fine, but its \(\Theta(n)\) is expected: hash-collision verifications re-read window bytes, so the hard guarantee again fails against adversarial input (though it becomes the right answer the moment there are many signatures at once).
