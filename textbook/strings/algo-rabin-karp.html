Rabin–Karp

Data Structures & Algorithms. Algorithm.
Substring search by fingerprint: hash the pattern once, then slide a window across the text carrying a rolling polynomial hash that updates in constant time, and compare characters only when two fingerprints agree. The Horner fingerprint, the rolling update derived and traced modulo a small prime (spurious hits included), the Monte Carlo and Las Vegas variants, the multi-pattern scan, the expected \(\Theta(n+m)\) bound with its collision argument, and the \(\Theta(nm)\) worst case. With full implementations and exercises.

Brute-force substring search compares characters (Substring Search: The Problem & Baselines); Knuth–Morris–Pratt and Boyer–Moore compare characters more cleverly. Rabin–Karp mostly does not compare characters at all: it compares numbers, one number per window of the text, each computed from the previous one in constant time. It is Hashing turned on the substring-search problem, and it is the one member of the family that scales to searching for thousands of patterns in a single pass.

1. Fingerprints instead of character comparisons

The problem is the standard one: given a text \(T[0..n-1]\) and a pattern \(P[0..m-1]\), find the first index \(i\) with \(T[i..i+m-1] = P\), or report that none exists. Brute force answers it by comparing the pattern against each of the \(n-m+1\) windows character by character, up to \(m\) comparisons per window: \(\Theta(nm)\) in the worst case.

Suppose every string had a short numeric summary, cheap to compare, such that different summaries certainly mean different strings. The scan could then reject a window with one integer comparison instead of up to \(m\) character comparisons. That summary is a hash value, and in this setting it has a name.

Definition (fingerprint) A fingerprint of a string \(s\) is a hash value \(h(s)\) in a small range, used as a proxy for \(s\) in equality tests. It is sound as a rejector: \(h(s) \ne h(u)\) implies \(s \ne u\). It is not sound as an acceptor: \(h(s) = h(u)\) leaves \(s = u\) merely likely, because a hash maps many strings to each value (Hashing: collisions are unavoidable).
Definition (spurious hit) A spurious hit (also false hit) is a window \(T[i..i+m-1] \ne P\) whose fingerprint nevertheless equals the pattern’s. Since a fingerprint cannot rule a hit in, every hit must be verified by comparing the window against the pattern character by character; verification is what turns a spurious hit into a rejection rather than a wrong answer.

Two obstacles stand between that idea and an algorithm. First, computing each window’s fingerprint from scratch reads \(m\) characters, so \(n-m+1\) windows would cost \(\Theta(nm)\): exactly what was to be avoided. The fingerprint must therefore be rollable, updatable in \(O(1)\) when the window slides one position. Second, spurious hits cost \(m\) character comparisons each, so the fingerprint must collide rarely enough that they are negligible. Rabin–Karp’s polynomial hash modulo a prime meets both requirements.

2. The fingerprint: a polynomial hash by Horner’s method

Read a string of length \(m\) as an \(m\)-digit number written in base \(R\), where \(R\) is the alphabet size (or any base at least as large as the largest character code), and reduce it modulo a prime \(Q\):

\[ h(s) \;=\; \bigl(s_0 R^{m-1} + s_1 R^{m-2} + \cdots + s_{m-2} R + s_{m-1}\bigr) \bmod Q . \]

The full number \(s_0 R^{m-1} + \cdots + s_{m-1}\) has as many digits as the string has characters, so for any realistic \(m\) it overflows a machine word long before it can be compared. Horner’s method avoids ever forming it: factor the polynomial as \(\bigl(\cdots((s_0 R + s_1) R + s_2)\cdots\bigr) R + s_{m-1}\) and reduce modulo \(Q\) at every step, which is legitimate because \((a + b) \bmod Q\) and \((a \cdot b) \bmod Q\) depend only on \(a \bmod Q\) and \(b \bmod Q\). Every intermediate value then stays below \(Q\), and one left-to-right pass of \(m\) multiply-add-reduce steps produces the fingerprint. This is the same string hash as in Hashing, with the base and modulus named explicitly because the rolling update needs them.

Example (Horner, worked) Take the digit alphabet, so \(R = 10\), and the deliberately tiny prime \(Q = 13\) (small enough that collisions show up in a short trace). The pattern is 26535, so \(m = 5\): 
  h = 0
  read 2:   h = (10·0 + 2) mod 13 =   2 mod 13 =  2
  read 6:   h = (10·2 + 6) mod 13 =  26 mod 13 =  0
  read 5:   h = (10·0 + 5) mod 13 =   5 mod 13 =  5
  read 3:   h = (10·5 + 3) mod 13 =  53 mod 13 =  1
  read 5:   h = (10·1 + 5) mod 13 =  15 mod 13 =  2
  fingerprint of the pattern:  h(P) = 2
The check on the arithmetic: \(26535 = 13 \cdot 2041 + 2\), so \(26535 \bmod 13 = 2\), which is what the running reduction produced. Horner’s method never held \(26535\); it never held anything larger than \(10 \cdot 12 + 9 = 129\).
Why a prime modulus, and how large A prime \(Q\) spreads the polynomial values evenly over \(\{0, \dots, Q-1\}\); a composite modulus (\(2^k\) especially) lets common factors of \(R\) and \(Q\) collapse whole families of strings onto the same value, exactly as in Hashing. The size of \(Q\) is a tuning knob, not a correctness condition: §8 shows that spurious hits arrive at a rate of about \(1\) per \(Q\) windows, so production code picks \(Q\) large (a prime near \(2^{31}\), or near \(2^{61}\) with 128-bit intermediate products) and the whole issue disappears. The traces here use \(Q = 13\) precisely so that it does not disappear.

3. The rolling update, derived

Write \(x_i\) for the numeric value of the window starting at \(i\), before reduction:

\[ x_i \;=\; T[i] R^{m-1} + T[i+1] R^{m-2} + \cdots + T[i+m-1]. \]

Sliding one position to the right drops the leading term \(T[i] R^{m-1}\), shifts every remaining term up one power of \(R\), and appends the entering character \(T[i+m]\) in the units place:

\[ x_{i+1} \;=\; \bigl(x_i - T[i] \cdot R^{m-1}\bigr) \cdot R \;+\; T[i+m]. \]

This is an identity on integers, and reduction modulo \(Q\) preserves it, so the same formula computes \(h_{i+1} = x_{i+1} \bmod Q\) from \(h_i = x_i \bmod Q\):

\[ h_{i+1} \;=\; \bigl(\,(h_i - T[i]\cdot \mathit{RM}) \cdot R + T[i+m]\,\bigr) \bmod Q, \qquad \mathit{RM} = R^{\,m-1} \bmod Q . \]

Three constant-time operations (one subtraction, one multiply-add, one reduction) advance the window, whatever \(m\) is. The constant \(\mathit{RM}\) is computed once during preprocessing, by \(m-1\) multiply-and-reduce steps (or by fast modular exponentiation), never by forming \(R^{m-1}\) itself.

The subtraction can go negative \(h_i - T[i] \cdot \mathit{RM}\) is a difference of residues and is routinely negative. In Python, % already returns a non-negative result, but in C++, Java and Rust the % operator takes the sign of the dividend, so a negative intermediate would poison the fingerprint and, if used as an array index anywhere, the program. The fix is to add a multiple of \(Q\) before reducing. The idiom used below reduces the product first, so that \(T[i] \cdot \mathit{RM} \bmod Q\) lies in \([0, Q)\), and then adds a single \(Q\): 
  h = (h + Q - (T[i] * RM) % Q) % Q;   // in [0, Q): one +Q suffices
  h = (h * R + T[i+m]) % Q;
Writing h = (h - T[i]*RM) % Q and hoping is the single most common bug in a hand-written Rabin–Karp.
Example (one roll, worked) Still \(R = 10\), \(Q = 13\), \(m = 5\), so \(\mathit{RM} = 10^4 \bmod 13 = 10000 \bmod 13 = 3\) (since \(13 \cdot 769 = 9997\)). The window 31415 has \(h = 31415 \bmod 13 = 7\) (Horner: \(3, 5, 2, 8, 7\)). Slide it right by one, dropping 3 and admitting 9, to reach the window 14159: 
  drop:   7 − 3·3 = −2      →  −2 + 13 = 11
  shift and admit:  11·10 + 9 = 119   →  119 mod 13 = 2   (13·9 = 117)
  check:  14159 mod 13 = 2      (13·1089 = 14157)   ✓
Constant work, and the answer agrees with hashing 14159 from scratch, which is the whole point.

4. The algorithm

Preprocessing computes \(\mathit{RM}\) and the pattern’s fingerprint, then hashes the first window. The scan compares fingerprints, verifies on equality, and rolls. The code below is the Las Vegas form (always correct, expected linear time); §7 gives the Monte Carlo form, which is the same code with the verification call deleted. 

// Rabin-Karp. R = alphabet size (base), Q = a large prime modulus.
// Fingerprint: h(s) = (s[0]*R^(m-1) + ... + s[m-1]) mod Q, by Horner.
static const long R = 256, Q = 1000000007L;

// Horner: fold the first k characters of s into one residue mod Q.
long hashOf(const string& s, int k) {
    long h = 0;
    for (int j = 0; j < k; j++)
        h = (R * h + (unsigned char)s[j]) % Q;   // reduce each step
    return h;
}

int rkSearch(const string& t, const string& p) {
    int n = t.size(), m = p.size();
    if (m > n) return -1;                        // no window exists

    long RM = 1;                                 // RM = R^(m-1) mod Q
    for (int j = 1; j <= m - 1; j++) RM = (R * RM) % Q;
    long hp = hashOf(p, m);                      // pattern fingerprint
    long h  = hashOf(t, m);                      // first window, T[0..m-1]

    for (int i = 0; ; i++) {
        if (h == hp) {                           // fingerprints agree: VERIFY
            int j = 0;
            while (j < m && t[i + j] == p[j]) j++;
            if (j == m) return i;                // true match
        }                                        // else: spurious hit, go on
        if (i == n - m) break;                   // last window done
        // roll: drop t[i], shift, admit t[i+m]; +Q keeps the residue positive
        h = (h + Q - (RM * (unsigned char)t[i]) % Q) % Q;
        h = (h * R + (unsigned char)t[i + m]) % Q;
    }
    return -1;                                   // no occurrence
}

def hash_of(s, k):
    """Horner: fold the first k characters of s into one residue mod Q."""
    h = 0
    for j in range(k):
        h = (R * h + ord(s[j])) % Q              # reduce each step

def rk_search(t, p):
    n, m = len(t), len(p)
    if m > n:
        return -1                                # no window exists

    RM = pow(R, m - 1, Q)                        # RM = R^(m-1) mod Q
    hp = hash_of(p, m)                           # pattern fingerprint
    h  = hash_of(t, m)                           # first window, t[0..m-1]

    for i in range(n - m + 1):
        if h == hp:                              # fingerprints agree: VERIFY
            if t[i:i + m] == p:
                return i                         # true match
        if i == n - m:                           # last window done
            break
        # roll: drop t[i], shift, admit t[i+m]   (Python % is never negative)
        h = ((h - ord(t[i]) * RM) * R + ord(t[i + m])) % Q
    return -1                                    # no occurrence

// Fingerprint: h(s) = (s[0]*R^(m-1) + ... + s[m-1]) mod Q, by Horner.
const R: u64 = 256;
const Q: u64 = 1_000_000_007;

// Horner: fold the first k bytes of s into one residue mod Q.
fn hash_of(s: &[u8], k: usize) -> u64 {
    let mut h = 0u64;
    for j in 0..k {
        h = (R * h + s[j] as u64) % Q;           // reduce each step
    }
    h
}

fn rk_search(t: &str, p: &str) -> i32 {
    let (t, p) = (t.as_bytes(), p.as_bytes());
    let (n, m) = (t.len(), p.len());
    if m > n { return -1; }                      // no window exists

    let mut rm = 1u64;                           // rm = R^(m-1) mod Q
    for _ in 1..m { rm = (R * rm) % Q; }
    let hp = hash_of(p, m);                      // pattern fingerprint
    let mut h = hash_of(t, m);                   // first window, t[0..m-1]

    for i in 0..=(n - m) {
        if h == hp && &t[i..i + m] == p {         // agree: VERIFY
            return i as i32;                     // true match
        }                                        // else: spurious hit, go on
        if i == n - m { break; }                 // last window done
        // roll: drop t[i], shift, admit t[i+m]; +Q keeps the residue positive
        h = (h + Q - (rm * t[i] as u64) % Q) % Q;
        h = (h * R + t[i + m] as u64) % Q;
    }
    -1                                           // no occurrence
}

The loop structure is worth a second look: the roll must not run after the last window (there is no \(T[i+m]\) to admit), so the break sits between the test and the roll rather than in the loop header. Note also that the text pointer never moves backward during the scan; only verification re-reads characters, and only at a hit.

Brute force on the same instance makes \(11\) character comparisons, so Rabin–Karp does not win on a sixteen-character text with a small modulus; what the trace shows is the shape of the cost, which is \(\Theta(n)\) arithmetic plus verification, with verification the only term that can misbehave.

6. Every case the scan can take

One window is disposed of in exactly one of these ways, and a correct implementation (and a correct hand-trace) has to handle all of them:

  1. Fingerprints differ. The window cannot equal the pattern (a fingerprint is sound as a rejector), so it is discarded with zero character comparisons. This is the common case and the source of the speed. Trace rows \(i = 0, 2, 3, 4\).
  2. Fingerprints agree, verification succeeds. A true occurrence: report \(i\) (or record it and continue, if all occurrences are wanted). Costs \(m\) comparisons. Trace row \(i = 6\).
  3. Fingerprints agree, verification fails. A spurious hit: the window is discarded and the scan continues. Costs between \(1\) and \(m\) comparisons, and in practice usually \(1\), since two unequal strings typically differ early. Trace rows \(i = 1, 5\), both failing on the first character.
  4. No window exists (\(m > n\)). Return “not found” before hashing anything; without this guard the first window’s Horner loop reads past the end of the text.
  5. The last window (\(i = n - m\)). It must be tested, but must not be rolled: there is no entering character \(T[i+m]\). This is why the break sits mid-loop in §4.
  6. The intermediate residue goes negative (\(h_i < T[i] \cdot \mathit{RM} \bmod Q\)). Correct by adding \(Q\) before reducing, as in the §3 aside. Every roll in the §5 trace takes this branch.

Case 3 is the one that distinguishes Rabin–Karp from the other searchers: it is the only case whose frequency, rather than whose cost, depends on the input and the choice of \(Q\), and it is therefore the case the cost analysis of §8 has to bound.

Example (case 3 at full cost) Verification is cheap when two strings differ early and expensive when they differ late. Searching for AAAAB in AAAAAAAAAA, a spurious hit on a window AAAAA would compare four matching As before failing on the fifth: the full \(m\) comparisons wasted. An adversary who knows \(Q\) can arrange exactly that at every window, which is where the \(\Theta(nm)\) worst case of §8 comes from.

7. Monte Carlo, Las Vegas, and many patterns at once

Verification is the only place the algorithm touches characters, and deleting it produces a different (and faster) algorithm with a different guarantee. The two names are the standard vocabulary for randomized algorithms.

Definition (Monte Carlo, Las Vegas) A Monte Carlo algorithm has a fixed running time and may return a wrong answer, with a probability the designer can bound. A Las Vegas algorithm is always correct and has a running time that is a random variable, bounded in expectation.
varianton a fingerprint hitrunning timecorrectness
Monte Carloreport the match, no check\(\Theta(n+m)\) alwaysmay report a spurious hit as a match; probability \(\approx n/Q\)
Las Vegasverify character by character\(\Theta(n+m)\) expected, \(\Theta(nm)\) worstalways correct

The Monte Carlo version is not a toy. With \(Q\) a prime near \(2^{61}\), scanning \(n = 10^6\) characters carries an error probability of about \(10^6 / (2^{61}-1) \approx 4 \times 10^{-13}\), and it buys the one property Las Vegas cannot offer: a hard time bound. It is the version used when the text is a stream too large to re-read, where verification would be impossible anyway. The Las Vegas version is the default everywhere else, and is what §4 implements: a spurious hit costs time, never correctness. The same pair of options appears in Bloom Filters (a Monte Carlo membership test with one-sided error) and in Quicksort with a random pivot (Las Vegas: always sorted, expected \(\Theta(n \log n)\)).

Many patterns in one pass

Rabin–Karp’s distinctive strength appears when there are \(k\) patterns to look for, all of the same length \(m\). Hash all of them into a hash set (or a map from fingerprint to the list of patterns with that fingerprint), then run the same single rolling scan and test each window’s fingerprint against the set: expected \(O(1)\) per window, so the whole search costs \(\Theta(n + km)\) expected, independent of \(k\) in the scan itself. Knuth–Morris–Pratt and Boyer–Moore have no such trick: each pattern needs its own tables and its own pass, costing \(\Theta(kn)\). This is the engine inside plagiarism detectors (fingerprint every \(m\)-word window of the submission, look each up in the corpus index) and signature scanners (thousands of malware signatures, one pass over the file).

Example (three patterns, one scan) Text 3141592653589793, patterns 14159, 26535, 89793, with \(R = 10\), \(Q = 997\). Preprocessing builds the fingerprint set \(\{201, 613, 63\}\) (the three values computed in §5). The scan rolls one hash across the text and looks it up: 
  window  1:  14159   h = 201  ∈ set  →  verify against 14159  →  match at 1
  window  6:  26535   h = 613  ∈ set  →  verify against 26535  →  match at 6
  window 11:  89793   h =  63  ∈ set  →  verify against 89793  →  match at 11
  (the other nine windows: h ∉ set, rejected with no character comparisons)
Three patterns, one pass, twelve hash lookups, fifteen character comparisons. Adding a thousand more patterns of length \(5\) would not change the scan at all, only the size of the set.
Patterns of different lengths The rolling hash is tied to a single window width, so \(k\) patterns of \(d\) distinct lengths need \(d\) rolling hashes maintained in parallel (still one pass over the text, \(d\) constant-time updates per position). When \(d\) is large, the multi-pattern problem is usually handed to an automaton-based method instead (Regular Expressions & Automata), which handles all lengths in one machine.

8. Cost, and how often a fingerprint lies

Preprocessing is \(\Theta(m)\): \(m-1\) multiply-reduce steps for \(\mathit{RM}\), \(m\) Horner steps for \(h(P)\), \(m\) more for the first window. The scan performs \(n-m\) rolls of \(O(1)\) arithmetic each, plus one integer comparison per window, plus verification. The first two terms are \(\Theta(n+m)\) unconditionally. Everything interesting is in the third.

Proposition (worst case \(\Theta(nm)\)) The Las Vegas version makes \(\Theta(nm)\) character comparisons in the worst case.
Proof. Take \(P = \texttt{A}^m\) and \(T = \texttt{A}^n\) and ask for all occurrences. Every one of the \(n-m+1\) windows equals the pattern, so every window is verified in full: \((n-m+1)\,m = \Theta(nm)\) comparisons. This instance is honest rather than adversarial (the output itself has \(n-m+1\) entries), but the same bound is reachable with no occurrences at all: since \(Q\) is a fixed public constant in most implementations, an adversary can solve for windows whose polynomial value is congruent to \(h(P)\) modulo \(Q\) while differing from \(P\) only in the last character, making every window a spurious hit costing \(m\) comparisons. ∎

So the linear bound must be a statement about typical, not worst-case, behavior, and it is obtained by modelling the fingerprint as random.

Proposition (expected cost \(\Theta(n+m)\)) Model the fingerprint as a uniformly random value in \(\{0, 1, \dots, Q-1\}\), independently for each window that differs from the pattern. Then the expected number of spurious hits in a scan is at most \(n/Q\), the expected number of character comparisons spent on them is at most \(nm/Q\), and the total expected running time is \(\Theta(n + m + nm/Q)\), which is \(\Theta(n+m)\) whenever \(Q \ge m\).
Proof. Fix a window \(i\) with \(T[i..i+m-1] \ne P\). Under the model, its fingerprint equals \(h(P)\) with probability \(1/Q\). Let \(X_i\) be the indicator of that event. The number of spurious hits is \(X = \sum_i X_i\) over at most \(n\) windows, and by linearity of expectation (which needs no independence), \(\mathbb{E}[X] \le n/Q\). Each spurious hit costs at most \(m\) character comparisons, so the expected verification work is at most \(mn/Q\). Adding the unconditional \(\Theta(n+m)\) of preprocessing and rolling, plus the \(m\) comparisons of the single successful verification, gives \(\Theta(n + m + nm/Q)\). If \(Q \ge m\) then \(nm/Q \le n\) and the whole expression is \(\Theta(n+m)\). ∎

The proposition makes the choice of \(Q\) concrete. For \(n = 10^6\) and \(m = 100\):

\(Q\)expected spurious hits \(\approx n/Q\)expected wasted comparisons \(\le nm/Q\)
\(997\)\(\approx 1003\)\(\approx 10^5\) (a tenth of the scan)
\(1{,}000{,}003\)\(\approx 1.0\)\(\approx 100\)
\(2^{31}-1 = 2{,}147{,}483{,}647\)\(\approx 0.00047\)\(\approx 0.047\)

At a 32-bit prime the expected number of spurious hits over a megabyte of text is under one in two thousand: verification effectively never runs, and the measured cost is the rolling scan alone.

What the uniformity assumption is doing Real fingerprints are not random; they are a fixed function of the text, and for a fixed \(Q\) an adversary can defeat them (the second half of the worst-case proof). Two honest positions are available. The empirical one: on inputs that are not adversarial the model predicts well. Scanning \(200\) random \(1000\)-digit texts for a random \(5\)-digit pattern (\(996\) windows each) produced an average of \(76.1\) spurious hits per text at \(Q = 13\) against a predicted \(996/13 = 76.6\), and \(0.95\) at \(Q = 997\) against a predicted \(0.999\). The rigorous one: choose \(Q\) at random from a large set of primes at run time. A window differing from the pattern gives a nonzero difference of polynomial values, bounded by \(R^m\), so that difference has fewer than \(m \log_2 R\) prime factors; a fingerprint collision requires the chosen \(Q\) to be one of them, an event of probability at most \(m \log_2 R / \pi(N)\) when \(Q\) is drawn uniformly from the \(\pi(N)\) primes below \(N\). That version has no bad inputs, only unlucky draws, which is the same move as choosing a random pivot in Quicksort or a random hash function in Hashing.

Space is \(\Theta(1)\) beyond the input: a handful of integers, with no table proportional to \(m\) (unlike Knuth–Morris–Pratt’s failure function) or to the alphabet (unlike Boyer–Moore’s skip table). The scan is also single-pass and forward-only apart from verification, so it runs on a stream with an \(m\)-character buffer, and in the Monte Carlo form with no buffer at all.

Where this sits

The problem statement, the brute-force baseline and the comparison table for the whole family are in Substring Search: The Problem & Baselines. The two comparison-based fast searchers are Knuth–Morris–Pratt (guaranteed \(\Theta(n+m)\), never backs up, the right call when a hard bound is required) and Boyer–Moore (sublinear on typical text, the usual choice for a single pattern in a file). The fingerprint itself, the reason a prime modulus is used, and the collision arithmetic all come from Hashing; Bloom Filters is the other place in the catalog where a hash is trusted without verification and the error probability is engineered rather than eliminated. When the same text will be searched many times for many patterns, the right move is to preprocess the text instead of the pattern: Suffix Arrays and Tries & Ternary Search Trees. And when the target is a whole family of strings rather than one fixed string, the problem becomes pattern matching against a language: Regular Expressions & Automata.

9. Exercises (with solutions)

  1. Using \(R = 10\) and \(Q = 997\), the window 31415 has fingerprint \(31415 \bmod 997 = 508\). Roll it one position to the right (drop 3, admit 9) using the update of §3, and check the answer against a direct computation.
    solution \(\mathit{RM} = 10^4 \bmod 997 = 10000 - 10 \cdot 997 = 10000 - 9970 = 30\). The update: \((508 - 3 \cdot 30) = 508 - 90 = 418\), then \(418 \cdot 10 + 9 = 4189\), and \(4189 \bmod 997 = 4189 - 4 \cdot 997 = 4189 - 3988 = 201\). Direct: \(14159 \bmod 997 = 14159 - 14 \cdot 997 = 14159 - 13958 = 201\). They agree. Note that this particular subtraction stayed positive; the \(+Q\) correction of §3 is still mandatory, because whether it stays positive depends entirely on the characters involved (every roll in the §5 trace went negative).
  2. A student writes the roll as h = (h - t[i]*RM) % Q; h = (h*R + t[i+m]) % Q; in Java and reports that the search sometimes misses occurrences that are plainly there. Diagnose the bug precisely, and explain why the same two lines are correct in Python.
    solution In Java (as in C++ and Rust) % is the remainder operation, which takes the sign of the dividend, so when \(h < T[i] \cdot \mathit{RM}\) the first line stores a negative value. The stored residue is then \(h' - Q\) instead of \(h'\), and every subsequent roll propagates the error, so the window fingerprints stop matching the pattern’s and true occurrences are silently skipped. (The bug is intermittent because a text whose leading characters are small may never trigger a negative intermediate.) The fix is h = (h + Q - (RM*t[i]) % Q) % Q;: reducing the product first puts it in \([0, Q)\), so adding one \(Q\) is enough to make the difference non-negative. Python’s % implements mathematical modulo and always returns a result with the sign of the divisor, so (-25) % 13 is \(1\), not \(-12\), and the naive lines are already correct there.
  3. With \(R = 10\) and \(Q = 13\), §5 found that the windows 14159, 26535 and 89793 all have fingerprint \(2\). How many spurious hits would the scan of §5 report if it were asked for all occurrences rather than the first, and how many character comparisons would each cost?
    solution Continuing past index \(6\), the remaining windows are 65358 (\(h = 7\)), 53589 (\(3\)), 35897 (\(4\)), 58979 (\(11\)) and 89793 (\(2\)). Only the last is a hit, so the full scan has \(4\) fingerprint hits in all: spurious ones at \(i = 1, 5, 11\) and the true match at \(i = 6\). Each spurious hit fails on its first character (1, 9 and 8 against the pattern’s 2), so each costs exactly \(1\) comparison: \(3\) wasted comparisons plus \(5\) for the match. Against the prediction \(n/Q \approx 12/13 \approx 0.92\) spurious hits, three is high; \(12\) windows is far too small a sample for the expectation to mean much, and \(Q = 13\) is far too small a modulus for anything but a trace.
  4. A plagiarism detector fingerprints every \(5\)-word window of a \(2000\)-word submission and looks each fingerprint up in a set of \(10^7\) fingerprints drawn from a corpus, using \(Q = 2^{31}-1\). Estimate the expected number of spurious hits for one submission. What changes if the corpus set is replaced by a Bloom filter?
    solution There are \(1996\) windows, and each has \(10^7\) chances to collide with a corpus fingerprint, each of probability \(1/Q\) under the uniform model: expected spurious hits \(\approx 1996 \times 10^7 / (2^{31}-1) \approx 9.3\): about ten wasted verifications per submission, negligible against the scan, and all of them caught. The lesson is that the relevant ratio is not \(n/Q\) but (windows \(\times\) patterns)\(/Q\): a large pattern set eats into the modulus budget, so \(Q\) must grow with it. Replacing the set by a Bloom filter adds a second, independent source of false positives (the filter’s own one-sided error) on top of the fingerprint collisions; both are still caught by the same verification step, so correctness is unaffected and the memory saving is usually the better trade.
  5. Give a text and pattern on which the Las Vegas version makes \(\Theta(nm)\) character comparisons even though the fingerprint never once lies, and explain why this does not contradict the expected-cost proposition of §8.
    solution \(P = \texttt{A}^m\), \(T = \texttt{A}^n\), asking for all occurrences. Every window truly equals the pattern, so every fingerprint hit is genuine and every verification succeeds after \(m\) comparisons: \((n-m+1)m = \Theta(nm)\) with zero spurious hits. There is no contradiction because the proposition bounds only the work spent on spurious hits; work spent confirming real occurrences is output-dependent, and here the output has \(n-m+1\) entries, so \(\Theta(nm)\) is unavoidable for any algorithm that reports each occurrence by verifying it. Asking only for the first occurrence costs \(m\) comparisons on this instance.
  6. A firewall must scan a non-seekable stream at line rate for \(3000\) fixed \(64\)-byte signatures. Argue for a variant of Rabin–Karp, and say what the other members of the family would cost here.
    solution Monte Carlo Rabin–Karp over the set of \(3000\) fingerprints. One rolling hash and one hash-set lookup per byte gives a hard \(O(1)\)-per-byte bound with no buffering and no re-reading, which is what line rate requires; the Las Vegas version cannot promise that, since verification would need the last \(64\) bytes buffered and its cost is only bounded in expectation. With \(Q\) near \(2^{61}\) the probability of a false alarm is about \(3000 \cdot n / 2^{61}\), negligible for any \(n\) a firewall will see in its lifetime, and a false alarm here is a packet flagged for inspection rather than an incorrect answer, so the one-sided error costs nothing but a rare extra check. Knuth–Morris–Pratt gives the hard bound for one pattern, but \(3000\) of them means \(3000\) failure functions and \(3000\) parallel scans: \(\Theta(kn)\). Boyer–Moore needs an \(m\)-byte lookahead and has a \(\Theta(nm)\) worst case, so an adversary can break line rate deliberately. Brute force fails on both counts at once.
  7. Adapt Rabin–Karp to two dimensions: find an \(m \times m\) pattern block inside an \(n \times n\) image, treating pixel values as characters. What is the cost?
    solution Apply the one-dimensional idea twice. First, for each row of the image, roll a horizontal hash of width \(m\) across it, producing an array \(H[r][c]\) = fingerprint of the \(m\) pixels starting at \((r, c)\); this costs \(\Theta(n^2)\) in total, \(O(1)\) per position. Now treat each column of \(H\) as a string over the alphabet of fingerprints and roll a vertical hash of height \(m\) down it, combining \(m\) consecutive row-fingerprints into one block fingerprint, again \(O(1)\) per position and \(\Theta(n^2)\) overall. Compare each block fingerprint against the pattern block’s (computed the same way) and verify hits by comparing \(m^2\) pixels. Total: \(\Theta(n^2 + m^2)\) expected, versus \(\Theta(n^2 m^2)\) for the brute-force block comparison. The composition works because the second hash never needs the underlying pixels, only the first hash’s values, which is exactly the property that a rolling hash of a rolling hash is still rollable.
