Huffman Coding

David Huffman found his algorithm in 1951 as a term paper for Robert Fano’s information theory course at MIT, which students could write instead of taking the final exam. It beat the code Fano and Shannon had published. D. A. Huffman, “A Method for the Construction of Minimum-Redundancy Codes,” Proc. IRE 40, 1952

The Dijkstra’s Algorithm handout named the greedy pattern when Dijkstra introduced it; Prim and Kruskal (the Prim’s Algorithm and Kruskal’s Algorithm handouts) deepened the habit; and the Greedy Method handout develops the method in general: the licensing properties, the exchange argument, and the counterexamples that demolish an unproved rule. This handout applies all of it to one problem done end to end: Huffman coding, where a single repeated greedy move (merge the two least-frequent symbols) builds an optimal compression code, proved optimal by that handout’s own technique.

1. Huffman coding: an optimal prefix-free code

The problem is data compression: store text in fewer bits. Start with what a code is. A computer stores text as bits, so every symbol needs a bit pattern. The distinct symbols of the text form its alphabet, and a code assigns each symbol a codeword, a string of bits. To encode a text you replace each symbol by its codeword and concatenate; to decode you recover the symbols from the bit stream. The quantity to minimize is the total length, \[ \operatorname{cost} \;=\; \sum_{\text{symbols } s} f_s \cdot \lvert \operatorname{codeword}(s) \rvert, \] with \(f_s\) the number of times \(s\) occurs. A fixed-length code gives every codeword the same width: \(\lceil \log_2 6 \rceil = 3\) bits for \(6\) symbols, the same idea as ASCII’s \(8\) bits for \(256\). It is trivial to decode (chop the stream into equal pieces), but it spends the same on a symbol that appears a hundred times as on one that appears once, which is wasteful whenever the frequencies are skewed. A variable-length code fixes this by giving frequent symbols short codes and rare symbols long ones, lowering the average bits per symbol. But variable-length codes raise a hazard:

Example (ambiguity) With \(a = 0\), \(b = 1\), \(c = 01\), the bit string \(01\) could be “\(ab\)” or “\(c\)”: undecodable. The trouble is that \(a\)’s code \(0\) is a prefix of \(c\)’s code \(01\).
Definition (prefix-free code and its trie) A code is prefix-free if no codeword is a prefix of another. Such a code is exactly a binary trie (a tree whose paths spell things out, here one codeword per root-to-leaf path; the Tries handout studies tries in their own right) with the symbols at its leaves: the code of a symbol is the sequence of turns from the root (left \(= 0\), right \(= 1\)). Because a leaf is never an ancestor of another leaf, no code is a prefix of another, so decoding is unambiguous.

Decoding a prefix-free code is a walk down the trie: read bits, turn left or right, and emit a symbol the instant you reach a leaf, then restart at the root. The cost above now reads off the tree, because a symbol’s codeword length is its depth: \[ \operatorname{cost}(T) \;=\; \sum_{\text{symbols } s} f_s \cdot d_s, \] where \(f_s\) is \(s\)’s frequency and \(d_s\) its depth in the trie (the length of its code). Minimizing this over all prefix-free codes is the question Huffman answers.

Huffman’s greedy idea

A deep leaf has a long code, so it should hold a rare symbol; the two rarest symbols can afford to be the deepest, as sibling leaves. That is exactly the greedy move: repeatedly merge the two least-frequent nodes into a new parent whose frequency is their sum, until one tree remains. The “two smallest” query is answered by a min-heap, the structure from the Heaps & Priority Queues handout again. 

// A Huffman tree node. Leaves carry a symbol; internal nodes just a frequency.
struct Node {
    long freq; char sym;            // sym is '\0' for internal nodes
    Node *left, *right;
};

// Build the Huffman tree: repeatedly merge the two lowest-frequency nodes. A
// min-heap of Node* keyed by frequency answers "the two smallest" in O(log n).
Node* buildHuffman(const vector<pair<char,long>>& freqs) {
    auto cmp = [](Node* a, Node* b) { return a->freq > b->freq; };  // min-heap
    priority_queue<Node*, vector<Node*>, decltype(cmp)> pq(cmp);
    for (auto [sym, f] : freqs)
        pq.push(new Node{f, sym, nullptr, nullptr});
    while (pq.size() > 1) {
        Node* x = pq.top(); pq.pop();          // two smallest frequencies
        Node* y = pq.top(); pq.pop();
        pq.push(new Node{x->freq + y->freq, '\0', x, y});   // merge under a parent
    }
    return pq.top();                           // the single remaining root
}

Node buildHuffman(Map<Character, Long> freqs) {
    PriorityQueue<Node> pq =
        new PriorityQueue<>((a, b) -> Long.compare(a.freq, b.freq));  // min-heap
    for (var e : freqs.entrySet())
        pq.add(new Node(e.getValue(), e.getKey(), null, null));
    while (pq.size() > 1) {
        Node x = pq.poll();                    // two smallest frequencies
        Node y = pq.poll();
        pq.add(new Node(x.freq + y.freq, '\0', x, y));   // merge under a parent
    }
    return pq.peek();                          // the single remaining root
}

    sym: Option<char>,

impl Ord for Node {
    fn cmp(&self, other: &Self) -> Ordering { other.freq.cmp(&self.freq) }
}
impl PartialOrd for Node {
    fn partial_cmp(&self, other: &Self) -> Option<Ordering> { Some(self.cmp(other)) }
}
impl PartialEq for Node { fn eq(&self, o: &Self) -> bool { self.freq == o.freq } }
impl Eq for Node {}

fn build_huffman(freqs: &[(char, u64)]) -> Node {
    let mut pq: BinaryHeap<Node> = freqs.iter()
        .map(|&(sym, freq)| Node { freq, sym: Some(sym), left: None, right: None })
        .collect();
    while pq.len() > 1 {
        let x = pq.pop().unwrap();            // two smallest frequencies
        let y = pq.pop().unwrap();
        pq.push(Node {                        // merge under a new parent
            freq: x.freq + y.freq, sym: None,
            left: Some(Box::new(x)), right: Some(Box::new(y)),
        });
    }
    pq.pop().unwrap()                         // the single remaining root
}

Starting from \(n\) leaf nodes, each merge removes two roots and adds one, so there are exactly \(n-1\) merges, ending with a single tree of \(2n-1\) nodes. Every internal node has two children (the tree is full), which is what guarantees every symbol lands on a leaf.

Example (a worked build, the CLRS frequencies) Symbols with frequencies \(a{:}5,\ b{:}9,\ c{:}12,\ d{:}13,\ e{:}16,\ f{:}45\) (total \(100\)): The rarest symbols \(a\) and \(b\) merge first and sink deepest; the most frequent, \(f\), waits until the final merge and lands one hop from the root. The internal-node sums \(14, 25, 30, 55, 100\) build up to the total character count.

Seen as the priority queue’s contents (the state the build actually maintains), each step removes the two smallest roots (shaded) and pushes their sum. Leaf roots are written with their symbol; internal roots are bare sums.

Once the tree is built, one traversal collects every code: append 0 going left, 1 going right, and record the path at each leaf: 

// Walk the finished trie once, building each leaf's root-to-leaf path
// (left = '0', right = '1'). Fills code[sym] for every symbol. O(n).
void extractCodes(Node* node, string path,
                  unordered_map<char, string>& code) {
    if (!node) return;
    if (!node->left && !node->right) {         // a leaf: record its code
        code[node->sym] = path;
        return;
    }
    extractCodes(node->left,  path + "0", code);
    extractCodes(node->right, path + "1", code);
}

Proposition (Huffman cost) Building the tree and extracting the codes takes \(O(n\log n)\) time for \(n\) symbols.
Proof. Heapifying \(n\) leaves is \(O(n)\). The build does \(n-1\) merges, each two delMins and one insert, each \(O(\log n)\), for \(O(n\log n)\). Extracting the codes is a single DFS over \(2n-1\) nodes, \(O(n)\). The heap operations dominate: \(O(n\log n)\). ∎
Breaking ties When two nodes tie for smallest frequency, Huffman may merge either: different tie-breaks yield different trees and even different individual code lengths, but every resulting tree is optimal, so the total encoded length is identical. This is exactly the minimum-spanning-tree situation: the optimal cost is unique, the optimal structure need not be.
Example (a tie, resolved both ways) Frequencies \(a{:}1,\ b{:}1,\ c{:}2,\ d{:}2\), total \(6\). The first merge is forced, since \(a\) and \(b\) are the only \(1\)s, and it manufactures the tie: three roots of weight \(2\), any two of which may be popped. Popping \(c\) and \(d\) gives one tree; popping \(ab\) and \(c\) gives another: The two trees give different code lengths for every symbol except \(c\), and the same total:

2. Why Huffman is optimal

Two lemmas, in the standard greedy shape: the first shows the greedy merge is safe (greedy-choice property), the second shows the rest is the same problem (optimal substructure). Together with induction they prove every Huffman tree minimizes \(\operatorname{cost}(T) = \sum_s f_s d_s\).

Lemma 1 (the two rarest may be deepest siblings) Let \(x, y\) be the two lowest-frequency symbols. Some optimal prefix-code tree has \(x\) and \(y\) as sibling leaves at maximum depth.
Proof (exchange). Take any optimal tree \(T\). An optimal code tree is full (a one-child node could be deleted, shortening its subtree and lowering the cost), so its deepest internal node has two leaf children; call them \(a, b\), sibling leaves at maximum depth. Swap the rarest symbol \(x\) with whatever sits at \(a\). The only costs that change are those of the two symbols moved, so \[ \Delta\operatorname{cost} = (f_x d_a + f_a d_x) - (f_x d_x + f_a d_a) = (f_a - f_x)(d_x - d_a) \le 0, \] because \(f_a \ge f_x\) (\(x\) is a rarest symbol) and \(d_x \le d_a\) (\(a\) is at maximum depth). The swap cannot increase the cost, so the result is still optimal. Swapping \(y\) with the occupant of \(b\) likewise, we reach an optimal tree with \(x, y\) as deepest sibling leaves, which is exactly Huffman’s first merge. ∎
Lemma 2 (merging shrinks the problem) Merge \(x, y\) into a single symbol \(z\) with \(f_z = f_x + f_y\). For any tree \(T\) in which \(x, y\) are siblings, let \(T'\) be \(T\) with that sibling pair replaced by the single leaf \(z\). Then \(\operatorname{cost}(T) = \operatorname{cost}(T') + f_x + f_y\).
Proof. The symbols other than \(x, y\) occupy the same positions in \(T\) and \(T'\), contributing equally. In \(T\), \(x\) and \(y\) sit one level below \(z\)’s position in \(T'\), so each occurrence of \(x\) or \(y\) pays one extra bit compared with \(z\): the difference is \(f_x d_z' + f_y d_z' \) replaced by \(f_x(d_z'+1) + f_y(d_z'+1)\), i.e. an extra \(f_x + f_y\). Hence \(\operatorname{cost}(T) = \operatorname{cost}(T') + f_x + f_y\). ∎

Since \(f_x + f_y\) is a constant independent of the tree’s shape, minimizing \(\operatorname{cost}(T)\) is the same as minimizing \(\operatorname{cost}(T')\), a Huffman instance on \(n-1\) symbols. By Lemma 1 the first merge is safe; by Lemma 2 the remaining problem is a smaller Huffman instance; by induction on the number of symbols, Huffman’s tree is optimal. This two-lemma structure (greedy choice is safe, then the rest is the same problem) is the canonical greedy-optimality proof, the same shape as the MST cut property and activity selection.

3. Encoding, decoding, and the limits of compression

With the trie in hand, encoding replaces each symbol with its code and concatenates the bits: no separators, because the code is prefix-free. Decoding walks the trie from the root, emitting a symbol at each leaf and restarting.

Example (a round trip) Using the codes \(f{=}0,\ c{=}100,\ d{=}101,\ e{=}111,\ a{=}1100,\ b{=}1101\): The decode shows the crux: after emitting \(d\) you jump back to the root, and the lone remaining \(0\) is a complete code. No delimiter was needed; the tree’s leaf boundaries are the delimiters, which is why prefix-free codes are also called instantaneous.

Three things are worth reading off the table. The decoder never looks ahead: it commits to a symbol the instant it lands on a leaf, at bit 1 for f and only at bit 5 for a. It never needs to know where a codeword began, because it is always either at the root (between codewords) or partway down (inside one). And the stream ends at a leaf with the node back at the root, which is the only way a well-formed stream can end: a stream that runs out at an internal node was truncated.

The bits alone do not decode; the decoder needs the same trie, so a compressed file carries either the frequency table (the decoder re-runs the build to get the identical tree) or a serialization of the tree in its header. For a fixed alphabet (say \(256\) byte values) that header is a few hundred bytes, negligible against a large file.

Theorem (Shannon’s limit) No code can beat the entropy \(H = -\sum_s p_s \log_2 p_s\) bits per symbol on average, where \(p_s\) is \(s\)’s probability. Huffman comes within \(1\) bit of \(H\) per symbol, and is exactly optimal among codes that use an integer number of bits per symbol.

It is worth putting a number on that guarantee rather than leaving it abstract. For this handout’s own frequencies, \[ H \;=\; -\!\!\sum_{s \in \{a,\dots,f\}} p_s \log_2 p_s \;=\; 2.2199 \ \text{bits/symbol} \;\Longrightarrow\; 222 \ \text{bits}, \] against Huffman’s \(224\): a gap of \(0.02\) bits per symbol, not the \(1\) bit the theorem allows. The bound is a worst case, and Huffman is usually far inside it. Note also that \(222\) is a floor no prefix code can reach here, not a target: attaining it would need fractional code lengths, which is precisely what the next paragraph is about.

Kraft’s inequality: which code lengths are even possible Before asking which prefix code is best, ask which are legal. Kraft’s inequality says a binary prefix code with codeword lengths \(\ell_1, \dots, \ell_n\) exists if and only if \[ \sum_{i=1}^{n} 2^{-\ell_i} \;\le\; 1. \] The reason is exactly the trie: a codeword of length \(\ell\) is a leaf at depth \(\ell\), which claims a \(2^{-\ell}\) fraction of the leaves of a full depth-\(D\) tree, and disjoint leaves’ fractions cannot exceed the whole. Huffman is then the solution to a clean optimization: minimize \(\sum_i f_i \ell_i\) over all integer lengths satisfying Kraft. Relax the integers to real lengths and calculus gives the optimum \(\ell_i = -\log_2 p_i\), whose cost is the entropy \(H\), the theoretical floor of the theorem above. Huffman pays for rounding those lengths back to whole bits, which is the entire “within one bit” gap, and is what arithmetic coding sidesteps by never rounding.

The residual sub-bit gap (Huffman must spend a whole number of bits per symbol, while \(H\) may be fractional) is why arithmetic and ANS coders exist, squeezing closer to \(H\). And Huffman rarely works alone: it captures frequency skew but not repetition, so real compressors first find repeats (run-length or LZ77) and then Huffman-code the residual. This is DEFLATE, the engine inside ZIP, gzip, and PNG; Huffman also codes the quantized data in JPEG and MP3. Not bad for the answer to a 1952 term-paper assignment.

4. Adaptive Huffman: coding without a table

Everything above assumes the frequencies are known before encoding starts. That assumption costs twice. First, it forces two passes: read the whole input to count, then read it again to encode, impossible for a stream that has no end. Second, the decoder cannot decode without the code, so the table travels with the message, and a table is not free.

Example (the table is not free) Spend \(8\) bits naming the symbol, \(4\) bits for its code length, and the codeword itself, per symbol:
mississippiabracadabra
characters, distinct symbols11, 411, 5
ASCII88 bits88 bits
Huffman body21 bits23 bits
body + the table78 bits96 bits
against ASCIIstill a winnow a loss
The body is what the earlier sections counted; it is not what you transmit. A short message with many distinct symbols spends most of its budget introducing them.

There is a second, subtler failure. A Huffman code is optimal for the frequencies it was built from, and only for those. Meet it with a text drawn from some other distribution and it can cost more than the fixed-length code it replaced: not because the algorithm went wrong, but because the bet was wrong. Under a code built for average English prose (26 letters plus the space, the space at 18% of characters), she sells sea shells on the sea shore costs 138 bits against the 5-bit fixed code's 185, while jazzy vixen quips costs 103 against 85. The mechanism is Kraft's inequality: the codeword lengths of any prefix code satisfy \(\sum_s 2^{-\ell_s} \le 1\), a fixed budget, so buying e a 3-bit code forces z up to 10. Huffman spends that budget where the model says the mass is.

One tree, two machines

Adaptive Huffman removes both problems at once. Encoder and decoder start from the same empty tree and, after every symbol, run the same update. The encoder codes symbol \(s\) with the tree built from symbols \(1 \ldots s-1\); the decoder, having just decoded \(1 \ldots s-1\), holds exactly that tree, so it can decode \(s\); only then does either side update. No table is transmitted because none is needed: it is derived, in lockstep, at both ends.

A symbol not yet seen has no leaf, so the tree keeps one weight-0 leaf called NYT (“not yet transmitted”) whose path is the escape prefix. Encoding a brand-new symbol emits the path to NYT followed by the symbol’s 8 plain ASCII bits; NYT then splits into a new NYT and a leaf for that symbol. The very first symbol of a message is the degenerate case worth checking: the tree is NYT, its path is empty, and the symbol costs exactly its 8 raw bits.

The sibling property

Rebuilding a Huffman tree after every symbol would cost \(\Theta(n \log n)\) each time. Instead the algorithm maintains the property that characterizes Huffman trees. Number the nodes bottom-up, left to right, so the root has the highest number. A tree has the sibling property when every node has a sibling and weight never decreases as the number grows.

Gallager’s theorem A binary tree is a Huffman tree for its leaf weights exactly when it has the sibling property.

Nodes of equal weight form a block, and within a block the numbering is free; that freedom is what the update exploits. Incrementing one leaf can break the ordering in only one way: the node now outweighs a same-weight node that sits higher in the numbering. Moving it into that node’s slot first repairs it. 

// Adaptive Huffman (FGK): the update the encoder and the decoder both run
// after every symbol. Nodes are numbered bottom-up, left to right, the root
// highest; a number belongs to a POSITION, so a swap trades numbers back.
struct Node {
    int weight = 0;
    int number = 0;
    char symbol = 0;                      // a leaf's symbol; NYT, internal: 0
    Node* parent = nullptr;
    Node* left = nullptr;
    Node* right = nullptr;
};

struct AdaptiveTree {
    static const int TOP = 512;           // the root's number
    vector<Node*> byNumber = vector<Node*>(TOP + 1, nullptr);
    map<char, Node*> leafOf;              // the leaf of each symbol seen
    Node* nyt;                            // "not yet transmitted", weight 0
    Node* root;

    AdaptiveTree() {
        nyt = new Node();
        nyt->number = TOP;
        byNumber[TOP] = nyt;
        root = nyt;
    }
    ~AdaptiveTree() {
        for (Node* n : byNumber) delete n;
    }

    bool isAncestor(Node* a, Node* n) {   // is a above n?
        for (Node* p = n->parent; p != nullptr; p = p->parent) {
            if (p == a) return true;
        }
        return false;
    }

    // The highest-numbered node of node's weight, if it outranks node. The
    // weights never decrease with the number, so that block of equal weights
    // is the run of numbers just above node's.
    Node* leader(Node* node) {
        Node* lead = nullptr;
        for (int k = node->number + 1; k <= TOP; k++) {
            if (byNumber[k]->weight != node->weight) break;
            if (!isAncestor(byNumber[k], node)) lead = byNumber[k];
        }
        return lead;
    }

    // Exchange two positions, subtrees and all; the numbers stay put.
    void swapNodes(Node* a, Node* b) {
        Node* pa = a->parent;
        Node* pb = b->parent;
        bool aLeft = (pa->left == a);
        bool bLeft = (pb->left == b);
        if (aLeft) pa->left = b; else pa->right = b;
        if (bLeft) pb->left = a; else pb->right = a;
        a->parent = pb;
        b->parent = pa;
        swap(a->number, b->number);
        byNumber[a->number] = a;
        byNumber[b->number] = b;
    }

    // A new symbol: NYT becomes an internal node over a new NYT (left) and
    // the symbol's leaf (right), weight 1. The walk starts at the old NYT.
    Node* splitNYT(char s) {
        Node* old = nyt;
        Node* leaf = new Node();
        leaf->weight = 1;
        leaf->symbol = s;
        leaf->number = old->number - 1;
        leaf->parent = old;
        nyt = new Node();
        nyt->number = old->number - 2;
        nyt->parent = old;
        old->left = nyt;
        old->right = leaf;
        byNumber[leaf->number] = leaf;
        byNumber[nyt->number] = nyt;
        leafOf[s] = leaf;
        return old;
    }

    void update(char s) {
        Node* node;
        if (leafOf.count(s) == 0) {
            node = splitNYT(s);           // a new symbol: split NYT first
        } else {
            node = leafOf[s];
        }
        while (node != nullptr) {
            Node* lead = leader(node);
            if (lead != nullptr) {        // a same-weight node outranks it
                swapNodes(node, lead);    // positions swap, numbers stay
            }
            node->weight++;
            node = node->parent;
        }
    }
};

    int weight = 0;
    int number = 0;

static class AdaptiveTree {
    static final int TOP = 512;           // the root's number
    Node[] byNumber = new Node[TOP + 1];
    Map<Character, Node> leafOf = new HashMap<>();   // each symbol's leaf
    Node nyt;                             // "not yet transmitted", weight 0
    Node root;

    AdaptiveTree() {
        nyt = new Node();
        nyt.number = TOP;
        byNumber[TOP] = nyt;
        root = nyt;
    }

    boolean isAncestor(Node a, Node n) {  // is a above n?
        for (Node p = n.parent; p != null; p = p.parent) {
            if (p == a) return true;
        }
        return false;
    }

    // The highest-numbered node of node's weight, if it outranks node. The
    // weights never decrease with the number, so that block of equal weights
    // is the run of numbers just above node's.
    Node leader(Node node) {
        Node lead = null;
        for (int k = node.number + 1; k <= TOP; k++) {
            if (byNumber[k].weight != node.weight) break;
            if (!isAncestor(byNumber[k], node)) lead = byNumber[k];
        }
        return lead;
    }

    // Exchange two positions, subtrees and all; the numbers stay put.
    void swapNodes(Node a, Node b) {
        Node pa = a.parent;
        Node pb = b.parent;
        boolean aLeft = (pa.left == a);
        boolean bLeft = (pb.left == b);
        if (aLeft) pa.left = b; else pa.right = b;
        if (bLeft) pb.left = a; else pb.right = a;
        a.parent = pb;
        b.parent = pa;
        int t = a.number;
        a.number = b.number;
        b.number = t;
        byNumber[a.number] = a;
        byNumber[b.number] = b;
    }

    // A new symbol: NYT becomes an internal node over a new NYT (left) and
    // the symbol's leaf (right), weight 1. The walk starts at the old NYT.
    Node splitNYT(char s) {
        Node old = nyt;
        Node leaf = new Node();
        leaf.weight = 1;
        leaf.symbol = s;
        leaf.number = old.number - 1;
        leaf.parent = old;
        nyt = new Node();
        nyt.number = old.number - 2;
        nyt.parent = old;
        old.left = nyt;
        old.right = leaf;
        byNumber[leaf.number] = leaf;
        byNumber[nyt.number] = nyt;
        leafOf.put(s, leaf);
        return old;
    }

    void update(char s) {
        Node node;
        if (!leafOf.containsKey(s)) {
            node = splitNYT(s);           // a new symbol: split NYT first
        } else {
            node = leafOf.get(s);
        }
        while (node != null) {
            Node lead = leader(node);
            if (lead != null) {           // a same-weight node outranks it
                swapNodes(node, lead);    // positions swap, numbers stay
            }
            node.weight++;
            node = node.parent;
        }
    }
}

class Node:

        self.weight = weight
        self.number = number
        self.symbol = symbol              # a leaf's symbol; NYT, internal: None
        self.parent = parent
        self.left = None
        self.right = None

class AdaptiveTree:
    TOP = 512                             # the root's number

    def __init__(self):
        self.nyt = Node(self.TOP)         # "not yet transmitted", weight 0
        self.root = self.nyt
        self.by_number = {self.TOP: self.nyt}
        self.leaf_of = {}                 # the leaf of each symbol seen

    def is_ancestor(self, a, n):          # is a above n?
        p = n.parent
        while p is not None:
            if p is a:
                return True
            p = p.parent
        return False

    # The highest-numbered node of node's weight, if it outranks node. The
    # weights never decrease with the number, so that block of equal weights
    # is the run of numbers just above node's.
    def leader(self, node):
        lead = None
        for k in range(node.number + 1, self.TOP + 1):
            if self.by_number[k].weight != node.weight:
                break
            if not self.is_ancestor(self.by_number[k], node):
                lead = self.by_number[k]
        return lead

    # Exchange two positions, subtrees and all; the numbers stay put.
    def swap_nodes(self, a, b):
        pa, pb = a.parent, b.parent
        a_left = pa.left is a
        b_left = pb.left is b
        if a_left:
            pa.left = b
        else:
            pa.right = b
        if b_left:
            pb.left = a
        else:
            pb.right = a
        a.parent, b.parent = pb, pa
        a.number, b.number = b.number, a.number
        self.by_number[a.number] = a
        self.by_number[b.number] = b

    # A new symbol: NYT becomes an internal node over a new NYT (left) and
    # the symbol's leaf (right), weight 1. The walk starts at the old NYT.
    def split_nyt(self, s):
        old = self.nyt
        leaf = Node(old.number - 1, old, weight=1, symbol=s)
        self.nyt = Node(old.number - 2, old)
        old.left = self.nyt
        old.right = leaf
        self.by_number[leaf.number] = leaf
        self.by_number[self.nyt.number] = self.nyt
        self.leaf_of[s] = leaf
        return old

    def update(self, s):
        if s not in self.leaf_of:
            node = self.split_nyt(s)      # a new symbol: split NYT first
        else:
            node = self.leaf_of[s]
        while node is not None:
            lead = self.leader(node)
            if lead is not None:          # a same-weight node outranks it
                self.swap_nodes(node, lead)   # positions swap, numbers stay
            node.weight += 1
            node = node.parent
// Adaptive Huffman (FGK): the update the encoder and the decoder both run
// after every symbol. Nodes are numbered bottom-up, left to right, the root
// highest; a number belongs to a POSITION, so a swap trades numbers back.
// Nodes live in one vector and refer to each other by index.
const TOP: usize = 512;                   // the root's number

struct Node {
    weight: u32,
    number: usize,
    symbol: Option<u8>,                   // a leaf's symbol; NYT, internal: None
    parent: Option<usize>,
    left: Option<usize>,
    right: Option<usize>,
}

struct AdaptiveTree {
    nodes: Vec<Node>,
    by_number: Vec<usize>,                // by_number[k] = the node numbered k
    leaf_of: HashMap<u8, usize>,          // the leaf of each symbol seen
    nyt: usize,                           // "not yet transmitted", weight 0
    root: usize,
}

impl AdaptiveTree {
    fn new() -> Self {
        let nyt = Node { weight: 0, number: TOP, symbol: None,
                         parent: None, left: None, right: None };
        let mut by_number = vec![usize::MAX; TOP + 1];
        by_number[TOP] = 0;
        AdaptiveTree { nodes: vec![nyt], by_number, leaf_of: HashMap::new(),
                       nyt: 0, root: 0 }
    }

    fn is_ancestor(&self, a: usize, n: usize) -> bool {   // is a above n?
        let mut p = self.nodes[n].parent;
        while let Some(i) = p {
            if i == a { return true; }
            p = self.nodes[i].parent;
        }
        false
    }

    // The highest-numbered node of node's weight, if it outranks node. The
    // weights never decrease with the number, so that block of equal weights
    // is the run of numbers just above node's.
    fn leader(&self, node: usize) -> Option<usize> {
        let mut lead = None;
        for k in self.nodes[node].number + 1..=TOP {
            let c = self.by_number[k];
            if self.nodes[c].weight != self.nodes[node].weight { break; }
            if !self.is_ancestor(c, node) { lead = Some(c); }
        }
        lead
    }

    // Exchange two positions, subtrees and all; the numbers stay put.
    fn swap_nodes(&mut self, a: usize, b: usize) {
        let pa = self.nodes[a].parent.unwrap();
        let pb = self.nodes[b].parent.unwrap();
        let a_left = self.nodes[pa].left == Some(a);
        let b_left = self.nodes[pb].left == Some(b);
        if a_left { self.nodes[pa].left = Some(b); } else { self.nodes[pa].right = Some(b); }
        if b_left { self.nodes[pb].left = Some(a); } else { self.nodes[pb].right = Some(a); }
        self.nodes[a].parent = Some(pb);
        self.nodes[b].parent = Some(pa);
        let t = self.nodes[a].number;
        self.nodes[a].number = self.nodes[b].number;
        self.nodes[b].number = t;
        self.by_number[self.nodes[a].number] = a;
        self.by_number[self.nodes[b].number] = b;
    }

    // A new symbol: NYT becomes an internal node over a new NYT (left) and
    // the symbol's leaf (right), weight 1. The walk starts at the old NYT.
    fn split_nyt(&mut self, s: u8) -> usize {
        let old = self.nyt;
        let number = self.nodes[old].number;
        let leaf = self.nodes.len();
        self.nodes.push(Node { weight: 1, number: number - 1, symbol: Some(s),
                               parent: Some(old), left: None, right: None });
        let fresh = self.nodes.len();
        self.nodes.push(Node { weight: 0, number: number - 2, symbol: None,
                               parent: Some(old), left: None, right: None });
        self.nodes[old].left = Some(fresh);
        self.nodes[old].right = Some(leaf);
        self.by_number[number - 1] = leaf;
        self.by_number[number - 2] = fresh;
        self.leaf_of.insert(s, leaf);
        self.nyt = fresh;
        old
    }

    fn update(&mut self, s: u8) {
        let mut node = if self.leaf_of.contains_key(&s) {
            Some(self.leaf_of[&s])
        } else {
            Some(self.split_nyt(s))           // a new symbol: split NYT first
        };
        while let Some(n) = node {
            if let Some(lead) = self.leader(n) {   // a same-weight node outranks it
                self.swap_nodes(n, lead);          // positions swap, numbers stay
            }
            self.nodes[n].weight += 1;
            node = self.nodes[n].parent;
        }
    }
}

Numbers belong to positions, not to nodes, so a swap exchanges them back; this is the detail implementations most often get wrong. Never swap with a parent or a descendant: that tangles the tree instead of reordering equals. A new symbol first splits NYT: the old NYT becomes the internal node over a new NYT and the symbol’s leaf, which starts at weight \(1\), and the walk starts at that internal node. The walk makes one increment and at most one swap per level, \(d\) levels for a tree of depth \(d\). The code above finds each leader by scanning the block upward, which costs the block’s size; an implementation that keeps a pointer to every block’s leader finds it in constant time, for \(O(d)\) per symbol on both sides.

The update, run on the first four symbols

The rule has three cases, and abracadabra shows all of them in its first four symbols. Nodes are drawn with their number and weight, and the numbering is checked after every step: read the nodes in increasing number and the weights never decrease, which is the sibling property.

stepsymbolcasesentwhat the update walk does
1anew symbol, and the tree is NYT(empty path) + 8 raw bits = 8 NYT splits: new NYT #1, leaf a #2, the old NYT becomes the internal root #3. Walk visits #3 only: no other node has weight 0, so no swap; \(0 \to 1\).
2bnew symbol 0 + 8 raw bits = 9 NYT #3 splits into #1 NYT, #2 b, #3 internal. Walk: #3 \(0 \to 1\), then the root #5 \(1 \to 2\); no swap at either.
3rnew symbol, and the walk hits a swap 00 + 8 raw bits = 10 NYT #3 splits into #1 NYT, #2 r, #3 internal, weight \(0 \to 1\). Next up is the internal node #5, weight 1; the weight-1 block is #2, #4, #5, #6 and its leader is the leaf a #6, which outranks it, so swap, then \(1 \to 2\). Root #7: \(2 \to 3\).
4asymbol already in the tree0 = 1 bit Leaf a is now #5, weight 1, and no higher-numbered node has weight 1, so no swap: \(1 \to 2\). Root #7: \(3 \to 4\).

The swap at step 3 is what makes step 4 cheap. Before it, \(a\) sat as an ordinary leaf; the swap lifts it to depth 1, so the next \(a\) costs a single bit, and every later \(a\) does too. That is the adaptation happening: the symbol that has been seen most rises toward the root without anyone recomputing a tree. Note also what the swap moved. Positions #5 and #6 exchanged subtrees; the numbers stayed with the positions, which is why \(a\) is #5 afterwards and the internal node is #6.

Two leaves can swap with each other as well. At the ninth symbol, the second \(b\), the leaf \(b\) has weight 1 and sits at #5 while the leaf \(r\), also weight 1, sits at #6: the two exchange places before \(b\)’s increment. Its codeword 110 is emitted first, from the tree the decoder still holds, and the tenth symbol, \(r\), then finds itself at #5 and sends 110 in its turn: the same three bits for a different symbol, one step apart, which is exactly the behaviour a static code cannot have.

Static Huffman’s body is unbeatable among prefix codes for those exact frequencies (that is the theorem of §2), but the body is not the message. Priced honestly, adaptive wins all but the last row, where nothing works: 27 distinct symbols in 43 characters means both schemes spend their lives introducing symbols they never see again. Compression is a bet on repetition, and no coder manufactures redundancy that is not there.

Adaptive Huffman itself is now mostly of historical and teaching interest; modern compressors keep an adaptive model but pair it with arithmetic coding or ANS, which escape Huffman’s whole-bit-per-symbol floor. What survives is the architecture: both ends maintain the same model under the same update rule, so the model never has to be sent, and it adapts to the data in front of it rather than to an average. A code that is provably optimal is not automatically the code you ship.

5. Exercises (with solutions)

  1. Build the Huffman tree for frequencies \(x{:}1,\ y{:}1,\ z{:}2,\ w{:}4\). Give the codes and the total encoded length \(\sum f_s d_s\).
    solution Merge \(x{+}y \to 2\); pool \(\{2(z),\ 2(xy),\ 4(w)\}\). Merge the two \(2\)s \(\to 4\); pool \(\{4(w),\ 4\}\). Merge \(\to 8\), the root. Codes: \(w = 0\) (frequency \(4\), shallow), \(z = 10\), \(x = 110\), \(y = 111\). Total \(= 4{\cdot}1 + 2{\cdot}2 + 1{\cdot}3 + 1{\cdot}3 = 14\) bits. The rarest symbols \(x, y\) sink deepest, as the greedy merge guarantees.
  2. Frequencies \(a{:}1,\ b{:}2,\ c{:}3,\ d{:}3\). The second merge faces a three-way tie. Build both trees the tie allows, give the codes, and compare the totals.
    solution The first merge is forced: \(a + b \to 3\), leaving the pool \(\{3(ab),\ 3(c),\ 3(d)\}\), where any two roots are “the two smallest.” Popping \(c\) and \(d\) gives \(6\), then merging with \(3(ab)\) gives the root \(9\): codes \(a = 00\), \(b = 01\), \(c = 10\), \(d = 11\), total \(1{\cdot}2 + 2{\cdot}2 + 3{\cdot}2 + 3{\cdot}2 = 18\). Popping \(ab\) and \(c\) instead gives \(6\), then merging with \(3(d)\) gives the root \(9\): codes \(d = 0\), \(c = 10\), \(a = 110\), \(b = 111\), total \(3{\cdot}1 + 3{\cdot}2 + 1{\cdot}3 + 2{\cdot}3 = 18\). The trees differ, every codeword length but \(c\)’s differs, and the totals agree, which is the general fact: ties change the tree, never the cost.
  3. In Lemma 1’s exchange, the cost change is \((f_a - f_x)(d_x - d_a)\). Explain why each factor has the sign claimed, and what would go wrong if \(x\) were not a lowest-frequency symbol.
    solution \(f_a - f_x \ge 0\) because \(x\) is chosen as a minimum-frequency symbol, so no symbol (including \(a\)) has smaller frequency. \(d_x - d_a \le 0\) because \(a\) sits at maximum depth, so no leaf (including \(x\)) is deeper. Their product is \(\le 0\), so the swap does not raise the cost. If \(x\) were not a rarest symbol, \(f_a - f_x\) could be negative while \(d_x - d_a\) is negative, making the product positive; the swap could increase cost, and the argument that the rarest belongs deepest would fail.
  4. A file uses only two symbols, \(a\) with frequency \(999\) and \(b\) with frequency \(1\). What codes does Huffman assign, how many bits does it use, and why can it not do better?
    solution With two symbols there is one merge, giving a tree with both as leaves at depth \(1\): \(a = 0\), \(b = 1\) (or the reverse), one bit each. Total \(999 + 1 = 1000\) bits. It cannot do better because a prefix-free code for two distinct symbols needs two distinct nonempty codewords, and the shortest such pair is two single bits; you cannot give \(a\) a zero-length code. This is Huffman’s one weakness against entropy: the entropy here is far below \(1\) bit per symbol, but integer-length codes cannot spend a fraction of a bit, which is what arithmetic coding is for.
  5. Give a set of interval activities on which the greedy “pick the activity that starts earliest” rule selects fewer than the optimum, and state the optimum.
    solution Activities \([0, 10)\), \([1, 2)\), \([3, 4)\), written half-open as in the Interval Scheduling handout. Earliest-start greedy takes \([0,10)\) first, which conflicts with both others, yielding \(1\) activity. The optimum takes \([1,2)\) and \([3,4)\): \(2\) activities, compatible because \(2 \le 3\). Earliest-finish greedy would take \([1,2)\) first and then \([3,4)\), matching the optimum, which is why the correct rule sorts by finish time, not start time.
  6. True or false, with justification: “A prefix-free code always uses no more bits than a fixed-length code on the same text.”
    solution False in general, true for the Huffman prefix code. A prefix-free code can be chosen badly (e.g. giving a frequent symbol a long code) and use more bits than the fixed-length code. What is true is that Huffman’s prefix code is optimal, so it uses no more than any other prefix code, including the fixed-length one (which is itself a prefix code, the balanced tree). When frequencies are uniform, Huffman ties the fixed-length code; when skewed, it beats it.
  7. A code built for average English gives e 3 bits and z 10. Explain, using Kraft’s inequality, why no prefix code can give both of them short codewords, and what that implies about a text made mostly of rare letters.
    solution Any prefix code satisfies \(\sum_s 2^{-\ell_s} \le 1\): each codeword of length \(\ell\) claims a \(2^{-\ell}\) share of the leaf budget, and the shares cannot exceed the whole. Giving e 3 bits spends \(1/8\) of the budget on one symbol, so the remaining symbols must share what is left and some are pushed deep. The lengths are therefore competitive, not independent. A text made of rare letters pays those deep codewords on every character, which is why jazzy vixen quips costs 103 bits under the English code against the fixed code’s 85. Huffman is optimal for the frequencies it was given, not for whatever text arrives.
  8. In adaptive Huffman, why must the encoder update the tree after emitting a symbol’s codeword rather than before? What would break?
    solution The decoder can only reproduce the tree the encoder used if it has already seen everything that tree was built from. It decodes symbol \(s\) using the tree over symbols \(1 \ldots s-1\), so the encoder must have coded \(s\) with that same tree, i.e. before applying \(s\)’s update. Updating first would code \(s\) with a tree that includes \(s\)’s own increment, which the decoder cannot construct until it knows \(s\): a circular dependency, and the streams desynchronize from the first symbol.
  9. Why does Huffman’s build produce a full binary tree (every internal node has two children), and why does optimality require fullness?
    solution Every merge creates a parent from exactly two popped nodes, so no internal node is ever built with one child; the tree is full by construction. Fullness is necessary for optimality: a one-child internal node adds a bit to every symbol in its subtree without any branching benefit, so deleting it (promoting its child) lowers every affected code length and strictly reduces \(\sum f_s d_s\). An optimal tree therefore cannot contain a one-child node.
  10. You must compress a stream but cannot afford a first pass to count frequencies. Name the property of static Huffman this violates and the variant that resolves it.
    solution Static Huffman needs the symbol frequencies before it can build the tree, so it requires either a first counting pass over the data or a transmitted frequency table, impossible on a single-pass stream of unknown composition. Adaptive Huffman resolves it by building and updating the tree as symbols arrive, keeping encoder and decoder in lockstep from the same running counts, so no prior pass or transmitted table is needed (at the cost of continual tree maintenance).
  11. In the adaptive trace, the update for the third symbol swaps an internal node with the leaf \(a\) before incrementing. Why is the swap necessary, and why must a node never be swapped with its own parent?
    solution At that moment the internal node is #5 with weight 1 and the leaf \(a\) is #6 with weight 1. Incrementing #5 in place would leave a weight-2 node numbered below a weight-1 node, so weights would no longer be nondecreasing in the numbering: the sibling property, and with it Gallager’s guarantee that the tree is a Huffman tree for its weights, would break. Moving the node to the top of its equal-weight block first makes the increment safe, because it then sits above every other node of that weight and below every heavier one. A swap with the parent is different in kind: a parent’s weight already counts the child’s, so the two are not interchangeable positions, and exchanging them would make a node an ancestor of itself. The same applies to any ancestor, which is why the leader search skips them.
