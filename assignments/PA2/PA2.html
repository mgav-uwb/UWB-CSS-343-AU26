You build the same graph twice, in the two representations from Lecture 9, and give each one the algorithms that suit it:

  • GraphM: an adjacency matrix that computes shortest paths from every vertex with Dijkstra's algorithm in its linear-scan form (no priority queue), and reconstructs each path;
  • GraphL: an adjacency list of raw, heap-allocated EdgeNodes, with an iterative depth-first search (explicit stack), a breadth-first search (queue), and a destructor that frees every node.

Both read the same file format, with named vertices and several graphs per file. In Part 4 you race the matrix version against your heap-based dijkstra from Homework 6 on dense and sparse graphs, predict the outcome from the bounds, and explain what you measure.

The file format

The first line is the vertex count n, followed by n lines of vertex names (names contain spaces, so read them with getline), then one from to cost triple per line, ended by a line that starts with 0. A file may hold several graphs back to back: buildGraph consumes exactly one and leaves the stream ready for the next. Vertices are numbered 1 to n (slot 0 is unused). See simple_graph.txt (two graphs) and complex_graph.txt (ten vertices).

Part 1: GraphM (matrix, all-pairs Dijkstra)

The data members are declared in graphm.h: the vertex names, adjM (a cell holds the edge weight, INF means no edge; a repeated edge in the file overwrites the earlier one), and pathM, one row of TableType { visited, dist, prev_node } per source.

  1. buildGraph, insertEdge and removeEdge. The edge operations return -1 for an endpoint outside 1 to n, a self-loop, or a negative cost.
  2. findShortestPath(): Dijkstra from every source. Each round finds the nearest unsettled vertex by a linear scan of the row, settles it, and relaxes its out-edges. No priority queue.
  3. getDist and getPath, so the class can be used as a component, and the two display methods, whose formats are fixed by expected-output.txt.

The table stores only each vertex's predecessor on its best path. getPath has to turn that into the path from the source, in order.

Part 2: GraphL (list, iterative traversals)

Each GraphNode heads a singly linked list of heap-allocated EdgeNodes. Every new edge is inserted at the head of its list, so each list holds its edges in reverse input order. That rule makes every traversal order deterministic, and expected-output.txt is computed under it.

  1. Constructor and destructor: every EdgeNode is freed, and calling buildGraph on an object that already holds a graph frees the old one first.
  2. buildGraph (the weights are read and ignored), getSize, displayGraph, edgeList(id).
  3. DFSorder(start): iterative, with an explicit stack. Push the start; then repeatedly pop a vertex, skip it if it is already visited, otherwise visit it and push its unvisited neighbors in list order. Recursion is not accepted.
  4. BFSorder(start): a queue, marking a vertex visited when it is enqueued.

Copying. The class declares GraphL(const GraphL&) = delete;. With raw pointers, the compiler-written copy would share the edge lists and free them twice. PA1 answered the Rule of Three by implementing deep copies; deleting the operations is the other legitimate answer. Keep the = delete and say why in a comment, or implement a real deep copy. Either way, document the decision.

Part 3: your own testing (driver.cpp)

The given sample_driver.cpp never feeds a malformed file, never inserts an invalid edge, never starts a traversal anywhere but vertex 1, and never rebuilds an existing object. Your driver.cpp does all of that, on both provided files.

Part 4: the representation race

Compile gen_graphs.cpp and run it: it writes fixed-seed families dense_V.txt (E ≈ V2/2) and sparse_V.txt (E ≈ 4V) for V = 200, 400, 800, 1600. Then paste your Homework 6 dijkstra into race.cpp, unchanged, and run it on each file:

g++ -std=c++17 -O2 race.cpp graphm.cpp -o race
./race sparse_400.txt

It times all-pairs shortest paths two ways (your GraphM::findShortestPath(), and your Homework 6 dijkstra looped over every source) and checks that the two agree. If you have not finished Homework 6, write its heap-based dijkstra for this part anyway; Lecture 11 covers it.

Report (one page)

  1. Prediction. Before you measure, state the running time of each all-pairs method as a function of V and E, and what it becomes on each family. Predict the doubling ratio (the time at 2V divided by the time at V) for each method on each family.
  2. Measurement. One table per family: V, both times, and both doubling ratios.
  3. Explanation. A few sentences: where the measurements agree with the prediction, and where they do not, why. If a result departs from the bound, look at what the bound assumes. For example, count how many times your dijkstra pushes onto the heap per source and compare that with E.

No hand trace is required: the diff against expected-output.txt checks the same thing.
